# ADR-0035 — 题材无关的空间模型 v2 与按项目涌现的空间类型

- **状态**: Accepted / 未实施（产品方向由用户 2026-10-15 裁定；技术评审修订后由用户 2026-10-15 采纳）
- **日期**: 2026-10-15
- **关联追踪**: ADR-0005（自定义类型与 AI 边界）、ADR-0012（统一地图）、ADR-0017（事实权威）、
  ADR-0026（不可变修订）、ADR-0036（世界演化空间发现）、ADR-0039（对象档案，共用词表与锚点规则）、
  [地图系统增强设计](../plans/2026-10-15-map-system-enhancement.md) §2–§5、§8

## 背景

当前空间文档（`MapDocument`，`schema_version=1`，`backend/modules/world/map_structure_schemas.py`）
按陆地平面设计，各部分都是写死的：

- 结构层级 `StructureLevel` 固定为区域、城市、街区、街道、室内 5 级；地图册节点 `AtlasLevel`
  另有封面、世界共 7 级（`map_atlas_schemas.py:11`，数据库 CHECK `ck_map_atlas_nodes_level`）；
- 图元只有地点、地标、道路、河流、区域五种；
- 关系 `SpatialRelation` 共 15 个值：包含、八方位、相邻、连通、途经（`passes_through`），
  以及沿街、入口、朝向三种街道关系；
- 没有距离、耗时、交通方式、通行条件、生效时间和可信度；
- 只有一棵从“世界”开始的节点树。

小说题材差异很大：洞天秘境、无限流副本、梦境、网络空间、多星球、地下城、
不分东西南北的星际空间、御剑与传送、修辞夸张、不可靠叙述、毁城与改名、移动城市等。
用户 2026-10-15 裁定：

- 内置类型肯定不够。对齐世界演化的“涌现”思想，允许模型在演化过程中总结出常用类型，按项目维护。
- 未列举的情况要预留用户自定义。

世界演化已有可借鉴的做法：发现阶段回读项目既有的派生主题（稳定 UUID、按修订演进），
新主题必须有逐字证据并经独立复核，作者判断不被模型覆盖；派生理解不是正典
（`backend/modules/evolution/ledger_contracts.py`）。

必须保留的既有约束：

- 空间版本只追加（PostgreSQL trigger 保护）；
- 底图校准绑定 `geometry_hash`；
- 读者预览按依赖闭包与揭示过滤；
- 地图不回写 World 正式事实。

## 决策

### 1. 两层：小型计算特性内核加开放的项目类型

**类型是开放的，按项目维护。** 类型包括：空间类型、层级名称、图元类型、关系类型、
交通方式、旅行者类别、通行条件、势力形态、领地控制方式。类型有两个来源：

- 作者自定义；
- 模型在世界演化中总结（第 4 条）。

不设“必须映射到某个内置类型”的封闭清单。

**计算特性内核小而封闭。** 每个类型声明自己具备哪些可组合的计算特性。程序中的确定性布局、
检查和读者投影只读这些特性，不读类型名。特性如下：

| 维度 | 特性 |
|---|---|
| 几何 | 点、线、面、无几何 |
| 容纳 | 可容纳其他地点、自成独立空间 |
| 连接 | 可通行、有向、跨空间、受距离约束 |
| 方位 | 方位有效、上下关系 |
| 其他 | 可移动、远近（定性） |

- 类型的其余含义保存在名称、别名和描述中，以文字身份进入写作简报、问答等模型上下文
  （ADR-0037），不需要内核表达。
- 没有声明任何特性的类型只参与显示、检索和模型上下文，不参与确定性计算。
- **特性何时生效**：类型声明的特性（无论来自作者还是模型）只有在作者采用了引用该类型的地图版本后，
  才参与该版本的布局和空间提醒。模型涌现的类型在复核通过后可以显示、检索和被模型复用（第 4 条），
  但它声明的特性不会绕过作者采用直接改变提醒结果。
- 内核扩充要像世界演化台账扩类（P4-C）那样带方法版本、有效与无效样例和评测，并修订本 ADR，
  不因单个项目的需要临时增加。

### 2. 空间文档 v2 的加性扩展

`schema_version=2` 只增加内容，不改变 v1 字段的含义：

- **空间**：项目可有多个互不相连的空间，已有节点归入默认主空间；
  空间之间只能用具备“跨空间”特性的连接相连。
- **层级**：层级的显示名来自项目类型，深度由父链推导。存储上保留现有 `level` 列及其 CHECK 约束，
  作为系统粗层（布局和既有查询继续使用）；新增可选的 `level_type_ref` 指向项目层级类型。
  不改写已有节点，不改变已有节点的父子关系、`semantic_key` 和路径身份。
- **类型引用**：图元、关系、路线可选携带 `type_ref`（项目类型 ID）。v1 的 `kind`、`relation`、
  `path_kind` 值保留，作为系统默认类型。
- **行程声明**：独立列表，字段为起点、终点、交通方式、可选旅行者类别、可选耗时区间、
  可选距离区间、通行条件、模态和逐字引文，至少要有一条引文。
- **模态**：直接复用世界演化的 `ObservationModality`（`backend/modules/evolution/contracts.py:120`，
  共 7 个值），处置如下，都不进入客观地图和读者预览，除第一项外都不参与确定性计算：
  - `event_observed`：参与确定性计算；
  - `figurative`：修辞，只作文字；
  - `character_statement`、`belief`、`hypothesis`：只进入角色认知或作者视图；
  - `author_plan`：原文中的作者计划或预告，只进入作者视图，标为“计划”；
  - `unclear`：进入待核对，作者判断前不参与任何提醒。
- **v1 已采用约束**：v1 约束没有模态和生效区间，读取时视为作者确认（等同 `event_observed`）、全书有效。
- **生效区间**：图元、关系和行程声明可带按章节或 Scene ID 锚定的起止点，用于表达毁城、开路、改名等变化。
  锚点规则（ADR-0039 的档案条目和势力账本共用）：
  - 读取时按当前章节和 Scene 顺序解析锚点，不保存序号；Scene 会重排（`scene_order` 锁）和被融合替换，
    现有地图版本的 `writing_chapter_index` 只作兼容读取。
  - 锚点所在 Scene 被融合替换（`replaced_by_scene_ids`）时，起点跟随最早的替换 Scene，终点跟随最晚的。
  - 锚点被删除且没有替换关系时，区间标为“锚点失效，待核对”，进入统一提醒（ADR-0040 §13），
    作者处理前不参与确定性检查，不静默改成全书有效。
  - 重排使起点晚于终点时，同样标为待核对。
- **世界线**：v2 不落字段。故事内世界线 ADR 落地时再扩展；v2 实现不得假设只存在一条世界线。

### 3. 兼容规则

- 读取 v1 文档时按系统默认类型解释为 v2，不批量迁移已有版本（遵守 ADR-0026 与只追加 trigger）；
  作者下次保存时才写 v2 新版本。
- **几何指纹不因升级变化**：现有 `geometry_hash`（`map_structure_geometry.py:32`）对图元用字段白名单，
  对约束却用排除名单（只排除 `sources`、`generated_by_task_id`），约束上新增任何字段（即使取默认值）
  都会改变指纹，使服务端拒绝已有底图校准（“底图校准必须绑定当前空间版本”）。因此在 v2 任何字段落地前，
  先把约束部分改为 v1 字段白名单（`id`、`subject`、`relation`、`target`、`via`、`path_kind`、
  `path_label`），并用回归测试证明旧文档指纹不变。之后：`type_ref` 只有在改变了计算特性时才影响布局，
  否则不进入几何指纹；行程声明、通行条件、模态和生效区间只进入内容与来源 hash。
  已有底图校准、结构引导图片和读者白名单因此保持有效。
- API 只做加性扩展。客户端遇到不认识的类型或特性时按文字显示，不报错。
- 新元素同样经过依赖闭包和揭示过滤。

### 4. 项目类型由作者和模型共同维护

- **身份与修订**：项目类型按 `novel_id` 隔离，有稳定 UUID 和不可变修订；
  名称变化不改身份，数据只按 ID 引用。
- **统一的项目词表**：空间类型、ADR-0039 的档案面向，以及势力形态和领地控制方式，都存放在 World 的
  同一份项目词表中，按词表种类区分。身份、修订、来源、涌现、合并、墓碑和题材预设的规则只实现一次；
  各种类只声明自己的计算特性或读取语义。
- **来源**：作者创建，或模型在世界演化空间发现（ADR-0036）中总结。模型总结的类型必须带来自
  至少两个 Scene 的逐字证据，并经过独立复核；只出现一次的说法保持“涌现中”，只当文字显示。
  复核通过后自动启用，不需要作者逐个批准。
- **模型读取既有类型**：发现阶段按相关性回读本项目已有类型（数量设上限并披露省略数），
  优先复用已有 ID，不重复创建。类型会在运行中途涌现，因此类型清单只在批次准备时冻结，其修订指纹记入
  该 Scene 的 `consumer_read_set`，不进入方法指纹（否则续读时方法版本对不上，ADR-0036 §1）。
- **并行时去重**：发现阶段并行生成、按 Scene 顺序写入。新类型提议在顺序写入时只与严格更早的提议和已有类型
  比较；别名经确定性归一后等价的，合并为同一个涌现中类型并累计证据，不创建重复类型。
- **证据失效**：支撑某个类型的 Scene 被重算或撤销后，重新统计有效证据。不足两个 Scene 时，模型创建的类型
  退回“涌现中”，已引用它的数据按文字显示；作者创建或作者确认过的类型不受影响。
- **合并**：模型可以提出合并建议（如“传送阵”与“传送法阵”）。只有两者都由模型创建、
  别名经确定性归一后等价或独立复核高置信时，才自动合并；被合并的 ID 保留重定向。
- **作者优先**：作者可以改名、改特性、合并、拆分和归档。模型不得覆盖作者的判断，也不得
  修改作者创建的类型，只能提出建议。归档后，已引用的数据按文字显示并提示作者。
- **墓碑**：作者归档或拒绝的类型保留墓碑（ID、名称、别名归一键）。模型在后续发现中回读墓碑，
  不得以相同或等价名称重建；确有需要时只能提出“恢复”建议，由作者决定。
- **题材预设**是带版本的初始类型包（首批修仙、西幻、都市、科幻、悬疑），可以混搭。
  应用时复制进项目类型并记录预设版本，之后与涌现类型一同演进；预设更新不会悄悄改变已有项目。
- **与 ADR-0005 的关系**：本条只针对空间类型，允许模型读取和维护项目类型；
  ADR-0005 对 World 对象类型的 AI 边界不变。

### 5. 移动性是特性，不是对象类型

- 人物、物品（小船）、势力单元（大船、舰队）和地点（移动城市、世代飞船）都可以移动。
  位置投影沿用 `map_scene_context_v1` 的 `confirmed_in_scene / last_observed / unknown` 语义，
  扩展到非人物对象；不从档案回填，不推算坐标。
- 可移动地点的内部地图随宿主移动，只表达所属关系，不派生外部坐标。
- 同一艘船可按 ADR-0005 的 `EntityTypeTransitionService` 在物品与势力之间转换；
  对象身份不变，位置投影不受影响。

### 6. 势力领地只预留只读投影接口

- 地图不保存势力数据。领地是只读图层，由势力侧按章节生效的控制关系计算；
  势力数据模型由势力路线图阶段 1 的 ADR 决定。
- 势力形态和领地控制方式同样是开放的项目类型。可上图的控制方式通过特性声明呈现为成片、
  据点、通道、移动单元或叠加影响；没有特性的只在势力面板显示。
- 地理层级与势力层级相互独立；领地只示意着色，不画精确边界。
- **现有字段**：`FactionProfile.territory_refs_json` 与 `LocationProfile.controlling_faction_ids_json`
  （`world/models/profiles.py:69`、`:83`）没有生效区间。本 ADR 保留它们原样，地图不读取；
  是否迁移为带生效区间的控制关系由势力路线图阶段 1 的 ADR 决定。阶段 1 之前不提供领地图层。

### 7. 权威边界不变

空间声明、行程、通行条件和项目类型都是带来源的作者资料或派生理解，不是 World 正式事实，
不进入 CanonRevision（ADR-0017），也不回写 World。与 World 规则重合的通行条件可以引用规则对象，
但不复制规则内容。

## 后果

- 第一步是把 `geometry_hash` 的约束部分冻结为 v1 字段白名单（第 3 条），先于任何 v2 字段。
- 需要 migration：统一项目词表及其修订与墓碑、空间归属、可选 `level_type_ref`、生效区间等。还需要扩展
  schema、确定性布局（跨空间、上下、远近的排布）、类型管理界面和前端编辑器。
- 新题材和新说法由模型在演化中总结，或由作者补充，不必改代码；确定性计算的正确性只依赖特性内核。
- 风险：
  - 涌现类型可能膨胀或重复，靠复用优先、合并建议和作者归档控制。
  - 模型给类型声明的特性可能出错，因此特性声明同样要经独立复核，作者可以修正。
  - 发现阶段回读类型清单会增加输入成本，靠相关性排序和上限控制。
  - 锚点按当前顺序解析，Scene 删除会产生“锚点失效”的待核对条目，需要作者处理。
  - 统一词表让多个功能共用一张表，各种类的读取语义要靠种类声明和契约测试隔离，避免互相影响。

## 备选方案

### A. 按题材分别建模

拒绝。组合会爆炸，混搭题材（如都市修仙）无法表达。

### B. 封闭的内置类型清单，自定义项必须映射到其中之一

拒绝。用户判断内置类型不够，新说法会被硬塞进不合适的类别。

### C. 完全开放，连计算特性也由模型自由定义

拒绝。程序无法对未知特性做确定性计算，检查与布局会失去依据。

### D. 模型不读项目类型，只由服务端匹配名称

拒绝。同义说法会不断产生重复类型，也违背演化“复用既有身份”的做法。

### E. 引入真实坐标或三维坐标

拒绝。与地图“示意”的定位不符，原文通常也不提供坐标。
