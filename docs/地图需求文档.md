# 动态地理拓扑与旅行时间计算服务：产品需求文档 (PRD) v1.0

## 1. 背景与业务痛点

在长篇小说（如玄幻、奇幻、史诗推演类）的创作过程中，世界观的地理设定往往随着剧情主线的推进而发生剧烈变迁（例如：因“神战”导致两块大陆永远分割不可通航、因阵营交战导致边境要塞锁死、或由于秘境封印解除暴露出史前古道）。

目前，本系统的地理、时间线等基础设施模块已完成基础的 CRUD 维护，但这些地理数据在逻辑上是**静态**的。如果作者在第 50 章安排了一场破坏航线的神战，而在第 100 章的正文草稿或章节卡中随手写到“普通商人乘船平稳渡海”，系统目前无法自动识别并拦截这种严重的**时空逻辑前后矛盾（“吃书”）**。

为了彻底解决这一痛点，本需求旨在构建一个**主线事件驱动的动态地理拓扑与旅行时间计算服务**。

---

## 2. 核心设计原则

* **坚决不改动现有 DDL 结构**：不允许为了地理系统的演变去拆分或新建历史快照表，必须完全复用现有的 `geo_edges`、`timeline_events` 等基表及 JSONB 弹性字段。
* **时空解耦查询**：地图的历史变化不以“物理删除”或“物理覆盖”的形式存在，而是以“时间线事件”作为增量补丁，在内存中动态复写编译。
* **垂直模块化通信**：`geo` 模块不直接查询 `timeline` 模块的数据表，必须严格通过 `TimelineFacade` 跨模块数据契约获取事件效应。

---

## 3. 业务范围与功能边界

### 3.1 在业务范围内的功能 (In Scope)

* **动态图编译**：能够根据传入的 `chapter_index`（章节索引），自动加载基础地图并动态应用截止该章节所有已发生事件的地理改动脚本（`geo_effects`）。
* **连通性与耗时计算**：利用拓扑图论算法（Dijkstra），精确测算出当前章节节点下，两地是否可达、最短耗时（小时）以及途径节点。
* **跨模块能力输出**：为 `review`（结构复查）模块和 `context`（上下文编译）模块提供标准的解耦判定接口，用于正文逻辑拦截及 RAG 过滤。

### 3.2 明确不在范围内的功能 (Out of Scope)

* **宏观纪元级动态演变**：正如技术方案所确定的，纪元级（Era）在本阶段只作为前端表现层的“静态历史地图”图层展示，不参与后端的动态路径计算，以降低系统复杂度。
* **专业 GIS 与物理测绘**：不做专业 GIS、PostGIS 扩展或地图瓦片服务。

## 4. 功能需求详情

### 需求 4.1：内存动态网络编译器 (Memory-Based Topology Compiler)

* **场景描述**：当系统需要评估特定章节（如第 $X$ 章）的地理环境时，需实时组装出一张“当前章节专属”的地图连通图。
* **业务规则**：
1. 系统首先读取 `geo_edges` 中该项目所有的基础静态路线。
2. 调用外部外观层（Facade），捞出所有满足 `chapter_index <= X` 且 `geo_effects` 不为空的主线历史事件。
3. 依据事件内的 `edge_mutations` 脚本，在内存中执行覆写（Override）：
* 若 `action == "block"`：在内存图中彻底**移除**该路径（连通权值设为 $\infty$）。
* 若 `action == "connect"` 或 `"reveal_hidden"`：在内存图中**动态添加或恢复**该路径，并指定新的耗时权重。





### 需求 4.2：动态可达性与时空旅行耗时测算 (Dijkstra Routing & Travel Time Estimator)

* **场景描述**：系统或创作者需要查验在当前剧情进度下，主角或军队能否从 A 地移动到 B 地，以及需要花费多长时间。
* **业务规则**：
* **权重解析规范**：系统需具备将文本类型的旅行耗时（如 `3天`, `12小时`）自动转化为标准浮点小时数的解析能力。
* **连通性判定**：基于加权有向图，若两地之间所有的路径均被主线事件“阻断（`blocked_path`）”，则判定为 `is_reachable = False`。
* **最短时空开销求解**：若多条路线均可达，算法必须返回总耗时（`total_hours`）最低的那条最优路径，并输出沿途经过的全部 `geo_locations` 节点的 UUID 链条。



### 需求 4.3：跨模块逻辑联动契约 (Cross-Module Facade Interaction)

* **场景描述**：该地理计算服务不仅服务于前端展现，更核心的是为系统的“辅助层”模块提供底层事实依据。

| 使用模块 | 联动触发场景 | 地理计算服务的核心产出与应用 |
| --- | --- | --- |
| **`review` (结构复查)** | 用户提交正文草稿（`writing_drafts`）或章节卡（`chapter_cards`）进行审查时。 | 审查引擎调用本服务，若发现角色跨越了已被阻断的区域，则在 `review_reports` 中精准写入逻辑冲突警告。 |
| **`context` (上下文编译)** | 准备为 AI 生成正文提供 RAG 检索增强背景时。 | 过滤器基于路径计算结果，动态将由于地理断绝而无法传递的长期记忆（`memory_records`）和知识边界剔除，极大地节约大模型 Token 预算。 |

## 5. 非功能性需求与异常控制

### 5.1 性能与计算延迟

* 由于长篇小说的世界对象节点（Nodes）通常在 1,000 以内，地理边（Edges）在 5,000 以内，而后端采用纯内存计算和 Python 原生高效堆栈（`heapq`），任何单次可达性与路径的计算损耗必须控制在 **50ms** 以内，确保创作者在前端拖动时间线滑块时毫无卡顿感。

### 5.2 稳健性与异常兜底

* **节点不存在处理**：若输入的 `source_id` 或 `target_id` 在系统中无法匹配，系统不应崩溃，必须安全返回可达性为 `False`，并在错误原因中明确提示“地理节点不存在”。
* **解析失败处理**：若主线历史事件中的 `travel_time` 文本因为人工编辑导致格式混乱（如输入了乱码），文本解析器必须能够安全降级，采用默认的系统兜底参数（如默认为 24 小时）执行计算，并记录警告日志。
