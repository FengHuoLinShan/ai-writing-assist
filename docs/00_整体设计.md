# AI 长篇小说结构化创作引擎：整体设计 v2.0（实际实现）

## 1. 项目定位

本项目当前阶段不以"AI 直接生成完整正文"为核心目标，而是构建一个面向中文长篇小说创作者的 **结构化创作引擎**。

系统核心产物是结构化创作资产：

- 核心实体（CoreEntity，统一管理所有世界对象）
- 人物档案（Character，entity_id FK → core_entities）
- 人物知识边界（CharacterKnowledge）
- 剧情线（PlotThread）
- 篇章纲（OutlineArc）
- 章节卡（ChapterCard）与场景卡（Scene）
- Scene 卡（Scene，最小叙事单元，独立 `scenes` 表）
- Delta 变更日志（DeltaLog，结构化字段变更审计）
- 文本归档（TextArchive，长文本字段版本历史）
- 伏笔计划（ForeshadowingPlan）
- 信息揭示计划（RevealPlan）
- 长期记忆（MemoryEvent + MemorySnapshot，事件溯源）
- 轻量时间线（Event，entity_type="event"，v3 中由 core_entities 统一管理）
- RAG 检索上下文（RagChunk）
- 正文草稿（WritingDraft，人工撰写+导入）

## 3. 核心原则

### 3.1 少 Agent，强 Context

当前不构建复杂多 Agent 创作工厂。系统当前活跃的 Prompt 族包括：

1. `structure_world_character.md` — 世界与人物结构生成
2. `structure_plot.md` — 剧情结构生成
3. `structure_chapter_scene.md` — 章节与场景结构生成
4. `structure_extraction.md` — 从章节正文补抽世界对象
5. `scene_entity_extraction.md` — 从 Scene 正文抽取实体/关系/Delta（深度导入 Phase 2）
6. `extract_chapter_scene.md` — 从正文提取章节卡字段
7. `extract_character.md` — 从正文提取人物档案字段
8. `scene_segmentation.md` — 正式 Scene 字段切分 / 小样本与单章恢复路径
9. `shared_rules.md` — 所有结构化 Prompt 的共享防御与输出规则

`structure_review_memory.md` 仍保留在仓库中，但 `review` 模块已移除，它不再属于当前活跃调用链。

所有 Prompt 通过 `infrastructure/llm/prompt_loader.py` 从 `backend/prompts/` 加载。
深度导入 60 章主链的 Phase 0 / Phase 1a / Phase 1b prompt 由
`modules/imports/workflow_llm_adapters.py` 组装，并通过结构化 adapter、token 预算和
schema guard 执行；`scene_segmentation.md` 主要服务正式 Scene 字段切分、小样本检测和
单章恢复，不代表主链的最终写入策略。Phase 0 / 1a 输出是中间候选，正式 Scene 写入仍由
imports workflow 的融合与 commit 阶段决定。

### 3.2 Prompt 按创作阶段合并

不要按数据库表拆 Prompt。一次 Prompt 输出多个 JSON 数组，入库时分别写入对应表。

### 3.3 数据按对象类型拆分

Prompt 可以合并，但数据库仍按对象类型拆分。一次 Prompt 可以输出多个数组，入库时分别写入对应的表。

### 3.4 候选先行，人工确认正史（深度导入例外）

AI 默认不直接创建正史对象。统一流程：

```text
AI 生成候选
    ↓
Schema 校验 / 服务层约束检查 / 去重判断
    ↓
用户确认 / 编辑 / 拒绝
    ↓
写入 canonical 正史库
```

**例外**：用户明确启动的深度导入流水线（imports 模块）可在不中断流水线的情况下自动写入派生数据，并保留 `content_json._meta.auto_ingested = true`、来源章节/Scene 和批次元数据。当前实体抽取结果写入 `core_entities` 时仍使用 `status="candidate"`，后续可由用户清洗、提升或回滚。

### 3.5 对象抽取不是 NER，而是长期创作资产识别

系统不是要抽取尽可能多的名词，而是识别值得长期维护的创作资产。不重要对象、路人、普通道具、一次性地点不应直接进入世界对象库。

## 4. 系统三层结构

### 4.1 事实层

维护小说当前正史事实。world 模块（v3 因果时空网）统一管理 CoreEntity、Character、Event、EntityRelation，已吸收原 character 和 timeline 模块。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| project | projects | 小说项目元信息 |
| world | core_entities, characters, character_knowledge, entity_relations, events, delta_log, text_archive | 核心实体、人物档案、知识边界、关系、事件、变更日志、文本归档 |
| memory | memory_events, memory_snapshots | 长期记忆（事件溯源 + 阶段性全景快照） |

> geo 模块已移除（地理对象走 core_entities entity_type="location"）；character/timeline 已合并至 world。

### 4.2 结构层

把事实组织成可执行的剧情计划。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| outline | plot_threads, outline_arcs, scenes, chapter_cards, foreshadowing_plans, reveal_plans | 剧情线/篇章纲/Scene 卡/章节卡/伏笔/揭示 |

### 4.3 辅助层

负责检索、上下文编译、写作与导入导出。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| rag | rag_chunks | 检索增强（向量 + 关键词 + 项目词典 + 关系 + 重要性） |
| context | context_confirmations / context_snapshots | 上下文编译、AI 参考资料确认与自动上下文快照审计 |
| writing | writing_drafts | 正文草稿与 AI 候选来源追踪 |
| imports | import_records | 小说文件导入 |
| settings | global_llm_defaults, global_author_preferences, project_author_preferences | 全局 LLM 默认 / 全局作者偏好 / 项目覆盖（owner_id 预留账户系统） |
| infrastructure | async_tasks | 异步任务系统（LLM 调用、任务队列） |

> review 模块已移除（结构复查功能暂缓）。

## 5. 实际目录结构

```text
backend/
├── app/
│   ├── main.py              — FastAPI 应用入口
├── core/
│   ├── base.py              — ORM 基类（UUIDMixin / TimestampMixin / StatusMixin / NovelMixin）
│   ├── config.py            — 配置管理（dataclass + get_settings() 单例）
│   ├── database.py          — 数据库连接管理（DatabaseManager）
│   ├── crud.py               — BaseCRUDService 通用 CRUD 模板（novel-scoped）
│   └── dependencies.py      — 依赖注入（DbSession / AppSettings）
├── shared/
│   ├── constants.py         — 全局常量
│   ├── enums.py             — 全局枚举
│   ├── types.py             — 类型别名
│   └── utils.py             — 工具函数
├── infrastructure/
│   ├── llm/                 — LLM 客户端
│   │   ├── client.py        — LLMClient（generate / generate_structured / generate_stream）
│   │   ├── providers.py     — Provider（OpenAI 兼容）
│   │   ├── retry.py         — 指数退避重试
│   │   ├── schemas.py       — LLM 请求/响应 Pydantic schema
│   │   └── errors.py        — LLM 错误类型
│   └── tasks/               — 异步任务系统
│       ├── models.py        — AsyncTask ORM
│       ├── worker.py        — Worker 循环（FOR UPDATE SKIP LOCKED）
│       ├── registry.py      — 任务处理器注册（@task_handler）
│       └── api.py           — 任务提交/状态查询 API
├── modules/                 — 9 个业务模块（见上文列表）
├── prompts/                 — 结构化创作/抽取 Prompt 与 shared_rules
├── tests/                   — 集成测试与 API 测试
├── pyproject.toml
└── alembic/                 — 数据库迁移
```

每个业务模块标准文件：`contracts.py` / `models.py` / `schemas.py` / `repositories.py` / `services.py` / `api.py`。`facade.py` 和 `tasks.py` 按需可选。

## 6. 模块通信规则

- 跨模块生产代码只能导入 `contracts.py`、`facade.py` 或 DI port
- `api.py` 是 HTTP 入口，不作为模块间调用接口
- API 层和 facade 不写复杂业务逻辑；非平凡编排下沉到拥有领域概念的模块实现

## 7. 前端架构

纯 Vanilla JS SPA，当前注册 10 个一级路由：project / writing / world / map / rag / outline / generate / context / settings / project-settings。地图已升级为一级工作台；`world` 中旧地图入口仅保留兼容跳转；`llm` 路由保留为 `project-settings` 的向后兼容别名。详见 `docs/modules/14_frontend.md`。

## 8. 明确不做

复杂多 Agent 协同写正文、自动正史合并、Neo4j/GraphRAG、多用户权限、商业功能。

## 9. 技术栈

- **后端**：Python 3.13 + FastAPI + async SQLAlchemy 2.0 + Pydantic v2
- **数据库**：PostgreSQL 17 + pgvector + pg_trgm
- **ORM 基类**：UUID 主键 / 时间戳 / NovelMixin（novel_id）/ StatusMixin（status）
- **LLM**：OpenAI 兼容 API（支持结构化输出 response_format）
- **任务队列**：PostgreSQL 表 + 进程内 worker（FOR UPDATE SKIP LOCKED）
- **前端**：Vanilla JS + CSS 变量 + Proxy 响应式状态
- **测试**：pytest + pytest-asyncio + SQLite 内存引擎
- **容器**：Docker Compose（PostgreSQL 17 + pgvector）
