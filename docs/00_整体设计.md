# AI 长篇小说结构化创作引擎：整体设计 v2.0（实际实现）

## 1. 项目定位

本项目当前阶段不以"AI 直接生成完整正文"为核心目标，而是构建一个面向中文长篇小说创作与
世界探索的 **结构化创作引擎**。

产品服务两类核心用户：

- 专业或业余作家：长期维护正文、幻想设定、故事历史、事件、人物、物品、关系与结构；
- 想进入幻想世界的 RP 用户：不要求技术或专业写作技巧，只需用自然语言说明世界、身份和
  开场愿望，再通过行动、纠正、重新生成、其他分支或持续观看推进私人故事。

两类用户共享账号级模型连接与可追踪 AI 基础设施，但采用不同默认入口、业务领域和复杂度。
首页当前以两个大框分别进入 `我是作家` 与 `我是 RP 用户`：作者路径强调完整控制、证据、
版本和整理效率；RP 路径以自然语言开场、选中分支历史、持续故事、回顾和低摩擦重抽为核心。

RP 第一版是模型知识互动旅程，不读取作者项目的 World、Outline、RAG、writing 或 memory，
也不提供原作导入、按章节分叉、项目共享或公开发布。更广泛的人物/地图世界探索仍是未来范围，
不能由当前双入口反向宣称已交付。
具体画像、内容权利边界和功能体验门禁以
[`product/user-personas.md`](product/user-personas.md) 为准。

系统核心产物是结构化创作资产：

- 核心实体（CoreEntity，统一管理所有世界对象）
- 人物档案（Character，entity_id FK → core_entities）
- 人物知识边界（CharacterKnowledge）
- 小说总纲（StoryOutline，小说级上位结构的不可变版本聚合）
- 剧情线（PlotThread）
- 篇章纲（OutlineArc）
- Scene 卡（Scene，最小叙事单元，独立 `scenes` 表）
- Delta 变更日志（DeltaLog，结构化字段变更审计）
- 文本归档（TextArchive，长文本字段版本历史）
- 伏笔计划（ForeshadowingPlan）
- 信息揭示计划（RevealPlan）
- 长期记忆（MemoryEvent + MemorySnapshot，事件溯源）
- 轻量时间线（Event，entity_type="event"，v3 中由 core_entities 统一管理）
- RAG 检索上下文（RagChunk）
- 正文草稿（WritingDraft，人工撰写+导入）

RP 路径另有独立的互动旅程资产：不可变消息节点、代码级分支选择、生成 attempt、分段概要和
总回顾。它们只维护私人互动故事，不进入上述作者正史资产。

## 3. 核心原则

### 3.1 从用户喜欢与舒适体验出发

用户可见功能首先回答“谁会喜欢、解决什么摩擦、为什么愿意再次使用”，再讨论技术实现。
后端可实现、模型能生成或自动测试通过，都不能单独证明功能成立。

前端默认围绕当前任务组织：主操作、当前状态和下一步可直接理解；高频动作就地完成；专业
能力渐进展开；不要求用户理解 raw ID、JSON、Prompt/token 或内部状态。适用的首次进入、
空态、失败/冲突、保存反馈、离开恢复、误操作保护和窄屏体验属于功能完成条件。

功能可以明确只服务一类画像，但不得把作者后台复杂度无差别转嫁给 RP 用户，也不得为了
降低门槛而削弱作者需要的来源、版本、权限和回滚控制。

### 3.2 少 Agent，强 Context

当前不构建复杂多 Agent 创作工厂。运行时 LLM 调用使用受控 step：调用方显式定义
schema、预算、超时、日志与权限；不允许自主选工具或自主业务写入。Prompt 的活跃清单、
调用方与输出契约只在 [`prompts/Prompt体系设计.md`](prompts/Prompt体系设计.md) 维护，避免
把会随工作流演进的文件名重复写入整体架构。

通用 Prompt 模板通过 `infrastructure/llm/prompt_loader.py` 从 `backend/prompts/` 加载；阶段性
深度导入 Prompt 由 adapter 组装。
深度导入 60 章主链的 Phase 0 是确定性窗口与上下文计划，不调用 LLM；Phase 1a / 1b / 1c
Prompt 由 `modules/imports/workflow_llm_adapters.py` 组装，并通过结构化 adapter、token
预算和 schema guard 执行。Phase 1a / 1b 输出是中间候选，正式 Scene 写入仍由 imports
workflow 的融合与 commit 阶段决定；不存在独立的 legacy Scene 切分入口。

### 3.3 Prompt 按创作阶段合并

不要按数据库表拆 Prompt。一次 Prompt 输出多个 JSON 数组，入库时分别写入对应表。

### 3.4 数据按对象类型拆分

Prompt 可以合并，但数据库仍按对象类型拆分。一次 Prompt 可以输出多个数组，入库时分别写入对应的表。

### 3.5 待处理建议先行，作者采用后生效（授权流水线例外）

普通 AI 生成默认不直接改写当前有效资产。作者面对的统一流程是：

```text
AI 生成待处理建议或临时预览
    ↓
Schema 校验 / 服务层约束检查 / 去重判断
    ↓
作者采用 / 编辑后采用 / 合并 / 设为别名 / 忽略
    ↓
目标领域写入当前有效资产
```

内部可继续使用 `candidate` / `proposal` / `canonical` 等兼容状态，但前端统一投影为
`review / active / archived`，分别显示“待处理 / 已采用 / 历史”。`conflicted`、低置信、
`needs_review` 和 POV 风险是注意原因，不是并列生命周期。人工创建世界对象、关系和别名时，
保存动作本身即表达采用意图；正文则保留“工作稿 → 已发布”的内容成熟度。

**例外**：深度导入等自动流水线必须在启动时由用户一次性授权，并把授权策略、章节范围和
时间写入任务 meta/result。授权范围内、规则明确且可回滚的结果可自动写入派生或已采用资产；
冲突、低置信和无法消歧的实体、关系、别名或结构结果进入待处理。所有自动写入保留
`auto_ingested`、workflow、来源章节/Scene、证据和回滚元数据，完成结果按“已采用 / 待处理 /
未采用”汇总。

### 3.6 对象抽取不是 NER，而是长期创作资产识别

系统不是要抽取尽可能多的名词，而是识别值得长期维护的创作资产。不重要对象、路人、普通道具、一次性地点不应直接进入世界对象库。

## 4. 系统三层结构

三层按创作资产和工作流划分。`account` 不承载小说创作资产，而是三层之外的公开身份与
项目 owner 边界；`infrastructure/tasks` 与 `infrastructure/llm` 是共享基础设施，不计入
业务模块数量。可编辑模块图见
[`architecture/module-architecture.drawio`](architecture/module-architecture.drawio)，
无需 Draw.io 时可打开
[`architecture/module-architecture.html`](architecture/module-architecture.html)
查看兼容交互预览。图中箭头只表示主要调用或资料流，不能据此绕过稳定接口或推断完整
import 依赖。

### 4.0 身份与项目所有权边界

| 模块 | 核心表 | 职责 |
|------|--------|------|
| account | accounts, account_identities, web_sessions, email_login_challenges, account_security_events, account_consents | 公开身份、浏览器会话、重新认证、协议同意与延期删除；仅通过 contracts/facade 向 project/settings 提供 owner 语义 |

每个 `projects.owner_id` 必须引用一个 `accounts.id`。账号状态门禁不替代项目内所有业务读写的
`novel_id` 条件；二者分别解决 owner 与项目隔离。

### 4.1 事实层

维护小说当前正史事实。world 模块（v3 因果时空网）统一管理 CoreEntity、Character、Event、EntityRelation，已吸收原 character 和 timeline 模块。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| project | projects | 作者项目或隐藏互动隔离根的元信息；`project_kind` 区分两者 |
| world | core_entities, characters, character_knowledge, entity_relations, events, entity_revisions, text_archive，以及 Profile/World Bible/知识边界表 | 核心实体、人物档案、知识边界、关系、事件、版本归档与世界书 |
| memory | memory_events, memory_scene_checkpoints, memory_scene_snapshots, memory_snapshots, delta_log | Scene 事件溯源、分维度 checkpoint、稀疏全量快照与字段变化日志 |

> geo 模块已移除（地理对象走 core_entities entity_type="location"）；character/timeline 已合并至 world。

### 4.2 结构层

把事实组织成可执行的剧情计划。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| outline | story_outline_heads, story_outline_revisions, plot_threads, outline_arcs, scenes, scene_spans, scene_summary_checkpoints, scene_chapter_links, foreshadowing_plans, reveal_plans | 小说总纲、剧情线/篇章纲/Scene 卡、版本绑定片段、可见摘要、伏笔与揭示 |

结构粒度遵循 `World → StoryOutline → OutlineArc → Scene`。StoryOutline 用不可变 revision
保存至少半部小说尺度的长期方向，head 通过 base/current CAS 选择当前版本；采用总纲本身
不展开或创建 PlotThread、OutlineArc、Scene、伏笔与揭示等下层资产。

### 4.3 辅助层

负责检索、上下文编译、写作与导入导出。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| rag | rag_chunks, rag_index_state, rag_entity_appearances | canonical/working 独立的可重建候选召回、索引新鲜度与对象出场派生索引 |
| context | context_confirmations, context_confirmation_asset_refs, context_snapshots, evidence_links, context_retrieval_traces, activation profile tables | 统一可见性、精确失效索引、证据编排、检索追踪及 AI 参考资料/快照审计 |
| writing | writing_drafts, writing_conflict_checks, writing_conflict_items | 正文工作稿/已发布事实源、AI 建议采用与不自动改文的冲突检查 |
| imports | import_records, imported_chapters, import_workflow_runs | 文件导入、来源章节兼容承载与持久化授权/恢复状态的深度导入 workflow |
| settings | account_llm_credentials, global_llm_defaults, global_author_preferences, project_author_preferences | 按 owner 的已验证模型凭据和当前模板、全局作者偏好及项目作者偏好覆盖 |

> review 模块已移除（结构复查功能暂缓）。小说检索不新增平行
> retrieval/narrative 模块：writing 管原文，outline 管 Scene 映射，rag 管派生索引，
> context 管可见性与证据链，world 管对象/人物知识。

### 4.4 RP 互动领域

`interaction` 位于作者创作资产三层之外，但仍使用隐藏项目作为统一隔离根。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| interaction | interaction_journeys, interaction_message_nodes, interaction_branch_selections, interaction_generation_attempts, interaction_summary_segments, interaction_overview_revisions, interaction_account_preferences | 私人 RP 旅程、不可变选中历史、流式生成恢复、重新生成/其他分支、自动回顾、看海循环与低频体验确认 |

interaction 只消费 project/settings/tasks 的稳定 facade。普通故事结果只进入互动旅程；
不能写回作者 World、Outline、writing 或 memory。看海模式由确定性 step 循环驱动，每一步
都有预算、任务、lease、selection epoch 和终态，不构成自治 Agent 运行时。

### 4.5 共享基础设施

| 边界 | 核心承载 | 职责 |
|------|----------|------|
| `infrastructure/tasks` | `async_tasks` | PostgreSQL 任务队列、lease / retry / recovery 与 worker；业务 handler 仍由所属模块注册 |
| `infrastructure/llm` | 无业务事实表 | provider 客户端、结构化输出校验、预算、超时与受控 step；不承载业务编排或资产写入 |

带 `novel_id` 的业务 LLM 调用必须先通过 `project.open_project_llm_client()` 或可恢复任务的
project snapshot seam，再进入 `infrastructure/llm`。project 根据 owner 解析已验证的账户级
provider/model/Key；项目只能叠加非 secret 工作流设置。业务模块不得直接拼装
provider/profile。

## 5. 实际目录结构

```text
backend/
├── app/
│   ├── main.py              — FastAPI 应用入口
├── core/
│   ├── base.py              — ORM 基类（UUIDMixin / TimestampMixin / StatusMixin / NovelMixin）
│   ├── config.py            — 配置管理（dataclass + get_settings() 单例）
│   ├── database.py          — 数据库连接管理（DatabaseManager）
│   ├── crud.py               — BaseCRUDService 通用 CRUD 模板（novel-scoped）
│   └── dependencies.py      — 依赖注入（DbSession / AppSettings）
├── shared/
│   ├── constants.py         — 全局常量
│   ├── enums.py             — 全局枚举
│   ├── types.py             — 类型别名
│   └── utils.py             — 工具函数
├── infrastructure/
│   ├── llm/                 — LLM 客户端
│   │   ├── client.py        — LLMClient（generate / generate_structured / generate_stream）
│   │   ├── providers.py     — Provider（OpenAI 兼容）
│   │   ├── retry.py         — 指数退避重试
│   │   ├── schemas.py       — LLM 请求/响应 Pydantic schema
│   │   └── errors.py        — LLM 错误类型
│   └── tasks/               — 异步任务系统
│       ├── models.py        — AsyncTask ORM
│       ├── worker.py        — Worker 循环（FOR UPDATE SKIP LOCKED）
│       ├── registry.py      — 任务处理器注册（@task_handler）
│       └── api.py           — 任务提交/状态查询 API
├── modules/                 — 11 个业务模块（见上文列表）
├── prompts/                 — 结构化创作与抽取 Prompt
├── tests/                   — 集成测试与 API 测试
├── pyproject.toml
└── alembic/                 — 数据库迁移
```

模块只创建当前职责需要的文件。跨模块存在稳定消费时使用 `contracts.py` / `facade.py` 或
DI port；`models.py` / `schemas.py` / `repositories.py` / `services.py` / `api.py`、
`tasks.py` 也都按领域需要存在，不为统一目录外观创建空 seam。

## 6. 模块通信规则

- 跨模块生产代码只能导入 `contracts.py`、`facade.py` 或 DI port
- `api.py` 是 HTTP 入口，不作为模块间调用接口
- API 层和 facade 不写复杂业务逻辑；非平凡编排下沉到拥有领域概念的模块实现

## 7. 前端架构

SPA 控制台使用 Vue 3 SFC。Vue shell 拥有 topbar、sidebar、命令栏、主题、快捷键和静态
service host；`home` / `journeys` / `interaction` / `project` / `today` / `writing` / `world` /
`map` / `rag` / `outline` / `generate` / `settings` / `project-settings` 的主 DOM 均由
Vue 组件拥有。既有 hash router 继续作为窄的
命令式 route-host seam 管理 URL、兼容别名、项目同步和 `#workspace-content` 子树，Vue 视图
经 `vue/mountIsland.js` 接入同一生命周期。外壳收口时已评估 Vue Router，当前不引入，
避免新增依赖和 URL/wire 迁移。AI 地图册由 `MapWorkspaceView` 直接拥有层级、候选对比、来源、
标注和审查交互，不保留 Leaflet/Canvas 命令式视口。toast/modal 保留集中式命令服务。动态用户、
AI 与 API 内容禁止 `v-html`。router 不缓存活 DOM，写作等会话通过项目隔离的显式 snapshot 恢复。
详见 ADR-0009、其附录 A 与 ADR-0012。
当前 router 识别 14 个 hash 名称：
home / project / today / journeys / interaction / world / rag / outline / scene / writing / map /
generate / llm / settings / project-settings。`scene` 只重定向
`outline/scenes`，`llm` 只重定向全局或项目设置，两者都不拥有独立页面 DOM。
地图册是一级作者工作台，`world` 中地图入口只保留路由跳转。
作者壳层默认按任务组织为“首页、写作、人物与世界、故事结构、地图、查找”；`today` 是
有效作者项目的智能续接首页，生成中心和设置保留兼容深链但不占主导航。移动端以五项带文字
底栏和“全部”面板承接相同能力，不建立第二套路由或 wire 契约。
详见 `docs/modules/14_frontend.md`。

## 8. 明确不做

复杂多 Agent 协同写正文、未经用户确认或流水线授权的自动资产合并、Neo4j/GraphRAG、
项目共享/多人协作权限和商业功能。

## 9. 技术栈

- **后端**：Python >=3.12 + FastAPI + async SQLAlchemy 2.0 + Pydantic v2
- **数据库**：PostgreSQL 17 + pgvector + pg_trgm
- **ORM 基类**：UUID 主键 / 时间戳 / NovelMixin（novel_id）/ StatusMixin（status）
- **LLM**：OpenAI 兼容 API（支持结构化输出 response_format）
- **任务队列**：PostgreSQL 表 + 进程内 worker（FOR UPDATE SKIP LOCKED）
- **前端**：Vue 3 SFC + CSS 变量；保留 hash router、Proxy 状态和 Leaflet/Canvas 作为窄命令式 seam（ADR-0009）
- **测试**：pytest + pytest-asyncio + SQLite 内存引擎
- **容器**：Docker Compose（PostgreSQL 17 + pgvector）
