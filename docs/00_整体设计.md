# AI 长篇小说结构化创作引擎：整体设计 v2.0（实际实现）

## 1. 项目定位

本项目当前阶段不以"AI 直接生成完整正文"为核心目标，而是构建一个面向中文长篇小说创作者的 **结构化创作引擎**。

系统核心产物是结构化创作资产：

- 核心实体（CoreEntity，统一管理所有世界对象）
- 人物档案（Character，entity_id FK → core_entities）
- 人物知识边界（CharacterKnowledge）
- 小说总纲（StoryOutline，小说级上位结构的不可变版本聚合）
- 剧情线（PlotThread）
- 篇章纲（OutlineArc）
- Scene 卡（Scene，最小叙事单元，独立 `scenes` 表）
- Delta 变更日志（DeltaLog，结构化字段变更审计）
- 文本归档（TextArchive，长文本字段版本历史）
- 伏笔计划（ForeshadowingPlan）
- 信息揭示计划（RevealPlan）
- 长期记忆（MemoryEvent + MemorySnapshot，事件溯源）
- 轻量时间线（Event，entity_type="event"，v3 中由 core_entities 统一管理）
- RAG 检索上下文（RagChunk）
- 正文草稿（WritingDraft，人工撰写+导入）

## 3. 核心原则

### 3.1 少 Agent，强 Context

当前不构建复杂多 Agent 创作工厂。运行时 LLM 调用使用受控 step：调用方显式定义
schema、预算、超时、日志与权限；不允许自主选工具或自主业务写入。Prompt 的活跃清单、
调用方与输出契约只在 [`prompts/Prompt体系设计.md`](prompts/Prompt体系设计.md) 维护，避免
把会随工作流演进的文件名重复写入整体架构。

通用 Prompt 模板通过 `infrastructure/llm/prompt_loader.py` 从 `backend/prompts/` 加载；阶段性
深度导入 Prompt 由 adapter 组装。
深度导入 60 章主链的 Phase 0 是确定性窗口与上下文计划，不调用 LLM；Phase 1a / 1b / 1c
Prompt 由 `modules/imports/workflow_llm_adapters.py` 组装，并通过结构化 adapter、token
预算和 schema guard 执行。Phase 1a / 1b 输出是中间候选，正式 Scene 写入仍由 imports
workflow 的融合与 commit 阶段决定；不存在独立的 legacy Scene 切分入口。

### 3.2 Prompt 按创作阶段合并

不要按数据库表拆 Prompt。一次 Prompt 输出多个 JSON 数组，入库时分别写入对应表。

### 3.3 数据按对象类型拆分

Prompt 可以合并，但数据库仍按对象类型拆分。一次 Prompt 可以输出多个数组，入库时分别写入对应的表。

### 3.4 待处理建议先行，作者采用后生效（授权流水线例外）

普通 AI 生成默认不直接改写当前有效资产。作者面对的统一流程是：

```text
AI 生成待处理建议或临时预览
    ↓
Schema 校验 / 服务层约束检查 / 去重判断
    ↓
作者采用 / 编辑后采用 / 合并 / 设为别名 / 忽略
    ↓
目标领域写入当前有效资产
```

内部可继续使用 `candidate` / `proposal` / `canonical` 等兼容状态，但前端统一投影为
`review / active / archived`，分别显示“待处理 / 已采用 / 历史”。`conflicted`、低置信、
`needs_review` 和 POV 风险是注意原因，不是并列生命周期。人工创建世界对象、关系和别名时，
保存动作本身即表达采用意图；正文则保留“工作稿 → 已发布”的内容成熟度。

**例外**：深度导入等自动流水线必须在启动时由用户一次性授权，并把授权策略、章节范围和
时间写入任务 meta/result。授权范围内、规则明确且可回滚的结果可自动写入派生或已采用资产；
冲突、低置信和无法消歧的实体、关系、别名或结构结果进入待处理。所有自动写入保留
`auto_ingested`、workflow、来源章节/Scene、证据和回滚元数据，完成结果按“已采用 / 待处理 /
未采用”汇总。

### 3.5 对象抽取不是 NER，而是长期创作资产识别

系统不是要抽取尽可能多的名词，而是识别值得长期维护的创作资产。不重要对象、路人、普通道具、一次性地点不应直接进入世界对象库。

## 4. 系统三层结构

### 4.1 事实层

维护小说当前正史事实。world 模块（v3 因果时空网）统一管理 CoreEntity、Character、Event、EntityRelation，已吸收原 character 和 timeline 模块。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| project | projects | 小说项目元信息 |
| world | core_entities, characters, character_knowledge, entity_relations, events, entity_revisions, text_archive，以及 Profile/World Bible/知识边界表 | 核心实体、人物档案、知识边界、关系、事件、版本归档与世界书 |
| memory | memory_events, memory_snapshots, delta_log | 长期记忆（事件溯源 + 阶段性全景快照 + 字段变化日志） |

> geo 模块已移除（地理对象走 core_entities entity_type="location"）；character/timeline 已合并至 world。

### 4.2 结构层

把事实组织成可执行的剧情计划。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| outline | story_outline_heads, story_outline_revisions, plot_threads, outline_arcs, scenes, scene_spans, scene_summary_checkpoints, scene_chapter_links, foreshadowing_plans, reveal_plans | 小说总纲、剧情线/篇章纲/Scene 卡、版本绑定片段、可见摘要、伏笔与揭示 |

结构粒度遵循 `World → StoryOutline → OutlineArc → Scene`。StoryOutline 用不可变 revision
保存至少半部小说尺度的长期方向，head 通过 base/current CAS 选择当前版本；采用总纲本身
不展开或创建 PlotThread、OutlineArc、Scene、伏笔与揭示等下层资产。

### 4.3 辅助层

负责检索、上下文编译、写作与导入导出。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| rag | rag_chunks, rag_index_state | canonical/working 独立的可重建候选召回与索引新鲜度 |
| context | context_confirmations / context_confirmation_asset_refs / context_snapshots / evidence_links | 统一可见性、精确资产失效索引、证据编排与 provenance，以及 AI 参考资料/快照审计 |
| writing | writing_drafts | 正文工作稿/已发布版本事实源、稳定范围引用与 AI 建议采用来源追踪 |
| imports | import_records | 小说文件导入与持久化批量授权的深度导入工作流 |
| settings | global_llm_defaults, global_author_preferences, project_author_preferences | 全局 LLM 默认 / 全局作者偏好 / 项目覆盖（owner_id 预留账户系统） |
| infrastructure | async_tasks | 异步任务系统（LLM 调用、任务队列） |

> review 模块已移除（结构复查功能暂缓）。小说检索不新增平行
> retrieval/narrative 模块：writing 管原文，outline 管 Scene 映射，rag 管派生索引，
> context 管可见性与证据链，world 管对象/人物知识。

## 5. 实际目录结构

```text
backend/
├── app/
│   ├── main.py              — FastAPI 应用入口
├── core/
│   ├── base.py              — ORM 基类（UUIDMixin / TimestampMixin / StatusMixin / NovelMixin）
│   ├── config.py            — 配置管理（dataclass + get_settings() 单例）
│   ├── database.py          — 数据库连接管理（DatabaseManager）
│   ├── crud.py               — BaseCRUDService 通用 CRUD 模板（novel-scoped）
│   └── dependencies.py      — 依赖注入（DbSession / AppSettings）
├── shared/
│   ├── constants.py         — 全局常量
│   ├── enums.py             — 全局枚举
│   ├── types.py             — 类型别名
│   └── utils.py             — 工具函数
├── infrastructure/
│   ├── llm/                 — LLM 客户端
│   │   ├── client.py        — LLMClient（generate / generate_structured / generate_stream）
│   │   ├── providers.py     — Provider（OpenAI 兼容）
│   │   ├── retry.py         — 指数退避重试
│   │   ├── schemas.py       — LLM 请求/响应 Pydantic schema
│   │   └── errors.py        — LLM 错误类型
│   └── tasks/               — 异步任务系统
│       ├── models.py        — AsyncTask ORM
│       ├── worker.py        — Worker 循环（FOR UPDATE SKIP LOCKED）
│       ├── registry.py      — 任务处理器注册（@task_handler）
│       └── api.py           — 任务提交/状态查询 API
├── modules/                 — 9 个业务模块（见上文列表）
├── prompts/                 — 结构化创作与抽取 Prompt
├── tests/                   — 集成测试与 API 测试
├── pyproject.toml
└── alembic/                 — 数据库迁移
```

每个业务模块标准文件：`contracts.py` / `models.py` / `schemas.py` / `repositories.py` / `services.py` / `api.py`。`facade.py` 和 `tasks.py` 按需可选。

## 6. 模块通信规则

- 跨模块生产代码只能导入 `contracts.py`、`facade.py` 或 DI port
- `api.py` 是 HTTP 入口，不作为模块间调用接口
- API 层和 facade 不写复杂业务逻辑；非平凡编排下沉到拥有领域概念的模块实现

## 7. 前端架构

SPA 控制台使用 Vue 3 SFC。Vue shell 拥有 topbar、sidebar、命令栏、主题、快捷键和静态
service host；`project` / `writing` / `world` / `map` / `rag` / `outline` / `generate` /
`settings` / `project-settings` 的主 DOM 均由 Vue 组件拥有。既有 hash router 继续作为窄的
命令式 route-host seam 管理 URL、兼容别名、项目同步和 `#workspace-content` 子树，Vue 视图
经 `vue/mountIsland.js` 接入同一生命周期。外壳收口时已评估 Vue Router，当前不引入，
避免新增依赖和 URL/wire 迁移。Leaflet/Canvas 地图视口保留在 `mapView` controller seam，
toast/modal 保留集中式命令服务。Writing 仅通过 Vue bridge 调用 `mapQuickCreateView`，
并复用 `sceneAlerts` / `versionDiff` 纯 helper；没有其他旧视图运行时依赖。动态用户、AI 与 API
内容禁止 `v-html`。router 不缓存活 DOM，写作等会话通过项目隔离的显式 snapshot 恢复。
这些前端内部重构不改变 HTTP API、数据库 schema 或前端 wire shape。详见 ADR-0009 及其附录 A。
当前 router 识别 11 个 hash 名称：
project / world / rag / outline / scene / writing / map / generate / llm / settings /
project-settings。其中 9 个实际渲染目标全部是 Vue 视图；`scene` 只重定向
`outline/scenes`，`llm` 只重定向全局或项目设置，两者都不拥有独立页面 DOM。
地图已升级为一级工作台，`world` 中地图入口只保留兼容跳转。
详见 `docs/modules/14_frontend.md`。

## 8. 明确不做

复杂多 Agent 协同写正文、未经用户确认或流水线授权的自动资产合并、Neo4j/GraphRAG、多用户权限、商业功能。

## 9. 技术栈

- **后端**：Python >=3.12 + FastAPI + async SQLAlchemy 2.0 + Pydantic v2
- **数据库**：PostgreSQL 17 + pgvector + pg_trgm
- **ORM 基类**：UUID 主键 / 时间戳 / NovelMixin（novel_id）/ StatusMixin（status）
- **LLM**：OpenAI 兼容 API（支持结构化输出 response_format）
- **任务队列**：PostgreSQL 表 + 进程内 worker（FOR UPDATE SKIP LOCKED）
- **前端**：Vue 3 SFC + CSS 变量；保留 hash router、Proxy 状态和 Leaflet/Canvas 作为窄命令式 seam（ADR-0009）
- **测试**：pytest + pytest-asyncio + SQLite 内存引擎
- **容器**：Docker Compose（PostgreSQL 17 + pgvector）
