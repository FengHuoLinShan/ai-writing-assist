# AI 长篇小说结构化创作引擎：整体设计 v2.0（实际实现）

## 1. 项目定位

本项目当前阶段不以"AI 直接生成完整正文"为核心目标，而是构建一个面向中文长篇小说创作者的 **结构化创作引擎**。

系统核心产物是结构化创作资产：

- 世界对象（WorldEntity）
- 人物档案（Character）
- 人物知识边界（CharacterKnowledge）
- 地理关系与宏观历史（GeoLocation / GeoEdge / GeoEra）
- 剧情线（PlotThread）
- 篇章纲（OutlineArc）
- 章节卡（ChapterCard）与场景卡（SceneCard JSONB）
- 伏笔计划（ForeshadowingPlan）
- 信息揭示计划（RevealPlan）
- 长期记忆（MemoryRecord）
- 轻量时间线（TimelineEvent）
- RAG 检索上下文（RagChunk）
- 结构一致性复查结果（ReviewReport）
- 正文草稿（WritingDraft，人工撰写+导入）

## 3. 核心原则

### 3.1 少 Agent，强 Context

当前不构建复杂多 Agent 创作工厂。系统使用 4 个核心创作 Prompt + 3 个工具型抽取 Prompt：

1. `structure_world_character.md` — 世界与人物结构生成
2. `structure_plot.md` — 剧情结构生成
3. `structure_chapter_scene.md` — 章节与场景结构生成
4. `structure_review_memory.md` — 结构复查与状态抽取
5. `structure_extraction.md` — 从章节正文抽取世界对象候选
6. `extract_chapter_scene.md` — 从正文提取章节卡字段
7. `extract_character.md` — 从正文提取人物档案字段

所有 Prompt 通过 `infrastructure/llm/prompt_loader.py` 从 `backend/prompts/` 加载。

### 3.2 Prompt 按创作阶段合并

不要按数据库表拆 Prompt。一次 Prompt 输出多个 JSON 数组，入库时分别写入对应表。

### 3.3 数据按对象类型拆分

Prompt 可以合并，但数据库仍按对象类型拆分。一次 Prompt 可以输出多个数组，入库时分别写入对应的表。

### 3.4 候选先行，人工确认正史

AI 不直接创建正史对象。统一流程：

```text
AI 生成候选
    ↓
Schema 校验
    ↓
结构复查
    ↓
用户确认 / 编辑 / 拒绝
    ↓
写入 canonical 正史库
```

### 3.5 对象抽取不是 NER，而是长期创作资产识别

系统不是要抽取尽可能多的名词，而是识别值得长期维护的创作资产。不重要对象、路人、普通道具、一次性地点不应直接进入世界对象库。

## 4. 系统三层结构

### 4.1 事实层

维护小说当前正史事实。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| project | projects | 小说项目元信息 |
| world | world_entities, relationships, entity_aliases, entity_candidates | 世界对象与关系 |
| geo | geo_locations, geo_edges, geo_eras | 地理关系与宏观历史 |
| character | characters, character_knowledge | 人物档案与知识边界 |
| memory | memory_records, memory_update_proposals | 长期记忆 |
| timeline | timeline_events | 轻量事件顺序 |

### 4.2 结构层

把事实组织成可执行的剧情计划。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| outline | plot_threads, outline_arcs, chapter_cards, foreshadowing_plans, reveal_plans | 剧情线/篇章纲/章节卡/伏笔/揭示 |

### 4.3 辅助层

负责检索、上下文编译、审查与导入导出。

| 模块 | 核心表 | 职责 |
|------|--------|------|
| rag | rag_chunks | 检索增强（向量+关键词+metadata） |
| context | 无独立表（读取其他模块数据编译） | 上下文编译 |
| review | review_reports | 结构复查 |
| writing | writing_drafts | 正文草稿 |
| imports | import_records | 小说文件导入（原设计以外新增） |
| infrastructure | async_tasks | LLM 调用与异步任务 |

```text

│   ├── database.py          — 数据库连接管理（DatabaseManager）
```

每个业务模块标准结构：

```text
modules/<name>/
├── __init__.py              — 导出 facade 函数
├── contracts.py             — 跨模块数据契约（dataclass）
├── models.py                — SQLAlchemy ORM 模型
├── schemas.py               — Pydantic 请求/响应 schema
├── repositories.py          — 数据访问层
├── services.py              — 业务逻辑

├── api.py                   — FastAPI 路由
├── tasks.py                 — 异步任务处理器（可选）
└── tests/
    ├── conftest.py          — SQLite 内存测试夹具
    └── test_*.py            — 三层测试
```

## 6. 模块通信规则

- 其他模块只能导入某模块的 `contracts.py` 和 `facade.py`
- 禁止跨模块直接导入 `models.py`、`repositories.py`、`services.py`
- API 层不写复杂业务逻辑
- facade 不写复杂业务逻辑，只做稳定对外入口

## 7. 前端架构

## 9. 明确不做

当前阶段不做：复杂多 Agent 协同写正文、20+ Agent 管理系统、完整正文自动生成主流程、复杂时间锚点和相对时间推理、自动合并正史对象、Neo4j / 专用图数据库、复杂 GraphRAG 社区摘要、对所有 Mention 实时 embedding、多用户权限系统、商业化和运营、专业 GIS / PostGIS / 地图瓦片。

## 10. 技术栈

- **后端**：Python 3.13 + FastAPI + async SQLAlchemy 2.0 + Pydantic v2
- **数据库**：PostgreSQL 17 + pgvector + pg_trgm
- **ORM 基类**：UUID 主键 / 时间戳 / NovelMixin（novel_id）/ StatusMixin（status）
- **LLM**：OpenAI 兼容 API（支持结构化输出 response_format）
- **任务队列**：PostgreSQL 表 + 进程内 worker（FOR UPDATE SKIP LOCKED）
- **前端**：Vanilla JS + CSS 变量 + Proxy 响应式状态
- **测试**：pytest + pytest-asyncio + SQLite 内存引擎
- **容器**：Docker Compose（PostgreSQL 17 + pgvector）
