# 模块当前能力与跨模块需求能力分析

> 日期：2026-07-11  
> 性质：基于当前代码、稳定接口、测试和本地运行状态的时间点分析。本文不是新的架构契约；当前实现仍以模块 README、`contracts.py`、`facade.py`、ORM 与迁移为准。

## 1. 结论摘要

当前系统已经不是“若干 CRUD 模块”的集合，而是形成了较清晰的事实源、结构源、检索、上下文和自动流水线分工：

- `project/settings` 提供项目生命周期和有效配置；
- `writing` 是正文事实源；
- `world/memory` 提供当前事实、知识边界和历史状态；
- `outline` 提供 Scene 与剧情结构；
- `rag` 只做候选召回；
- `context` 负责选择、可见性、证据校验和确认；
- `imports` 在一次性用户授权下批量生产上述资产。

九个活跃模块的确定性工程能力总体为“中高到高”：novel 隔离、schema guard、候选/采用语义、版本 hash、用户确认、软废弃和回滚已经覆盖主要危险路径。初始审计发现的三个 P0 错位已在 2026-07-12 形成工程闭环：

1. **配置消费已统一**：`settings -> project context -> project runtime` 物化项目、全局和系统默认，novel-scoped 业务调用使用统一 seam；可恢复任务使用 secret-free 提交时快照。
2. **语义质量已可重复测量，但当前质量仍有明确缺口**：通用 Pilot v1.1 已重冻结 351 条；旧 RAG 聚合/可见性与 World 0÷0 指标错误已修复。fresh RAG 已证明 R@10/leakage 通过而 P@5/MRR/abstention 失败；corrected World 已证明 entity/alias precision 通过，但 relation coverage 为 0 且 ordinary pollution 失败。
3. **系统门禁已统一**：`make test-fast` 使用单 pytest session，root fixture 归属与全 backend 测试源 conftest import 守卫已固化。

综合判断：系统的下一阶段不应继续横向增加大模块或更多 API，而应使用
P0 已形成的配置、评测和测试闭环，优先补齐**Scene/证据覆盖遥测、context
确定性查询计划和任务 stale 生命周期闭环**，再按已测失败项逐模块提质。

## 2. 分析口径

### 2.1 范围

本文覆盖仓库定义的 9 个活跃业务模块：

`project / imports / world / memory / outline / rag / context / writing / settings`

另补充两个横向层：

- `infrastructure`：LLM client、受控 step、PostgreSQL 任务队列；
- `frontend-console`：所有后端能力的作者工作台和确认面。

地图不是独立业务模块，按 `world` 子系统评估。

### 2.2 “当前能力”与“需求能力”

- **当前能力**：当前代码已经能完成、具有稳定入口、存在真实消费方，并有测试或运行证据支撑的能力。
- **需求能力**：其他模块实际依赖该模块提供的语义，不等同于该模块 README 中声称的职责。
- **工程成熟度**：接口、状态机、失败/恢复、隔离、安全和测试的成熟程度。
- **结果质量证据**：真实内容质量、相关性、召回、误判和模型方差是否被量化。

成熟度使用“高 / 中高 / 中 / 低”作相对判断，不把测试通过率伪装成业务准确率。

## 3. 全局能力供需图

| 能力提供方 | 主要消费方 | 消费方真正需要的能力 | 当前匹配度 |
|---|---|---|---|
| project | context、imports、world、settings、所有 novel-scoped 数据 | 稳定 novel 根、软删除生命周期、项目上下文、有效运行配置 | 高 |
| settings | project、所有 LLM 工作流 | 项目 > 全局 > 系统的统一 effective 配置、字段来源、安全 Key 语义 | 中高：计算完整，运行时采用不完整 |
| writing | imports、outline、rag、context、world | 正文版本事实源、稳定 hash/range ref、canonical/working 选择、字面读取 | 高 |
| world | context、imports、writing、project | 正史对象、人物知识、关系、地图事实、候选采用、去重和回滚 | 中高 |
| memory | context、writing、imports | 可重放历史、章级全景、连续性证据、幂等 Delta 写入 | 中高，消费面偏窄 |
| outline | imports、writing、rag、context、world | Scene/结构资产、版本绑定 span、揭示边界、结构整理 | 中高到高 |
| rag | context；经 context 间接服务 outline/world | 高相关候选召回、metadata/时间过滤、freshness 和降级诊断 | 工程中高，语义质量未知 |
| context | writing、outline、world、imports、frontend | 可见性、预算、确认、证据重定位、snapshot/provenance | 中高到高 |
| imports | writing、outline、world、memory、context | 批量解析与受控生产、覆盖质量、provenance、恢复和整批回滚 | 工程中高，语义质量中等证据 |

关键依赖链如下：

```text
settings -> project context -> LLM workflows

writing -> outline SceneSpan -> rag candidate -> context verified evidence
   |              |                                |
   +--------------+------------------------------> AI workflows

imports -> writing / outline / world / memory
        -> context snapshots + workflow provenance + rollback
```

任何模块都不应把 RAG chunk、LLM 输出或 context confirmation 本身视为正史。正史仍由对应领域模块拥有。

## 4. 各模块分析

## 4.1 project

### 当前能力

- 项目 CRUD、列表、回收站、恢复和永久删除入口；
- 标题、题材、语言、创作阶段、默认 reveal policy 等项目元信息；
- 项目级 LLM 配置安全保存，不回显 API Key；
- `get_project_context()` 对外提供项目上下文，并通过 settings 物化 effective settings；
- 项目级智能去重只做跨领域聚合，实际判断和写入委托 `world/outline`；
- `ProjectSummary` 为 settings 聚合提供轻量读取面。

工程成熟度：**高**。项目生命周期、Key 脱敏和去重确认边界清楚。

### 其他模块需求能力

- 所有模块要求 `novel_id` 存在且不跨项目；
- context 需要稳定的题材、语气、语言和 reveal 默认值；
- imports/world 需要已经物化的项目级 LLM profile；
- settings 需要只读项目摘要和 raw project settings；
- 永久删除需要完整级联，软删除不能让项目继续出现在普通入口。

### 匹配与缺口

- 核心需求基本满足。
- `get_project_by_id()` 和 `list_active_projects()` 仍返回 ORM；虽然当前调用方只读，但比 dataclass/Pydantic contract 更容易形成隐式耦合。
- README 末尾“仅实现 CRUD 和项目上下文读取”的 MVP 描述已落后于智能去重、回收站和 effective settings 能力。
- 项目配置能否生效最终取决于下游是否使用 `get_project_context()` 和 `LLMClient.from_project_settings()`；这不是 project 的计算缺陷，但会表现为“设置保存成功却没有改变模型调用”。

### 建议门禁

- novel 隔离错误：0；
- API Key 明文响应/日志：0；
- active/recycle-bin 集合交叉：0；
- effective settings 在同一项目内的解析一致率：100%。

## 4.2 settings

### 当前能力

- 全局 LLM 默认和全局作者偏好；
- 项目级作者偏好覆盖；
- 字段级继承和字段级恢复默认；
- effective response 对每个字段标注 `project/global/system/unset` 来源；
- API Key 永远项目级，全局 schema 和 service 双重拒绝 Key；
- `materialize_effective_project_settings()` 把 raw project settings 转成运行时 profile；
- 统计哪些项目仍使用全局默认。

工程成熟度：**中高到高**。继承语义和 Key 安全明确。

### 其他模块需求能力

所有调用 LLM 的模块真正需要：

- 相同项目、相同时间点解析出相同 provider/base URL/model/Key/timeout；
- 运行调用和设置页展示使用同一套 precedence；
- 日志、任务结果、健康检查只使用脱敏 summary；
- 项目设置改变后，后续新任务必须实际消费新配置。

### 匹配与缺口

effective 计算与运行时消费已闭环。Writing、Outline、World/Imports 和
RAG reranker 的 novel-scoped 文本/结构化调用都使用 project runtime seam；
深度导入任务在提交时持久化 secret-free effective-profile snapshot，
使恢复后的 model/参数不因 worker 延迟而漂移。AST 守卫阻止新的
DB-backed direct-client 回归。

RAG query/chunk embedding 有意保留独立 `EMBEDDING_*` 配置，它不是
项目 chat profile 消费缺口。无 novel 的 health/development tool 和独立
P0.2 Codex generator/judge 也不属于业务 runtime seam。

此外：

- demo 阶段 owner 仍是 nil UUID，没有多用户授权；
- 全局 deep-import 参数按既定范围故意不实现，不应误报为缺陷；
- `/refresh` 是调试通知，不是分布式缓存失效协议。

### 建议门禁

- 所有带 `novel_id` 的 LLM 生产调用都能追溯到同一 effective profile；
- 项目设置端到端消费覆盖率：100%；
- API Key 泄漏：0；
- provider/model/base URL 来源在 UI、任务 artifact、health 中一致。

## 4.3 writing

### 当前能力

- 正文 draft/published/candidate/canonical/deprecated 兼容生命周期；
- published 不可原地修改，编辑使用 copy-on-write；
- AI candidate 通过 copy-on-adopt 生成新的 working draft，保留来源和采用审计；
- canonical/working 两套严格正文选择规则；
- SHA-256 source hash、range hash、稳定 offset 引用；
- 有上限、可分页的字面 grep 和范围读取；
- 保存/发布触发 working/canonical RAG index state；
- 断章时通过可注入 outline port 同步 Scene；
- 规则冲突检查聚合 outline Scene、world map、memory continuity；
- AI 软复核和修复建议需要 fresh context confirmation；
- 已存在 `POST /api/writing/generate`，可从已确认 context 生成正文 candidate，并支持 POV guard。

工程成熟度：**高**；AI 结果质量证据：**中等**。

### 其他模块需求能力

- imports 需要可靠批量写入章节；
- outline 需要章节正文和章节索引构建结构；
- RAG 需要稳定 draft/hash/offset 重建索引；
- context 需要从 writing 回读并验证所有证据；
- world 生成需要受限章节材料；
- 前端需要不会覆盖新版本的自动保存、采用和版本历史。

这是系统中最不能模糊的事实源之一。其他模块要求的不是“能读到文本”，而是：

- canonical 不得偷偷回退 working；
- candidate 不得进入 working 或 RAG；
- published 不得原地修改；
- source/range ref 必须可重新验证；
- 范围不得跨 draft 或跨章。

### 匹配与缺口

- 事实源能力与需求高度匹配。
- README 仍称“不是核心 AI 正文生成模块”“不负责 AI 自动生成完整正文”，但当前已经有确认后生成 candidate 的完整异步入口。准确表述应是：writing 不自动发布/采用正文，但已负责受控正文候选生成。
- `WritingGenerationService`、冲突 AI review/修复建议已使用 project
  runtime seam，candidate 保留 secret-free managed provenance；确认检查
  仍在 LLM 调用之前。
- 默认测试验证状态机、side effect 和 schema，不评价正文连贯性、POV 文学质量或长章稳定性；真实 LLM 测试也明确不固定生成文本。
- writing 触发 RAG 索引，但“索引最终完成”由任务系统负责，写作成功不等于检索已 fresh。

### 建议门禁

- source/hash/range 验证成功率：100%；
- published 原地修改：0；
- candidate 进入 working/canonical：0；
- AI 结果未确认即影响当前稿：0；
- 项目 LLM profile 消费率：100%；
- POV 隐藏知识泄漏率：0。

## 4.4 world

### 当前能力

world 是当前最宽的事实模块，已经覆盖：

- CoreEntity、Character、CharacterKnowledge、Event、EntityRelation；
- 名称/别名/拼音/embedding 去重与候选融合建议；
- suggestion queue 的采用、编辑后采用、合并、设为别名和忽略；
- canonical/review/archived 作者态投影；
- 关系、别名、对象版本和 TextArchive/EntityRevision 回滚；
- World Bible、profile、知识标签、生成模板及模板版本；
- reader/character 可见性所需的公开信息和人物知识；
- map config、terrain、location binding/layout、marker、territory、observation/fact、dashboard/playback；
- 为 writing 提供 Scene 地图摘要；
- 为 context/imports 提供 world context 和派生 world background；
- 为 project/imports 提供去重、融合和 workflow rollback seam。

工程成熟度：**中高到高**；语义判断质量证据：**中等**。

### 其他模块需求能力

- context 需要只返回允许状态的对象、人物知识和 reveal-safe 内容；
- imports 需要高吞吐、幂等、可回滚的对象/关系/别名/地图 observation 写入口；
- writing 需要稳定的地图和人物状态摘要，而不是 world 内部表；
- project smart dedup 需要建议与应用 seam；
- RAG 需要实体、人物和别名词典；
- outline/context 需要世界背景，但不能复制一份新的正史。

高风险不变量：

- canonical 与 review 必须严格分开；
- 低置信实体不能自动污染正史；
- Character/Knowledge 必须挂在同 novel、正确类型且有效的 CoreEntity；
- observation 只是候选，fact 才是已确认地图事实；
- canonical-to-canonical 合并必须有额外明确确认。

### 匹配与缺口

- 主要领域闭环已存在，并有本轮 487 个模块测试支撑。
- 模块能力面过宽：对象、人物、知识、世界书、生成模板、去重、地图和动态事实共享一个模块与超大 API surface。内部已拆 service/facade，但回归半径仍明显高于其他模块。
- `contracts.py` 除 dataclass 外仍从 `schemas.py` re-export 多个 Pydantic response；稳定契约与 HTTP schema 没有完全分离。
- compatibility shadow、legacy revision、多个 facade hub 增加状态理解成本，调用方必须优先消费 `display_state/source/attention_reasons`。
- 融合/去重的流程安全较强，但缺少人工标注的“同一对象/别名/应分离”质量集；RAG 证据质量也会影响 LLM 辅助判断。
- 地图的 observation -> fact -> playback 闭环已落地，但真实长篇中的时间化事实覆盖和作者纠错成本尚无量化基线。

### 建议门禁

- novel/type/FK 错挂：0；
- 未确认 suggestion/observation 进入 active fact：0；
- canonical 自动错误合并：0；
- reader/character 隐藏事实泄漏：0；
- 去重建议 P@5 建议 ≥ 0.95，召回可低于 precision；
- workflow rollback 不影响人工编辑或其他 workflow：100%。

## 4.5 memory

### 当前能力

- 按 `(novel_id, chapter_index, sequence)` 幂等记录 memory events；
- 清理被新事件流替代的章内尾部事件；
- 从最近 snapshot 开始增量重放 panorama；
- keyset 分页应用大事件流；
- snapshot capture、状态查询和指定章节重建；
- entity timeline；
- typed `MemoryDeltaEventIngest` 批量写入 delta log；
- 为 imports 保存 workflow、Scene、context snapshot provenance；
- 为 writing 提供上一章人物位置连续性证据和可打开目标；
- 对 deep-import delta 提供计数和 workflow rollback 标记。

工程成熟度：**中高**；业务覆盖度：**中等**。

### 其他模块需求能力

- imports 需要把 Scene Delta 幂等写入并在放弃 workflow 时回滚；
- context 需要指定章节的历史全景；
- writing 冲突检查需要轻量、可追溯的连续性证据；
- 长篇运行最终需要可确定重放、可诊断 stale、不会复制 world 正史。

### 匹配与缺口

- 当前实现很好地守住“历史变化，不是第二份正史”的边界。
- 真实消费面仍较窄：主要生产者是 imports 和 publish snapshot，主要消费者是 context/writing。world 的普通人工编辑并没有全面形成 memory event/delta 事件流。
- panorama 是宽松 `dict` 结构，跨模块字段级稳定性弱于 writing range contract 或 outline Scene contract。
- character reveal 路径不能直接使用 raw snapshot full state，context 已做防御阻断；这说明 memory 本身尚未提供完整的角色可见历史投影。
- 缺少针对“同一操作序列重放得到相同状态”的大规模长期基线和故障注入报告。

### 建议门禁

- 同一事件流重放确定性：100%；
- batch 重试产生重复 delta：0；
- workflow rollback 越界：0；
- snapshot + tail replay 与全量 replay 等价；
- 对 context 输出的历史状态必须带章节边界和 provenance。

## 4.6 outline

### 当前能力

- PlotThread、OutlineArc、Scene、ForeshadowingPlan、RevealPlan 全生命周期；

- 删除/合并默认软废弃，危险操作需要 preview + confirmed；
- AI 结构生成和 Scene 提取先生成 preview，作者 apply 后才创建工作资产；
- deep import Phase 1/3 的 Scene/结构写入、修复、fallback 和 workflow cleanup；
- SceneChapterLink；
- 从 `scene_chunks` 派生、版本绑定的 SceneSpan；
- exact/reanchored/chapter_only/unresolved 映射状态；
- Scene summary checkpoint 和 deterministic reader reveal decision；
- 跨章 Scene 建议持久队列；
- 结构资产去重建议和确认应用；
- 对 writing/rag/context/world 暴露稳定 Scene/Span seam。

工程成熟度：**中高到高**；语义结构质量证据：**中等**。

### 其他模块需求能力

- writing 需要 Scene 约束、Scene 树和断章同步；
- RAG 需要版本一致的 SceneSpan 做 chunk 归因；
- context 需要 Scene、前序 brief、summary checkpoint 和 reveal decision；
- world map 需要 Scene anchor；
- imports 需要批量创建、修复、结构补齐和 workflow rollback；

需求的核心不是“有 Scene 表”，而是：

- Scene 的逻辑结构与正文物理范围必须分开；
- 只有精确、版本绑定的 span 可用于自动证据归因；
- 同章顺序不明时必须保守排除 reveal；
- merge/split/fusion 要同步所有派生映射且不丢 provenance；

### 匹配与缺口

- 主要需求已被明确建模，是当前跨模块价值最高的结构 seam。
- facade 是大型兼容 re-export hub；内部已拆子 facade，但外部公共面仍很宽，任何语义变化都需要大量调用方回归。
- 当前本地 RAG 数据 18 个 chunk 中 `scene_id/scene_span_id` 均为空，因此代码虽有严格 Scene 归因，当前运行数据不能证明 Scene 级召回覆盖。
- “人工接受章节级定位”不会提升为 exact，这是正确的安全选择，但会造成角色 Scene 上下文安全为空；系统需要区分“安全低召回”和“索引故障”。
- AI 结构质量仍主要以 schema、覆盖、引用和状态机验证，缺少剧情结构的人工 gold set。
- README 与当前代码存在大量 compatibility 说明，说明迁移已相当成熟，但也意味着长期应收敛 legacy candidate/hub 负担。

### 建议门禁

- exact span 错归因：0；
- source/hash 失效 span 自动用于证据：0；
- merge/split 后派生索引不同步：0；
- AI preview 未确认写入普通资产：0；
- SceneSpan exact coverage 应按正文/Scene 数据集单独监控，不能只报 Scene 总数；
- 结构生成应建立引用有效率、重复率、低置信率和人工采用率基线。

## 4.7 rag

### 已确认的当前能力

- 中文小说分块、offset/hash/index version；
- canonical/working 独立索引和 freshness 状态；
- 关键词、项目词典、关系、importance、向量混合召回；
- entity/character/thread/chapter/Scene/visibility metadata 过滤；
- embedding 失败降级、熔断、重试和维度诊断；
- source_id/source_content_hash 与 SceneSpan 归因；
- context 回读 writing 后才把候选转换为证据；
- 当前本地数据：18 chunks、2 novels、5 个 indexed chapter/mode 状态，18/18 有 embedding，0 failed，0 pending，0 缺 source binding，freshness 均 succeeded；
- 当前本地 18 个 chunk 没有 Scene/SceneSpan 映射，因此 Scene 精度不可实测。

工程成熟度：**中高**；真实检索精度证据：**未知到中等**。

### 其他模块需求能力

- 手动搜索需要 precision/recall 平衡；
- context/writing/outline generation 需要 precision 优先的 Top-K 证据；
- reader/character context 要求泄漏率 0、版本有效率 100%、Scene 错归因 0；
- world/outline fusion/dedup 需要极高 precision，允许较低 recall；
- 跨章 Scene 检测需要在限定章节范围内兼顾 recall；
- imports Phase 2a 当前不需要普通 RAG Top-K，而使用精确 Scene span activation。

### 已确认的精度缺口

1. 仓库有 MRR/NDCG/P@5/R@5 调优器，但自动评估集使用“chunk 前 80 字作查询、共享 entity_id 即相关”的弱标签，没有提交人工标注集或历史评测报告。
2. meaningful-match 只要求任意关键词分数 `> 0` 或任意向量相似度 `> 0`，没有按场景校准的最低相关性阈值。
3. 中文查询会扩展大量 2-4 字 n-gram，SQL 关键词召回使用 OR，长查询容易引入弱相关噪声。
4. `hybrid_search()` 已先截断到 `top_k`，外层只有结果数 `> top_k` 才 rerank，因此 reranker 当前条件不可达；默认配置也关闭 reranker。
5. runtime metrics 只有查询数、空结果、降级、延迟和 embedding 失败，是进程内单例，没有用户相关性反馈。本轮运行实例 `query_count=0`，无法提供线上 precision 证据。
6. context 的通用 loader 直接用 `options.task` 作为 RAG query；像“生成剧情结构”这样的通用任务描述不足以表达当前 Scene、对象或冲突的检索意图。

### 建议验收门槛

以下是建议门槛，不是当前实测成绩：

| 场景 | 建议门槛 |
|---|---|
| 手动检索 | P@5 ≥ 0.80，MRR ≥ 0.85，R@10 ≥ 0.75 |
| 通用创作 context | P@8 ≥ 0.88，source/hash 有效率 100% |
| reader/character | 泄漏率 0，source/hash 有效率 100%，Scene 错归因 0 |
| world/outline 融合与去重 | P@5 ≥ 0.95，允许 recall 约 0.60-0.70 |
| 跨章 Scene 检测 | P@6 ≥ 0.85，限定范围 R@6 ≥ 0.80 |

### 优先补齐

- 建立按消费模块分组的人工 query/relevant/hard-negative 数据集；
- 修复候选池与 reranker 调用条件；
- 分开校准 search/context/fusion/boundary profile；
- 增加 Scene mapping coverage、valid-source rate、stale-drop rate；
- 增加作者“相关/不相关/缺少关键证据”反馈并持久化聚合。
