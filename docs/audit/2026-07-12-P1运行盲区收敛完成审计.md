# P1 运行盲区收敛完成审计

> 日期：2026-07-12
> 实施计划：[`2026-07-12-p1-observability-query-planning-stale-closure.md`](../superpowers/plans/2026-07-12-p1-observability-query-planning-stale-closure.md)
> 结论：工程闭环完成；context planner 按用户授权的放宽口径验收，严格语义质量目标仍未达到。

## 1. 最终判定

P1.1、P1.2 和 P1.3 已形成可运行、可查询、可回归的闭环：

- SceneSpan 与 RAG Scene 映射覆盖由各自模块的稳定 facade 计算，context 只组合 health。
- context 使用不调 LLM 的确定性 planner，最多生成 3 条 clause，执行后回读
  writing 事实源并校验 hash/可见边界。
- 每次 `RagChunksLoader` 运行写入一条隐私安全 trace，包括空结果和子查询异常。
- task 保持五状态，使用冻结 recovery policy、attempt 和 lease fencing；旧 worker 不能
  finalize 新 attempt。
- stale imports 收敛为 `failed + recovery_required`，前端只消费 `available_actions`。
- context snapshot 优先与 owner task 对账，不再只依赖创建时间。

这不表示 RAG 语义精度已达标。P0 corrected RAG 基线和本次 planner 评测仍分开报告。

### 2.2 P1.2 Context 确定性查询计划

- `RetrievalQueryPlanner` 支持 10 种受控 purpose，输入相同时 plan/hash 完全一致。
- clause 总数不超过 3，总候选预算不超过 `max(2k, k+4)`。
- character + Scene 只使用 strict Scene clause；world fusion 没有结构化关系锚点时不扩大为
  task-only 全局搜索。
- loader 串行执行 clause，用稳定 reciprocal-rank fusion 合并，按 chunk ID 去重，
  同分时稳定排序。
- hydrated evidence 包含 `retrieval_clause_ids` 和 `activation_reasons`；section 加性返回
  `retrieval_metadata`。
- writing/conflict/outline/reader/character 通过 confirmation/facade 得到受控 purpose；
  world entity fusion 通过 context 稳定 facade 传入真实 entity IDs。imports Scene activation 保留既有
  专用确定性 source-range 路径，因其不执行 RAG 查询，不伪造 retrieval trace。

planner 纯函数的 500 次本地 p95 门禁为 `< 2ms`，已通过。

### 2.3 P1.3 stale 任务闭环

| 规则 | 结果 |
|---|---|
| claim | `FOR UPDATE SKIP LOCKED` + 新 lease + `attempt += 1` |
| heartbeat/finalize | `id + running + lease_id` 条件更新 |
| stale auto task | 只有 `auto_requeue` 且 attempt 未耗尽时回 pending |
| stale manual task | failed + recovery flags + resume/abandon |
| unknown handler | 最终写入 `never_retry` |
| API | task status 加性 lifecycle/actions；受策略限制的 `/retry` |
| cancellation | 用户取消清空 lease，下次 heartbeat 会取消本进程 runner |
| snapshot reconciliation | fresh running owner 保留；terminal/stale owner 分类关闭 |
| frontend | 后端 actions 驱动；轮询网络错误显示状态未知并继续轮询 |

迁移 `20260712_p1_observe_lifecycle` 已在本地 PostgreSQL 开发库执行到 head。

放宽门禁全部通过：总体 P@5/R@10 不退化，单个 precision-first 分层允许最多 1 个
百分点的小幅差异，延迟比不超过 1.8，泄漏为 0，原因覆盖为 100%。

严格目标明确未达：

- no-answer FP 仍为 1.0，未达 `<= 0.20`；
- writing 的 P@5 相对提升约 7.3%，未达 20%/0.80；
- conflict P@5 下降 0.87 个百分点，R@10 下降 4.35 个百分点；
- fusion 分层缺少合法的结构化输入投影。

因此本次的 `acceptance_status` 是 `pass_with_known_quality_and_dataset_limits`，不是
RAG 质量达标。

## 5. 实施偏差与后续

1. 未增加可长期关闭 lease fencing 的 feature flag。新旧 worker 混跑会破坏围栏语义，
   所以迁移时必须先停 worker、升级 schema/代码、再启动。
2. planner 未设默认开关；回滚时必须保留 visibility/hash rehydrate，不能回到旧的直接取
   cached chunk text。
3. fusion 的正式金标需新增不泄漏 gold 的结构化 entity/relation input projection，然后再启用
   strict fusion precision gate。
4. no-answer FP 和 precision 严格目标是后续 RAG abstention/语义质量项，不得用本次的可观测性
   完成状态遮蔽。
