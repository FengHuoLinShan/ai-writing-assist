## 1. 处置边界与状态含义

- `已直接修复`：程序无法正常运行，且修复不需要产品/架构决策；必须保留回归测试和运行时证据。
- `已验证修复`：本轮没有实施修复，但已用测试和真实运行路径证明外部修复消除了原问题。
- `已确认，仅记录`：运行时可稳定复现，但修复涉及交互、内容语义或优先级判断，本轮不擅自修改。
- `风险待收窄`：已经观察到异常信号，但还需新场景或代码证据才能定性。
- `通过`：只代表表中写明的具体场景本轮工作正常，不推导为整个模块无问题。

严重度用于排查排序，不是修复授权：

- `P1`：会阻断核心流程、泄露越界信息，或使用户在错误上下文中继续创作。
- `P2`：主流程可继续，但状态丢失、发现性差、监控误报或结构明显失真。
- `P3`：局部可用性、文案、键盘或无障碍问题。

### RUNTIME-003：正文生成运行中允许重复提交

- 场景：第 3 章第一次真实“AI 续写”提交后约 0.5 秒，再次点击仍能打开参考资料弹窗并提交；
- 实际：两个 DeepSeek 任务同时进入 running，均完成并分别创建 v2、v3 待处理候选；前端第二次
  调用会让第一个 controller 轮询失效，但不会取消已经提交的后端任务；
- 影响：一次快速重复操作会造成双重模型调用/费用和重复候选，历史中两份结果时间相同且难辨；

  API、队列 coalescing、schema、wire 或候选数据；
- 验证：新增并发 deferred 单测和 Vue 按钮态单测，两个定向测试文件共 34 项通过；两个真实候选
  作为精确证据保留，没有采用、拒绝、发布或删除。

### RUNTIME-004：空正文索引在 worker 重启后形成失败风暴

- 场景：连续页面操作和代码热重载后，按最近 3 小时聚合 `async_tasks`；
- 实际：31 条失败任务中有 24 条 `rag_index_chapter` 报“章节源在索引期间持续变化”，另有 6 条
  历史索引任务因重载 heartbeat timeout。24 条 source_changed 集中于“机动战士高达”第 1–3 章
  和主项目新建的第 61 章，均为空工作稿，按 worker 启动批次反复出现；
- 根因：`collect_chapter_sources()` 把 `content == ""` 的具体 draft 当作“无源”，准备计划得到空
  source_id/hash；`RagIndexStateService._get_source()` 仍返回该真实 draft 及空文本 SHA-256，
  preflight 三次都判 source_changed。任务失败后 state reconciliation 又会在 worker 重启时重排；
- 修复：空 draft 保留真实 source ID/hash，跳过无意义的标注/embedding，以 0 chunk 完成替换并
  收敛为 succeeded；仅确实没有 draft 时继续使用空 source。稳定 facade、HTTP API、数据库 schema、
  wire shape、`novel_id` 隔离和正常正文索引流程不变；
- 验证：新增空 draft task 回归，连同事务释放和真实 source-change 防线共 3 项通过；RAG 模块
  240 项非真实 LLM/外部数据测试全部通过。代码热重载后的真实 reconciliation 一次完成 4 个空章，
  requested/indexed source_id 一致、状态均为 succeeded，未再生成 source_changed 失败。

### RUNTIME-005：宽限期后终态化未再次收敛领域 owner

- 场景：worker 在旧任务最后心跳仍处于 120 秒宽限期内热重启；启动时 stale scan 合理地暂不处理
  旧 running task，但任务在后续周期才达到 heartbeat timeout；
- 实际：通用 lifecycle 会把 task 终态化，启动时只运行一次的 RAG/imports owner reconciler 却已
  错过该状态变化，RAG state 会继续保持 pending 并指向 failed task，直到下一次 worker 重启；
- 根因：领域 owner 恢复只绑定进程启动，不绑定真正发生的 stale 状态转换；宽限期制造了一个确定的
  crash window；
- 修复：`recover_stale_tasks()` 每次实际发生自动重排或失败终态化后，立即运行既有领域
  reconcilers；没有新增恢复机制、任务类型或 schema，原有 keyed coalescing、generation fence、
  `novel_id` 和 project gate 不变；
- 验证：新增“最终 stale failure 同轮重跑 reconciler”单测；任务基础设施 124 项测试通过。真实
  worker 中 3 条旧 owner 在约 21:24 终态化后，同轮立即生成唯一 replacement，不再依赖下一次重启。

### RUNTIME-006：回收站项目的索引 owner 无限补排

- 场景：追踪 RUNTIME-005 的真实 replacement，发现 3 个索引 owner 都属于两个已软删除项目；
- 实际：RAG reconciler 扫描所有 state 并补排任务；worker 的 active-project preflight 随即拒绝回收站
  项目，project deletion fence 又有意阻止 runner 写终态。任务因而只留下 claim 时心跳，约 120 秒后
  被 stale scanner 标为失败，再由 reconciler 立刻补排，形成约 4 分钟一轮的后台循环；
- 根因：项目软删除已取消未完成任务，RAG owner reconciliation 却没有使用同一 active-project
  边界，两个各自正确的防线组合成无限重试；这不是 embedding 卡住或独立 heartbeat 故障；
- 修复：RAG reconciler 通过现有 project facade 获取 active projects，只修复活跃项目的 owner；
  回收站项目的 state/chunk 和历史任务全部保留，不删除数据。项目恢复后由后续索引请求或 worker
  reconciliation 重新接管；HTTP API、数据库 schema、前端 wire 和 owner 门禁不变；
- 验证：新增回收站项目终态 owner 不补排测试，同时覆盖正常终态 owner 替换、FK 清空恢复与空正文
  收敛；定向 4 项、RAG 241 项、任务基础设施 124 项全部通过。真实库中最后一批 3 个 replacement
  于约 21:30 终态化，21:34 后仍无新任务；3 个 state 保留并指向最后失败 owner，两个项目均仍在
  回收站，循环停止且没有手工改库或删除审计记录。

### RUNTIME-007：无效章节范围静默触发全量索引重建

- 场景：主项目索引维护选择“工作稿”，填写起始 62、结束 61，点击“重建索引”；
- 实际：页面没有范围错误，提示任务已提交并最终显示 100%。任务 meta 的起止章均为 null，结果实际
  重建全部 61 章、创建 238 个 chunk；只填任一端、填 0 或小数也会经过同一静默丢弃路径；
- 根因：前端只在“两端都合法且 start <= end”时附带范围，其他非空输入不报错而是省略两个字段；
  后端现有 `RagRebuildRequest` 本来能校验正整数和反向范围，但收到的是合法的 null/null 全量请求；
- 修复：空两端仍明确表示全量；只要任一端非空，就要求两端齐全、均为大于等于 1 的整数且结束不
  小于起始，否则在 API 前提示并返回。后端 schema、HTTP/wire、数据库和任务契约不变；
- 验证：新增不完整、反向和非正整数三条单测，单文件 17 项、前端 RAG 9 个文件 90 项、生产构建
  全部通过。Vite 热更新后真实 `62–61` 只显示“结束章节不能小于起始章节”，按钮不进入提交态，
  数据库最新任务 ID/时间不变。修复前误触发的全量任务一次完成，仅改可派生索引，无正文写入。

### WRITE-009：未采用候选稿污染写作字数仪表盘

3,388 字 v1，也没有提示后台已有新结果。只有主动打开“历史”，才能看到 20:48 的 v2“待处理”。

预览确认候选为 3,693 字并保持只读、采用/拒绝隔离；候选没有自动覆盖工作稿。问题不是后台任务
中断，而是 controller 在写作页卸载时停止轮询后，没有全局消费者承接任务状态和结果发现。

### WRITE-011：正文生成缺少进度与取消控制

RUNTIME-003 修复后，在第 4 章提交真实续写，按钮会正确变为 disabled 的“生成中…”，但页面没有
任务 ID、阶段、百分比、已用时间或“取消”入口。后端任务在 running 0.1 后约 12 秒完成；期间用户
只能留在页面等待，或者离页并进入 WRITE-010 的“完成后无通知”路径。

单飞门禁已阻止重复提交，数据库也确认本轮只有一条 `writing_generate`；本问题不影响结果正确性，
但长耗时或误触任务缺少可控退出，与深度导入/发布流程已有的 workflow progress/cancel 模式不一致。

### WRITE-012：版本历史缺少候选生成来源

RUNTIME-003 留下的第 3 章 v2/v3 都在 20:51 生成。版本历史对两者只显示“待处理”、同一分钟时间和
“预览”，没有模型、生成模式、作者指令、context confirmation、task id 或“第几次生成”的可理解
来源。用户在列表第一眼无法判断是重复提交、不同提示词，还是不同模型结果。

把左侧选为 v2、右侧选为 v3 后，比较工具能正确显示 5,138/4,915 字、修改 34 段、移动 0 段和
逐段对应差异；因此正文辨别能力存在，但必须先逐一打开/比较，不能替代候选列表的生成溯源信息。

### CONTEXT-001：上下文出现未来章节并以内部结构展示

在当前章节执行上下文编译，结果含不相关的未来章节；预览直接显示近似 Python dict 的内部
结构。前者可能污染当前创作并突破时间边界，后者让作者无法快速判断每段证据的来源与用途。

### CONTEXT-002：AI 参考清单暴露内部分类和项目 UUID

在“机动战士高达”空第 1 章整理 AI 续写参考资料后，弹窗显示 149 tokens、4 个 context sections，
但作者可见清单直接使用 `writing_objective`、`delta_timeline`、`style_assets`、`hard_constraints`
等内部类型名；“记忆与时间线变化”的来源还只显示项目 UUID
`f2726b88-2d94-4612-9756-0074a376e92b`。这些值对定位后端证据有用，但不能解释给作者“引用了什么、
来自哪里、为什么与本章相关”。

正向证据：弹窗仍明确显示已发布/待处理模式、范围、token 和逐项排除入口；整理动作不调用 LLM，
也不修改章节或世界数据。

### SCENE-001 / SCENE-002：编辑状态和冲突状态不显眼

- Scene 详情打开即可以改写，没有明确查看/编辑切换、脏状态或离开前预期；
- 个别 Scene 的 must 与 must_not 约束存在潜在互斥内容，但页面没有冲突或需注意提示。

正向证据：带 Scene 标识的 Scene 工作台深链刷新后能恢复同一页与详情。

### SCENE-003：零章状态仍开放采用性正文提取

“移动端线路 E2E”的 Scene 工作台明确显示“尚无有效章节”和 0 Scene，但工具栏的“从正文提取
Scene”仍启用。点击后对话框默认第 1–10 章，主按钮“确认并开始提取”可用，说明还明确写着通过
门禁的 Scene、高置信合并和工作结构资产会自动采用。页面已有足够信息在入口前说明“请先创建或
导入章节”，却把无素材判断推迟到采用性流水线提交。因动作会携带持久授权，本轮只打开并取消，
没有提交、创建任务、调用 LLM 或写结构资产。

### CONFLICT-001：冲突检查把已发生情节批量判为缺失

在第 3 章已发布 v1 上执行“剧情设定冲突检查”，规则命中 5 条，全部是“必须发生项缺失”：确认
转运仪式并审视记忆、藏起左轮手枪、与梅丽莎进行怀表/早餐/购物对话、梅丽莎出门上学、独自
思考回家并道歉。可见正文实际逐项覆盖了这些事件，末尾甚至原文出现“抱歉，我真的想回家……”。

代码侧确认 `backend/modules/writing/services.py` 的确定性检查把 Scene 的 `must` 拆成短语后直接执行
`phrase not in content`，因此只要大纲短语不是正文逐字复现就会误报。与此同时，
`backend/modules/writing/conflict_ai.py` 的 AI 软冲突提示明确要求按语义判断、不要求逐字命中，两套
判定口径不一致。本轮继续使用真实 DeepSeek `deepseek-v4-flash` 补充 AI 判断，状态变为“已生成”且
返回 0 条；原有 5 条规则命中仍保留，AI 复核不能给误报降级或纠正。

这会让正常正文第一眼呈现 5 个中严重度警报，削弱冲突检查可信度，也可能诱导作者对正确文本
进行无谓修改。修复需要决定语义匹配、证据阈值以及 AI 与确定性规则的合并策略，属于产品判断，
本轮仅记录，没有标记已处理/忽略/稍后，也没有生成或采用修复建议。

### CONFLICT-002：冲突问题的“证据”入口无法就地核验正文

CONFLICT-001 的每张问题卡都展示“证据”，并提供可点击的“定位”和“来源”。点击末项“定位”后，
结果弹窗保持不变，只出现“该问题暂无正文定位”提示；按钮事前没有 disabled 状态或无定位说明。
点击首项“来源”则关闭检查结果、跳到 Scene 工作台，并直接打开“夜晚计划与回忆”的可编辑详情。

浏览器后退能恢复第 3 章 v1，但检查结果不会随之恢复，需要重新执行检查。来源跳转本身准确，能看到
同一条 must 规则和第 3 章字符 0–3312 的精确映射；问题在于正文证据与规则来源混为相邻入口，且
“定位”承诺与实际能力不符，用户无法在不离开结果的情况下核对误报。全程未修改或保存 Scene。

## 5. RAG 与防剧透

### RAG-001：读者视角命中隐藏身份

在读者视角、World-only 搜索中，结果暴露标题“克莱恩的穿越者身份”，摘要还显示
“无，是隐藏信息”。即使正文没有展开，标题本身已经泄露关键设定；这属于防剧透边界问题，
不应以搜索相关性较低为由降级。

正向证据：

- 命令面板的普通文本搜索和结果页跳转可用；
- 针对写作候选稿的字面搜索没有把未采用候选稿混入结果；
- `/廷根` 能进入 RAG 搜索并返回结果；
- 普通表单输入框内输入 `/` 或 `:` 不会被全局命令面板劫持。

### RAG-002：索引“正常”与创作证据降级同时存在

索引维护页第一张概览卡显示“索引是否可用：正常”，同时有 238 个已索引章节片段、0 个降级
片段、已发布新鲜度 60/60，实际/配置向量维度也都是 768，worker 可用。继续向下查看第二张卡
和近期检索记录，才会发现：

- 24 小时证据健康状态是 `degraded`，原因是 6 个悬空 Scene-span 映射以及应映射片段覆盖低于
  98% 目标；
- 47 个 Scene 都有 span，但 76 个 span 中仍有 4 个只能定位到章节，精确定位率为 94.74%；
- 238 个章节片段中，预期与 Scene span 重叠 202 个，只有 196 个是有效 span 映射，合格映射率
  为 97.03%；
- 近 24 小时共 14 次 context 检索，其中 7 次为空；这 7 次全部来自
  `writing.generate`，`candidate_count`、`unique_count`、`hydrated_count` 均为 0，
  原因为 `no_retrieval_match`。

这些空检索就是此前真实写作生成尝试留下的记录：生成流程可以继续到后续步骤甚至成功产出候选，
但 RAG 没有提供任何证据。第一眼的“正常”只表达索引服务可用，不表达创作链路是否实际取到证据；
用户需要展开技术诊断并理解内部原因码，才能发现当前项目一半检索为空的质量风险。

正向边界：本轮只读取状态、健康摘要和隐私安全检索摘要，没有点击重建、预热或重试，没有修改
索引或创建后台任务；后端返回的 trace 没有正文、提示词或密钥。

### RAG-003：反向章节范围被当成空结果

在字面搜索中输入“克莱恩”，先用第 1–1 章检索能正确得到第一章 1 个章节结果、6 处命中。随后
把起始章改为 10、结束章改为 5：

- 高级筛选摘要直接显示“第 10–5 章”，没有指出范围无效；
- 提交后 URL 也写入 `chapter_from=10&chapter_to=5`；
- 请求正常完成，页面显示“未找到匹配结果”，而不是“起始章不能晚于结束章”。

这会把用户条件错误误判成小说中没有内容；代码中的 payload 构造只分别验证两个字段是正整数，
没有验证 `chapter_from <= chapter_to`。

### RAG-004：无效筛选仍可选，空提交没有反馈

- 切换到“字面搜索”后，“世界对象”和“结构”被正确禁用，检索范围只能是正文；但“包含待处理
  世界对象”仍保持 enabled，可以勾选；
- 勾选后高级筛选摘要显示“含待处理对象”，URL 也写入 `include_pending=1`，实际 scope 仍只有
  `manuscript`，给用户造成待处理对象参与检索的错觉；
- 在关键词为空时点击“检索”，界面、焦点和提示均不变化；结果区仍是初始的“输入关键词后搜索”，
  没有表单校验状态或 toast。

这些都不会造成数据越界，但让“当前生效条件”和“用户已选择条件”不一致。

### RAG-005：空项目与真实零命中共用同一结果空态

切换到章节数为 0 的“移动端线路 E2E”后，检索页没有说明当前项目尚无正文或索引来源，关键词框、
检索方式和“检索”按钮均保持正常可用。实际搜索一个明确不存在的测试词后，结果区只显示
“未找到匹配结果”，与有正文项目的真实零命中完全相同。

用户第一眼无法判断应该先创建/导入正文，还是应该调整关键词；页面也没有回到写作或导入的入口。
实现中的 `RagResultList` 只依据 `searched` 在“输入关键词后搜索”和“未找到匹配结果”之间切换，
没有当前项目正文/索引是否存在的状态分支。本轮检索未产生结果，也没有修改索引或业务数据。

在“机动战士高达”3 个空工作稿完成 RUNTIME-004 索引修复后，索引维护页能正确显示工作稿新鲜度
3/3、0 个片段；但空态仍写“还没有检索数据，导入正文后……”。该项目实际已有导入大纲和 3 章，
只是正文为空，进一步确认空态无法区分未导入、空正文和真实零命中。

### RAG-006：近期检索记录缺少用户操作关联

空正文项目的索引维护页显示 3 次近期 context 检索和 3 次空证据运行。展开记录后，三项只显示
`writing_generation · canonical`、秒级时间、候选/去重/回读/丢弃均为 0，以及内部原因
`no_retrieval_match`。它们实际来自一次写作生成的参考整理，但列表没有章节号、生成任务、用户
请求、context confirmation 或可点击关联；用户无法判断为什么一次操作出现三条记录，也无法
把记录回溯到第 1 章的失败续写。该信息可供开发诊断，但第一眼不具备作者可理解的证据链。

### RAG-007：索引维护的正文版本筛选刷新后重置

“机动战士高达”的索引维护页使用稳定 `/rag/status` 路由，整页刷新后能恢复项目和维护子页；但把
底部“正文版本”从“已发布”改为“工作稿”后刷新，选择会静默回到“已发布”。筛选值没有写入 URL，
页面也没有提示发生重置。空正文项目两种列表当前都为 0，所以本轮未造成错误结果；但在工作稿与
已发布索引有差异的项目中，用户可能以为仍在核验工作稿，实际已经查看另一套片段。

### RAG-008：检索子导航缺少键盘和 tab 语义

可访问性树把页面顶部“检索”和“索引维护”都呈现为 generic。源码进一步确认 `RagView.vue` 使用
两个只有 `@click` 的 `<span class="subnav-item">` 承担子页切换，没有 `button`/`tab`、键盘事件、
`aria-selected` 或 `aria-current`；键盘与辅助技术用户无法像操作真正的子导航一样发现和切换。
状态页底部“返回检索”是正常 button，因此存在返回路径，但不能替代页头的双向导航语义。

### RAG-009：上一个项目的 RAG 子页会影响新项目主入口

先在“机动战士高达”停留 `/rag/status`，再从项目列表切换到“诡秘之主：1”的 writing，随后点击
侧栏“检索”。新项目没有进入预期的检索首页，而是直接打开
`/workbench/{新项目}/rag/status`。数据会根据新项目 ID 正确重载，没有跨项目显示旧索引；问题在于
模块子页偏好是全局会话状态，项目切换没有清理，使侧栏主入口的落点由上一个项目决定。对第一次想
“查找小说资料”的用户，第一眼看到的是重建、预热和技术指标，而不是搜索框。

### RAG-010：索引重建离页后失去全局可见性

主项目手动重建共 61 章的已发布索引时，页面正确显示任务卡、进度和 disabled 的“提交中…”按钮，
后端也只创建一个 `rag_reindex_novel` 父任务。切到项目页后，任务继续运行约 49 秒并正常完成，但
项目页及全局 shell 均没有任务进度、运行标识或完成提示。浏览器后退返回 `/rag/status` 后才恢复
同一任务 ID 的 100% 完成卡。用户可以安全离页，但如果忘记返回技术子页，就无法知道重建是否完成，
也无法从其他页面进入任务详情；这与任务执行正确性无关，属于长任务发现性缺口。

## 7. 动态地图

### MAP-001：刷新只恢复部分状态

地图 ID、焦点和模式可从 URL 恢复，但时间线 Scene 游标、播放速度与轨迹开关会重置。用户刷新后
看到“同一个地图”，实际时间状态已经改变。

### MAP-002：焦点过滤静默改变统计

镜头/territory 焦点会改变仪表盘计数，但页面没有持续、醒目的“当前正在过滤”标识，也没有
第一眼可见的清除动作，容易把局部统计误认为全局统计。

### MAP-003 / MAP-004：标签与移动布局

- Scene 1 场景下仍出现“未来队列”等标签，但与当前时间点、预测和已发生事件的关系不清；
- 小屏下地图、控制区和信息区拥挤，关键内容需要更多滚动和横向辨识；
- Leaflet 关键资源依赖外部 CDN，离线或 CDN 异常时存在地图不可用风险。

### MAP-005：“最近地图”操作与空态相互矛盾

“移动端线路 E2E”有 1 张“移动端道路图”、0 个地点。地图总览顶部启用“打开最近地图”，下方
“最近地图”区域却显示“暂无最近地图”。实际点击顶部按钮会正常打开这张唯一地图，并进入带
`map_id` 的 dashboard URL。

这不是运行阻断，但用户无法判断“最近地图”到底不存在，还是系统把唯一地图当作最近地图回退；
同一屏的状态与动作语义互相冲突。本轮只打开地图，没有编辑设置、创建地点或运行 Scene 补充。

### MAP-006：无 Scene 项目仍可提交 Scene 地图事实补充

同一零章项目已有一张空地图，但没有章节、Scene 或地点。总览仍默认起始章 1、勾选双阶段高质量
审计，并启用“确认并开始补充”。点击后后端在创建任务和调用 LLM 前以 400 正确拒绝：该项目暂无
可导入章节，请先上传小说文件或创建章节；候选数和地图数据保持不变。运行边界是安全的，但前端
已经展示 0 章相关状态却不做门禁，让用户完成一次明确授权后才得知操作不可能执行。

### MAP-007：零候选任务仍宣称结果已入队

“机动战士高达”有 3 个章节记录但正文全空、0 Scene、0 地图和 0 地点。地图补充因此通过“存在章节”
门禁并创建真实 `map_observation_enrichment` 任务；任务 attempt 1 正常完成，没有错误，也没有调用出
任何候选：`scene_count=0`、`proposal_count=0`、`candidate_created_count=0`。页面却显示“地图事实
补充完成；结果已进入地图待处理队列”，下一行才写“扫描 0 个 Scene，新增待处理 0 条”，收件箱也
仍为 0。运行结果安全，但主完成文案把“没有可处理输入”表述成已经产出并入队。

## 8. World 与项目数据

### WORLD-001：重复实体与关系积压

“诡秘之主：1”可见 157 个 World 对象、325 个待处理关系，同时存在重复实体和别名。对象页能
打开、关系页能切换，但第一眼难区分已采用资产、待处理建议和导入噪声。

### WORLD-002：World Bible 与结构化统计不一致

部分项目的 World Bible 有叙述内容，结构化 World 对象统计却为 0 或明显偏低。界面没有解释
“文本背景”和“可查询结构化资产”的差异，用户容易误判某一侧没有保存。

### WORLD-003：待处理数量混用候选、对象分组和关系组

从“待处理 (325)”进入后，默认落在“对象 (0)”子页，主标题显示“共 0 个”，正文是“没有待处理
对象”。虽然旁边还能看到“别名 (67)”“关系 (258)”，第一眼很容易把 325 的待处理队列理解成
已经清空或统计失真。

继续进入两个有数据的子页后，又出现三套没有明确单位的数字：

- 别名页顶部“共 67 个”，第一页实际渲染 39 个别名选择框，页脚却写“第 1 / 2 页，共 36 条”；
  36 实际是承载别名的对象分组，不是别名数；
- 关系页顶部“共 258 个”，第一页显示 20 个对象对关系组，页脚写“第 1 / 10 页，共 185 条”；
  258 是候选关系数，185 是对象对关系组数；
- 使用“同对象对多类型”快捷筛选后，顶部变为 119，页脚变为 46，但仍只写“个/条”，没有说明
  “119 条候选、46 个关系组”。

筛选本身能正确写入 URL、显示可清除的条件 chip，并且全选文案明确作用于当前页；问题在于同屏
计数单位不透明，用户无法快速估算待处理工作量或解释为何总数不同。

### WORLD-004：World 审核导航与筛选缺少语义

- “对象库 / 待处理 / 关系 / 别名 / 世界书 / 地图”和“对象 / 别名 / 关系”两层子导航在
  accessibility tree 中都是 generic，不是 tab、link 或 button；当前关系页的 tab 数为 0；
- 关系高级筛选中的“全部类型/推荐类型/自定义类型”和“每页 20/50 组”两个 combobox 都没有
  可访问名称，辅助技术只能把它们识别为两个匿名下拉框。

可见文案和鼠标点击仍可用，但键盘/辅助技术无法稳定识别导航层级、当前子页或两个下拉框各自用途。

### WORLD-005：正式别名包含自别名，溯源只显示内部 UUID

正式别名页只有 6 条已采用记录，其中一条手工记录的对象名和别名都是“罗塞尔大帝日记”，类型
却是“化名”。同一个字符串没有提供任何别名能力，却会进入正式资产和后续匹配范围，说明采用/
手工创建边界没有阻止自别名。

深度导入产生的正式别名虽然显示来源、章节、Scene 和置信度，但 Workflow 与 Scene 都直接展示
完整 UUID，例如用户只能看到一串内部标识，不能点击追溯到导入任务或 Scene。与此同时待处理
队列有 67 条别名，正式页只有 6 条；正式关系页为 0，待处理关系为 258。页面分别准确显示各自
状态，但从待处理证据到正式资产的清理成本和来源可理解性都很差。

本轮没有点击新建、删除、批量采用或编辑任何别名/关系。

### WORLD-006：世界书已采用页面仍直接进入无脏标识编辑态

从图鉴打开已采用的“世界基本背景”后，主区立即显示标题、类别、排序、页面概览、分区和关联资产
等可编辑控件，同时提供“保存工作稿”“保存并发布”等动作；没有明确的查看/编辑切换，也没有
“未保存”标识或“取消本次编辑”入口。用户只要在字段中输入，就只能依赖切换页面/离开模块时的
原生确认框来放弃。

正向边界：实际输入临时标记后切换页面，系统确实弹出“当前页面有未保存修改”的保护框；本轮
选择放弃测试输入，没有保存、发布或创建工作稿。随后后端只读复核确认“世界基本背景”的
`free_text` 仍为 `null`，另一页仍为空字符串，临时文字没有入库。

### WORLD-007：世界书当前页不是可恢复导航状态

在同一个 `/world/bible` URL 内从“七大正神”工作稿切到已采用的“世界基本背景”时，URL 没有
加入 `page_id` 或 `draft_id`。刷新后页面静默回到“七大正神教会”工作稿，而不是刚才选中的
“世界基本背景”；新开同一 URL 也落到这份工作稿。

实现其实支持读取 `page_id` / `draft_id` deep link，但 `openPageCard()` 和 `openDraft()` 只更新
模块会话，不同步路由。因此分享、刷新和浏览器恢复都不能表达当前编辑对象；用户可能以为仍在
原页面，继续操作到另一份工作稿。Round 37 进一步确认，“用 AI 完善此页”再从生成中心返回时
会显式带回 `page_id`，刷新也能恢复正确页面；缺口集中在世界书内部的页面/工作稿选择路径。

### WORLD-008：零章对象库把自动提取显示为“就绪”

零章、零对象项目的对象库空态正确提供“手动新建对象”，但“自动提取”展开后仍默认第 1–10 章、
显示“状态：就绪”并启用“确认并开始提取”。源码确认提交前只检查项目存在和起止顺序，不读取
章节数；该阶段还会携带持久化自动采用授权。由于这不是无副作用的探测，本轮没有点击提交。问题是
首屏同时知道对象/章节素材为空，却仍把不可执行的采用性路径呈现为 ready。

### WORLD-009：同标签跨项目加载期间保留旧世界书和编辑动作

从主项目的“七大正神教会”工作稿，直接把同一标签 URL 切换为零章项目的
`/world/bible?page_id=<主项目页面 ID>` 后，首个导航完成快照已经显示目标项目 URL，但：

- 顶栏项目名暂时为空；
- 主区仍显示旧项目“2 个页面”“七大正神教会”、完整正文及“保存工作稿 / 保存并发布 /
  丢弃工作稿 / 用 AI 完善此页”等可操作控件；
- 约 1.8 秒后的复核才收敛为目标项目的 0 页面空态，旧标题和内容消失。

后端 `novel_id` 隔离本身通过：目标项目页面列表和工作稿列表均为 0，携带目标项目 ID 读取旧页面
统一返回 404；浏览器 console 也没有异常。问题位于前端过渡生命周期：`mountIsland.onEnter()`
等待目标项目 `loadWorld()` 全部预取完成后才替换/卸载旧 island，期间没有 loading 遮罩、同步
禁用或清空旧内容。地址已经变为新项目，旧项目编辑表单却仍可交互，用户可能在错误路由上下文中
继续阅读或误点保存；是否会实际写回旧项目没有执行，因为验证该风险需要修改真实业务数据。

这不是后端跨项目查询返回错误数据，但属于真实的跨项目旧数据短暂暴露和错误上下文写入风险。
按照仓库“发现跨 `novel_id` 泄漏立即停止”的安全协议，本轮停止继续发散，不擅自修改共享路由/
Vue island 生命周期。

### PROJECT-001 / PROJECT-003：同名对象辨识不足

- 项目列表中有 4 个 `Project A`，卡片缺少唯一描述、创建时间或最近活动等快速区分信息；
- 回收站存在与活跃项目同名的条目，恢复和永久删除操作的误选风险更高。

跨项目隔离正向证据：在本轮抽查的项目切换、World、Outline 和 Writing 路径中，没有看到前一
项目的对象串入后一项目；这只证明所测组合，不代表全量隔离审计。

### PROJECT-002：导入说明与真实能力不一致

可见文案只列出部分扩展名，没有说明 `.htm`、`.azw3` 和 50MB 限制，而文件控件和后端实际上
支持这些约束。Round 31 再次从真实 DOM 确认 `accept` 精确为
`.txt,.epub,.html,.htm,.mobi,.azw3`，与可见的“txt/epub/html/mobi”仍不一致。用户可能在选
文件前误以为不支持，或到提交后才知道大小限制。

### PROJECT-004：编辑表单的可访问名称缺失

编辑项目时，“项目标题”和“题材”输入在 accessibility snapshot 中没有可访问名称；“基调”
因 placeholder 能被识别。可见标签存在并不等于辅助技术建立了 label/control 关联。

项目编辑的正向证据：

- 现有标题、题材和基调均正确预填；
- 不改内容点击“取消”会直接关闭；
- 修改标题后离开会触发未保存确认；
- 本轮由用户手动确认放弃，重新打开后标题保持原值，项目数仍为 10；
- 没有创建、保存或删除项目。

### PROJECT-005：空白校验前后端不一致，失败后还关闭编辑框

把标题填为一个空格时，前端的 `if (!title)` 检查没有拦截，“保存”仍可点击；后端
`ProjectUpdate` 会 trim 后拒绝纯空白并返回 422。页面显示了明确的校验错误，但通用 modal
在 handler 捕获异常并正常返回后仍自动关闭，用户无法就地修正，已经填写的其他字段也会丢失。

本轮只发送了必然被后端拒绝的安全请求。随后 API 复核结果为：项目总数 10、原项目标题精确
匹配 1 个、纯空白标题 0 个，因此没有产生数据写入。

### PROJECT-006：批量选择文案与实际范围不一致

筛选“项目A-面包屑”后显示 4 个项目，点击“全选当前项目”实际选中这 4 个筛选结果。这里的
“当前项目”通常指单个 active project，第一眼容易误解为只选当前项目，而实际语义是“全选
当前可见项目/搜索结果”。

批量范围保护本轮通过：把搜索词改为“诡秘”后，之前 4 个隐藏选择会清空，计数回到 0，
批量移入回收站重新禁用；清除搜索后仍为 0。因此没有出现“看不见的隐藏选择被继续批量处理”。

### PROJECT-007：新建项目的必填提示会关闭表单

打开“新建项目”，不填写任何字段直接点击“创建”。页面正确提示“请输入项目标题”，但表单
随即自动关闭，用户必须重新打开才能补填。代码路径与 PROJECT-005 相同：通用 modal 把
handler 的 `undefined` 返回值当作成功并强制关闭，而调用方的前端校验分支没有 `return false`。
项目数保持 10，没有发出创建请求或产生新项目。

新建表单还补充了 PROJECT-004 的无障碍证据：项目名和基调依靠 placeholder 获得可访问名称，
题材、语言两个 combobox 的可见 label 没有与控件建立可访问名称。

### PROJECT-008：回收站批量动作没有零选择禁用态

回收站有 6 条记录，未勾选任何项目时，“批量恢复”和“批量永久删除”仍是 enabled。点击
“批量恢复”后只提示“请先选择项目”，没有恢复数据，说明内部 guard 存在；但第一眼状态与项目
主页的 disabled 批量按钮不一致，也让危险的“永久删除”看起来随时可执行。

正向证据：取消回收站后，之前打开的导入抽屉仍保持展开；没有恢复或永久删除任何项目。

### PROJECT-009：导入文件标签没有建立控件关联

导入抽屉视觉上有“选择文件（txt/epub/html/mobi）”标签，源码也给文件控件设置了
`id="pv-import-file"`，但 `<label>` 没有 `for`。真实 accessibility snapshot 因而只把控件暴露为
英文 `Choose File`，没有把中文用途和允许格式关联到控件。键盘和鼠标路径仍可用，且选中文件后
页面会显示文件名、启用两个导入入口；问题集中在屏幕阅读器语义和中英文体验不一致。

Round 69 使用浏览器的 file chooser 事件直接选择专用临时 `.txt`，没有打开原生 macOS 文件选择器。
只验证前端选中态后收起抽屉，没有点击“上传并导入”或“导入为新项目”。临时文件已删除，数据库
仍为 10 个活跃项目、0 条同名导入记录，也没有创建导入任务。

### PROJECT-010：同一导入抽屉的两个入口不共享所选文件

抽屉把一个文件控件与“上传并导入”“导入为新项目”并排放置，第一眼会理解为先选文件、再选择
导入目标。真实操作却是：文件已经选中且文件名可见时，点击“导入为新项目”仍打开第二个文件
选择器；只有在第二次选择后才显示“创建新项目并导入”的确认框。源码确认该按钮完全不读取
`ImportDrawer` 的 `fileInput`，而是调用 `importAsNewProject()` 临时创建另一枚隐藏 input。

这会让用户重复选文件，并可能在两个选择器中选到不同文件；关闭确认后，抽屉仍保留第一次选择的
文件，进一步增加“当前到底会导入哪个”的歧义。Round 71 自动捕获了两次 file chooser，并在创建
确认处取消；没有创建项目、导入记录或任务。

### PROJECT-011：失败导入历史隐藏持久错误原因

在零章 E2E 项目上传只有空白字符的合法 `.txt` 后，后端把记录明确写为 `failed`，并持久保存
`error_message="文件中未检测到有效章节"`。导入历史卡却只渲染文件名、“失败”、“成功 0 / 共 0
章”和时间；折叠再展开重新加载后依然没有失败原因。用户一旦错过瞬时 toast，就只能知道失败，
无法判断是空内容、格式、编码还是解析问题。源码确认 `ImportDrawer.vue` 收到了 record，却没有渲染
`error_message`。

后端保护本轮通过：失败记录 `423a333b-04fc-427a-aaff-e51a183c492f` 已立即终态化，没有卡在
`processing`；关联 imported chapter 为 0，目标项目 writing draft 为 0，也没有创建 import task。

### PROJECT-012：项目卡的整卡点击没有键盘语义

页面说明“点击项目卡片即可进入创作流程”，真实鼠标点击标题/卡片也确实会触发整卡 `@click`。
但 10 张卡在 DOM 中都是没有 `role`、`tabindex`、可访问名称或键盘 handler 的 `article`；末尾
“创建新项目”卡同样是只有 click 的 `div`。因此整卡这条主视觉交互不在键盘焦点序列中。

这不是完全阻塞：每张卡内部仍有真正的“继续写作”button，页面顶部也有“新建项目”button；编辑、
删除和勾选同样可达。问题是鼠标用户获得的宽大点击目标与键盘/辅助技术用户的入口不对等。

## 9. 设置、命令与全局反馈

### SETTINGS-001：全局显示与项目有效配置容易混淆

项目设置中 `deepseek-v4-flash` 可真实使用；全局默认区域却仍出现 Custom OpenAI / `gpt-4o`
等信息，同时页面又显示 DeepSeek。用户很难判断“保存的全局默认”“项目覆盖”和“当前真正
被工作流消费的配置”分别是什么。

本轮只读复核得到更精确的表现：

- 项目设置清楚显示 DeepSeek、`https://api.deepseek.com`、`deepseek-v4-flash`，各字段标为
  “已覆盖”，并提供“继承全局 / 已覆盖 / 系统默认”图例；
- 全局默认却选择“自定义 OpenAI 兼容接口”，Base URL 为 OpenAI、模型为 `gpt-4o`，显示名称
  又是 `DeepSeek-v4-flash`；
- “引用此默认的项目”仍包含诡秘项目，说明它至少有部分字段继续继承全局。

因此“显示名称”最像当前模型，实际却只是自定义标签；在真实 DeepSeek 已可用的项目旁边查看
全局页时，尤其容易把显示名误当为生效 provider/model。

正向保护：页面明确说明全局不保存 API Key、Key 仅项目级；本轮输出主动排除了所有 Key/password
相关 DOM 行，没有读取、显示或修改密钥。

### SETTINGS-002：项目设置子页的恢复范围前后矛盾

项目设置的“主配置 / 深度导入 / 作者偏好”都共用同一个
`#/workbench/<project>/project-settings` URL。实测在作者偏好页刷新，URL 完全不变，但内容回到
主配置；浏览器 history 也无法回到刚才的子页。反过来，不刷新而从“诡秘之主：1”的深度导入
离开、切到“机动战士高达”再打开项目设置，页面会沿用前一个项目的深度导入 Tab。

代码证据与运行时一致：`projectSettingsSession.tab` 是模块级单例，注释明确“整页刷新后重置、
不按项目隔离”。这不会把 A 项目的表单值带到 B 项目，数据仍按新 `projectId` 加载；但 UI 状态
同时具有“刷新即丢”和“跨项目保留”两种相反边界，用户无法收藏某个设置子页，也容易误以为
另一个项目此前就在同一配置区。

正向保护：未保存作者偏好时点击全局设置会弹出原生离页确认；本轮确认路径由用户手动处理，
没有把确认框导致的自动化超时登记为产品故障，也没有保存测试值。

### SETTINGS-003：深度导入设置直接暴露实现参数平面

真实桌面首屏直接展示 `Global`、`Phase 0 Plan`、`Phase 1A Scene Slicing`、`Phase 1B`、
`Phase 1C Scene Fusion` 等内部阶段名，以及 `Max tokens / 字符`、`Reducer`、`Enrich`、
`Provider 超时`、`Batch 并发` 等混合中英文标签。DOM 精确计数为 44 个数字输入、3 个下拉框、
7 个阶段标题，共 47 个可编辑参数；首屏只解释“深度导入不继承默认输出上限”，没有预设方案、
常用/高级分层、字段后果或推荐范围，保存按钮还在长表单底部屏外。

顶部来源摘要渲染成“深度导入参数 系统默认—”，能说明没有项目覆盖，但破折号与 47 个已填默认值
并列，第一眼更像状态缺失。对于只想确认“当前导入质量/速度配置是否正常”的作者，这一页首先
要求理解工作流实现，而不是先给出可判断的策略摘要。

### SETTINGS-004 / SETTINGS-005：设置标签和作者偏好仍使用实现语义

- 三个子页控件都是普通 button；当前项只靠 `class="active"`，没有 `role=tab`、`aria-selected`

- 作者偏好的“编辑器字体”直接给出 `system / serif / sans / mono`，来源值也原样显示 `system`；

  “跟随系统 / 衬线 / 无衬线 / 等宽”和“关闭”。

### SETTINGS-006：账号边界在全局设置里仍显示为 demo 占位

当前本地运行模式确实是 `auth_mode=local`，但全局设置标题不是从当前 account principal 渲染，
而是在 Vue 模板中硬编码 `owner: local（demo 占位）`。同页“引用此默认的项目”还把 10 个项目
逐条显示为“标题 + 完整 UUID”；顶部头像则只有静态字母 `U`，没有账户名称、菜单或可访问说明。

后端收窄结果是正向的：settings 表按 `owner_id` 唯一隔离，项目列表聚合通过 project facade
读取当前 owner；owner 隔离与 settings API 16 项测试全部通过。因此本轮没有发现跨账号读取，
问题是公开账号能力已经存在时，界面仍无法让用户判断“这是哪个账号的全局默认”，并把实现 ID
放在作者主界面。

### SETTINGS-007：本地偏好迁移是无预览的批量写操作

全局设置底部只有一句“将浏览器 localStorage 中的旧作者偏好一次性迁入后端”和一个始终可点的
“手动迁移所有项目本地偏好”。界面不显示待迁移项目数、目标字段、跳过原因或预览，也没有说明
成功后会删除旧本地值。

代码路径会在一次点击后枚举所有 `novel_author_preferences:*` 键，对每个项目读取服务端设置、
直接 PUT 项目作者偏好，并在已有服务端覆盖或迁移成功后删除相应 localStorage；没有二次确认。
owner 门禁能拒绝不属于当前账号的项目，但不能弥补作者不知道本次会改哪些项目。由于它属于跨项目
写入和本地数据清理，本轮没有点击，只记录操作后果不透明的风险。

### GENERATE-001：持久化回复与上下文审计记录生命周期不一致

在生成中心以真实 `deepseek-v4-flash` 发送一次只读聊天：

> 仅审视当前项目已有世界对象：指出两组可能的重复命名或别名冲突，并说明依据；不要新增设定，
> 不要生成、应用或采用任何资产。

回复成功后，“查看最近聊天上下文”显示本次使用 `generation_background`、状态 included、
3940 tokens，并给出 revision、source hash、block hash、context snapshot、stale=false 和
fallback=false。刷新页面后，用户消息和模型回复都能恢复，但“查看最近聊天上下文”入口消失；
切到另一个项目再切回也不会恢复。于是持久化输出失去了与它对应的可审计来源。

跨项目保护本轮通过：高达项目的生成页没有出现诡秘项目的提示词/回复；切回诡秘后原会话恢复。

### GENERATE-002：真实回复夹带内部标识且只部分满足请求

同一次回复的第一组“克莱恩·莫雷蒂 / 周明瑞”确实识别出两个独立 character 实体可能代表同一
叙事人物，与现有重复实体观察一致；但回复直接展示截断的内部 UUID。第二组改为比较“七大正神”
与“世界基本背景”的页面内容重叠，不再是请求中的“重复命名或别名冲突”。这会让作者面对实现
标识和未经区分的“实体重复 / 页面职责重叠”结论，降低结果可执行性。

正向边界：本轮只使用“共创聊天”；没有点击“生成世界对象建议”，没有创建待处理建议、应用
世界书工作稿或采用任何资产。空消息只提示“请输入要聊的内容”，不会调用 LLM。

### GENERATE-003：“检查当前章节”允许没有当前章节

复现组合：

1. 在写作台选中第 1 章；
2. 进入生成中心→任务→“检查冲突”；
3. 不展开高级设置，直接点击“预览上下文”。

预设文案是“检查当前章节”，并把 scope 设为 `chapter`，但没有继承写作台章节，也没有校验
`chapter_index`。请求仍成功，预览标为“范围：chapter”，实际加载 8 段、27,394 tokens；
`retrieval_evidence_packs` 单项 19,966 tokens。渲染 Markdown 后确认：

- 证据包含第 6、40、51、57 章等未来章节；
- `pov_knowledge`、`world_entities` 和 retrieval pack 直接显示 Python dict、UUID、hash、
  offsets、score 等内部结构；
- 在第 1 章任务中暴露了“因斯·赞格威尔”“0-08”“扮演法”等后续信息。

`retrieval_evidence_packs` 降至 7,320，检索证据只出现第 1 章。这证明未来章节不是任务需要，
而是入口缺少章节绑定/校验造成。该证据同时收窄了 CONTEXT-001 的触发条件。

### GENERATE-004：“应用到聊天”没有携带已编译 bundle

把上述明确指定第 1 章的 8 段、14,748-token bundle 点击“应用到聊天”后，聊天中出现：

> 已加载 8 段上下文，共 14748 tokens。

但 `applyTaskToChat()` 只把任务文本和这句摘要写入 `session.messages`；下一次聊天的
`buildWorldPayload()` 只发送消息、章节选择和实体/Scene 等筛选字段，不包含
`lastContextBundle`、section IDs、snapshot 或 Markdown。用户看到“已加载”的确定陈述，
实际模型请求不会收到这份已编译 bundle，容易对防剧透、冲突检查和成本边界产生错误信任。

本轮没有继续发送这条聊天，因此没有为验证该缺口额外消耗 LLM 或生成内容。

### GENERATE-005：生成页的可访问控件语义不完整

### GENERATE-006：生成中心不同状态使用不一致的恢复生命周期

### GENERATE-007：请求期间离页会形成无状态的孤立消息

在世界设定聊天发送明确的只读短消息后，发送按钮立即 disabled，说明同一组件存活期间能阻止
重复点击。约 100ms 后切到项目页，5 秒后返回生成中心：用户消息已出现在会话末尾，但原来的
“正在思考…”助手占位、请求中状态、失败说明、重试入口和 AI 回复都不存在，发送按钮重新启用。
再等待 10 秒并整页刷新，仍只有用户消息；错误徽标没有增加，console 也无 warning/error。

代码路径可以完整解释该状态：`captureComposer()` 先持久化用户消息，再加入 `pending=true` 的
助手占位；会话序列化会主动过滤 pending 消息。组件卸载时 `owner.dispose()` abort 当前 fetch，
晚到响应被 `isActive()` 丢弃；于是重新挂载只能读到用户消息。客户端离页后的 abort 是否同步
终止 provider 侧计算，本轮没有服务器级证据；如果未能终止，还会产生用户不可见的模型成本。
更确定的风险是，返回后页面允许再次发送，却没有告诉用户上一请求已经取消还是仍在服务端运行。

本次短消息明确禁止创建、生成、应用或采用资产；World chat 接口本身也只返回对话，不写业务资产。

### GENERATE-008：空项目的角色正文入口没有呈现前置条件

代码中的提交 guard 能阻止无效请求，所以本轮没有调用 LLM，也没有创建正文建议；问题在于前置条件

### GENERATE-009：移动端长对话把输入和发送动作拆到两端

在 390×844 视口打开已有三组消息的世界设定会话时，首屏能看到模式、来源、目标和顶部

### ROUTE-001：非侧栏导航后主导航 active 状态漂移

按以下顺序建立浏览历史：

`项目列表 → 写作台 → World 对象库 → World 关系`

随后逐次使用浏览器后退：

- 关系→对象库：URL、主体、面包屑和 World active 一致；
- 对象库→写作台：URL、主体和面包屑变为写作，但侧栏仍标记 World active；
- 写作台→项目列表：主体变为项目，侧栏仍标记 World active。

再逐次前进也重现同样状态：writing 路由仍标记 World；回到 World 后看似恢复。说明内容路由
能够恢复，但 Vue shell 的 `currentView`/active 订阅没有随 popstate 同步，第一眼会误导用户
所在模块。浏览器控制台未出现 warning/error。

同一问题也发生在项目卡片内部导航：

- 在项目页点击“继续写作”或直接点击项目卡片，URL、面包屑和主体进入正确项目的 writing；
- 侧栏仍保留“项目” active，甚至点击另一项目后也一样；
- 在 writing 页面再直接点击一次侧栏“写作”，active 才会校正。

因此问题不限于 popstate，更接近 router 已更新 vanilla state，但 Vue shell 的订阅没有收到
非侧栏入口造成的 `currentView` 变更。

Round 17 又补充了同类入口：RAG 结果抽屉点击“跳转章节”后，URL 和主体正确进入第 1 章写作，
但主导航没有任何模块呈 active；浏览器后退回带完整查询条件的 RAG 页面后，主导航仍无 active。
搜索表单和结果能从 URL 恢复，漂移仍只发生在 shell 导航状态。

### ROUTE-002：无效项目 URL 停在半可用工作台

### TASK-001：任务轮询把完整内部 meta 暴露给浏览器

读取“机动战士高达”已完成的地图事实补充任务时，`GET /api/tasks/{task_id}` 的 200 响应约
4.4 KB。除进度、结果和可用动作外，`meta` 还完整包含：

- 用户授权策略和回滚范围快照；
- 无密钥的项目 LLM provider/model 执行快照、配置来源和配置哈希；
- 深度导入每个阶段的大量内部预算、并发、超时和阈值。

响应没有返回实际 API Key，只包含“是否已配置”的布尔状态；跨项目请求也被统一 404 正确拒绝。
风险不是已证明的越权泄漏，而是通用浏览器 wire 暴露了远超当前地图进度卡所需的内部实现契约，
且运行任务会每 1.5 秒重复传输。后端只过滤 `result` 顶层以下划线开头的私有 checkpoint，
`meta` 则原样返回；源码检索未发现前端使用 `llm_execution_snapshot` 或
`authorization_snapshot`。若要收窄响应，需要先定义稳定的 public task meta 投影，属于共享 wire
契约决策，本轮仅记录。

### ERROR-001：历史错误长期占据全局徽标

在 Round 3 后，全局错误徽标显示 3 条：其中一条是已经修复且随后真实生成成功的旧 writing

### ERROR-003：422 响应可能把 API Key 带入错误日志

现有项目标题 422 已证明错误面板会展示 FastAPI `detail[].input`。代码路径中，前端虽然明确不
记录请求体，却会把整个错误响应经 `_stringifyDiagnostic()` 放进 `_lastApiError.response`。
该函数能按敏感字段名和常见 `sk-`/`Bearer` 文本模式脱敏，但 FastAPI 把字段值放在通用键
`input` 中；脱敏逻辑没有根据同一条错误的 `loc=["body","api_key"]` 判断 `input` 是密钥。

使用明确的假标记做了零写入验证：

- 向现有项目 LLM 设置接口发送 4600 字符的 `FAKE_DIAGNOSTIC_MARKER_...`，只为超过
  `api_key` 的 4096 长度上限；
- 后端返回 `string_too_long`，`loc` 精确指向 `body.api_key`，并在 `input` 中完整回显
  4600 字符，假标记可检出；
- 请求前后只读获取的项目 LLM 配置完全相同，说明 422 发生在持久化前；
- 没有使用、读取、显示或改变真实 DeepSeek Key。

因此对于不符合当前文本模式的供应商密钥，前端可能把响应前 500 字符存入 localStorage 错误桶，
并在面板显示、后续同步诊断。该机制违反“不得记录 API Key”的硬约束。当时按照仓库
`AGENTS.md` 的安全停止规则暂停排查，没有擅自修复或清理日志。

2026-07-25 外部修复后的复验结论：

- 后端现在统一从 `RequestValidationError` 的序列化结果中移除所有 `input`，保留 `type`、`loc`、
  `msg` 和约束上下文；不再由敏感值格式决定是否安全；
- 前端 API 层会在生成 `_lastApiError.response` 前，按敏感 `loc` 对通用 `input` 做脱敏；错误日志层
  对对象响应、合法 JSON 字符串和无法解析的残缺响应再次防御性清理；
- 后端项目 LLM 设置测试 23 项、前端相关测试 55 项通过，Ruff lint 通过；受控的真实浏览器请求
  用 4121 字符假值触发 422，错误面板只显示 `body.api_key`、`string_too_long` 和长度上限，响应中
  不再有 `input`，假标记全文和前缀均不可检出；
- 刷新项目设置后，DeepSeek provider、`deepseek-v4-flash`、360 秒超时和“密钥已保存”状态保持
  不变，证明失败请求仍发生在写入前；全程未读取、显示或修改真实 Key；
- 当前剩余的交付缺口仅是新增后端测试文件尚未通过 `ruff format --check`，登记为 TEST-001，
  不影响本次运行时修复成立。
