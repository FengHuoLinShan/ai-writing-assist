## 1. 执行结论

本轮先由多个子代理并行扫描真实运行路径，再按相互独立的模块边界分批修复；每个实现批次均交给未参与实现的子代理复核，复核发现的问题继续在同批修复和补测，直至该批无新增可操作发现。

最终结论：

- 已修复本轮确认且能在现有稳定边界内安全落地的正确性、`novel_id` 隔离、并发、资源生命周期与明显低效问题。
- 对本轮选定、且未列入暂留项的高风险 LLM 任务，按各自风险收紧 provider 前事务释放、来源重验、任务 fence 与最终提交；需要 owner/confirmation/profile/receipt 的任务额外采用专用 prepare/execute/finalize。
- 未通过放宽断言、弱化 schema、绕过安全检查或吞掉异常来获得测试通过。
- 就本轮扫描修复项自身而言，没有新增依赖、基础设施、migration 或 ADR；没有移除/破坏既有公开字段，新增的是任务 fence、项目锁和 writing chapter lock 等窄 additive seam。任务状态 API 另有一项安全收紧：顶层下划线私有 checkpoint 不再公开投影。工作树中同时存在的其他 migration/ADR 属于既有并行改动，本报告不据此归因。
- 仍有 9 项 P1 需要 migration、持久化状态机、跨模块/独立 session port 或领域级任务重启契约，另有 1 项 P2 需要 PostgreSQL 专用批量查询设计。按用户要求，这些难以安全局部修复的问题已明确标记并暂留，不与已修项混报。

本轮没有发现仍未处置的 P0、已证实的跨 `novel_id` 泄漏或真实数据丢失路径。

## 3. 已修复与优化清单

### 3.1 门禁、Imports 切分与 Scene 基线

- 修复仅有 `start_offset` / `end_offset` 的 Scene chunk 正文取值。
- 补齐 legacy split 的 chapter 映射、索引、span、布尔 offset 与边界校验。
- checkpoint 保存实际消费文本指纹；Phase 2b 合并、持久化和混合非法 chunk 采用整章 fail-safe。
- 未知项目 / `novel_id` 的 E2E 回到稳定 404；地图软删除 owner 使用明确 `map_not_found` 语义。
- 真实 LLM 测试加入 marker 与环境门禁，快速套件不会误调外部服务。

### 3.2 前端异步状态、缓存与测试漂移

- router 以 generation 隔离过期渲染，项目、Scene、地图和 focus 切换不再被旧异步结果回写。
- 修复地图未保存状态、缓存/索引失效、语义 no-op、listener 清理和重复绑定。
- 前端批量操作与精确失效采用确定性上限，避免无界请求和重复加载。
- Playwright helper、API contract 和场景断言同步当前 404、归档、批量与写作生命周期语义；测试服务器支持独立端口，避免复用脏服务。

### 3.3 Outline、Writing 与 Scene 一致性

- Scene reorder 拒绝重复 ID、跨项目对象、已废弃 Scene 和不完整集合，并保持历史 ID 与 not-found 语义。
- Scene split 写入前完成全部校验，同步迁移 `chapter_ids`、chunks、spans 和 indexes。
- writing → outline 的 split seam 同时识别现代 offset 与 legacy position，且不原地修改调用方 JSON。
- writing 版本创建和正文原地更新共享同一 chapter advisory lock，消除并发重复版本和写覆盖窗口。
- 发布/生命周期相关测试改为验证真实状态转换，不再依赖过时 fixture 或弱断言。

### 3.4 Memory、Context 与 RAG 数据路径

- memory rebuild 将旧 current 置为 stale，保留可解释历史，并在删除前取得 SQL max 边界。
- count/filter 转为 SQL；事件查询使用 UUID 稳定 keyset、正确 tail limit 与失败回滚。
- PostgreSQL / SQLite JSON 语义、同章并发 current advisory lock 和历史尾页均有回归覆盖。
- context trace 采用 SQL aggregate/prune，修复空字符串、JSON scalar 和恶意输入计数。
- RAG client 的所有权及正常、异常、取消关闭路径明确；manual upsert 改为批量查询，重复输入保持 last-row-wins。
- RAG 写入、发布和 retry 路径补齐任务终态与重复执行边界；未把下文 D-01 的持久化 owner/generation 状态伪装成已解决。

### 3.5 Project runtime、Tasks、LLM 与 Embedding

- 所有带 `novel_id` 的新业务 LLM 路径继续通过 project facade 取得“项目覆盖 → 全局默认 → 系统默认”配置。
- project provider snapshot 每次显式 restore 都拒绝配置漂移；要求 task-specific profile fence 的专用 finalizer 会在最终提交前再次 restore，其他任务不在此处被过度声明。
- 通用 submit 的 `meta` 经注册的 Pydantic schema 重建并 fail closed；LLM 结构化输出由各调用方 Pydantic schema 校验。动态定位、provider 和校验错误不会泄露密钥或原始敏感 payload。
- BGE 请求/响应串行化访问，超时迟到响应不会污染后续任务。
- `BgeOnnxWorker` 改为 start 时惰性创建 multiprocessing queues，启动失败和 stop 均确定性 `close/join_thread`；生命周期与 encode/health 共用可重入锁，旧进程未退出时拒绝二次 start，stop 后正常 restart 会创建全新队列。
- worker 的 lease/attempt、取消和 terminal finalize 增加 CAS/fence；已完成任务的 apply seam 只暴露冻结的完整 result 与严格白名单 apply context，窄结果更新以 `updated_at` CAS 防止覆盖新状态。
- 稳定 task facade 不再要求业务模块直接导入 `AsyncTask` ORM 来完成已完成任务的窄更新。

### 3.6 World / Map 并发、wire 精度与查询效率

- 地图可视资产变更先锁定 owner；presence 配置、layer node 和融合指纹依赖改为批量取得。
- 实体类型迁移先用 SQL UUID 预过滤，避免全量 Python 扫描；类型转换依赖保持可解释失败。
- 地图空间锚点保留精确数值 wire，修复 path presence 缺键、整数坐标和多地图 layer 加载边界。
- world 实体融合一次性取得关系、Character、Event 与现有指纹，消除多条 N+1。
- World Bible synopsis 任务冻结来源与 LLM snapshot，provider 期间不持有事务，最终写入与任务 checkpoint 原子提交；自动重排保留 `active_task_id`。

### 3.7 智能去重与 Scene Workbench

- `keep_separate_many` 收敛为一次项目锁、一次 pair-only tuple 查询和一次 flush。
- Workbench 首屏使用轻量 health/fingerprint 投影，只为当前页加载完整 Scene ORM，assigned chapters 改为 scalar 查询。
- 历史多 active pair 清理与页外 pending suggestion 的当前性检查均有回归测试。
- 未把 D-02 的完整 `smart_dedup_scan` 长任务重构混入本批局部性能修复。

### 3.8 高风险 LLM 任务的事务与重试边界

这些任务按实际恢复模型分层收敛，没有假设所有 handler 都能共享同一 finalizer：

| 层级 | 任务 | 本轮保证 |
|---|---|---|
| 专用 prepare/execute/finalize | writing conflict、writing candidate generation、World Bible synopsis、手动补抽任务 `world_alias_relation_extraction`、Scene auto extraction | 冻结所需来源/授权/profile/确认，provider 阶段无事务；最终按任务专用锁序和 fence 原子写入。各任务的 receipt/replay 语义以其 README 与测试为准 |
| 来源重编译型 | outline AI workflow | provider 前释放事务；结果入库前重新编译/校验适用来源。不宣称拥有 durable provider receipt 或统一的 owner/profile 二次 fence |
| 分批 checkpoint 型 | `world_entity_fusion_suggestions` | provider 边界外不保留长事务；每 batch 持久化 checkpoint/写 task result 前重验 source fingerprint。不宣称单一全局 finalizer |

它们的共同底线只有三项：先前存在 DB 读写时，慢 provider I/O 前释放事务；入库前重验该任务适用的来源状态；所有 handler commit 受 worker 的 project/lease fence。更强的 owner、confirmation、profile、attempt、receipt 和 replay 保证只在相应任务明确实现并有测试时成立。

Scene auto extraction 还将 `replace_existing` 纳入 prepare 指纹和最终 fence；空结果或覆盖不完整会回滚整个 finalizer，只有 `done` 才能提交旧 Scene 替换、新 Scene、融合建议和 RAG 入队。Writing generation 的 terminal fence 被拒时则回滚 candidate/binding；它不是“已提交结果通用重放”的例子。

`world_alias_relation_extraction` 的内部 receipt 采用有界 Pydantic envelope，校验状态互斥、Scene 唯一、长度、hash 和二次脱敏；实际 timeout/concurrency 固化到 receipt，最终写入使用 Scene-local refs。final checkpoint fence 被拒时恢复最后持久状态，不会把 detached `done` 带入 terminal result。

### 3.9 最终门禁追加收敛

- 原子地图编辑在“同批创建覆盖图层并画格”时严格验证 client alias，再将合法 alias 映射为正式 layer UUID；恶意跨层、重复/错序 alias 仍 fail closed，直接 terrain API 校验未放宽。
- 地图进入编辑、旧 map loader、保存与 unmount 均加入 lifecycle/map identity fence；dirty 更新保留当前路径选择，旧异步响应不能复活已卸载视图或覆盖新地图。
- World 对象写入与刷新结果分开表达：“写入成功但刷新失败”不会误报写入失败或诱导重复提交；编辑、创建、强制创建均有本地 in-flight 防重入。
- E2E 删除普通 `ai_novel_engine` 默认回落；任何 engine 创建前要求显式专用 PostgreSQL URL，并以 backend/host/port/database 规范化比较 fail closed。全局 manager 在 function event loop 内安装、同 loop dispose，隔离 scope 内 reset/丢失/替换会立即拒绝。
- Context 编译时间改用 timezone-aware UTC 生成后再保持既有 wire 形状，Python 3.13 严格 warning 门禁不再触发 `datetime.utcnow()` 弃用。
- 写作台只在发布后的章节状态刷新完成后显示成功；后台 RAG / memory 后处理完成不再二次重载编辑器。进度清理定时器与轮询响应均绑定当前任务代际，不会清空或回写新任务。

## 4. 独立复核发现并修复的问题

独立复核不是形式验收，而是对每批 diff、锁序、重试与异常路径做第二轮对抗检查。主要追加修正包括：

| 批次 | 复核发现 | 修正 |
|---|---|---|
| Imports 基线 | 混合非法 chunk、布尔 offset 和消费文本指纹边界 | 整章回退、严格拒绝与真实文本 fingerprint |
| Memory / Context | 双数据库 JSON 差异、同章并发 current、空文本/JSON scalar | SQL 语义、advisory lock 与稳定计数/尾页 |
| Runtime / Embedding | BGE 迟到响应和任务错误敏感内容 | 响应隔离、fail-closed 脱敏 |
| World / Map | path 缺键、整数 wire、多地图 layer N+1 | 容错、精确序列化与批量加载 |
| Workbench | 页外 pending suggestion 未验证当前性 | 轻量 fingerprint 投影复核 |
| World synopsis | auto-requeue 丢失 `active_task_id` | 重排复用持久化任务 owner |
| Completed-task seam | 任意 task meta 暴露过宽且缺少并发 CAS | 白名单 apply context 与 `updated_at` CAS |
| Writing generate | 确认归属/状态不足、profile 可漂移、confirmation TOCTOU | owner/status/stale/chapter 校验、profile 重验、`FOR UPDATE` 与 fresh populate |
| Scene auto extraction | `replace_existing` 未冻结；失败覆盖会提交部分资产 | 纳入 fingerprint/fence；非 `done` 回滚整个 finalizer |
| Alias / relation | 私有 receipt 暴露、跨 Scene refs 串写、receipt 无界、动态超时漂移、拒绝提交后 detached `done` | 私有 checkpoint 投影、严格 receipt schema、Scene-local refs、冻结执行参数与 checkpoint 回退 |
| Embedding lifecycle | 测试/生产 queues 未确定性关闭；旧进程存活可被二次 start 覆盖；stop 可与活动请求竞态 | queues 惰性创建/确定性关闭、存活进程防重启、生命周期与请求共用 `RLock` |
| E2E 数据库隔离 | Context trace 独立 session 绕过注入库、跨 event loop 复用、默认回落普通库、scope 内可 reset 重建 | 显式专用 URL、同库规范化 guard、function-loop manager scope、active identity fail closed |
| Map / World 最终 E2E | 新图层 client alias 未解析、路径 selection 被 dirty 清除、旧 loader 覆盖新 mount、刷新失败误导重复提交 | alias 严格解析、lifecycle/map fence、保留编辑选择、写入/刷新分态与 in-flight guard |
| Writing 发布最终 E2E | 成功 toast 早于章节刷新，后续编辑被误判为离线备份；旧 timer / poll 可污染新任务 | 等待刷新后通知、取消后处理二次重载、任务代际隔离与确定性进度清理 |

## 5. 明确暂留的问题

这些问题不是“忘记修”，而是无法在不新增 migration、状态模型或跨模块协议的前提下安全局部修改。它们不作为本轮完成阻断，但应进入后续架构批次。

### D-01（P1）：RAG index state 缺少任务 owner / generation

| 字段 | 内容 |
|---|---|
| 位置 | `backend/modules/rag/models.py::RagIndexState`、`index_state.py`、`indexing.py`、`tasks.py` |

| 位置 | `backend/modules/context/services/loaders/rag_chunks_loader.py::_default_record_trace()`、Context 组合根/DI 边界 |
| 风险 | loader 直接调用全局 `get_manager().session_factory()` 创建独立提交 session，绕过调用方注入；生产通常仍是同库，但连接所有权、事务语义和测试隔离依赖隐藏全局状态 |
| 本轮已做 | E2E 强制全局 manager 与注入 session 同专用库、同 event loop dispose，scope 内 reset/替换 fail closed；不再有普通库回落 |
| 暂留原因 | 不能简单改用调用方事务，否则会改变“trace 是否独立于业务事务提交/回滚”的产品与可观测性语义；需要正式 port 和组合根决定 |
| 后续最小方案 | 在 Context 定义 trace session factory/recorder port，由组合根绑定同一 DatabaseManager；明确独立提交、失败降级和关闭责任，再删除 loader 内 `get_manager()` |

### D-09（P1）：`publish_chapter` 后处理失败缺少可用的 restart-origin seam

| 字段 | 内容 |
|---|---|
| 位置 | `frontend-console/views/writing/publish.js::retry()`、`backend/modules/writing/api.py::create_draft()`、tasks lifecycle |
| 风险 | 已发布正文是事实源，但 RAG / memory 后处理任务失败后，当前“手动重试”会重新调用发布 API；同一正文被判为 `new_version=false` 且不再入队，因而不能真正恢复派生索引/快照 |
| 当前安全边界 | 发布正文不丢失，失败任务与错误保留可见；本轮未将无变化发布强行改成新版本或绕过 recovery policy |
| 暂留原因 | 通用 `/tasks/{id}/retry` 只允许 `auto_requeue`，而 `publish_chapter` 明确为 `restart_origin`；局部重置旧 task 会绕过 fresh source、attempt 和 owner/fence 语义 |
| 后续最小方案 | 在 writing 领域增加显式后处理重启入口：重验当前 published source，以新 owner/attempt 入队 `publish_chapter`，返回新 task ID，并补 PostgreSQL 失败恢复与重复点击测试 |

### D-10（P2）：实体融合候选的 per-source `pg_trgm top_k` 仍逐源查询

| 字段 | 内容 |
|---|---|
| 位置 | `backend/modules/world/entity_fusion.py::_candidate_pairs()` 与 `CoreEntityRepository.find_similar_by_search_text()` |
| 影响 | 候选阶段仍有 O(N²) 比较和每 source 相似查询，大型实体集吞吐受限；当前结果正确 |
| 暂留原因 | 简单全局 `LIMIT` 会破坏每个 source 的 `top_k`、`max_pairs` 和 tie-break 语义 |
| 后续最小方案 | PostgreSQL 用 `LATERAL` 或分区窗口保留 per-source top-k；SQLite 保留独立 ILIKE/Python 回退，并先建立大型实体基准 |
