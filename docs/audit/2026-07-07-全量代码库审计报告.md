## 二、三大系统性风险

### 1. 模块膨胀与缺乏子包分层

**影响范围**：imports、world、outline

- **imports 模块**：50 文件 / ~21K 行，扁平目录混杂文件解析、旧场景流水线、新 deep import 工作流、实体提取
- **world/services/**：42 文件 / ~17K 行，map（16 文件）、实体核心、世界构建全部混放同一层级
- **world/models.py**：1189 行，混合核心实体、6 种 profile、Bible 页/投影、标签/策略、建议/冲突队列、生成模板

**这是当前代码库最大的架构债务，建议优先处理。**

### 2. 基础设施层并发能力缺失

**影响范围**：embedding、LLM、tasks

三个基础设施组件均无法并发处理：
- `BgeEmbeddingClient` 被单一 `asyncio.Lock` 串行化所有 embedding 生成
- `TaskWorker.run_forever()` 逐任务串行执行，LLM I/O 期间 worker 大部分空闲
- `LLMClient` 无限流、无熔断、无并发控制

同时业务层 `PHASE1B_ENRICH_CONCURRENCY=200` 的极端值与基础设施能力严重不匹配，说明业务层与基础设施层缺乏协调。后续处理决定保留该默认值以维持兼容，由 LLM limiter、TaskWorker 并发上限与 embedding batch queue 背压共同缓解风险。

### 3. 跨模块架构边界侵蚀

**影响范围**：outline、writing、project、settings、world

- **outline ↔ writing**：双向 facade 依赖（writing 导入 outline.facade，outline 导入 writing.facade）
- **project ↔ settings**：在 effective values 语义上交叉，互相通过 facade import 计算有效值
- **world facade**：直接包含业务编排逻辑（suggest/apply entity_fusion 循环操作）
- **outline facade**：直接编写 SQLAlchemy 查询，违反 facade 薄层转发原则

这些边界侵蚀如果不及时修正，会在后续重构中增加大量成本。

## 五、正面发现

分析中也发现了多个值得肯定的设计实践：

1. **Memory 模块**是架构规范的参考实现：严格通过 contracts/facade 跨模块访问，模块结构规范
2. **RAG 模块**关注点分离清晰：indexing、chunking、retrieval、scoring、reranker 各司其职，DI 使用合理
3. **POV Hidden Guard** 是有效的后生成安全验证：通过 `HiddenGuardBuilder` + `CharacterRevealGuard` 进行确定性隐藏信息泄露检测
4. **Context Loader 的 reveal_mode 过滤**：`author_safe` 模式对 `hidden_truth` 添加警告前缀，`false_belief` 用 `misconception` 替换 `summary`
5. **Writing 模块** services.py 三个 Service 类职责分离清晰
6. **Character 模块**已完全移除且无残留引用，迁移干净
