## 0. 用户裁定（2026-10-15）

- 两个痛点：新建地图麻烦、冷启动太长；地图对写作和其他模块帮助有限，没有参与创作决策。
- 地图保持“示意与提醒”级，暂不升级为写作必须遵守的约束。
- 路程、通行条件等空间数据：作者不填时只从原文抽取并经作者审核，不强制作者录入。
- 冷启动自动进行：在后台生成地图草图，作者只负责审核；草图允许绑定仍是候选的地点对象。
- 深度导入即将被世界演化替代并下线，冷启动改为世界演化阅读中的空间发现步骤。
- 内置基础语义不够用。对齐世界演化的“涌现”思想，允许模型在演化中总结常用类型，按项目维护。
- 同步增强助手，帮助作者使用地图修改、势力控制等功能（不限于这两项）。
- 势力路线图先单独推进，后续再合入地图。领地要支持多种形态（例如海上按船规划），
  多层级势力可以相互嵌套。
- 船可以是势力单元；小船也可以只是物品，不必扩展成势力，两者要能灵活处理。
- 题材和风格差异很大，没有列举到的情况要预留“用户自定义”。
- 首批验收覆盖五类题材：修仙、西幻、都市、科幻、悬疑。
- 技术评审后（2026-10-15）：参考维度的省略只提醒不阻断（ADR-0037 §1）；草图尽量在已有版本上做增量候选，
  必要时才重做（ADR-0036 §7）；为演化可选步骤建立统一契约（ADR-0036 §1）。

## 1. 现状与差距

地图本身已经比较完整：七层节点、只追加的空间版本、候选逐项采用、图片生成/上传/校准、
按章读者预览、场景人物位置面板（见 [地图模块](../modules/15_map.md)）。差距集中在三处：

1. **冷启动成本高。** 深度导入明确不生成地图（`docs/modules/15_map.md` “上游智能整理”）。
   结构生成一次最多 20 个地点、每批 5 个，每次 run 要确认一次 Context，且按节点逐个进行；
   从正文抽出的地点仍是候选对象，而地图只消费已采用资料。世界演化已经逐 Scene 完成身份解析
   并生成 World 候选（`docs/modules/22_evolution.md`）；地图经 G8a 接收正文变化后的来源核对，
   但不读取演化结果。
2. **地图只出不进。** 知识维度 `map_spatial` 只被地图自身 5 个能力声明；写作维度
   `_WRITING_DIMENSIONS`（`backend/modules/evidence/compilation/knowledge/policies.py:157`）、
   剧本、问答世界、RP 都不读地图。地图对写作的帮助只有提醒：G8a 正文变化后提示核对地图、
   G8b 冲突检查比较地图 head、前瞻 `world.map_precondition.v1` 一条“先核对通行条件”
   （`backend/modules/world/forecast.py`）。
3. **空间模型偏向陆地平面。**
   - 关系只有包含、八方位、相邻、连通、途经和三种街道关系，共 15 种
     （`backend/modules/world/map_structure_schemas.py:29`）；没有上下、传送、远近。
   - 图元只有地点、地标、道路、河流、区域（同文件 `MapFeature.kind`）；路线类型只有道路和河流。
   - 没有路程、耗时、交通方式、通行条件；层级名称写死为区域/城市/街区/街道/室内。
   - 只有一棵从“世界”开始的树，副本、秘境、梦境、网络空间、多星球之间无法连接。
   - 场景位置只投影人物，不支持物品保管和非人物对象（`docs/modules/15_map.md` “场景人物位置”）。

势力侧现状：`FactionProfile` 只有文本字段、`territory_refs_json` 和无 schema 的
`resources_json`；`LocationProfile.controlling_faction_ids_json` 没有有效期
（`backend/modules/world/models/profiles.py:69,83`）。关系有 `member_of`、`leader_of`、
`subordinate_of`、`controls` 等类型，但没有有效期。势力路线图见
[世界编辑历史任务 §4](../../.agent/tasks/2026/T-20261004-world-edit-history/TASK.md)。

## 2. 设计原则：鲁棒性与兼容性

1. **计算内核少而稳，类型开放。** 程序只依赖一小组可组合的计算特性（几何、容纳、连接、方位、
   移动等，见第 5 节）；类型本身开放，由作者自定义或由模型在世界演化中总结，按项目维护。
   题材差异放在项目类型数据里，不写成代码分支。
2. **拓扑必填，度量可选。** 任何题材都能表达“谁在谁里面、谁和谁相通”。距离和耗时只在
   有原文依据时出现，用区间表示，并且必须写明交通方式。
3. **认不出就降级为文字，不丢弃也不猜。** 抽不准的留在待审队列，排不下的标“待核对”；
   没有声明计算特性的类型只显示、检索和进入模型上下文，不参与确定性计算。
4. **只产生候选和提醒。** 抽取和草图都是候选，不改写已采用的地图；写作侧只提示，
   不拦截、不降级正文。
5. **向前兼容。** 空间文档升到第 2 版，第 1 版照常读取并按系统默认类型解释；已采用版本不做
   批量改写，作者下次保存时才生成第 2 版。为“故事内世界线”预留维度：同一地点在不同
   世界线里可以不同。
6. **区分客观与认知。** 直接复用世界演化的观察模态 `ObservationModality`：只有 `event_observed`
   进入客观地图、计算和写作简报；修辞、角色说法、信念和猜测只进入角色认知或保留为引文；
   作者计划只进作者视图，模态不明的进待核对（ADR-0035 §2）。

## 3. 题材压力表

以下现象用来检验模型是否够用，也是题材矩阵评测的覆盖清单（第 10 节）。

| 现象 | 典型题材 | 模型应对 |
|---|---|---|
| 洞天秘境、副本、梦境、网络空间、多星球 | 修仙、无限流、科幻、赛博 | 多个独立空间，用传送阵、星门、入口等非几何连接相连 |
| 地下城、高楼、飞船内部 | 西幻、赛博、科幻 | 上下关系与楼层，不做三维坐标 |
| 方位失效的空间 | 星际、虚空、克苏鲁 | 方向可缺省；“相通但方位未知”“远/近” |
| 层级名称不同（星系、洞天、峰、楼层） | 全部 | 层级只表示深度，显示名来自项目类型（预设、作者或模型总结） |
| 作品独创的空间说法（界域、灵脉节点、锚点） | 全部 | 模型在演化中总结为项目类型并声明计算特性；没有特性的只当文字 |
| 御剑、传送、骑马、跃迁 | 修仙、西幻、科幻 | 路程绑定交通方式与旅行者类别；传送不受距离约束 |
| “十万八千里”“转眼千里” | 全部 | 标为修辞，只留引文，不参与计算 |
| 不可靠叙述、传闻、角色记错路 | 悬疑、群像 | 标为认知或传闻，不进客观地图 |
| 毁城、改名、时间旅行 | 末日、历史、科幻 | 地点和连接带按章节的生效区间；改名走别名历史 |
| 同名不同地、一地多名 | 全部 | 一律按世界对象身份绑定，名称只做显示 |
| 宫斗、校园、本格推理 | 悬疑、都市 | 室内层到房间级；推理题材的时间与动线只提示 |
| 地理信息稀薄 | 言情、系统流 | 先测地理密度，太稀就跳过昂贵抽取，写作侧静默 |
| 真实地名 | 都市、历史 | 先当普通地点；真实地理底图暂缓 |
| 移动的地点 | 移动城市、世代飞船、龟背城 | 移动性是特性，地点本身也可以移动，内部地图随之移动 |

## 4. 通用空间模型 v2（草案）

- **空间（space）**：每个项目可有多个空间，空间类型是项目类型（主世界、副本、梦境、网络、星球、
  洞天…）。现有节点树成为默认主空间。空间之间只能用具备“跨空间”特性的连接相连，不要求几何关系。
- **层级**：节点层级只表示深度，显示名来自项目类型；现有 `region/city/district/street/interior`
  作为系统默认类型保留。
- **图元与路线**：几何只有点、线、面；图元类型开放（港口、传送阵、航线、海域、楼层…），
  每个类型声明自己的几何特性。v1 的 `kind`、`path_kind` 值保留为系统默认类型。
- **关系**：关系类型开放，每个类型声明计算特性（可容纳、可通行、有向、跨空间、方位有效、上下、
  远近等）。v1 的 15 种关系保留为系统默认类型。
- **行程声明**：`{起点, 终点, 交通方式, 旅行者类别?, 耗时区间?, 距离区间?, 通行条件[], 模态, 原文引文}`。
  耗时取决于路线、方式、旅行者和条件；检查只比较同一方式、同一旅行者类别的声明。
  模态复用 `ObservationModality`，只有已审核的 `event_observed` 声明参与计算。
- **通行条件**：自由文本加可选结构（时间窗、季节、所需物品或身份、封锁状态）；条件类型同样开放。
- **时间**：图元、关系和行程声明可带按章节或 Scene ID 锚定的生效区间，与势力路线图“生效点锚定到
  章节 ID”保持一致；以后可再锚定到大纲节点或故事内纪年。锚点读取时按当前顺序解析；Scene 被融合替换时
  起点跟随最早的替换 Scene、终点跟随最晚的；锚点被删除时标“锚点失效，待核对”（ADR-0035 §2，
  对象档案和势力账本共用）。
- **移动性**：移动性是对象特性，不是对象类型。人物、物品（小船）、势力单元（大船、舰队）、
  地点（移动城市）都可以移动；位置由 Scene 投影，沿用现有
  `confirmed_in_scene / last_observed / unknown` 语义，不从档案回填。
- **兼容**：`schema_version=2`；读取第 1 版时按系统默认类型解释、无度量；已采用的 v1 约束视为
  作者确认、全书有效。现有 `geometry_hash` 对约束用排除名单，新增字段会改变指纹，所以先把约束部分
  冻结为 v1 字段白名单，再加 v2 字段，已有底图校准和读者白名单因此保持有效；来源 hash、CAS、
  候选审阅、读者投影等既有合同不变（ADR-0035 §3）。

## 5. 项目类型：作者自定义与模型涌现

内置类型不够用，类型因此开放：作者可以自定义，模型也可以在世界演化中总结。
程序只依赖一个小而封闭的计算特性内核（ADR-0035 §1）：

| 维度 | 特性 |
|---|---|
| 几何 | 点、线、面、无几何 |
| 容纳 | 可容纳其他地点、自成独立空间 |
| 连接 | 可通行、有向、跨空间、受距离约束 |
| 方位 | 方位有效、上下关系 |
| 其他 | 可移动、远近（定性） |

开放的类型包括：空间类型、层级名称、图元类型、关系类型、交通方式、旅行者类别、
通行条件、势力形态、领地控制方式。每个类型声明自己具备哪些特性；没有特性的类型只显示、
检索和进入模型上下文。类型的其余含义保存在名称、别名和描述里，以文字进入写作简报和问答。

- **身份**：按项目隔离，稳定 UUID 加不可变修订；改名不影响已有数据（按 ID 引用）。
- **模型涌现**：模型在演化空间发现中回读本项目已有类型（按相关性排序、设上限、披露省略数），
  优先复用已有 ID。新类型需要至少两个 Scene 的逐字证据并经独立复核，通过后自动启用；
  只出现一次的保持“涌现中”，只当文字显示。模型可以提出合并建议。
- **作者优先**：作者可以改名、改特性、合并、拆分、归档；模型不得覆盖作者判断，也不改作者
  创建的类型。归档后已用数据按文字显示并提示作者。
- **可复现**：类型清单在批次准备时冻结，修订指纹只进入该 Scene 的 `consumer_read_set`，不进入方法指纹
  （类型会在运行中途涌现）。并行生成、按 Scene 顺序写入，新类型提议只与严格更早的提议去重；
  支撑证据被重算后不足两个 Scene 的，模型创建的类型退回“涌现中”。
- **统一词表**：空间类型、对象档案面向（ADR-0039）、势力形态和控制方式共用 World 的一份项目词表，
  按种类区分，涌现、合并、墓碑和预设规则只实现一次（ADR-0035 §4）。
- **与 ADR-0005 的关系**：这是空间类型对 ADR-0005“AI 不读项目自定义类型”的有意偏离；
  World 对象类型的规则不变。
- **题材预设**是带版本的初始类型包：首批提供修仙、西幻、都市、科幻、悬疑，可以混搭
  （例如都市修仙）。应用时复制进项目并记录预设版本，之后与涌现类型一同演进。
- **内核扩充**像台账扩类（P4-C）那样带方法版本、样例和评测，并修订 ADR-0035，不临时增加。

## 6. 自动冷启动（世界演化空间发现）

深度导入即将下线，冷启动改为世界演化阅读中的可选步骤（ADR-0036）。演化已经逐 Scene 完成
身份解析并生成 World 候选；空间发现在此之后运行。所有可选步骤（现有持续发现、空间发现、
对象档案发现）按同一份可选阅读步骤契约登记（ADR-0036 §1）：开关默认值、失败隔离、并行生成顺序写入、
根预算内按步骤子额度、覆盖四态、补扫、重算取代和方法指纹规则只定义一次。

1. **开关与授权**：`ReadingRequest` 增加 `discover_spatial`（名称待定），与现有 `discover_details`
   一样 API 默认关闭；新界面在授权预览中默认勾选并显式开启，预览披露预计请求次数并提示可能计费，
   作者可以取消；append/continue 沿用原运行设置。演化成为默认导入入口之前，只在作者发起的演化阅读中
   运行，手动地图结构生成保留为回退。请求共用运行的根预算，授权预览为每个步骤划分子额度，
   子额度用尽只把本步骤剩余 Scene 记为缺口；每批调用在 journal 冻结计量，结果未知不重发。
2. **地理密度预检**：不调用模型；统计本 Scene 的地点类对象和空间词汇命中（含项目类型名称与别名）。
   零命中的 Scene 记为“已检查、密度不足”；整次运行都低于阈值时告诉作者原因。
3. **空间线索抽取**：输入本 Scene 精确正文、身份解析结果、按相关性召回的项目类型和已有线索
   （均设上限、披露省略）；输出包含、方位、相通、行程声明、通行条件和生效变化，每条带端点身份、
   类型 ID 或新类型提议、模态和逐字引文。服务端重验后再经独立复核。
4. **不阻断主阅读**：空间步骤失败只把该 Scene 的空间覆盖记为缺口，不影响理解回执和台账发现。
5. **草图构建（程序完成）**：用包含线索、World 的 `located_at`/`contains`
   关系和跨空间连接搭出多空间与层级目录，沿用现有确定性布局（方向分层与网格避让），
   冲突或放不下的标“待核对”。父节点来源冲突时按“已采用 World 关系 > 已采用地图父子 >
   复核通过的线索 > 候选 World 关系”取舍，矛盾处标“待核对”（ADR-0036 §7）。按空间和层级分片，每片仍遵守现有单次上限，
   不再需要作者每 20 个地点手动跑一次。
   - **增量优先**：每个节点最多一条待审的自动草图候选（`auto_draft`）。有新线索时，以该节点的待审候选
     （没有则以已保存版本）为基础只加入新增内容，已有图元位置不动；旧候选标“已取代”（版本状态新增
     `superseded`），已保存版本从不修改。
   - **节奏**：每个阅读批次结束、运行结束或作者打开“自动草图”视图时合并生成一次，每次使用独立的
     草图任务 ID（满足 `uq_map_revision_task_node`），不在每个 Scene 提交后重建。
   - **必要时才整片重做**：方法或内核版本变化、重算使线索被取代、层级来源冲突改变父节点、增量放置失败、
     作者要求重做。
6. **草图状态**：全部是候选，界面标“自动草图·未审核”。草图可以绑定演化 World 候选地点：
   候选融合时绑定跟随融合目标，被拒绝或删除时降级为文字标签。采用地图节点时可以显式勾选
   “一并采用该地点”，走世界模块原有的采用入口（重验回执前缀）；不勾选也能保存，
   但这些图元在地点采用前不进入读者预览、写作简报和空间检查（ADR-0036 §8）。
7. **审核**：按空间或层级批量采用，也可以逐项采用；未审核的线索和草图不进入写作简报。
8. **增量与重算**：append/continue 只处理新 Scene；revise/`scoped_recompute` 只重算受影响 Scene，
   旧线索标“已被取代”。新线索进入待审队列，新地点进入“待放置托盘”（附原文出处，
   拖到节点下即上图）。已采用地图不会被自动修改，针对已采用节点的新线索只生成增量候选。
9. **补扫**：已读但没做过空间发现的范围（旧运行、深度导入的作品），像类别补扫那样先预览、
   再由作者确认补扫。
10. **地图成为演化消费者**：线索失效时，扩展 G8a 的地图册消费端口覆盖线索派生节点，
    依赖它的地图节点显示“待核对”。
11. **已有地图图片**：作者上传后在图上点选绑定地点；可以让模型提议点位，但仍是候选。
    自动冷启动不生成图片。

## 7. 参与创作决策（只提示，不拦截）

1. **空间简报**：把 `map_spatial` 作为参考维度（ADR-0037，不是 ADR-0025 的必查维度，缺失或省略
   都不阻断，审查只出提示；省略单独记录，不进 `omitted`、不影响 `scope_complete`）加入 `writing.generate`、`writing.targeted_revision`、
   `writing.semantic_review`、`writing.conflict_check.ai_review`、`story.script`、`story.one_click`、`world.ask`。内容包括当前场景地点的上级链、相邻和相通
   地点、相关行程声明与通行条件、移动对象的最后位置。只使用已采用、模态为 `event_observed`、
   未失效的内容，按读者揭示过滤，设字数上限；没有地图时不注入、不提示。项目类型（含涌现类型）
   以名称和描述的文字进入简报；确定性检查只读计算特性。
2. **写作检查的空间提醒**：
   - 移动可能来不及：需要故事内时间。在故事内时间能力上线前，只使用正文中明确的场景间时间
     间隔，否则输出“无法确认”。
   - 同一地点方位描写前后矛盾。
   - 对象出现在已毁或尚未生效的地点；同一移动对象同时出现在两处。
3. **大纲与前瞻的地理视角**：提示旅程分段、剧情过度集中在少数地点、势力接壤处的冲突机会。
   只出建议。
4. **问答世界回答空间问题**：沿用 Ask World 现有的依据与拒答边界。
5. **后续**：RP 场景移动参考地图、角色认知地图、读者或出版用地图导出。

简报和检查结果记录所用的地图版本。地图变化沿用 G8b 的读时比对（与节点当前 head 比较），
正文变化沿用 G8a 的来源核对，不新增失效协议。Scene 没有位置身份时不猜地点，只在结构缺项中提示。
最小切片（参考维度、空间简报、确定性提醒）只依赖 v1 地图，可以先于空间模型 v2 实施（ADR-0037 §3）。

## 8. 势力接口（势力路线图合入时）

地图不保存势力数据，领地是地图上的只读投影，由势力侧按章节生效的控制关系计算。
势力形态和控制方式同样是开放的项目类型；下表是系统默认类型，作者和模型可以继续扩展，
新类型通过计算特性决定在地图上怎么画，没有特性的只在势力面板显示。

| 控制方式（系统默认类型） | 例子 | 地图画法 |
|---|---|---|
| 成片领土 | 王国、帝国 | 给受控区域、城市着色 |
| 分散据点 | 宗门、公会分部、公司办公点 | 只标点，不连成片 |
| 航线与通道 | 商路、海峡、制海权 | 线路着色；制海权落在港口和航道 |
| 移动单元 | 船、舰队、商队、游牧部落、移动城市 | 按场景显示位置和轨迹 |
| 渗透与影响 | 教会、情报网、地下组织 | 同一地点可叠加多个势力，不独占着色 |
| 不上图 | 网络组织、藏在洞天里的宗门 | 不上图，或落到对应的独立空间 |

- **船的两种处理**：大船、舰队作为势力单元，有船长、船员和补给账本，向上隶属舰队、海军、国家；
  小船作为物品，只有保管关系和位置。两者可以通过现有 `EntityTypeTransitionService`
  （可逆的 Profile 迁移，`docs/modules/02_world.md:95`）互相转换。移动性与类型无关，两种都能在地图上显示位置。
- **嵌套的三种关系**：组织内从属（海军→舰队→船、宗门→峰→堂）；势力间宗主与附庸
  （外交状态，随章节变化）；交叉身份（一个家族同时是帝国诸侯和教会成员）。整体是允许多个
  上级、不允许成环的有向图。
- **两棵树**：地理层级和势力层级分开，领地是两者之间按章节生效的多对多对应；地图按缩放
  程度聚合显示不同层级的势力。
- **限制**：地图没有真实比例和坐标，领地只做示意着色，不画精确国界。
- **地图侧预留**：海域和群岛区域、航线、非人物对象的位置投影、势力图层读取接口。

## 9. 助手能力同步增强（ADR-0038 §10）

用户要求同步增强助手，帮助作者使用地图修改、势力控制等功能，范围不限于这两项。

**现状**：助手只有四个“有界维护”地图操作（`backend/modules/world/assistant_map_tools.py`）：
加入已采用地点（位置留空）、改图元名称或备注、建空白节点、处理已有版本。读取地图只能经
`inspect_current` 查看选中节点。势力只能借用通用的建对象、改对象、加关系操作；
物品与势力的类型转换没有入口；助手不接触世界演化。

**原则**：

- 地图和势力的每项新能力交付时，同期注册助手操作或只读工具。
- 助手只调用领域注册的操作，先预览、再由作者按批确认，执行前重验基线（ADR-0023）。
  经操作注册表和 DI port 接入，不新增模块依赖边。
- **区分来源**：
  - 作者在对话里给出的空间安排（“黑港在东海群岛里，从白塔乘船三天到”），经确认后保存为
    “作者经助手”的新空间版本，与手动编辑同权；
  - 助手从正文推出的空间信息，必须附逐字引文和模态，只作为线索候选进入审核队列。
  - 两类都不由模型给坐标。

**能力清单**：

| 方面 | 助手能做的事 | 期 |
|---|---|---|
| 冷启动 | 准备演化阅读或空间补扫的授权预览，由作者确认付费；完成后汇总草图状态并带作者审核；引导流程 `map_cold_start` | M1–M2 |
| 草图与线索 | 按空间或层级准备批量审核；采用、拒绝、合并线索；把托盘地点放到节点下 | M2 |
| 结构编辑 | 按作者指令建、移、合并、改名节点和空间；增删改关系、行程声明、通行条件、生效区间 | M2 |
| 类型管理 | 创建、改名、调整特性、合并、拆分、归档类型；应用题材预设；处理模型的合并建议 | M0–M2 |
| 问答 | 只读工具查询空间简报、两地行程、对象某章位置；查不到返回 unknown。某章势力控制待势力路线图阶段 1 | M3；势力部分 M5 |
| 空间提醒 | 解释提醒，给出改正文（Writing 候选）或改地图（地图操作预览）两种修法；按条目静默 | M4 |
| 势力 | 阶段 1 前沿用通用操作；阶段 1 后建立势力与单元、设置三类嵌套、设置或转移控制、船在物品与势力单元间转换、账本条目；领地图层只读 | M5 |
| 主动提醒 | 持续授权内（默认关）合并提醒：托盘新地点、新类型、待核对增多、空间提醒 | M2–M4 |

**边界**：

- 新工具只进入新运行，旧运行冻结目录不变。
- 一次确认最多 20 项，大范围整理交给批量审核操作或引导流程。
- 地图图片仍在工作台受控页面完成。
- 不做：自动采用；跨域原子采用；助手编辑领地图层；RP 角色读取客观地图。

**验收**：按五类题材准备自然语言指令评测集，评估以下指标（Sol/xhigh，`human_validated=false`）：

- 目标解析正确率；
- 预览与意图一致率；
- 越权和猜测坐标的拒绝率；
- 问答 unknown 的正确率。

## 10. 验收：题材矩阵

- 首批题材：修仙、西幻、都市、科幻、悬疑。每类题材准备合成资料族，覆盖第 3 节相关现象。
  原文和期望放在仓库外私有目录，仓库只存脱敏指标、哈希和结论（沿用 G6 规范）。
- **冷启动指标**：线索精确率与召回率、修辞或传闻误收率、草图层级正确率、待核对比例、
  作者审核步数与耗时、费用。所有指标**按题材分别报告**，不只看总分。
- **类型涌现指标**：已有类型复用率、重复类型率、特性声明正确率、“涌现中”转为启用的比例，
  以及作者改名、合并、归档的次数。
- **写作侧指标**：同一批章节分别带与不带空间简报，比较空间一致性和正文质量是否下降；
  空间提醒的误报率。
- **方法**：冻结开发集加单次留出集，教师和评分沿用 Sol/xhigh。默认评测守卫
  `require_live_eval_calibration` 需要像 G6d 那样新开一个受限评分角色，并先做 seeded 自测。
- **端到端冒烟**：诡秘前 60 章（私有，沿用 G7b 链路与账本模板）。
- 代理验收保留 `human_validated=false`。

## 12. 待裁定与风险

- **ADR 状态**：ADR-0035 至 ADR-0038 已于 2026-10-15 经技术评审修订后由用户采纳（Accepted），
  实施从 M0 开始。
  候选地点上图已由用户裁定允许（2026-10-15）。
- **ADR 编号**：起草时 main（含 `4efe7f21a`）与本机所有 worktree 中最大编号为 ADR-0034；若其他分支先合入同号 ADR，
  合并前顺延编号并同步索引与引用。
- **风险**：
  - 简报噪声可能降低正文质量，需要对比评测证明有益后才默认开启。
  - 提醒过多会让作者疲劳，需要阈值和静默规则。
  - 长篇抽取成本高，靠密度预检、分片和根预算控制。
  - 涌现类型可能膨胀或重复，靠复用优先、合并建议和作者归档控制；模型给类型声明的特性
    可能出错，因此特性声明也要独立复核。
  - 空间类型允许模型读取项目类型，是对 ADR-0005 的有意偏离，评审时需要确认边界只限空间类型。
  - 世界演化仍在第四阶段实施和验收中，空间步骤开工前需要与相关任务划分写入者，
    并且不能削弱主理解提交的原子性和恢复语义。
  - 已用深度导入的作品没有空间线索，要靠演化阅读或空间补扫获得草图。
  - 助手按自然语言改地图可能错指对象：预览必须显示目标身份和前后差异，遇到同名或歧义先请作者选择；
    操作增多会挤占助手的工具预算，单轮做不完的整理交给引导流程。

## 13. 不做

- 强制约束或拦截写作。
- 自动冷启动阶段生成图片。
- 从图片像素推算距离或坐标；精确国界；三维坐标。
- 真实地理底图（暂缓）。
- 行为树、效用 AI 等游戏引擎机制（沿用势力路线图裁定）。
