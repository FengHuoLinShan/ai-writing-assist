## 2. 文档要回答什么

面向三种读者组织内容：开发者定位边界和修改入口，作者/RP 用户完成实际任务，维护者理解运行与恢复。每项能力区分：当前实现、默认开关、工程验证、真实质量、生产启用。未取得对应证据时，明确保留未知，不用测试数量填补质量结论。

本轮执行范围是根据当前代码校准说明、消除重复和断链、补必要的说明或派生文件。发现业务 bug 时记录来源、影响和建议，不借文档任务修改生产代码、测试断言、ORM/migration、运行配置或 Prompt 模板；不修改已采纳的安全/权限/架构规则来追认实现。不调用真实模型、真实/生产数据库，不清理其它工作树，不自动提交、推送、合并或部署。

## 4. 执行波次和阶段验收

### P0：基线与文档清点 — 主代理

1. 核实 B、适用 AGENTS、相关开放任务及 WIP；先查本聊天已有附件，优先复用合适且无冲突的任务工作树，否则从 B 创建独立 `codex/docs-refresh-*` 文档工作树。其它任务工作树不复用为可写目录。
2. 将实际 worktree 路径、B、角色与明确允许路径记录到主 TASK。并行文档写入默认分别使用独立 worktree/分支，按文件所有权集成；只读理解阶段可共用固定干净 checkout，输出写各自任务子目录。
3. 按 B 的 tracked 文档及现有清单建立 `doc-inventory.csv`：path、category、canonical_source、owner、baseline_sha、status、evidence、action。新增任务工件与当前未跟踪资料另列；secrets、受保护正文/真实稿件、原始模型请求/输出和私有库不得进入子代理输入。原任务只按需读取去原文的事实/约束摘要。
4. 运行 `make docs-check`，标明基线既有失败；清点当前/历史/参考/计划/派生/运行产物，特别核对旧 memory/outline 名称、图源与预览、用户指南两份源稿的实际生成关系。

**P0 完成：**每个已登记组件、中央文档、ADR 目录、部署与用户指南均有归属；机器登记与未登记当前文档都有处置状态；B 和现有 WIP 保护明确。清点不能标记成逐行理解。

### P1：先理解，暂不改正式文档 — 3 + 3 + 1

- 波次 1：L1 + L2 + L3。先厘清权限、事实所有权、作者正文/结构与演化的骨架。
- 波次 2：L4 + L5 + L6。消费第一波证据作为导航，仍自行追到代码和测试，不把他人总结当事实。
- 波次 3：L7。用已确认的服务边界校验真实前端调用与用户步骤。

每个角色输出一份 `research/Lx.md` 和一份自己的 `research/Lx-claims.json`；只有本人写自己的路径。正文写模块职责、关键入口/消费/写入/失败恢复图、已证实文档漂移、拟修改文件和必要新增件。主代理统一合并 `claims.csv`，其它子代理不并写该表。

一条 claim 至少包含：claim_id、baseline_sha、domain、文档路径/段落、实际结论、owning code 的路径/符号、调用方、对应测试及其证明范围、读取深度、验证身份、未知项、建议落点。重要结论查入口和真实执行实现；分拆后的 services 聚合壳不够。字段/约束查 ORM 与 migration；默认开关查配置；恢复查 worker、持久回执与执行状态。测试源码只是契约证据，未运行时标为未运行。

**P1 完成：**各组件稳定入口、主要状态流、读写拥有者、失败/恢复、权限/可见性和公开兼容均有证据；原始 tracked 路径按 inventory/static/targeted 等级登记。每个高风险入口和工作流至少一条完整调用链，未覆盖区段显式留下未知，不能宣称全库逐行审计。

### P2：证据审查与文档决定 — 主代理

逐项裁定保留、修订、合并重复、补入口、补文档、派生导出或历史标记。跨模块/权限/恢复冲突需主代理重新读 owning source；能凭代码和契约裁定就继续，无法裁定的部分保留 unknown 和具体证据需求，不传播为当前事实。

新增文档提案必须给出读者、要解决的问题、现有文档无法承载的理由、单一事实源、维护触发、入口和格式。能就近补 README 就不建立平行说明；新 ADR 只用于真实新增长期决定，本次核对不自动产生 ADR。

**P2 完成：**每项改动有证据、唯一文档拥有者、准确写入白名单和验收方法。得到具体改写任务前，子代理不编辑正式文档。

### P3：文档更新与主代理整合 — 按互斥范围分批

7 个领域角色按已经批准的白名单分批更新。若实际修改跨出白名单，交给主代理裁定和重新分配。派发新回合时附 B、owning-source 证据和已确认的跨域术语，不全量继承原对话。

主代理逐文件检查 diff 后整合领域文档，再校准中央设计、数据库/任务/路由/Prompt 目录、状态词汇和指南；同步现有 Draw.io 与对应 HTML，不只改单份预览。任何新当前架构/模块文档按已有 TOML 清单登记，ADR 正文变动按已有索引规则维护。

拆分依据是读者任务与稳定职责，不是文件行数。API/表/任务目录保留既有权威位置，其它文档链接引用，不重复列易漂移数字。历史计划/验收不回写成今天通过；引用变动按当前/历史身份标注，需归档的文件保留来源和链接。

**P3 完成：**所有确定漂移有更新或有证据的保留决定；不存在跨域多写入者、陈旧导出或无入口新文档；代码与运行配置没有变更。

### P4：独立复核、修订、交付 — R1 + R2 与主代理

R1/R2 各写只读问题清单：具体错误结论、触发/读者影响、源代码反证、最小修订和复核条件。主代理裁定后返给原拥有者修订，再复核受影响条目；不能靠删有效断言、弱化规则或把未知改为通过收尾。

交付以固定文档 diff、清单处置、语义复核和适用格式验收为准。记录文档维护触发与可执行下次核对入口；任务完成时保留 TASK、移出开放索引。本地更新、提交、远端 CI 和部署单独标注。

## 5. 按需要选择文件类型

| 格式 | 用途与采用条件 | 权威性与验证 |
|---|---|---|
| Markdown | 模块说明、开发/恢复手册、阅读指南与有明确缺口的新专题 | 默认源文；链接、来源、术语和语义复核 |
| CSV | 本任务文档清点、claim/变更/验收矩阵；字段需要排序筛选时 | 时间点核对账本；不替代 TOML 生产清单；解析、唯一键、必要字段与计数一致 |
| TOML | 现有 architecture-documents 清单需增改时 | 原位置唯一维护；不另建权威镜像；既有 parser/docs-check |
| JSON | 子代理结构化 claim、固定 SHA/文件指纹及脱敏检查摘要 | 明确字段与快照身份；不能把代码 symbol 清点当质量证据 |
| Draw.io + HTML | 跨模块责任、关键流程或作者入口需要直观看懂 | 复用现有可编辑图源/预览对；XML/ID/edge/登记检查加桌面与窄屏文字/连线检查 |
| XLSX | 作者/团队确需带筛选、冻结表头或条件标注的阅读表 | 由 CSV/JSON 生成的导出，保留源路径与时间；读取、值/公式/布局核验；不另建人工双写主表 |
| DOCX / PDF | 更新后的指南确需交付、打印或分享，或既有指南导出已过期 | 从核定源文生成，标明基线；按相应技能渲染并逐页核验，再交付 |

表格、Word、PDF 的制作阶段分别使用对应 artifact skill 和宿主提供的运行依赖；本轮不安装新全局工具或依赖。二进制通常在仓库外；确需入库遵守项目单件 <1MB、单轮 <5MB 及 `binary-growth-gate`。Markdown 是源文时，导出未更新必须标明未更新，不能继续展示为本轮交付。

可能的新专题只在 P2 证实缺口后建立，例如跨模块确认/失效/恢复的阅读路线，或可验证的本地开发故障诊断；不预建这些文件，不把已有模块/协议复制进新目录。

## 6. 子代理派发模板

领域理解/更新的宿主设置使用 `model="gpt-6-luna"`、`reasoning_effort="max"`；最终 review 使用 `model="gpt-6.1-sol"`、`reasoning_effort="high"`。两类均为 `fork_turns="none"`。`max` 是档位，不是 token 配额；未指定固定 token 上限或费用承诺。模型不可用时报告具体限制，不自动换档或从业务 LLM 通道绕行。子代理只向主代理报告，不自行派生子代理或给其它聊天发送消息。

```text
任务：{L1–L7 / R1–R2 名称}
阶段：{理解 / 文档更新 / 复核}；此阶段的完成标准：{引用本计划对应 P1/P3/P4 标准}
工作目录：{已核实的绝对 worktree 路径}
固定代码基线：{B 的完整 40 位 SHA}；任务记录：{主 TASK 的绝对路径}
先读：适用 AGENTS、CONTEXT、相关 ADR、development/testing guide 的相关部分。
读取范围：{源码根、稳定接口、调用方、ORM/migration、测试和当前文档}
允许写入：{此阶段完整列出的具体文件或本人 research 子目录}
交付：可定位证据、实际读取深度、正常与失败/恢复链、文档漂移、最小修订。
理解阶段只写本人的 research 文件。源码/真实数据/其它任务/WIP 均保持只读。
文档更新只写白名单；共享入口、清单、图源和导出由主代理整合。
区分当前实现、默认启用、代码断言、实际已执行检查、真实质量和生产状态。
报告实际完成、未知项、验证与一个具体下一步；不从历史或模型规则推断主干能力。
```

## 7. 完成门禁

- 每个已登记组件有明确拥有者与关键链证据；新旧文档均在清点中有处置状态。机器通过不证明语义正确。
- 关键结论与 B 的 owning source、稳定契约、ORM/migration 和测试一致；所有 source/owner/novel_id/confirmation/未知回执/恢复/默认关闭边界保留。
- 中央/领域/用户文档分工清晰；不存在复制的权威表、任务或路由目录、断链、把规划写成实现、把 green tests 写成作者质量的情况。
- 图源与 HTML 一致且实际查看；若生成 XLSX/DOCX/PDF，则完成适用的计算/渲染/逐页检查。纯文字说明更新不机械跑业务全测试；新脚本或生成逻辑需有真实失败路径的自检。
- 起始 `make docs-check`；收尾在集成工作树运行 `make docs-check BASE_REF=origin/main`、`git diff --check`，按本轮是否改 checker、图源、二进制选择 checker 单测/图形和体积门禁。记录执行时 `origin/main` 的 SHA；若主干推进，核对新差异并重新验证受影响内容。
- 所有未运行检查、原有失败和未知事实明确列出；无剩余关键语义矛盾；主代理审查各批 diff，完成 R1/R2 复核与必要定向返修。

本计划的角色/波次参数是执行建议；主代理可按任务负载调整批次和独立文件划分，保持模型档位、并发上限、事实边界与验收要求。计划不构成真实模型、数据外发、提交或生产发布授权。
