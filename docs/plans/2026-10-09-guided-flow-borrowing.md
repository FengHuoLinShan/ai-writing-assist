## 1. 结论

交接的方向成立：借成果导向入口、产物依赖、滚动规划和质量欠账，保留 Evidence 单一入口、作者授权、
正文版本、知识可见性与正式资产边界。按当前代码核对后，需要修正或补全八处：

1. **进度投影不需要新表，但要先补一个真实缺口。** 任务、运行信封、确认、候选与审查结果都有持久
   载体，可以只读拼出作品进度。缺的是服务端在途任务查询：前端在途任务只登记在浏览器 localStorage
   （`frontend-console/shared/workflowProgress.js:3`），任务 API 只有提交、单查、取消、重试
   （`backend/infrastructure/tasks/api.py:207-370`）。换设备或清缓存后作者看不到正在进行的生成，
   可能再次发起付费生成。同一 `operation_id` 的重放已有服务端幂等，问题只在“看不见”。
2. **作品进度挂在概览，不挂 Assistant。** Assistant 默认关闭（`backend/core/config.py:293-297`）；
   作品首页已经通过 DI provider 汇总各领域读模型（`backend/modules/project/workspace_service.py:49-62`），
   且其响应注释明写不含原始任务（`backend/modules/project/schemas.py:348-358`），需要扩展。
3. **创作流程不能装进现有协作蓝图。** ADR-0027 的 6 个蓝图是封闭的只读调查类型
   （`backend/modules/assistant/teams/contracts.py:15-24`），`select_plan` 绑定团队运行且要求知识复核
   通过（`backend/modules/assistant/teams/plans.py:22-48`），预算按调查设计
   （`backend/infrastructure/llm/agent_runtime.py:154-160`）。应在 Assistant 内新增一层薄的确定性编排
   （交接称“配方”，本计划称“引导流程”，`guided_flow`），复用操作目录、suggest 幂等执行与批次确认重验。Assistant 不能
   直接依赖 World（`scripts/check_module_imports.py:96-117` 冻结的依赖方向），World 步骤只能走已注册
   操作或 DI。
4. **三条流程里真正缺的能力只有两处。** 流程 1 缺“一句构想 → 多个方向候选”；流程 3 缺“编辑审读意见
   → Writing 局部修订”的交接——审读结果按设计不写 Writing 的独立复核（`backend/modules/assistant/README.md:208-210`），
   定向返修只接受语义审查的 finding（`backend/modules/writing/assistant_candidate_tools.py:31-35`）。
   流程 2 每一步都已存在，只是分散在两三个页面。实施顺序因此改为 流程 2 → 流程 3 → 流程 1，
   流程 1 的终点已裁定为较完整的世界观骨架（§6）。
5. **交接的三条硬要求在现有代码里各有一处违背，列为 P0 前置修复（BR-0）。**
   - “未知费用保留 unknown”：运行回执区分 `requests_unknown`、`usage_complete`、`charge_state`
     （`backend/infrastructure/llm/schemas.py:437-545`），但跨任务用量聚合只累加整数
     （`backend/modules/project/ai_usage.py:65-114`），未知用量被显示成具体数字。
   - “not_checked 不得显示为通过”：知识治理的组路径在必查维度未全部检查时降为 `unverifiable`
     （`backend/modules/evidence/compilation/knowledge/group.py:93-112`），写作生成使用的单次路径没有这道收口
     （`workflow.py:329-341` 不读 `dimensions[].checked`，该字段默认 `True`）。审查者自报某维度未查却给出
     `pass` 时，服务端仍判通过，候选可被采用。
   - “任务完成、候选可审阅、已采用不共用绿色完成”：知识复核未通过的候选，生成任务仍为 done 并弹成功提示
     （`frontend-console/vue/views/writing/controllers/writingCommandController.js:347`）；部分完成的冲突检查
     也弹成功并并入“已完成”。
6. **质量分层与 V4 统一结果外壳是同一件事。** V4 总计划 §3.4 已要求区分执行状态、实际覆盖、来源新鲜度、
   任务适用性、审查状态、采用状态（`docs/plans/novelcraft-v4/plans/00-MASTER-v4.md:82-84`）。交接的
   投影字段和三层处置都映射到这六个维度，不另造协议。
7. **滚动规划只到大纲级，不做多章正文。** 多章连续正文会突破 Writing 明示的“不负责自治式长篇生成”
   （`backend/modules/writing/README.md:40`）。按 §6 第 4 项裁定，正文只做单章，多章只提供故事线与
   篇章/Scene 级候选（BR-6），因此不需要未采用正文的读取覆盖层；上一轮 C2 的正文批量随之关闭。
8. **缓存先不建。** 当前没有资料物化缓存；唯一的业务进程内缓存是 60 秒的项目词表
   （`backend/modules/evidence/indexing/query_expansion.py:26-27`），只影响召回。先做成本可见与采纳归因，
   有测量证据后再决定缓存。

对照项目的四条“谨慎借鉴”说法经源码核实均准确，且都应列为明确不借鉴的反例（§7）。

## 4. 产品门禁结论

按 `docs/product/user-personas.md` §4.3。没有真实使用数据，以下均为产品假设。

**在途任务与作品进度（BR-1）**

```text
目标画像：A（长期创作作者）。
用户任务与情绪收益：离开、刷新、换设备后知道“完成了什么、依据什么、还有效吗、要我做什么”。
用户会喜欢的理由：不必记住自己点到哪一步，也不会因为看不见而重复付费生成。
前端舒适度判断：放在概览首屏“进行中”区，一项一句话加一个主操作；诊断细节进设置页次级入口。
主要摩擦与风险：状态词太多会变成任务后台；必须把“已完成运行/可审阅/已采用”分开而不堆字段。
验证方式：换设备恢复的 E2E；作者从首页回到同一候选的步数；重复提交次数。
结论：做。
```

**引导流程（BR-3/BR-4/BR-5）**

```text
目标画像：A；流程 1 兼顾新作者。
用户任务与情绪收益：继续写下一场、按审读意见改稿时不必在三个页面间跳转。
用户会喜欢的理由：只在真实选择（确认资料、选方向、选意见、采用）时停下，其余自动衔接。
前端舒适度判断：流程挂在现有页面上的伙伴区/首页卡片，不新增独立“流程页”；每个停点说明为什么停。
主要摩擦与风险：自动衔接会被误解为自动定稿；新书开篇一次产出二十条左右的世界对象，若不能逐条取舍和
整体撤销会破坏控制感；多章大纲候选若可无限补窗，会变成“一键写完一本书”的错觉。
验证方式：到首个可审阅候选的步数与时间、作者实际选择次数、采用率、人工改动幅度、放弃点。
结论：流程 2、3 做；流程 1 做，终点为较完整的世界观骨架（逐条取舍、可整体撤销）；多章只到大纲级候选。
```

**BR-0c 知识复核单次路径的覆盖收口。** 让单次路径与组路径一致：必查维度缺失、重复或 `checked=false`
时，服务端裁决降为 `unverifiable`，覆盖回执标明遗漏原因。范围：
`backend/modules/evidence/compilation/knowledge/workflow.py` 的裁决与回执构造。测试：审查者给 `pass` 但某
必查维度未查或缺失 → `unverifiable`、候选不可采用；全部维度已查 → 行为不变。风险：写作候选的“无法核实”
比例可能上升，上线后观察；这是让结果如实，不是放宽。文档：`backend/modules/evidence/README.md` 知识治理段。

### BR-2 质量状态分层与显示

不新建状态表，也不另起一套判定。三层只是对现有状态的投影规则：

- **硬性阻断**：以现有采用门禁为唯一事实源（`validate_candidate_upstream`，W `semantic_review.py:361-498`；
  知识复核未通过；确认、来源或正文 hash 失效；owner/授权变化）。投影只读取门禁结果，不重复判断。
- **有限返修**：可定位的 major 问题（合同未完成项、带引文的连续性问题）走已有定向返修。流程中的自动返修
  每个候选至多一次，与 ADR-0025 的单次返修一致；之后只能由作者点“返修”发起，并显示本次调用会产生费用。
  流程提交的任务使用由流程运行与步骤确定的 `operation_id`，重复推进不会产生第二个任务。
- **可延期修订**：minor 问题、跨章复读、审读意见。作者“带问题采用”时，在采用记录里写入当时未处理的
  finding 标识、审查输出 hash 与检查版本；审读意见沿用其已有处置。不建独立的问题真相表。

后端最小补充：把知识回执已有的 `output_hash`、`policy_version` 写入候选的 `knowledge_review`；语义审查回执
记录检查版本与输出 hash；采用记录追加“带问题采用”字段（均为 JSON，预期无 migration，实施时核实）。

前端：区分四种状态并使用不同视觉——运行完成、可审阅（含“审查未通过/无法核实”的细分）、已采用、已发布；
生成完成但复核未通过时提示“已生成，资料复核未通过，暂不能采用”（警告色），不弹成功；部分完成的检查显示
“部分完成”并说明遗漏，不并入“已完成”；结果详情展示知识复核的遗漏维度；发布前确认框提示部分完成的检查。
发布不加服务端门禁（发布是作者对自己正文的决定），只保证提示如实。

验收：交接 P0-3 原文；not_checked/unverifiable 在任何入口都不显示为通过或绿色；带问题采用可追溯到问题与
检查版本。测试：投影映射单测；`workflowProgress`、写作控制器、结果详情组件测试；一条“复核未通过不可采用”
的 E2E。文档：`backend/modules/writing/README.md`、`docs/modules/11_writing.md`、`docs/modules/14_frontend.md`。

依赖：BR-0c。

### BR-4 流程 3“按审读意见定向修订”

桥接编辑审读与 Writing 批注修订：作者在审读台选中一条或多条意见并说明处置 → 按选区定位契约把意见转为
批注修订输入 → 已有批注修订（只返回选区替换、治理复审，`backend/modules/writing/comment_run.py`）生成
替换候选 → 候选内复审与采用门禁 → 采用后触发审读改后复核（`backend/modules/assistant/editorial.py:575`）。

**选区定位契约**（审查意见 1–4 条证据、可跨章，不假设唯一选区）：

- 证据引文只证明问题，不自动指定修改范围。作者从证据中勾选需要修改的位置；单条证据可预选，多条证据
  必须确认取舍，不静默只取首条，也不自动把所有证据都改写。每个选区绑定章号、基稿 ID/hash、偏移与原文 hash；
  手动标选同样经过这些校验，不能绕过正文漂移后的重新审读。
- 仅按作者选定的修改章拆分：每章一个批注修订任务与候选，逐章审阅、采用；其他章的证据只作受授权的参考，
  不形成修改范围。跨章分别校验冻结正文与当前稿，不把多章合并为一个候选。
- 同章多意见在提交前展示一个联合修订清单，作者确认后复用批注修订的多批注任务，产出一份候选；重叠选区
  展示合并后的范围和关联意见，由作者确认再生成。作者也可只选一条、逐次处理，不自动替作者选择或融合意见。
- 逐次处理时，采用或编辑基稿后，旧意见与同基稿的其他候选在展示及采用前均标记“基稿已变化”，不可继续采用
  或直接重生成；须重新审读、重新确认选区后再提交。仅凭重新匹配到同一句引文不能视为来源仍新鲜。

Writing facade 新增批注修订的稳定入口供 Assistant 调用（Assistant → Writing 是已冻结的合法边）。审读
意见仍标为 `editorial_suggestion`，不写独立复核；冻结正文 hash 与当前工作稿不一致时失败关闭，提示重新
审读。不做：把审读意见转换成语义审查 finding；多意见自动融合。验收：交接流程 3 原文；引文已不在当前稿
时不生成候选；只修订作者选定的章与选区，同章联合修订一次覆盖已确认的意见；重叠范围先确认；采用或编辑后
旧意见与同基稿候选明确失效并要求重新审读；改后复核只给“仍在/可能改善/无法判断”。测试：桥接单测
（多证据取舍、未选章不提交、定位成功、手选不绕过 hash 漂移、跨章拆分、同章联合候选、重叠确认、
同基稿候选失效与重新审读）、Writing facade 契约测试、一条 E2E。文档：
Assistant 与 Writing README。

依赖：BR-3 运行层（可先做无流程的单次桥接，再挂流程）。

### BR-5 流程 1“新书开篇”：构想 → 方向 → 世界观骨架

终点按 §6 第 1 项为“比较完整的世界观骨架”。现状：World 没有一次产出骨架的入口——生成中心每次只出
1 条待处理建议（`backend/modules/world/generation_center/suggestions.py:202-302`），`world_core` 预设只出
3–7 条规则且明确不生成人物、地理（`backend/modules/world/schemas/generation.py:307-328`），共创快照本体
不可采用（ADR-0021）。唯一的多对象载体是采用包：最多 32 条、v2 支持别名等专项条目
（`backend/modules/world/schemas/adoption.py:309-335`）、整包单事务采用；但保存后不能逐条编辑，
普通包也没有回滚路由（`backend/modules/world/api/adoption.py` 只有保存/读取/预览/采用）。

步骤：

1. **一句构想**：作者写一句到一段话，可附题材与篇幅意向。
2. **方向卡**（Assistant 新 LLM step，一次调用出 2–3 张）：题材承诺、主冲突、主角与目标、世界基调与独特
   设定、读者期待、主要风险。卡片只存在流程运行检查点，不是资产。作者选一张并可改字段；都不满意可再要
   一批（新调用，提示费用）。选定方向冻结为流程的作者决定。
3. **世界观骨架**（World 新增 suggest 操作，暂名 `world.draft_opening_skeleton`，入队 World 自有任务，
   与 `story.plan_structure → story.adopt_structure` 同构）：输入为选定方向、构想与项目已有世界对象；
   一次结构化调用（修复至多 2 次）；输出一个待审采用包（v2）。覆盖面：世界前提与基调、核心规则或力量体系
   2–4、主要地点 3–5、势力/组织 2–4、关键人物 3–5（含主角）、历史/传说/秘密 1–3、核心关系；实体至多 20、
   关系至多 12。规则部分沿用 `world_core` 的约束写法。生成器先读已有对象，包内与已有对象去重；同名者改为
   补充已有对象，别名只附着已有对象，不新建重复实体（同类型相似度达 0.9 会触发创建冲突，
   `backend/modules/world/services/core/entity_service.py:135-155`）。
4. **停点“骨架待确认”**：作者逐条勾选、排除、改名与简介；预览逐条标出冲突，作者排除冲突条而不是整包失败。
   World 新增“保存后条目级取舍与轻量编辑”。**排除依赖契约**：仅包内 `local:` 引用依赖所指条目被选中；
   作者排除实体/人物时，引用它的关系与别名等条目在预览中连带排除并说明原因。恢复端点不自动恢复作者显式
   排除的条目，其余依赖条目也须作者确认后恢复。引用既有对象的 UUID 无须虚构一个包内选项，但须重验同作品、
   owner、状态、可见范围与来源指纹。
   确认指纹覆盖编辑后的包、选中条目、依赖处理结果及来源；采用时按同一指纹重验。连带排除在确认前完成并计入
   回执；确认后依赖或来源发生变化则整次拒绝，返回新预览要求确认，不静默剔除已确认条目，也不吞掉权限或来源
   冲突。有效子包仍用单事务采用，保留回滚语义。确认后用现有 `world.adopt_package` 一次采用所选条目，来源沿用
   `world_adoption_package` 标记与回执。
5. **整体撤销**：World 为该类采用包增加回滚，复用 `applied_change_reversal.py` 的“回执逆序回滚、作者已改动的
   对象保留并说明原因”语义，与专项采用、表格迁移（ADR-0030）一致。
6. **停点“骨架可用”**，下一步由作者选：生成故事总纲建议（现有总纲生成，以选定方向预填作者意图与篇幅；
   BR-6 需要已保存的总纲）、继续深化某一部分（现有 `world_core` 共创与生成中心）、开始写第一章（流程 2）。

预算：方向卡一个生成步骤，骨架一个结构化生成步骤（修复至多 2 次）；骨架任务使用自己的 root capability
与 4–6 次请求上限，不走 `assistant_turn` 的 30 次上限。项目启用世界校验策略时另计一个 `world.review`
任务，按其分包、修复及实际覆盖展示独立预算，不把一个步骤当成一次供应商请求，也不承诺整套流程共 4–6 次。

改动范围：Assistant 方向卡 step 与 prompt 契约、流程定义；World 新 suggest 操作、任务、生成服务与 prompt 契约、
采用包条目级取舍 API、骨架包回滚路由；`backend/app/bootstrap.py` 合入操作并更新操作目录快照测试
（`backend/tests/unit/test_assistant_operation_registry.py`）；前端空项目首页流程卡、方向卡选择、骨架确认清单、
撤销入口。无新依赖边，预期无 migration（实施时核实条目级编辑是否需要字段）。

验收：新用户在空项目中不打开 World/Story/Scene 页即可得到已采用的世界观骨架；所有条目使用作者语言，
不显示 ID/JSON；秘密/真相类条目默认只对作者可见（实施时核实可见性字段与读者/角色上下文的过滤）；
一条预览冲突可通过排除该条及依赖条目后确认其余有效子包；整体撤销后作者已改动的对象保留并有说明；
中途离开可回到同一停点。未选方向卡及未采用骨架不进入常规 Context 或检索；选定且经作者编辑确认的方向卡
仅可作为本流程骨架/总纲步骤的显式输入，并冻结版本与指纹，不成为正式世界事实。

测试：方向卡 schema 与预算单测；骨架生成去重与上限单测（既有同名、包内近名、别名）；条目取舍与采用集成
测试（排除人物后关系/别名连带排除，其余有效条目可采用；恢复端点不恢复显式排除；既有 UUID 端点有效；
确认后端点漂移拒绝且无部分写入；未选方向不进生成、选定方向仅进获准步骤）；回滚测试（未改动 →
软废弃，已改动 → 保留）；owner 与 `novel_id` 隔离；一条从空项目到骨架可用的 E2E。
文档：World 与 Assistant README、`docs/prompts/Prompt体系设计.md`、`docs/product/new-user-guide.md`、
`docs/核心业务场景与预期行为.md`。

风险与待核：整包原子采用意味着去重必须在预览前完成；空项目能否取得 World 采用所需的 Evidence 确认与知识复核
未核实；骨架质量是假设，按 §8 盲评验证。

依赖：BR-3。

### BR-6 滚动规划：单章正文 + 多章故事线/大纲候选

按 §6 第 4 项：详细正文只做单章，多章只提供故事线与大纲级候选。因此不需要未采用正文的读取覆盖层，也不改
Writing 的边界声明。

现状：P20 结构规划一次处理一层（剧情线、篇章、计划 Scene），只出预览，经 3 路审计与至多 1 次修订，采用
走独占项目锁与新鲜确认（`backend/modules/story/outline_state/p20_service.py:548-581`）。篇章带起止章，计划
Scene 带计划章节范围、目标、必须发生/不得发生，采用后为 `planned`（`p20_service.py:1030-1064`）。缺口：
助手侧固定全书范围、只传起始章（`backend/modules/story/assistant_structure_workflow.py:79-91`），
起止章只是上下文里的软提示，提示词不使用，输出章号不校验。未采用的规划只存在任务结果与确认里，
不会进入写作上下文或检索；已采用的规划进入上下文时已标“计划/规划（不代表已发生）”
（`backend/modules/evidence/compilation/services/markdown_renderer.py:637-684`）。

流程：

1. **触发**：流程 2 中作者采用第 N 章后，流程从 Writing facade 读到采用结果，提出“接下来几章的走向”。
   只在流程内触发，不新增 Writing 事件；作者在写作页手动采用的章节不自动触发，可从首页流程卡发起。
2. **故事线与篇章层**：对第 N+1 至 N+K 章（K 默认 3、上限 5）生成剧情线推进与篇章梗概候选。每层是一个独立
   任务、一次只做一层，提交前显示预计调用次数。已有已采用篇章覆盖该窗口时改为“修订建议”，不重复新建。
   **窗口修订契约**：现有篇章目标、冲突、高潮及关联都是整篇字段，没有按章的局部字段，白名单本身不能保护
   窗外内容。因此跨窗篇章（如第 1–10 章覆盖第 4–6 章窗口）仅产出只读修订提示，不走 `_assign_arc`、不新建
   重叠篇章、不改变范围或叙事字段；窗口内细化通过下一步的计划 Scene 候选完成。整篇范围完整位于未来窗口内时
   才能采用叙事字段修订，服务端白名单限目标、冲突、对抗、转折/高潮/结果/衔接与关联字段；标题、序号及起止章
   保持原值。剧情线同样不得用滚动窗口替换跨窗的全局目标、隐藏真相或读者知识状态；范围缺失或不能证明完全
   位于窗口内时只给提示。该限制仅用于滚动入口，不缩减结构工作台原有整篇修订能力。
3. **作者确认与逐条取舍**：现有 `story.adopt_structure` 的 `AdoptStructure` 只接受 `task_id`、采用整份结果，
   `_validate_preview_scope` 还要求保留全部提案及顺序，不能直接复用。本包明确改动：`AdoptStructure` 增加
   选中条目列表（`proposal_refs`）与确认指纹；预览编辑校验允许原提案的子集且保序，未选原条目是合法排除，
   未知/重复引用、缺失所选条目、乱序或跨项目引用仍拒绝；全不选是明确拒绝，不提交空采用。选中提案引用未选
   新提案时，在预览中提示补选依赖或连带排除，作者确认后才能采用，不能等 `_resolve_many` 报错。确认指纹绑定
   原任务结果、选择及编辑、依赖处理与最新来源，采用重验并且只落地选中条目，未选条目无结构写入且回执列明。
4. **近期 Scene 层**：只为紧邻的 1–2 章生成计划 Scene（目标、必须发生/不得发生），作者确认后写入，作为流程 2
   下一章的 Scene 目标来源。
5. **补窗**：每采用一章检查前方已规划章数；少于 2 章时提议补足到 K。远期总纲与已采用篇章不被自动改写。

需要补的能力：起止章进入确认参数与提示词；新建提案生成后硬校验（章号必须落在窗口内、不得覆盖已写章节、
条数上限），违规条目丢弃并说明；修订提案先按上述原对象范围分类，跨窗条目保留为不可采用的提示，不能对其
套用新建过滤、缩小范围后采用或整体覆盖；流程调用不放宽 `_require_scope`：由作者另行确认完整结构范围；现有确认包含排除资产或权限不足时停止并提示，
不自动清除排除项或扩大授权以通过校验。操作签名变化同步
操作目录快照与修订号；**`operation_id` 幂等契约**：键由（作品、N、窗口、层、冻结输入指纹）确定，指纹取自
操作版本、完整参数、原确认的资料/排除项与可见性、基稿及规划状态的服务端摘要 hash，不用不稳定的重新生成
时间戳代替输入版本。作者确认时固定该指纹及首次尝试标识，提交前持久化；网络重试重发原确认、指纹与
operation_id，不能临时创建确认导致换键；同请求返回原任务，同键异请求仍冲突。资料变化后必须重新预览与确认，
生成新指纹和键；主动重抽另建持久尝试标识并在调用前保存。键还包含流程运行与步骤身份，避免不同授权流程复用
同一任务；重复推进不产生第二个任务，重抽与重试在回执可区分。

预算：P20 单层为 1 次生成 + 3 次审计 + 至多 1 次修订，任务上限 64 次请求
（`backend/modules/story/outline_state/tasks.py:281`）。作为独立任务提交并显示费用，不计入助手 12 次的作者模式
预算。前瞻引擎（`backend/modules/assistant/forecast/`）的范围至多 2 步且无结构 schema，不承载本能力，只借鉴其
`compute_key` 去重（键须包含窗口）与 prepare 子运行模式。

验收：采用一章后可得到后续 3 章的故事线与篇章候选，确认前不进入任何写作上下文与检索；越窗或指向已写章节的
新建条目被丢弃并说明；跨窗篇章/剧情线只给不可采用提示，原对象所有字段不变；完整位于窗口内的篇章修订
只改白名单字段，章范围不变；作者只选中部分条目时仅选中者落地、未选条目不写入且回执列明；资料变化后重新规划产生新任务，网络重试返回原任务，主动重抽产生带新尝试
标识的新任务；拒绝候选不影响正文与已有规划；下一章的流程 2 可直接用已确认的计划 Scene 作为目标；
全程不生成第二章以后的正文。

测试：窗口参数与确认指纹单测；新建章号硬校验；第 1–10 章篇章覆盖第 4–6 章窗口时不写原篇章且可细化
计划 Scene；完整位于窗口内的篇章才可修订且范围只读；范围缺失/跨窗剧情线不改全局字段；结构工作台整篇修订
回归；`AdoptStructure` 子集采用、未选条目不落地、全拒绝、未知/重复/所选缺失/乱序拒绝、依赖取舍；
`operation_id` 三态（刷新复用原确认与键、输入变化经重新确认得新键、主动重抽新键）；
排除资产不被清除、范围不足提示重新确认；未采用规划不进 Context 的回归；一条“采用第 1 章 → 确认后续 3 章篇章 → 第 2 章以计划
Scene 为目标”的 E2E。文档：Story 与 Assistant README、`docs/modules/` 对应模块文档、
`docs/prompts/Prompt体系设计.md`。

风险与待核：剧情线的隐藏真相在作者视角写作上下文中整条可见，依赖现有 hidden guard 防止正文提前揭示，
本计划不改变该机制，但新增规划会扩大其覆盖面，实施时补回归；P20 预览容易因来源变化失效，流程需在失效时
提示重新生成而不是静默采用。

依赖：BR-3；BR-5 停点或已有作品的已保存总纲；`T-20261008-world-evolution-audit` 两项缺陷修复（仅影响采用后
演化，不阻塞本包的规划部分）。

## 6. 用户裁定（2026-10-09）

1. **流程 1 的终点：比较完整的世界观骨架。** 不止故事总纲；首章是否生成由作者在骨架停点后决定（走流程 2）。
   落地见 BR-5。
2. **接受引导流程运行层与 ADR-0032。** 放 Assistant、新运行类型、默认关闭的开关、只用已冻结依赖边；
   不更换技术栈、不新增服务或表。ADR 随 BR-3 起草。
3. **换设备时的重复生成：提示已有生成并给出入口，作者仍可明确再生成。** 不做同 Scene 服务端互斥。见 BR-1a。
4. **详细正文只做单章；多章只提供故事线/大纲级候选。** 不做多章正文候选链，因此不需要修改 Writing 的
   “不负责自治式长篇生成”边界，也不需要未采用正文的读取覆盖层。上一轮 C2（批量候选生产）按此关闭为
   “不做正文批量”。多章大纲候选见 BR-6。
5. **生成后自动接独立语义审查：默认开启，作者可在流程设置中关闭。** 流程卡片说明增加一个审查任务，
   实际请求数受分段与修复影响；关闭后提供手动审查入口，采用门禁保持不变（BR-3）。

## 7. 对照项目：借什么、不借什么

**借鉴的机制**（结构，不是代码）：

- 产物依赖 DAG：步骤声明 requires/produces/overwrites，构建期校验单一生产者、未知类型与环；运行合同冻结
  计划版本（`server/src/modules/director/steps/planDefinition.ts`、`domain/plan.ts`）。我方用于引导流程注册校验。
- 进度由产物台账派生，不存当前步；上游产物变化按依赖反推下游失效，受保护的作者内容除外。
- 先登记欠账/停机信号再写产物，崩溃不漏记；停机只来自结构化信号或作者选择点。
- 守卫逐动作把关：步骤在授权范围内、上游已满足、不得覆盖受保护的作者内容；连续拒绝达到上限转人工恢复。
- 滚动窗口：最少 3、目标 5 章的近期路由窗口，逐章即时细化执行合同，每章后补窗。我方取“小窗口、采用后
  补窗”的结构，但只到大纲级：篇章层窗口 3–5 章，Scene 层只覆盖紧邻 1–2 章（BR-6）。
- 局部质量问题登记为欠账并继续，普通欠账不中止整体。我方仅用于非硬性问题（§3 P0-3）。

**不借鉴的反例**（交接已提示，源码核实后升级为明确不做）：

- 合同级 token 预算在生产与默认装配中均为 null，步骤用量缺失记 0 且不写用量事件——预算形同虚设。
  我方保持冻结预算与 unknown 语义。
- 下一章直接读取已落库但未审的上一章正文与摘要，错误逐章传播；待审状态提案可按天自动放行进正式状态
  （默认关）。违反我方候选/采用与领域确认原则。
- 非 gateable 产物自动视为已确认；我方 AI 产出一律先作建议。
- 人物变更后的派生重建 `.catch(() => null)` 吞错且无新鲜度标记；批次上下文缓存为进程内单例、按小说分桶、
  最多 8 本、30 分钟 TTL、世界更新不失效；开篇去重钩子默认空操作；章节终态靠风险标记字符串包含判断；
  两套质量欠账互不对账。

## 8. 评测方案

沿用 `testing-guide.md` 与 `backend/evals/` 的账本、dev/holdout 和盲评纪律；付费运行须单独授权预算，
含真实稿件或版权原文的原始请求/输出留在仓库外私有目录。

- 分组：A 单强模型 + 简单上下文；B 当前流程；C 当前流程 + 引导流程/滚动规划。固定模型、输入作品、
  预算、随机设置与审查规则；缓存、轻重审查、多 Agent 的消融另做，不把多项改动打包归因。
- 硬边界测试：交接评测表 13 项中，已有自动化覆盖的在 BR-0b 矩阵中标注现有用例，缺失项随对应包补齐；
  硬边界通过不代表文学质量。
- 文学质量盲评：情节推进、人物可信度、语言、悬念、作者可用性；同时记录采用率、人工改动幅度、到首个
  可采用成果的步数、成本（含未知）与恢复成功率。

## 9. 明确不做

- 不迁移技术栈，不做 Electron 桌面端，不做漫画/短剧衍生。
- 不新增第二套 World/Story/Evidence 数据；不把候选、摘要、角色陈述自动提升为正式事实。
- 不开放可由模型修改的工作流 DSL；不把引导流程做成通用自治 Agent。
- 不自动定稿、不批量自动采用、不按时间自动放行待审提案。
- 不生成多章正文；多章只到故事线、篇章与计划 Scene 级候选（§6 第 4 项）。
- 不按固定章节号设定爽点或质量标准；承诺结构按题材与作者选定的里程碑配置（P1-3，并入 panorama 任务）。
- 不在本计划内建资料物化缓存或模型结果缓存。
