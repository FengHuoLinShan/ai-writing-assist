# NovelCraft V4：演化式小说整体引擎长期总计划

版本：4.0｜2026-09-21｜状态：设计与实施计划，不是已完成的业务改造。

代码基线：`FengHuoLinShan/ai-writing-assist@b5a3ef2e660ddaa65b9bf0ac1ada48f795c53201`。本次是静态、定向跨模块审查和设计原型检查；没有运行完整 PostgreSQL、真实模型或生产应用端到端验收。依据、原计划及证据等级见 `06-SOURCES-AND-AUDIT.md`。界面中的小说、人物、文字与数字全部为虚构设计样例。

## 1. 本轮真正改变的方向

项目的目标不再是继续增加相互调用的小说工具，而是形成一个闭环：作者写作或导入正文，系统逐步建立对这本书的可验证理解；理解进入后续写作、检查、建议与地图；作者修订之后，相关理解被精确修正，而不是让作者重新管理一串抽取任务。

V4 对两份输入计划作出以下实质性整合，不是把章节拼接到一起。

| 决策 | 最终边界 | 对原计划的影响 |
|---|---|---|
| 演化系统替代深度导入 | 一个项目只有一个有效的演化写入世代；旧深度导入不再是独立编排器 | 原 W 计划扩展为 E 计划；Imports 最终只保留文件解析、来源差异与正文写入适配 |
| 事实重建与认知成长分开 | World/Story 管事实身份和状态；Collaboration 的认知子域管可修订解释与方法 | 不把“系统越来越会理解”实现为第二套正史表 |
| 推荐不是又一个认知引擎 | Assistant 消费有作用域的事实、理解与用户当前任务，生成解释性建议 | 原助手审计中的选区、作用域、轮询、引用问题进入前置工作包 |
| 地图不是独立世界 | Map 在 World 内负责空间表现与约束，人物在场和历史来自 Story，来源来自 Evidence | 地图基础体验可以独立交付；高级智能再依赖演化及认知 |
| 多 Agent 分为可靠性与创意两条轨道 | 事实不靠投票；创意不强迫共识；共同复用现有运行预算与领域操作 | 从“默认不用多 Agent”变为“按任务证明价值后启用注册配方” |
| 全前端按任务组织 | 一个主任务、一个右侧宿主、一个浮层根；不同领域共享来源与结果状态 | 不再让提醒、预测、共创、Agent 面板各自抢占界面 |
| 演化不等于自动采用 | 派生理解可以在持续授权范围内维护；正式设定和正文修改仍走领域采用 | 保留一次授权、精确采用、历史与可撤回边界 |

“不再保留旧深度导入”指替代其产品入口、运行所有权、重试恢复和阶段调度；不是抛弃已验证的解析器、逐字证据校验、身份解析、结构抽取和模型调用适配器。替代以退役清单验收，而不是靠改名宣告完成。

## 2. 一个整体，六种职责

```text
作者动作 / 正文来源变化
        │
        ▼
Writing：版本化正文与编辑命令
        │ source revision + transactional change receipt
        ▼
Evolution：读取 → 观察 → 身份解析 → 状态解释 → 校验 → 窄批次提交
        ├── World：对象身份、关系、正式设定、地图约束
        ├── Story：场景、叙事顺序、类型化事件、历史状态
        └── Evidence：原文范围、可见性、依赖与重验
                     │
                     ▼
Collaboration/Cognition：持久理解、竞争解释、开放问题、方法试验
        │                    │                    │
        ▼                    ▼                    ▼
Writing/Review          Assistant 推荐       Map/Scene 舞台
        │                    │                    │
        └────── 用户决定 → 领域命令 → 新版本/变更回执 ──┘
```

上图是职责与数据流，不表示新增六个服务、六个数据库或全局分布式事务。继续使用现有应用、PostgreSQL、异步 worker、项目 LLM 入口、运行信封、Vue 3 与 bridge。

### 2.1 每类信息只有一个权威所有者

| 信息 | 权威所有者 | 其他模块允许做什么 |
|---|---|---|
| 正文与版本 | Writing | 按指定版本、字符范围读取；提交明确修改命令 |
| 实体身份与已采用事实 | World | 引用、提出更新候选，不各建一份人物主表 |
| 场景顺序与状态事件 | Story | 读取带截止点的状态，不从当前 World 倒填过去 |
| 来源与权限证明 | Evidence | 统一检索、编译、确认、物化与验证 |
| 演化运行和推进游标 | Evolution | 展示其状态，不另起“导入推进”主游标 |
| 本书的派生理解与方法 | Collaboration/Cognition | 在合法快照下消费、提出更新，不据此自动准入正史 |
| 推荐呈现与处置 | Assistant | 排序、暂缓、展开、调用领域提案入口；不持有独立事实 |
| 地图几何、视觉与媒体选择 | World/Map | 作为有版本的表现资产；不证明人物知识或实际旅程 |
| 当前操作焦点 | 前端任务上下文 | 选择展示与请求范围；不能成为授权或事实 |

跨模块 facade 继续保持稳定。不要把大量业务判断搬进组合根；不要为了遵守形式再增加一层只转发参数的“总控服务”。

## 3. 本次再分析后的主要问题与整改顺序

### 3.1 不是所有“连接”都带来语义闭环

原审查及输入计划指出：实体和 Delta 已记录，不等于可查询历史状态发生了对应变化；同一人物的重复身份观察可能因去重而提前跳过；所有 Scene 输入预先冻结后再顺序落库，不等于后一 Scene 继承本轮前一 Scene 的解释。本计划把这些作为发布前必须验证的语义契约，而不是只检查模块接口能够互调。

本轮新增的定向核对还发现：`EventRepository.replace_scene_events()` 按 Scene 读取全部旧事件，再按 `scene_sequence` 覆盖、删除剩余行；该函数没有按来源保护作者确认事件。结合现有人工事件追加到同一 Scene 流的机制，重跑必须先解决“机器替换范围与人工确认共存”的问题。这里是静态实现风险，不是已观察到的生产数据丢失。

### 3.2 前端焦点、授权和结果身份不应共用一个模糊 hash

助手审计中的关键问题包括：选区未完整传递、后台与前台 Scene 焦点不一致、各组件各自轮询、任务意图未进入后端、整轮证据被误当成每条结论的支持。V4 不通过放宽来源校验解决“看不见建议”，而是分开授权作用域、证据快照、任务意图和界面焦点，再检查结果能否适用于此刻。

### 3.3 全部入口必须具有同一组领域副作用

API、助手、协作试改均能写入工作稿；来源失效、索引请求、演化排程不应依靠每个调用者记住补做一遍。V4 引入“领域命令 + 变更回执 + 确定性副作用投递”契约，并核对所有入口。批量纯持久化 helper 可以保留，但调用方必须显式取得并消费待交付副作用，不得返回普通成功后遗漏。

### 3.4 完成、可靠和采用是不同状态

统一结果外壳至少区分：执行状态、实际覆盖、来源新鲜度、当前任务适用性、审查状态、采用状态。局部完成不能在助手投影中折叠成全量完成；一份旧检查仍可作为历史查看，但不能计为当前有效严重问题。

## 4. 长程能力蓝图

### 4.1 第一层：可靠地理解刚刚写下的内容

从少量正文开始，不要求先建立完备设定。逐字观察、来源范围、身份解析和状态变化组成最小链。对未知、角色说法、传闻、假设、作者规划分别记录。一次授权可以推进多个 Scene，但每个状态提交都可追踪、可重验、可恢复。

### 4.2 第二层：理解不断反哺下一项真实任务

持久认知不是额外生成一份长摘要。新建的写作或调查 case 必须实际读取相关认知版本，明确列出哪些解释被使用、哪些因时态或来源变化不能用。变化触发局部重查；无变化允许 `no_change`。真实消费链未建立前，不宣称完成“认知成长”。

### 4.3 第三层：扩大认知，但不扩大未经授权的真相

逐步加入竞争动机解释、因果条件、承诺与代价、开放问题、制度规则、角色信念、读者信息分布、反事实与局部写作经验。外壳的来源、范围、方法与权限固定，内部表达可随本书形成；不预设无穷 taxonomy，也不允许模型自行迁移数据库、注册任意工具或改写安全策略。

### 4.4 第四层：推荐、创意与空间推演

推荐从“当前页面有什么未处理项”扩大为“作者正在做什么，这一步最值得注意什么”。保留一个主建议和少量可选方向；每项有依据、为什么现在、适用条件、新增叙事负担与局部行动。

地图智能从位置展示扩大为条件路线、通行约束、地理矛盾、行程准备和空间创意。明确区分已知事实、示意布局和假设方案；没有距离与路径证据就不承诺到达时间。高级角色视角与读者地图在独立安全门禁后开放。

## 5. 多 Agent 的整体定位

可靠性轨道和创意轨道共享执行底座，不共享裁判逻辑。

可靠性轨道：窄任务抽取者 → 代码检查 → 独立证据复核者 → 有限争议裁定 → 类型化候选。评审者不能只看生成者的解释；事实不能由多数同意决定。无法证明时进入待决定或未知。

创意轨道：先独立产生人物、悬念、情绪等不同方向，再对作者展示对比，不立即融合。作者选定方向或片段之后，才生成具体可预览修改。审美差异不能被可靠性裁判误判为错误。

初始上限沿用现有有限协作边界：单宿主、最多三名并发成员、一个根预算、共享租约及取消。更多角色通过分阶段复用，不以增加并发数量为目标。没有第二个真实模型连接时明确称为角色分工，不称为异构模型。

研究只能支持设计假设，不能替项目证明质量收益。受控架构研究表明多 Agent 收益依赖任务结构；无外部反馈的自我修正研究显示在其测试推理任务中可能退化；短篇创意实验同时提示个体收益与群体同质化风险。[R1–R4，详见 06]

## 6. 前端产品方向

默认导航保留“概览、写作、故事结构、世界资料、故事地图、待我决定”。运行、恢复、模型授权进入次级位置。作者不应看到 Phase2b、raw ID、JSON 或内部 token 枚举。

写作区以正文为主，伙伴区在“当前、讨论、历史”之间切换；不是三个悬浮窗。详情按三层展开：卡片要点 → 同宿主证据/备选 → 独立大任务工作区。全屏地图、全屏写作和大规模差异比较都是任务态，不覆盖底层未保存输入。

“智能排布”由可测试的界面策略决定：任务意图、内容宽度、当前焦点、输入法状态、是否阅读中、是否有未保存内容、是否已锁定选择。模型只提供结构化建议内容，不直接输出任意布局指令。

本轮设计包含 48 个工作流/状态画面及 1 个设计规范画板。它覆盖主要工作流族，不等于穷举所有字段、API 或所有输入组合。功能迁移仍须按 `04` 的等价矩阵验收。

## 7. 可并行交付的长期路线

| 里程碑 | 核心交付 | 进入下一阶段的证据 | 可并行工作 |
|---|---|---|---|
| G0 基线与保护 | 作者事件保护、状态契约、重复实现清单、入口副作用矩阵 | 不再误删人工确认；关键语义用例可复现；缺口明确 | 前端选区传递、地图壳、样例库 |
| G1 最小基础 | 演化运行/观察/类型化提交；持久认知最小读写；统一前端宿主 | 一条 Scene 提交有完整回执；一项新 case 真正消费认知 | 地图 M1：全屏、相机、媒体与对象浏览独立交付 |
| G2 整体纵切 | 原文→前序状态→后序理解→新 case→地图→修订失效 | 同一事实在各视图一致；无未来泄漏；重跑可恢复 | 小模型可靠性配方开始等预算对照 |
| G3 主链替代 | 项目级切换、旧 owner 排空、旧入口适配、旧编排退役 | 同项目只一个写入世代；历史读取与回滚路径可用 | 新统一写作/审阅前端逐页替换 |
| G4 可靠性产品化 | 注册多 Agent 配方、有限升级、部分结果与证据裁定 | 相同预算下对既定任务有实际收益；不合格任务仍用单 Agent | 创意方向独立实验 |
| G5 创意与推荐 | 独立发散、当前意图、机会建议、稳定去重与处置 | 人工任务测试：建议有用且不夺权，不重复制造问题 | 地图条件排演、制度压力测试 |
| G6 地图智能 | 真实位置/最后出现/未知、条件路线、约束解释、视觉状态 | 不伪造轨迹，不把图像当事实；抽屉避让与移动端可用 | 高级历史和受限视角安全测试 |
| G7 扩大认知 | 竞争解释、开放结构、方法试验、长书局部重算 | A–E 等预算对照；实际任务消费、纠错与遗忘均可证 | 长期作者试用，不以点击替代有效性 |
| G8 长期维护 | 大规模性能、删除清理、迁移回退、持续回归与灰度 | 工程、模型质量、用户效果三类门禁分别通过 | 按证据引入新的受限能力 |

这里的 G 不是固定周数估算。各包先得到代码与测量基线，再做容量排期；不以“AI 开发很快”省略迁移与真实验证。

关键依赖：`G0 → E01/E02/E03 → E04 → G2 → E07/E08 → G3`。地图壳、媒体管线与前端统一宿主不必等待完整认知；高级历史地图必须等待可靠状态与可见性契约。C 的首次消费也不必等待所有方法演化。

## 8. 不做什么

不新增通用自治 Agent 平台，不默认迁移 LangGraph，不建立第二个任务队列，不用新世界数据库替换现有领域；不把当前 World 注入过去；不把作者点击、模型一致或图像像素当事实；不把不支持的读者视角回退成作者全量；不将所有派生更新塞进一个跨全书大事务。

也不以“傻瓜式操作”为由隐藏费用、授权、删除范围和冲突。简单应当来自合理默认、自动维护和渐进展开，而不是省略真实状态。

# E：演化系统详细计划——替代深度导入

V4.0｜设计提案｜代码基线与证据等级同总计划。本文中的类型和新模块为拟议接口，除特别说明外不是已存在实现。

## 1. 替代范围与最终所有权

最终只有 Evolution 负责“理解推进”的运行所有权、批次、重试、恢复、状态提交与进度解释。Imports 保留格式解析、上传校验、章节识别、来源差异和 Writing 适配，不继续拥有 deep_import 的独立推进事实。

保留现有 PostgreSQL worker lease、项目所有权门禁、`AIRunEnvelopeV1`、账户模型连接、Evidence 物化、World/Story 领域命令及人工采用。新模块建议放在 `backend/modules/evolution/`；运行记录能合理迁移或适配现有 `import_workflow_runs` 时优先复用，不机械添加重复 ORM。名称和表结构最终由迁移设计核定。

### 1.1 四种用户任务，一条内部主链

| 用户任务 | 内部模式 | 来源边界 | 预期效果 |
|---|---|---|---|
| 让系统读懂这本书 | bootstrap | 已保存指定来源版本与范围 | 从有限初始信息逐步建立观察和状态 |
| 继续理解新章节 | append | 现有已提交前缀 + 新来源 | 继承前序状态，不重新盲扫全书 |
| 我修改了这里 | revise | 新旧版本差异 + 明确依赖闭包 | 使相关旧产物失效并局部重算 |
| 重新核对这件事 | scoped_recompute | 用户指定对象/命题/范围 | 定向查证、保留其他已完成产物 |

用户看到“读取正文—整理变化—需要决定—理解已更新”，不需要选择抽取 Phase 或手工串联按钮。没有 Scene 时系统先准备场景边界；没有世界对象时从观察开始，不阻塞写作。

## 2. 先修复现有语义风险

### 2.1 观察、变化日志与状态操作不能混为一谈

现有 `ingest_delta_events()` 会把 Delta 组织成 `manual_correction` 的 MemoryEvent。状态归约不能仅保存一条 changes 就宣称位置、实体或关系已更新。V4 定义独立的三层：

- Observation：原文确实出现了什么说法或行为；必须可定位，允许未解析身份。
- Interpretation：系统如何理解观察，可能含竞争解释、推断和不确定性。
- StateOperation：在明确权限与准入资格下，对指定状态做什么操作。

“逐字证据命中”只证明引用定位，不证明该引用一定蕴含解释。角色说“我已杀死某人”可以成为 statement/character_belief；不能仅因这句话存在就产生 objective death operation。

### 2.2 保护人工确认事件

当前 `replace_scene_events()` 按 Scene 的全部事件和序号替换，没有在此函数中过滤人工来源。V4 的替换操作必须明确命名其机器产物代际：

```text
replace_derived_scene_events(
  novel_id, scene_id, producer_family, generation, input_revision,
  owned_event_keys, new_operations, expected_parent_receipt
)
```

允许替换的仅是同一 producer/generation 的派生产物。作者确认、作者修复和已采用事实由独立 authority/source identity 标识，不能因机器输出条数减少、顺序改变或返回空列表而被删除。新证据反驳人工修正时产生争议决定，不直接覆盖。

身份键不能继续把“第几个输出”视为事件身份。使用来源范围、观察身份、操作语义及生产器版本构成稳定键；输出重新排序不改变事件身份。作者确认修复必须在空重跑、部分重跑、分章重排和历史恢复测试中保留。

### 2.3 统一归约语义，而非强行统一所有输出形状

同一契约版本的类型化操作只有一个解释内核。章节和 Scene 允许保留不同投影结构，但截止到同一叙事位置时，核心实体状态、关系、位置和知识必须一致。

建议 `StoryStateReducer` 做纯函数解释；Repository 负责序列化写入，ProjectionService 负责检查点与读取。历史事件通过显式版本 adapter 读取，不在数据库中就地改变其含义。

## 3. 类型契约草案

下面是实现边界说明，不是要求一次建出所有字段。

### 3.1 SourceRevisionRef

```text
novel_id; source_kind; draft_id; content_hash;
chapter_identity; start_offset; end_offset; range_hash;
source_revision; segmentation_version; source_visibility
```

章节序号用于展示与排序，不独自承担不可变来源身份。修改标题、同字数替换、复制工作稿、恢复旧稿和整章删除都必须产生可识别变化。

### 3.2 ObservationEnvelope

```text
observation_id; source_ref; observer_contract_version;
mention_refs[]; predicate_or_description; modality;
speaker_ref?; valid_story_time?; learned_at_position;
evidence_quotes[]; unresolved_parts[]; disposition;
producer_run_id; input_manifest_hash
```

modality 至少区分观察到的事件、角色陈述、信念、假设、作者规划、比喻/非字面表达、不明确。不能因 schema 只能填实体 ID 就让模型伪造 UUID；未解析提及保留可追踪 mention identity。

### 3.3 IdentityResolution

身份解析返回 `reuse / new_candidate / ambiguous / unrelated`，包含同名、别名、类型、证据与候选集合。去重分为：身份去重避免创建影子人物；观察去重避免同一来源同一断言重复记录。已有身份不能导致新的字段观察、反证和来源被跳过。

合并身份时保留别名来源和全部 observation lineage，按领域命令迁移引用；同名不同人、冒名、称号复用保持竞争身份，不能靠相似度阈值直接合并已采用对象。

### 3.4 TypedStateOperation

```text
operation_id; schema_version; operation_kind;
subject_ref; relation_or_field; before_precondition; value;
story_position; valid_time?; knowledge_subject?;
source_observation_ids[]; authority_basis; derivation_version
```

初始操作族：entity.create/update/remove、relation.establish/end、location.observe/move、knowledge.learn/revise/revoke、timeline.assert、causal_constraint.assert。不是为每种文学句式设计一个永久枚举；通用 documentary assertion 可承载尚不能安全投影的观察，但不得冒充已改变状态。

对于未知前值，操作可为 `assert_observed`，不能伪造 before 值。对位置要分“此处出现”与“从甲移动到乙”，后一项只有在移动事实有据时使用。物品 ownership、custody、carried_by 不混为一条关系。

### 3.5 EvolutionReceipt 与游标

```text
run_id; attempt_id; owner_epoch; producer_version;
source_manifest_hash; input_state_receipt; previous_receipt;
observation_dispositions; world_result_refs; story_result_refs;
evidence_result_refs; pending_decisions; coverage;
committed_prefix; blocked_dependencies; paid_call_receipts;
execution_status; outcome_status; freshness
```

Receipt 是跨模块交接证明，不是另存全部世界表。游标只在领域提交成功后推进，模型返回或任务进度到 100% 不足以推进 committed prefix。

## 4. 顺序语义与并行效率

### 4.1 正确的推进顺序

```text
读取冻结原文
  → 准备当前 Scene 的观察任务
  → 编译当前可用前序状态（前一批已提交）
  → 窄任务模型处理与确定性定位
  → 独立复核 / 冲突分流
  → 准备 World/Story/Evidence 写入
  → 短事务内重验来源与 parent receipt
  → 提交操作、来源、回执与推进游标
  → 编译下一 Scene 的依赖状态
```

前一 Scene 未完成的争议不必总是阻塞全书，但后续必须明确继承 unknown/blocked 的依赖，不能继承尚未提交的假结论。若某项身份裁决是后续解释的必要条件，则暂停相关依赖分支，不把其他无关范围一起停止。

### 4.2 可以并行什么

可并行纯来源读取、无副作用解析、当前 Scene 内独立命题的提取与复核、与时间推进无依赖的资料检查、不同小说运行。预取后续正文只提高 I/O 效率，不冻结其依赖前序理解的最终 Prompt。

不允许把所有 Scene 的“当前世界解释”提前冻结，再把顺序落库包装成顺序认知。可把大书分成有依赖的批次屏障，批次内已证明独立的任务并行；必须以 read-set / dependency key 证明，而不是模型自称“可以并行”。

### 4.3 小模型适配

Evidence 为每个窄任务提供最小充分资料、固定身份候选和原文范围。模型负责解释，不负责构造数据库写入、预算或 retry。输出短且有类型；当前 Scene 超出能力时显式分片并记录跨片覆盖，不能静默截断后宣称完整。

引用定位、来源版本、类型、单位、同项目约束、前置条件、矛盾检查先由代码完成；语义蕴含再交独立复核。多 Agent 使用场景见 03，不要求所有 Scene 走昂贵团队。

## 5. 窄事务及运行可靠性

Provider I/O 不在长期数据库事务内执行。每个窄批次的准备阶段收集输入 manifest 和 expected parent；最终提交短事务内锁定当前项目/运行 owner，重验来源、代际和领域写集。沿用项目锁定顺序，避免持有共享锁后升级排他锁形成死锁。

同数据库中的 World 工作变化、Story 事件、Evidence 引用和该批次回执可以组成一个有限 UoW；正文大范围改写、正式世界采用、媒体对象存储不必和它处于同一巨型事务。超范围成果由后续领域确认处理。

### 5.1 三种失败不能使用同一个重试

| 失败位置 | 恢复方式 | 禁止行为 |
|---|---|---|
| Provider 尚未返回，是否计费未知 | 优先读取供应商请求/任务回执；无法判定则标 unknown 并按策略要求确认 | 立即重发整条流水线造成重复计费 |
| Provider 已返回，持久化前失败 | 复用冻结返回内容重新验证；不重新采样模型 | 把数据库错误当模型质量问题重生成 |
| 领域提交完成，响应/投影失败 | 按 operation_id 返回原回执并补投递 | 再次执行领域写入或再次消耗模型预算 |

Root budget 跨重试、requeue、成员和人工恢复累计。并发调用先原子预留额度，再发请求；取消后已发调用可能仍计费，记录实际消耗，不显示“撤销了费用”。成员完成但根任务过期时，禁止晚到结果修改当前状态。

### 5.2 幂等键与 fencing

幂等键建议覆盖 novel、来源范围、输入状态回执、方法版本、任务意图和操作版本，而不是只含章节号。owner_epoch 随切换或重建推进；旧 epoch 的 worker 即使恢复也不能提交。未变化输入返回原 receipt；改变了来源或方法需要新 attempt 并保留旧结果。

## 6. 修改、重排、删除与失效传播

### 6.1 修订影响范围

正文变更先计算物理来源差异，再查询显式依赖；对尚无细粒度依赖的范围，采用保守扩大并向 UI 说明范围。不要以文字相似度证明完整因果影响。

同字数修改和标题变化也需要 source hash；复制、还原、切换当前工作版本意味着 current selection 改变，即使旧版本本身不可变。Scene 切分变化要保存旧新 lineage，不能复用不再匹配的 offsets。重排不仅重写 scene_index，还使依赖顺序的事件、检查点、角色知识与推荐失效。

### 6.2 发布与自动保存

自动保存默认只保存正文、标明变化并合并维护请求。长模型任务在安静窗口或明确授权条件触发，不逐按键运行。发布是正文成熟度变化，不等于语义理解完成；UI 可显示“正文已发布，相关理解待更新”。

统一写入命令须由 API、助手、协作采用、导入、恢复和批量操作消费。提议 `WritingChangeReceipt` 输出旧新 current source、affected chapters、requested effects；领域在同事务记录待投递变化，消费者按幂等键执行。已有 outbox 可扩展为窄协议，不另造泛化全局消息总线。

### 6.3 失效不是删除历史

旧推断标记失效，原观察与历史回执保留。历史首次阅读使用当时合法信息；事后解释可以读取后来的授权证据，但标为 retrospective。认知方法、题目、缩略图、图片和角色外观同样可能剧透，不能只过滤正文。

删除项目则不同：原文、观察、认知、派生索引、媒体引用和缓存都必须按现有删除工作流清理；不能以“追加式历史”为由保留用户已要求永久删除的数据。

## 7. 从旧系统迁移

### 7.1 不可省略的迁移资产分类

| 旧资产/能力 | 去向 | 处理要求 |
|---|---|---|
| 文件解析、章节识别 | Imports 保留 | 不变更已经验证的输入格式边界 |
| 原文 draft/hash/offset | Writing/Evidence 保留 | 不重新编号破坏引用 |
| 场景切分、补全、抽取 adapters | 迁为可调用步骤 | 保留 schema、预算、回读和实际测试，解除旧编排所有权 |
| import_workflow_runs | 迁移或适配为 Evolution legacy run | 历史只读、来源与已消耗预算可查 |
| 旧 deep_import handler/阶段调度 | 最终退役 | 所有新入口转向 Evolution；禁止双提交 |
| 旧 checkpoint | 版本适配器 | 不兼容则明确失效/人工续接，不无条件跳过 |
| manual_correction/Delta | 分级转换 | 有据可转 typed op；仅文献记录；缺依据则未知 |
| 人工确认与采用历史 | 原领域保留 | 不被机器回放删除或重新解释 |
| 旧进度文案与状态 | 兼容读取 | 不把旧 done 当作新版全部维度完成 |

不能因为历史信息已丢失就在 migration 中造出新的“原始证据”。只有真实来源可重读时才能重建；不存在的历史图像也无法凭放大恢复。

### 7.2 六步切换

**E07.a 先修旧链关键保护。** 在新模块开发前补人工事件保护、两视图归约契约测试、观察去重和入口副作用测试，避免迁移期间继续扩大风险。

**E07.b 影子运行。** 新引擎读取同一冻结来源，只保存隔离实验产物；禁止给正式 World/Story 写第二套有效事实。对比 observation disposition、typed state、coverage、实际调用及成本。

**E07.c 项目级 canary。** 为一个测试项目记录 active engine、schema version、owner_epoch。新旧运行不可同时拥有同项目的有效提交权。先排空或显式停止旧 owner，再切换代际。

**E07.d 在途兼容。** 能证明兼容的旧任务按冻结 contract adapter 继续；不兼容的保留费用与成果，提示从可验证批次继续。不得伪装原 task 原地换模型换方法。

**E07.e 入口重定向。** 新用户入口只显示“理解这本书/继续理解”；旧 deep-import API 暂作参数适配，返回真实新回执和 deprecation 提示。旧状态页可读不可启动第二个 owner。

**E08 彻底退役。** 移除旧独立调度、自动重跑策略、重复恢复 owner、旧前端阶段面板及无调用副本；保留历史读取 adapter 到明确的兼容期。完成登记表逐项核销。

### 7.3 回滚不是复活第二套世界

回滚到兼容二进制与已验证 active pointer，提升 epoch，使旧 worker 无权提交。已提交新版本不物理擦除；不能回到不能解释新事件 schema 的旧引擎继续写。必要时停止自动处理、保留只读和正文写作，再通过前向修复恢复。

## 8. 代码落点与包划分

| 包 | 建议位置 | 关键结果 |
|---|---|---|
| E00 | 现有 imports/story/writing tests | 复现与保护、入口副作用清单 |
| E01 | evolution/contracts、observations、sources | 来源与观察外壳，稳定观察 ID |
| E02 | world facade + evolution/identity | 身份去重与观察积累分离 |
| E03 | story/continuity reducer + evolution/commit | 单一语义内核、人工保护、窄提交 |
| E04 | evolution/orchestrator + existing tasks | 前序屏障、有限并行、游标与预算 |
| E05 | Evidence dependencies + evolution/invalidation | 修订、时态、重排、删除影响 |
| E06 | story checkpoints + evolution/recovery | 分页回放、检查点、owner fence |
| E07 | legacy adapters + migration | 影子、canary、在途与回滚 |
| E08 | handlers/frontend/旧文档退役 | 唯一编排所有权、旧代码删除证明 |
| E09 | end-to-end evaluation fixtures | 真实模型、长书、跨模块质量验收 |

## 9. 最小纵切与退出标准

虚构测试小说包含林舟、青竹、白石城、铜钥匙。第 1 个 Scene 建立人物；后续同名观察补充而不重复建人；青竹保管钥匙但所有权不变；林舟的移动与“最后出现”分开。下一 Scene 的输入必须实际包含前一 Scene 的已提交理解。新的独立写作 case 读取相同合法认知，地图展示来源一致的在场和未知。

然后修改前文为同长度文本、调换场景顺序、注入一次作者修复，分别在 provider 返回前、返回后、领域提交后中断。验收最终状态、来源与费用回执，而不是仅比较运行日志或页面有绿色成功条。

必须通过：人工事实不被重跑覆盖；同输入串行/分批/恢复语义一致；不同版本的历史有明确解释；失败不推进 committed prefix；旧 epoch 无权写；原文完整保存；认知和地图实际消费新回执；缺失来源不造假通过。

性能测试以 1k/5k/10k 场景分别测 checkpoint 命中与回放长度；这些是测量档位，不是已证明的性能承诺。长链不逐次全书重算，只有明确依赖和观察账本才能支持可解释的局部恢复。

# V + MI：地图、场景舞台与空间智能详细计划

V4.0｜设计提案。地图基础体验与演化主链并行交付，高级智能依赖可验证的 Story 状态和 Evidence 边界。空间画面是作品的一个视图，不是另一套事实数据库。

## 1. 地图系统的五层

| 层 | 所有者/数据 | 用户得到什么 | 不得混淆 |
|---|---|---|---|
| 地理与约束 | World/Map 采用的结构与关系 | 地点层级、空间拓扑、已知规则 | 图元拖动不自动改世界地理 |
| 时态与在场 | Story 的指定截止点投影 | 人物出现、物品保管、过去节点 | 最后见到不等于现在仍在此处 |
| 证据与作用域 | Evidence 物化回执 | 来源、范围、缺失及可见性 | 可搜索到不等于当前可见 |
| 表现与媒体 | Map revision/presentation/media | 底图、场景插画、人物与物品形象 | 图片不是事实证明 |
| 智能解释与排演 | 认知 + 注册协作配方 | 缺失条件、条件路线、地理创意 | 排演不等于已经发生的行程 |

保留当前地图结构与 API seam，优先抽出一个 `MapViewerShell`。不创建孤立的“认知地图数据库”，不把 World 对象复制进地图主表。地图内的成员引用现有 identity，并保存表现选择与来源版本。

## 2. 默认作者体验

作者进入地图时直接看到一个完整的空间舞台，可切换地图、配图与场景。当前章节和场景由工作焦点推导，但可明确切换；只有确实有位置依据的对象落点。未知对象进入可搜索列表，不为了“惊艳”随机撒点。

选择地点时在唯一详情抽屉中展示：地点图、当前在场、相关场景、一项最相关信息和返回正文按钮。抽屉不再打开另一个抽屉；需要更多证据时复用同一个宿主并提供返回栈。全屏模式仍在统一 overlay 根中，退出后恢复相机、选中对象、滚动、图层和编辑草稿。

场景舞台把背景图、人物图、物品图与当前原文连接起来。无配图时使用清晰的地点信息和抽象底图，不自动付费生成图片。角色图和物品图是表现参考，不能借图片暗示未揭露身份。

### 2.1 本轮 HiFi 对应

| 画面 | 设计目的 |
|---|---|
| S20 沉浸地图 | 浮动顶栏、探索范围、唯一详情抽屉、故事回看带；地名避让面板 |
| S21 场景舞台 | 背景、在场人物、物品与原文串联 |
| S22 历史旅程 | 有据节点与未知连接分开；明确首次阅读/事后解释 |
| S23 地图编辑 | 图元布局与事实变更分离；撤销、预览与离开保护 |
| S24 条件排演 | 已知约束、缺失条件、可选设想；不造出到达时间 |
| S25 配图与校准 | 媒体、范围、校准及候选采用分离 |
| S26 形象资料 | 人物、地点、物品视觉资产与来源 |
| S36 范围与视角 | 作者、当时已知和事后解释清晰分开 |
| S39 移动地图 | 可折叠底部详情，不将桌面三栏压缩到手机 |
| S46 图片调用确认 | 实际生成范围、费用未知、回执与不自动采用 |

画面中的点位、插画和路径全部是虚构设计样例，不是生产地图事实；地图坐标为示意，不按比例。

## 3. MapSceneContext 与在场语义

建议由 Map facade 聚合只读 DTO，数据来自合法 World/Story/Evidence，而非前端拼接一串原始表。

```text
MapSceneContextV1
  view_ref; scene_ref; map_revision; presentation_revision
  location_refs[]; presence_items[]; object_links[]
  source_receipts[]; coverage; omissions; unsupported_dimensions
  freshness; generation_stamp; request_context_id
```

`view_ref` 复用全项目经验视图的引用，不创建一张总快照表。正文来源、World/Story 版本、认知、地图、媒体及方法只绑定本次实际依赖，避免任何变化使全部视图过期。

### 3.1 人物与物品位置

| presence_kind | 可以怎样显示 | 禁止表达 |
|---|---|---|
| confirmed_in_scene | 本场在这里，有原文/已确认事件 | 不自动推出角色知道此地全部秘密 |
| profile_location | 仅当前作者资料中的常驻/档案地点 | 不回填成某历史 Scene 的实际在场 |
| last_observed | 最后一次明确出现于此，显示来源位置 | 不称“当前就在这里” |
| related_only | 和地点有关，放关联列表 | 不在地图上放实心位置点 |
| unknown | 位置未确定，保留搜索入口 | 不随机定位，不用档案地兜底 |

物品另列 custody、ownership、carried_by。青竹保管铜钥匙不表示她获得所有权，也不表示每个后续场景她都随身携带。一个角色关于位置的信念是 belief layer，不应进入客观在场层。

### 3.2 历史轨迹

只把明确出现节点画为真实节点。两个节点中间没有路线证据时可画有文字标记的虚线以表达“关系待定”，但默认不标路程、交通方式、速度或到达时间。已知道路的拓扑路径与人物实际走过的路线是两套不同的命题；前者也不能自动转成后者。

地图历史不仅按章节号。需要 story position、world valid time、learned position、source revision、interpretation mode；倒叙和后揭示必须可表达。新方法产生的回顾性解释不能以“这段原文在早期出现”为由混入首次阅读视图。

## 4. 渲染、相机与智能排布

### 4.1 相机坐标

世界坐标、底图像素坐标、归一化热点坐标和屏幕坐标分开。拖动与缩放修改相机矩阵；修改地理位置或底图校准必须是显式领域操作。重绘后保留同一语义锚点，不依赖 DOM 坐标碰巧一致。

`fitSelection` / `fitScene` 以扣除顶部工具条、侧抽屉和底部时间带后的可用画布为目标。展开抽屉不应挤动每个地点的世界坐标，而是调整相机或标签布局。必要时用“被遮挡地点列表”保持可达性；不把对象藏掉却不提供入口。

### 4.2 标签策略

以真实字体测量文本边界；优先显示选中对象、当前场景地点、关键路线端点，再显示普通地名。候选标签位置按锚点上下左右尝试，不能占用浮层障碍区；碰撞时缩短次级说明、聚合或转入列表，不缩小到不可读。

使用屏幕像素级碰撞索引，缩放时带迟滞，避免标签不断出现消失。每次相机微动不重排全部排名；对正在阅读的选中标签和卡片冻结位置。几何层、标签层、媒体层、交互层分别更新，避免鼠标悬停触发全书查询或整个地图重绘。

### 4.3 地图性能工作包

先以仓库当前支持规模作为实际基线，记录真实图元、边、图片数；输入 v3 提到的 200 图元/400 约束等限制须在实施时重核 schema，不能当成无限容量承诺。

建立固定 fixture：上限图元、长中文标签、密集地点、多个图层、抽屉开关、低端移动设备、网络慢与缓存失效。候选目标是交互有稳定反馈、可用帧率与有界媒体内存；阈值需要实机测量后冻结，不能用设计截图证明性能。

## 5. 媒体、热点与保留形象

### 5.1 媒体处理

沿用专用 owner/novel 门禁，不暴露私有对象存储 key。提议将展示图提升至适合大画布的分辨率档位，例如最长边 2048、显示资源约 1MiB 上限；这些是 v3 继承的设计候选，不是已实现规格，也不替代原上传输入限制。格式、透明度、WebP 编码和内存需实测；不能对已压缩旧图声称恢复原有细节。

人物/物品透明背景须在服务端保留 alpha，背景图按真实输入转换；不要统一 RGB 破坏透明形象。缩略图和展示图分级加载，较高分辨率只在需要时取。媒体管线复用共享 `PrivateMedia`，并发上限作为可配置资源策略，不由每个组件各起一套请求。

缓存键包含 account、novel、media revision、授权作用域；切换项目或视角先释放旧图和 object URL，取消旧请求，晚到结果不得挂回当前页面。卸载、替换、失败和删除均需释放资源。

### 5.2 Presentation revision

场景背景、形象选择、热点与裁切保存在独立版本化表现资产，不修改 CanonRevision 来表达视觉布局。热点使用归一化位置，绑定源图片身份与 hash；同一图片等比例派生不会丢失定位，换图或不同裁切映射必须重验，不能悄悄沿用旧热点。

单表现修订的热点数量可先采用 v3 的 50 个候选限制，使用完整 revision CAS 处理并发；数量不足则通过有版本的 schema 扩展，不让前端绕过限制。若当前 map schema 尚不支持室内/街道变体，先标 unsupported，再在独立工作包扩展，不临时塞入不被后端理解的字段。

### 5.3 图像生成

图像生成是单独授权和计费的命令。请求冻结实际可外发的资料，不把隐藏角色身份、私人正文或未授权的整个知识库交给供应商。返回候选后先审阅，再批准为某场景/角色使用。

超时后根据 request receipt 查询是否完成，不能默认再次付费。配额、保留数量、原图与派生文件、未被引用的失败资源均需要一致清理。删除项目清除所有媒体与残留；替换图片保留/释放的规则与配额账本不能各自实现。

## 6. MI：空间智能的逐级开放

### MI00 地理依据与缺失条件

从显式位置、连接和规则给出“已知什么、缺什么”。例如夜间城门关闭，但渡口是否通行未知。输出不是“无路可走”，而是“无法在当前证据下确认夜间通行”。

### MI01 路线与时间排演

只有采用的拓扑、方向、单位和通行规则可作为规划约束。模型解释叙事意义，代码做可执行约束与图搜索。若距离和速度缺失，输出路径选择或条件比较，不给分钟数。把方案标为 hypothetical；采用方案也只是采用作者规划，实际旅程需后来正文或作者事实命令确认。

### MI02 地理—剧情联动检查

校验人物跨场景移动、携带物品、地点进入条件与时间冲突。结果每项绑定来源与受检范围；没有完整路线不能宣称没有空间漏洞。修订地图或前文时通过依赖清单使旧判断失效。

### MI03 空间创意工作坊

三条独立提案可以围绕地形阻碍、社会规则、人物选择展开。必须保留一种不扩地图的方案；新增关卡、捷径或地理规则列出会约束后文的代价。不可自动画出新城、新路后把它当成既有正史。

### MI04 多视角与多尺度

角色所知地理、读者可见地图、历史政权/道路变化、室内场景等分别经过合约和访问门禁。外观、名称、连线和地图缩略图都参与泄漏测试。早期没有能力的视图返回 unsupported，不回退作者全量。

### MI05 长期空间认知

跨章节积累移动习惯、制度约束与空间叙事经验，只能作为可重验派生理解。统计相关性不能变成地理因果；“经常出现的地方”不是当前所在地。与 C 的方法实验使用相同输入和预算对照，验证其是否改善真实场景设计，而不是只增加图层数量。

## 8. 验收与反例

地图缩放或抽屉打开后，当前地点的名字不被遮挡；不能显示的次级地点仍可从列表定位。移动端底部详情不能盖住唯一当前状态和返回正文动作。全屏进出不丢失编辑草稿，ESC 首先退出当前最上层任务而非关闭整个作品。

甲地出现与乙地出现之间没有旅程时，不造连续实线；角色档案地不能回填历史在场；钥匙保管不改变所有权；角色知道某地点不等于客观位于该地。换到早期读者视角，作者图片、标签、缓存和晚到请求都不能泄漏。图片生成失败/重复恢复时不双扣配额；项目永久删除后对象存储清理可验证。

真实验收分别记录：地图数据语义、前端交互、媒体安全/资源、模型提案质量。高保真图是设计契约，不是这四类测试已经通过的证明。

# C + A + R：持久认知、多 Agent 与主动建议

V4.0｜长期设计。保留现有 PydanticAI、有限协作配方、项目账户模型入口与根预算；框架不是质量收益的替代品。

## 1. 三者怎样组成一条价值链

演化系统回答“原文发生了什么、当前哪些状态有据”；认知子域回答“这些信息怎样组织成可继续使用、可修订的理解”；协作配方决定“用哪些隔离任务取得更可靠或更多样的成果”；推荐层回答“作者此刻值得先看什么，并怎样安全地行动”。

避免三个反模式：为每个推荐重新全书理解；每个 Agent 各写一份人物事实；把历史对话自动升格为长期认知。对话、模型推断、作者采用与原文证据必须继续有不同资格。

## 2. 持久认知 C 的数据与生命周期

### 2.1 最小 durable domain

在 Collaboration 中建立独立于短期 run retention 的认知子域。可从 head、commit、record 三类持久实体及可重建索引开始；不要教条地限制为三张表，也不要预建庞大的不可演化字段全集。

`CognitionRecord` 外壳固定：novel、scope、record identity、kind、content schema/version、来源引用、依赖、有效时间、学得位置、方法版本、作者处置、freshness。content 可表达本书逐渐形成的关系、规律、竞争解释和开放问题。模型可以提议表达形式，不能自行执行 schema migration 或扩大工具能力。

`CognitionCommit` 冻结完整实际读集、记录变更、未决项与方法版本，用 CAS 指向该作用域的 head。认知更新不调用 World 准入来把推断变成事实；采用为正式设定是另一个可预览的领域命令。

### 2.2 新任务必须真实消费

第一批 C 交付就要接入一个新的、独立创建的写作或调查 case。InputManifest 记录读取了哪个 cognition commit、哪些记录实际进入模型、为什么有助于任务、哪些记录因范围/失效被排除。

任务完成后只沉淀有长期价值的内容：有来源的新理解、可复用决定、明确反证、有效工作方法。无需沉淀则 `no_change`。把整个聊天历史复制成摘要，或向所有后续 Prompt 默认加入全量记忆，不算完成这个目标。

### 2.3 依赖与负面证据

正向证据依赖绑定资源版本和范围；“在已检查范围没有发现另一条通路”还依赖查询范围、检索条件、集合版本与覆盖程度。后来加入新章节或新增对象，负面结论也可能失效。不能只登记被检索命中的几条来源。

A 由 B 推导、B 又被 A 的摘要支持，属于循环支持，不能提高可信资格。派生解释最终需追溯到合法原始观察/作者决定；循环引用用于组织索引可以存在，但不能当成独立证据。

### 2.4 历史视角

首次阅读视角仅使用截止点前合法的内容和可用方法成果；事后解释允许后来的授权资料但必须标为 retrospective。模型不能通过“去掉剧透句”把含未来知识的完整摘要变成安全历史版本，需要从受限来源重新编译或返回无法提供。

删除与用户纠正进入依赖链：纠正保留旧解释历史并改变 current selection；永久删除清理认知与索引，不因其“有用”而保留。作者拒绝的是建议呈现还是事实解释，应是不同命令。

## 3. 扩大认知的长期阶梯

| 层级 | 新能力 | 进入默认任务的条件 |
|---|---|---|
| C0 可继承 | 稳定人物、地点、事件及来源索引；任务间承接 | 新 case 真实读取，来源可回读 |
| C1 可修订 | 竞争动机解释、身份歧义、反证和待查问题 | 能保留分歧；来源改变可失效 |
| C2 因果与制度 | 行动前提、代价、规则例外、承诺和后果 | 条件关系不冒充确定因果；有可检查约束 |
| C3 多主体理解 | 人物信念、误解、读者已知与作者规划 | 各自 scope 隔离，防知识穿透 |
| C4 创作经验 | 本书叙事声音、节奏、作者保留项和局部写作方法 | 不能由点击率推断作者审美；允许例外和不采用 |
| C5 方法演化 | 调查顺序、证据策略、表达组织的有界实验 | 等输入/预算比较，真实收益后再成为默认 |

不能用单个“认知完成 95%”描述这些维度。每项能力列出 inspected、not_run、unknown、excluded、stale、unsupported。系统更复杂不等于认知更成熟。

## 4. 多 Agent：根据任务结构选择，而不是默认团队

### 4.1 研究依据和使用边界

R1（2026-04-08 v3）对 260 种配置、六个任务基准的受控分析强调架构与任务结构匹配；这支持“有依赖的演化推进不能自由并行”，不证明我们的小说任务已有收益。

R2 的推理自我修正研究指出，在其测试设定中，没有外部反馈的自纠错可能失败或退化。这支持加入原文、代码验证和可定位错误反馈；不意味着所有当代模型、所有任务都不具备自修正能力。

R3 的短篇写作实验同时观察到个体创意评价收益与故事间相似性上升。这支持保留独立方向和作者选择；它不是长篇小说专业作者的直接效果证据。

R4 的工程报告说明独立并行研究适合广度探索，也带来显著协调和消耗成本。R5 当前 PydanticAI 文档提供 delegation、程序交接等方式；实施时必须先核对仓库锁定版本，不能直接复制最新版 API。[完整出处见 06]

### 4.2 分流规则

| 任务 | 默认实现 | 升级条件 |
|---|---|---|
| 保存、来源校验、可见性、CAS、范围切分 | 确定性代码 | 永不委托模型决定权限/提交成功 |
| 简单润色、明确的小范围提取 | 单 Agent + schema/来源检查 | 有真实失败特征且团队对照有收益 |
| 身份、所有权、角色所知等高风险解释 | 窄生成 + 独立证据复核 | 争议仍未解时定向查证或人工决定 |
| 跨资料大范围调查 | 多个有界、互补的只读成员 | 可分解且不会共享一个未提交状态 |
| 创意构思 | 独立多输出或最多三名方向成员 | 按多样性/质量/预算比较选择，而非总上团队 |
| 后一 Scene 依赖前一 Scene 的解释 | 有顺序屏障的主链 | 无关叶任务可并行；提交顺序不可放开 |

“低端模型”使用实测能力 profile，而不是供应商名称。记录该模型对指定输出、上下文长度、结构遵循、引用定位、歧义识别的实际表现；允许账户只配置一个模型，系统仍可用独立回合和角色隔离。

## 5. A-Reliability：增强轻量模型可靠性的配方

### 5.1 默认有限流程

```text
Host（代码）冻结任务、资料、根预算与不可变输入
   ↓
Extractor：只提出当前窄范围的观察/解释
   ↓
Deterministic gates：来源/类型/单位/身份/时态/前置条件
   ↓
Verifier：独立回读原文，先作判断，再看候选差异
   ↓
Disagreement resolver：只查争议命题，最多有限返修
   ↓
Outcome：supported / contradicted / uncertain / not_checked
   ↓
Domain prepare/apply 或作者决定
```

主模型或 Planner 的名字不授予真值权威。Host 是代码级控制边界，不必为每次任务再消费一个“总负责人模型”。评审者的第一遍尽量不接收生成者的理由，以降低锚定；第二遍可接收具体命题、来源与代码诊断。

### 5.2 小模型输入设计

每个成员明确 objective、allowed tools、exact source range、identity candidates、expected output schema、stop condition、unknown handling。只发送当前任务必要信息，缺失信息在输出中显式登记；不能以缩减上下文为理由藏掉与判断相反的证据。

对长 Scene，先定义覆盖所有来源的分片和跨片连接，再做有界聚合；不能仅取头尾或摘要后仍写 complete。输出以原子命题为主，避免一个模型一次生成几十种混合结构和完整状态更新。

### 5.3 代码与语义复核分工

代码可以验证引用是否存在、版本是否一致、ID 是否同项目、区间是否越界、数量与单位是否合法、操作前置状态是否匹配。代码不能仅凭引用命中证明“这是赠予”。语义复核需要辨别说话者、否定、假设、时间、传闻和角色误信。

Verifier 的 `supported` 必须引用自己实际读过的来源，不能引用成员给的一段无来源总结。多名成员引用同一段正文是共享证据，不是多份独立证据，不能加票提高事实资格。

### 5.4 争议、升级与退出

修复优先使用具体失败位置和错误类别，不让模型无限“再认真检查”。策略登记最多轮数、累计 token/request、wall deadline 和争议条目上限；超出后返回 partial/uncertain，而非把最后一个答案视为正确。

配置了真实更强模型且有授权时，可仅升级争议命题；没有则请求用户决定或保留未知。升级不自动扩大来源、账户或外部网络权限。部分已验证的独立命题可保存，依赖它们之外的未知不能被补成确定结论。

### 5.5 初始角色配方

- identity-and-observation：提及识别 → 身份/反证核对 → 归并候选。
- continuity-review：人物位置、时间条件、物品持有按职责拆分，再统一来源与约束检查。
- world-rule-stress：规则解释、极端边界案例、叙事代价检查分别输出，不直接改规则。
- weak-model-repair：只有确定性定位到失败或独立复核明确的条目进入返修。

这些角色复用现有 Collaboration recipe、资源 port 和 Assistant domain operations。不要给每个配方独立 session 表、持久世界、计费账本和调度器。

## 6. A-Creative：帮助作者发散，而不是代替作者裁决

### 6.1 两阶段而非自由争论

第一阶段独立生成：各成员只看到用户目标、保留项、合法来源与自己的视角，不看到其他成员的方案。可采用人物主动性、情节悬念、情绪/文风三个初始角度；视角只是配方，可按任务调整，不永久固定所有创意为三种。

第二阶段形成比较：去除实际重复提案，但保留有意义分歧。聚合者输出可选择方向，不默认把它们写成一个折中故事。至少保留一个“不扩大情节/不新增世界规则”的方向，允许作者全部不选。

### 6.2 CreativeOption 外壳

```text
option_id; viewpoint; premise; proposal; intended_effect;
required_existing_facts; new_assumptions; story_debt;
what_is_preserved; what_changes; counterarguments;
source_refs; hypothetical_status; suggested_next_action
```

story_debt 指需要在后文兑现的因果、规则、关系或伏笔负担，不是负面评分。一个精彩的设想可以代价很高，作者应看得见。不同方向不能用未经校准的“创新度 98”或隐藏评分替作者选出正确剧情。

### 6.3 采用路径

作者可以只借一句对白、组合两个方向中的局部元素、要求反向思考或保留原文。选中后生成有限的 domain patch，展示原文/候选/影响/新增假设。通过对应审查后保存为工作稿，不自动发布。

事实核验者只能检查硬约束、来源和明确保留项，不以“我觉得节奏不好”为由否决作者审美。情绪偏好和风格选择进入解释性比较，而不是强制门禁。

### 6.4 前端不显示一堵 Agent 聊天墙

用户默认看到三个有区别的方向、每个方向的优点/代价/未知和一个行动。成员往返、Prompt、日志放诊断入口。研究流程和创意流程可用同一伙伴区域，但必须以“核对事实”与“探索想法”标清成果性质。

## 7. 共用运行底座的可靠性

使用 `TeamRunEnvelope` 适配现有根运行信封：root run、operation、owner、scope、allowed tools、model execution snapshot、总预算、每个成员剩余额度、deadline、lease epoch、cancellation token、producer contract。并发请求先做原子预算预留，失败/重试累计，而不是每个成员独享完整项目额度。

Agent 各自拥有受控历史和资料清单，跨成员传递以可重验 artifact 引用为主，避免自由文本接力导致来源丢失。任意工具注入、成员自行放宽 scope、子任务循环生成团队均禁止。跨模型共享资料需要逐成员权限物化；不能只在父 Agent 校验一次。

当前最多三名并发成员不阻止多轮复杂任务：可以分阶段轮换，但所有阶段累计同一个预算。内部只读工具失败可以有窄恢复；领域写入仍由确定性 prepare/apply 和最终来源重验完成。

## 8. R：主动推荐的统一设计

### 8.1 四种 key，而不是一个 hash 解决全部问题

| Key | 代表什么 | 改变后怎样处理 |
|---|---|---|
| authority_scope_key | owner、novel、视角、截止点、排除项、授权版本 | 必须重授权/重新物化，旧数据不能继续显示 |
| evidence_snapshot_key | 实际读取资源、hash、范围、集合版本 | 重验来源；失效结果不能标有效 |
| task_context_key | 当前目标、intent、draft/scene、任务范围 | 检查建议适用性，不自动扩大证据 |
| presentation_focus | 光标、选区、折叠态、当前页面、读取位置 | 影响排序与展示；不成为事实或权限 |

允许旧建议在新的焦点下继续显示，前提是领域 `is_applicable` 明确确认作用对象、来源和任务匹配；不是直接忽略 context_hash。

### 8.2 选区与未保存输入

优先级：显式选区 → 光标所在语义段落/当前场景 → 最近保存差异 → 有说明的尾部回退。完整传递 intent，例如“只润色”“探索反应”“校对事实”，不能只把它留在前端。

初版后台默认 saved-only。显式选择未保存文字的即时操作，可以在独立 U-Ephemeral 包通过后使用临时快照，绑定全文 hash、selection range、TTL、client epoch；禁止用新 UI 的 offset 读取旧 draft。该包未通过前禁用执行并提示保存，不伪装支持。HiFi S07 展示的是这一目标行为。

### 8.3 推荐候选、排序与处置

推荐来源包括受检问题、开放问题、认知解释、场景过渡、人物反应、世界规则决定、空间条件和创作机会。候选至少有 stable issue_key、basis、why_now、scope、unknowns、actions、freshness、coverage 和逐 claim 支持来源。

排序先过来源/权限/适用性硬门，再看当前任务相关性、影响、时机、成本、作者处置与方向多样性。模型输出分数不是概率；默认不展示“置信度百分比”。同一问题跨 Writing/World/Map 由稳定 issue identity 关联，不各弹一次。

屏幕只突出一个主建议、至多两个次要方向，其他进入 backlog；有限显示不等于未显示项消失，提供覆盖说明。排版可重排，但用户阅读、输入法组合、正在预览差异或已固定某卡时不抢焦点。来源变化可立即撤去“有效”资格，内容区用安静提示而非强弹窗。

暂缓/拒绝是呈现决定，不会删除事实或改写人物状态。再次提醒要有新的相关依据或用户指定条件；不能因定时器轮询又复活同一建议。

### 8.4 统一前端状态与后台执行

同账户/项目使用一个共享 feed store，组件订阅，不各起轮询。标签页焦点仍是本地，授权与持久结果来自服务端。读取 feed 无模型副作用；计算由单独显式请求或持久授权驱动。请求携带 context id/epoch，晚到结果不能盖回旧选区。

从建议进入操作时：重新物化依据 → 准备具体领域提案 → 一处差异预览 → 用户采用 → 返回领域回执 → 统一刷新。不要从三个面板各走一套采用实现。

## 9. 评估：可靠性和创意不能共用一个分数

### 9.1 可靠性对照

至少比较单模型一次、单模型有限自检查、单模型多采样/选择、隔离生成+复核、真实异构团队（仅真实连接可用时）。固定原文范围、工具、总预算和可见信息，记录语义准确、错误修改、未知保留、来源错配、调用/成本、延迟与恢复结果。

历史 v3 的小样本实验中存在预算不等和样本不足，不能作为团队质量提升已证实的结论。此处不预先写出收益百分比。错误类型按否定、传闻、冒名、时态、物品关系、伏笔与现实规则分层，避免平均分掩盖高代价错误。

### 9.2 创意对照

同题比较单强模型多方向、隔离同模型角色、异构/不同目标成员。由作者或独立读者盲评方向实质差异、符合保留项、可用性、意外性、叙事负担与最终采用片段。点击率不等于质量；不给模型自己的审美评分充当 ground truth。

### 9.3 认知 A–E 五臂实验

A：普通检索，无持久认知。B：固定表示+固定方法。C：开放表示+固定方法。D：固定表示+可调方法。E：开放表示+可调方法。相同作品分段、来源截止、工具和总预算；每臂都必须服务真实后续任务。展示用 fixture/oracle 不得进入模型输入或评估资产。

方法候选仅在留出任务与故障场景证明收益后提升为默认。失败可退回已验证方法版本，但不丢弃真实观察或作者决定。

## 10. 工作包

保留 C00–C06：隔离实验、持久域、Evidence 接入、维护、方法演化、作者视图、五臂验证。新增 C07 竞争解释/负面依赖、C08 多主体与历史、安全视角、C09 长书局部维护与真实消费。

A00 能力/成本基线；A01 共享根预算和隔离输入；A02 可靠性窄配方；A03 盲复核与争议裁定；A04 创意独立发散；A05 对比与领域采用；A06 等预算评估与受控默认路由。

R00 选区/intent/数据链修复；R01 scope/snapshot/task/focus 分离；R02 单 feed store；R03 逐 claim 支持与 stable issue；R04 排序和安静策略；R05 领域行动闭环；R06 认知驱动预测/机会建议；R07 真实用户与成本验证。

新增范围以阶段门禁控制，而不是给主 Agent 无限权限。未来可以扩角色和方法，但所有新增能力仍必须带来源、边界、预算、测试与实际消费者。

# U：全前端任务工作台与 HiFi 交付规范

V4.0｜设计方案与可点击示例。当前提供 48 个工作流/状态画面 + 1 个设计规范画板。不是已经迁移到生产的界面，也不代表全字段或所有 API 场景均已实现。

## 1. 产品标准怎样变成可验收规则

“傻瓜式操作”不是只留下一个聊天框，而是用户不必理解内部阶段、数据表与模型调度，也能知道当前状态、下一步和操作影响。

默认每张任务卡只有一个主操作；下一步由当前真实领域状态推导。自动完成不需要作者反复确认的只读整理，遇到有歧义的事实、正式采用、真实费用和破坏性动作才问。提供保留未知、稍后处理和不采用，而不是逼迫作者替模型补完一切。

“智能排布”不是让 LLM 任意生成 DOM。定义 `SurfacePolicy`：输入为用户任务、合法资料范围、屏幕尺寸、阅读/输入状态、是否 dirty、是否有活跃长任务与结果类型；输出为主内容、旁栏槽位、展开层级、主操作与面板锁定策略。每条策略都可用 fixture 测试。

## 2. 一套壳，六个默认入口

导航：概览、写作、故事结构、世界资料、故事地图、待我决定。运行恢复、模型授权、项目与版本在次级入口；Account 和 RP 保持各自入口，不向 RP 用户暴露作者后台。

用户页面不展示 raw UUID、JSON、Phase2a、Prompt 预算枚举或内部状态名。需要定位来源时使用章节、场景、人物名、日期与可读说明，诊断可按需展开精确版本。

当前代码中的 `--nc-*` 语义颜色与 Vue bridge 是应继承的接口。本轮温和纸色、深墨/青绿色主动作和紫色 AI 是 V4 提议的视觉主题，不声称与现有蓝色现代简约主题完全一致。实施时保留语义 token 名与现有主题能力，再通过新增主题/令牌映射切换，不硬编码逐页面颜色。

## 3. 四层状态，避免“看起来完成”

### 3.1 永久可见的最低信息

每个涉及 AI 成果的任务至少能找到：基于哪个保存范围；是什么性质（原文观察/系统理解/创作候选）；当前是否过期；是否需要作者决定；实际下一步。小卡片可以合并成一行，但不能删除这些语义。

### 3.2 OutcomeView 契约

```text
execution: pending | running | paused | terminal
outcome: complete | partial | failed | cancelled | unknown
coverage: checked / not_checked / excluded / unavailable
freshness: current | stale | historical
applicability: applicable | wrong_focus | unsupported
adoption: proposed | reviewed | adopted | superseded | not_applicable
primary_action; secondary_actions; evidence_refs; omissions
```

前端展示由后端结果和本地未保存状态组合，不凭内容长度/前几千字猜测来源新鲜度。后台停机、读取失败和权限拒绝不能呈现“没有问题”；旧检查可以留在历史区，但不计入当前可行动高风险问题数量。

### 3.3 不伪装用户操作反馈

服务端成功才显示“已保存”；仅本地备份成功显示“已在本机保留，尚未同步”；两处都失败必须明确提示并保留可复制内容。任务提交成功不显示理解完成，已采用工作稿不显示已发布，图片生成成功不显示视觉配置已批准。

## 4. 展开、抽屉、弹窗与合并策略

| 情况 | 默认表现 | 原因/退出行为 |
|---|---|---|
| 简短解释、为什么现在 | 卡片内折叠 | 不丢当前位置，按钮含展开状态 |
| 当前建议的原文、来源、少量备选 | 同一个右侧宿主切换内容 | 不新开第二个右栏，提供返回栈 |
| 自然语言讨论 | 伙伴“讨论”页签 | 当前任务上下文保留，不另起全局悬浮窗 |
| 长任务历史与恢复 | 伙伴历史摘要 → 独立运行页 | 不把日志墙铺在正文旁 |
| 多段差异、大规模审阅、版本冲突 | 独立宽工作区 | 足够宽度比较，保留返程锚点与本地输入 |
| 授权、真实计费、永久删除 | 单层模态 | 明确影响、取消与确认；禁止层层嵌套 |
| 地图/写作专注模式 | 全屏任务壳 | 退出恢复相机、选区、滚动及草稿 |
| 手机对象详情、建议 | 单底部 sheet | 限制高度，可扩展；关闭后回原文/地图 |
| 调试、模型、范围精确版本 | 第三级诊断 | 普通用户不必打开也能完成核心任务 |

只有一个 overlay root。DOM 焦点进入模态、Tab 保持在模态内、Escape 关闭当前模态，关闭后返回触发控件；长内容初始焦点可置于标题而不是把第一项按钮滚到不可见位置。依据 W3C APG 的模态模式（R6），还需实际键盘和辅助技术测试；截图不代表可访问性已经通过。

自动建议不得在 IME composition、拖拽、选区调整或用户正在阅读时抢焦点。真正来源失效可以立即显示状态，但不突然重排全部卡片。浮动宠物/伙伴图标只是同一 store 和宿主的另一种入口，不能另建轮询、推荐队列或确认操作。

## 5. 核心工作流重新组织

### 5.1 开始一本书：S02–S05、S34

上传、确认来源差异、授权整理、持续进度、单项歧义决定组成一条流程。正常路径只问一次批量整理授权；不要求选择 Scene/世界对象/关系/剧情结构阶段。首次空态不显示不存在的“已理解 12 章”，也不逼作者填世界表。

上传格式能力按已验证后端呈现；导入预览不是覆盖。来源确认之后，页面显示“哪些内容保存了、理解推进到哪里、哪些需要决定”。用户可以离开并继续写作，后台任务不靠页面挂着维持。

### 5.2 写作：S06–S10、S12、S37–S38

正文占据主要空间；伙伴区合并原提醒、预测与讨论入口。选区操作显示当前选段与本次意图；没有 Scene 时仍能继续，只明确哪些约束未检查。左侧保留章节导航/当前章节入口，富文本/段落格式与发布入口紧凑放置，不挤占正文。

按段续写、人物反应、只润色三种目标分开。创意比较默认不是事实检查。采用前查看精确差异、范围外保留项与新增假设；采用只保存新工作稿，不自动发布。

S07 的未保存选区属于目标能力，须在临时快照包完成后开放；此前执行按钮必须要求保存，不能拿 UI 新偏移去读取旧版本。

### 5.3 故事与信息推进：S11–S12、S45

上位总纲、剧情线、篇章与场景连贯展示，但不重复要求作者维护每一层。调整规划不等于实际发生。当前已采用剧本、人物反应、不得发生事项与写作入口在同一个场景工作区。

伏笔与揭示归入信息推进，不各自成为孤立顶级工具。自然产生的开放问题与明确作者计划分开；系统可以提醒潜在机会，但不把每个道具变成待回收伏笔。

### 5.4 世界资料：S13–S15、S19、S43–S44

资料库默认人物、地点、物品和规则等可理解主题。正式资料、派生理解和开放问题保持明显身份。对象详情同时提供摘要、当前版本、历史变化、证据和相关场景，不分散到多个相互不承接的编辑器。

同名对象去重先比较身份依据再准备合并；观察不得因去重被丢弃。高级认知和方法视图只在需要时出现，作者日常不必管理认知 schema、方法版本或调度状态。

### 5.5 检查与决定：S05、S16–S17、S33、S40

待决定中心按真正问题而不是模块来源分组。一项空间矛盾被写作、世界和地图同时发现时，关联为同一议题，仍保留各自检查范围；不能简单按文字相似就合并不同问题。

严重问题、创意机会、历史检查分别呈现。处理某条问题后返回原任务锚点。409 冲突使用左右对照保留双方，优先提供另存/手动合并，不以刷新覆盖本地文本。

### 5.6 地图与媒体：S20–S26、S36、S39、S46

见 02。主画布、唯一详情宿主、回看带与搜索可相互切换，不同时弹出地图设置、助手、对象编辑三个面板。读者/人物视角尚未支持时显示明确能力边界；不可把作者视图删掉几个字段冒充安全视图。

### 5.7 助手、任务与模型：S27–S29、S35、S42、S47

助手默认理解当前任务，但当前焦点不授予全书读取权。任务页统一显示执行、部分完成、费用与恢复，实际领域回执仍是权威。预算到限不会让已保存正文不可用；恢复继续累计原已耗预算。

模型连接在账户下配置，项目只提供非 secret 工作流偏好。已验证的连接不等于全部高级能力都有质量保障；多模型身份以真实配置而非 Agent 名称为准。命令面板区分导航（只读）与需要确认的付费/写入动作。

### 5.8 RP、版本与生命周期：S30–S32、S41、S48

RP 入口使用私人故事语言，选中分支、原作截止点、回顾与自然语言行动是主线；私人故事不写回原作。作者项目导出与 RP 分支导出分别核对来源；未选中的兄弟分支不进入后续故事。

项目归档和永久删除是不同动作，不能共用“危险删除”确认逻辑。永久删除清单覆盖正文、派生理解、索引、地图与媒体，提供先导出路径。前端不能声称删除已完成直到实际删除工作流有结果。

## 6. 数据装配与状态组织

`TaskWorkspaceContext` 可包含 novel/owner、draft/scene refs、selection/cursor、intent、saved revision、editor_state、client epoch、scope ref、active operation。存储分层：授权与持久任务在后端；跨组件 feed 在 account/novel store；标签页焦点在 tab-local；未保存稿有受控恢复存储。

编译服务器按场景返回最小充分 `ExperienceView`；首次加载不串行等待所有模块。每个分区有独立 loading/error/coverage，不用一个全屏 spinner 掩盖哪个范围失败。lazy details 不得在授权失效后复用旧缓存。

每个写入入口只调用领域命令，不在 Vue 页面重新实现采用、费用或状态转移。UI 读取 `ChangeReceipt` 来更新当前视图、失效标记和长任务，而不是通过广播“所有页面刷新”使项目进入抖动。

## 7. 自适应与操作稳定性

宽桌面：正文 + 单伙伴列；中等宽度：伙伴变侧抽屉；手机：单主内容 + 底部 sheet。使用独立移动稿而不是等比缩小桌面。具体断点在真实组件重构后按内容测量决定，不能把 HiFi 的固定尺寸当成业务硬边界。

地图和差异页需要更大操作面积，默认独立任务态。按钮可点击目标建议至少 44px；正文支持阅读宽度、字体和行距偏好。不能为了给更多信息而把正文缩成窄缝或让滚动被嵌套面板夺走。

智能排序具有 hysteresis：新卡只有明显更相关或更高风险时才替换主卡；被用户固定、展开或选中时保持位置。危险来源变化另以状态提示处理，不靠随机移动卡片。

## 7. 三类门禁分别报告

工程门禁：来源一致、数据库并发、幂等、权限、恢复、API 等价、前端状态、删除清理。

模型质量门禁：原子命题正确性、引用语义、未知保留、错误改写、创意有效差异、同预算对照。

用户门禁：首次任务完成、能否理解当前状态、采用前能否说清影响、建议是否打扰、能否找回来源和本地修改。样本、角色、设备、模型、作品与预算必须注明。

任何一个门禁通过都不能替代另外两个。百分比目标、延迟目标和帧率目标均在基线测量后冻结；当前设计图上的任何数字都不作为测量结果。

## 8. 开发 Agent 的协作分包

一个包一个明确产物与验收，不按目录让多个 Agent 同时改同一事实规则。先做契约和消费者清单，再给各执行成员互不冲突的实现范围。接口变更必须同步所有真实调用者；合并前由独立验证任务从端到端输入检查，而非只读实施者总结。

建议实施顺序：E00/I01/I02/R00/U00 先建立基线 → E01–04/C01–02/V01–05/U01–03 并行 → I03 纵切 → E05–08 主链替代 → A/R/MI/C 高级能力按实测推进。

每次提交记录：影响契约、来源/状态、修改路径、真实运行测试、未覆盖项、是否需要迁移、回退方案。没有运行命令就写未运行，不引用旧绿灯或其他分支结果。
