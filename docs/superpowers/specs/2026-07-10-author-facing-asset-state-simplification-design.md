# 作者可见资产状态简化设计

**日期：** 2026-07-10
**状态：** 设计方案，尚未实施
**范围：** world、writing、outline、imports、context、RAG 与 world/map 的作者可见状态和操作语义

## 1. 背景

当前产品同时使用了 `draft`、`candidate`、`proposal`、`pending`、`canonical`、
`published`、`confirmed`、`needs_review`、`conflicted` 等状态或近似概念。作者界面又将
它们翻译为“草稿”“候选”“待确认”“待处理”“正史”“已确认”“已发布”等文案。

这些词来自不同模块的内部实现，但被并列暴露后，作者需要先理解系统的数据模型，才能判断：

- 这项内容现在是否会参与后续创作；
- 是否仍需要自己处理；
- 点击“确认”“采用”“发布”或“提升为正史”分别会发生什么；
- “候选草稿”和普通草稿有什么差别；
- “需复核”是生命周期状态、风险提示，还是另一种确认流程。

当前代码中已经存在可合并的重复语义。例如 world 的 CoreEntity 同时允许 `draft` 和
`candidate` 通过同一条 promote 路径进入 `canonical`，前端对二者也提供相同的提升与合并
动作。这说明二者的主要差异其实是来源和生成方式，不值得继续占用两个作者可见状态。

本设计的目标不是删除 AI 输出的确认边界，而是缩小作者必须理解的状态接口，把模块内部的
技术状态隐藏在各模块内部。

## 2. 设计结论

作者界面只保留一个通用中间态：**待处理**。

| 作者可见概念 | 含义 | 典型操作 |
|---|---|---|
| 工作稿 | 作者正在编辑、尚未发布的内容，只用于正文、Scene 等确有编辑生命周期的创作内容 | 编辑、保存、发布 |
| 待处理 | 尚未采用的 AI 建议或需要作者裁决的变化 | 采用、编辑后采用、合并、设为别名、忽略 |
| 已采用 / 已发布 | 已进入当前有效世界设定或正式正文 | 编辑、回滚、查看来源 |
| 历史 | 已忽略、已合并、已回滚或已废弃的记录 | 查看、恢复（适用时） |

其中：

- 结构化资产使用“已采用”；
- 正文使用“已发布”；
- `candidate`、`proposal`、“候选”和“待确认”统一归入“待处理”；
- “建议”是待处理项的类型，不是另一种状态；
- `conflicted`、低置信度、POV 泄漏和 `needs_review` 是注意原因，不是并列生命周期；
- `ignored`、`merged`、`deprecated`、`rolled_back` 默认进入历史，不占据主工作区筛选项。

## 3. 作者心智模型

### 3.1 普通 AI 建议

```text
AI 生成建议
    ↓
待处理
    ├── 采用 ─────────→ 当前有效内容
    ├── 编辑后采用 ───→ 当前有效内容
    ├── 合并 / 设为别名 → 当前有效内容
    └── 忽略 ─────────→ 历史
```

作者只需要回答“是否把这项变化纳入作品”，不需要判断它是 candidate、proposal 还是 draft。

### 3.2 人工创建和编辑

人工操作本身已经表达作者意图：

- 人工创建世界对象、关系或别名时，保存后直接成为已采用内容；
- 人工编辑已采用内容时，保存后继续保持已采用；
- 正文和 Scene 等需要持续编辑的内容保存为工作稿，直到执行发布或明确采用动作；
- 不再要求作者把自己刚创建的世界对象再次“提升为正史”。

### 3.3 明确启动的自动流水线

深度导入等自动流水线可在启动时进行一次批量授权。授权后：

- 符合确定性领域规则的内容可以直接成为派生数据或已采用内容；
- 必须保存来源、workflow 标识、可编辑标记和可回滚信息；
- 冲突、无法消歧或低置信内容进入统一待处理入口；
- 流水线完成页展示“自动采用数量 / 待处理数量 / 忽略数量”；
- 提供按 workflow 查看和整批回滚的能力。

这将逐条确认收敛为一次授权加异常处理，同时保持 AI 不受控写入正史的安全边界。

## 4. 术语收敛

### 4.1 作者界面术语

| 现有词汇 | 新处理 | 说明 |
|---|---|---|
| 草稿 | 仅保留“工作稿” | 只描述正文、Scene 等编辑生命周期，不描述可信度 |
| 候选 | 改为“待处理” | 不再作为作者可见状态或对象名称 |
| 待确认 | 改为“待处理” | 待处理项不一定被确认，也可能合并、忽略或设为别名 |
| proposal / 建议 | 保留为对象类型 | 例如“创设建议”“修复建议”，不作为状态 |
| 正史 | 界面优先显示“已采用” | `canonical` 可继续作为内部术语 |
| 已确认 | 按领域显示“已采用” | 避免与确认记录、复核记录混淆 |
| 已发布 | 正文专用 | 表示当前发布版本 |
| 需复核 | 改为注意标签 | 必须同时给出原因，不再作为主状态 |
| 冲突 | 改为待处理原因 | 例如“名称冲突”“事实冲突”“来源冲突” |

### 4.2 保留的内部术语

以下概念表达真实实现差异，可以保留在模块内部、调试界面、接口兼容层和审计记录中：

- `MapObservation` 与 `MapFact`；
- `canonical` 与 `working` 上下文模式；
- `pending / running / succeeded / failed` 任务执行状态；
- deep import 内部的 `SceneCandidate`；
- `ignored / merged / deprecated / rolled_back` 历史状态；
- confirmation 和 snapshot 的审计状态。

本次简化只处理**持久化创作资产的作者可见状态**，不重命名任务队列、算法中间结果或审计记录。

## 5. 状态与属性分离

当前复杂度的一部分来自把多个维度都塞入 `status`。新设计将它们分开：

| 维度 | 示例 | 是否是作者主状态 |
|---|---|---|
| 生命周期 | review / active / archived | 是 |
| 来源 | manual / deep_import / ai_generated | 否，作为来源信息 |
| 注意原因 | conflicted / low_confidence / pov_risk / needs_disambiguation | 否，作为标签 |
| 处理建议 | create / merge / alias / ignore / temporary | 否，作为推荐动作 |
| 内容成熟度 | working / published | 仅正文等内容资产使用 |
| 运行状态 | pending / running / failed | 否，仅任务与流水线使用 |

推荐的作者展示模型为：

```text
display_state: active | review | archived
source: manual | deep_import | ai_generated | ...
attention_reasons: string[]
suggested_action: create | merge | alias | ignore | temporary | ...
```

`display_state` 是各领域模块根据内部数据派生的展示语义，不应立即替代所有现有数据库状态或
wire 字段。

## 6. 各模块落地方式

### 6.1 World：世界对象、关系和别名

这是本轮简化的首要模块。

#### 目标行为

- 人工创建的对象、关系和别名保存后直接已采用；
- AI 或导入产生且尚未授权采用的变化统一进入待处理；
- `draft` 和 `candidate` 不再作为两个作者可见状态；
- 待处理项展示来源、证据、注意原因和建议动作；
- 主操作统一为“采用”“编辑后采用”“合并”“设为别名”“忽略”；
- `canonical`、已复核等重复徽章默认隐藏，只在详情和审计中展示。

#### 数据归属方向

长期应优先让 `creation_suggestion_queue` 承载尚未采用的创设建议。确认建议时，再调用 world
拥有的领域操作创建或修改 CoreEntity、EntityRelation 或内联 Alias。

不建议继续把未采用的建议伪装成不完整 CoreEntity，再依赖 CoreEntity.status 区分它是否为
事实。建议队列应成为“待处理变化”的深模块：调用方只提交建议和执行裁决，不需要理解各类
资产的中间状态。

### 6.2 Writing：正文和 AI 写作建议

正文保留自身必要的版本生命周期：

```text
工作稿 → 已发布
```

- 手工正文和已经采用的 AI 文本都进入普通工作稿；
- AI 生成结果在采用前显示为建议预览，不称为“候选草稿”；
- 点击“采用到工作稿”后，它成为普通工作稿内容；
- POV 泄漏、解析失败或事实风险显示为警告标签；
- 高风险建议需要显式采用，但不引入新的正文状态；
- `candidate`、`canonical` 不再作为正文的常规作者可见状态；
- `deprecated` 仅存在于版本历史或恢复路径。

作者界面应使用“已保存”“工作稿”“已发布”等写作语言，不混用“正史”。

### 6.3 Outline 与 Scene

- 人工创建或编辑的结构资产保存为普通工作内容；
- AI 合并、拆分、补全结果先展示影响预览；
- 作者确认保存后，创建或更新普通 Scene；
- 未保存的 AI 结果是临时建议，不需要持久化为第二种 Scene 候选状态；
- deep import 内部 SceneCandidate 继续作为算法中间结构，但不直接暴露给作者；
- `candidate` 只在兼容期读取，不再作为新 Scene 的默认写入状态。

Scene 的 `draft` 是否继续保留，应由其实际编辑和发布语义决定；如果没有独立发布动作，界面
无需持续显示“草稿”徽章。

### 6.4 Imports：深度导入

深度导入采用“批量授权 + 异常待处理”：

1. 启动前说明将自动采用哪些资产，以及哪些条件会转入待处理；
2. 用户一次确认后启动流水线；
3. 规则明确且可回滚的结果自动落入目标领域；
4. 冲突、低置信、别名歧义和合并歧义进入待处理；
5. 完成页只展示三类汇总：已采用、待处理、未采用；
6. 所有自动写入保留 source、workflow_id、scene/chapter 证据和回滚信息。

imports 不拥有最终资产状态。它只能通过目标模块的稳定 interface 提交建议或执行已授权的
领域操作。

### 6.5 World/Map：地图观察与地图事实

地图内部保留 Observation 与 Fact 两层：

- MapObservation 是带证据的观察；
- MapFact 是经领域规则或用户确认后产生的时间化事实；
- Observation 的 `candidate / conflicted` 等 review_state 可继续用于内部筛选；
- 作者界面统一把尚未转化为 Fact 的可操作 Observation 显示为待处理；
- 确认后显示已采用，不需要同时展示“候选已确认”“事实 confirmed”等多层文案；
- 冲突、低置信和空间未解析作为注意原因展示。

不要为了统一文案而删除 Observation/Fact 的数据差异。这里应统一界面，不应压平领域模型。

### 6.6 Context 与 RAG

- `canonical / working` 继续作为内容选择模式；
- 作者界面分别显示“已发布内容 / 工作稿内容”；
- “是否包含待处理建议”作为高级开关，默认关闭；
- 使用待处理建议编译上下文时，结果标记“包含未采用内容”；
- context confirmation 和 snapshot 是审计记录，不进入作者的资产状态筛选；
- RAG 只负责索引和检索对应内容模式，不发明新的确认状态。

## 7. 信息架构

### 7.1 统一待处理入口

作者需要一个统一入口理解“现在有哪些内容需要我决定”，但后端不必建立跨模块通用状态表。

统一入口可以聚合：

- 世界对象建议；
- 关系与别名建议；
- 地图观察；
- Scene 合并、拆分或补全建议；
- 写作冲突修复建议；
- 其他确实会修改结构化资产的建议。

每项至少展示：

- 建议改变什么；
- 来源与证据；
- 为什么需要处理；
- 采用后的影响；
- 推荐动作；
- 可执行动作。

统一入口只聚合模块提供的稳定摘要和命令，不直接跨模块修改内部模型。

### 7.2 主工作区降噪

- 普通已采用对象不持续展示“正史”“已确认”“已复核”三个近义徽章；
- 只有存在异常或待处理事项时显示状态提示；
- 来源和复核记录放入详情层；
- 历史状态默认隐藏，通过“历史”筛选访问；
- 数量提示统一使用“待处理 N”，不混用“候选 N”“待确认 N”。

## 8. 稳定接口与 contract 风险

本设计会影响公共响应、前端 wire shape 和跨模块消费方式，因此实施时必须分阶段兼容。

### 8.1 第一阶段不破坏现有 contract

- 保留现有 `status`、`review_state`、`fact_status` 等字段；
- 在各模块现有 facade/contract 中按需增加派生展示字段；
- 前端优先使用派生展示语义，旧字段保留兼容；
- 不创建只转发参数的全局 StatusFacade；
- 不允许前端自行散落多套状态映射，应由领域模块提供语义或由一个明确的前端展示映射集中处理。

### 8.2 第二阶段收敛写入路径

- 新的 AI 世界资产写入统一走 suggestion queue；
- 新的人工世界资产直接走已采用领域命令；
- 新的正文 AI 结果先作为建议，采用后才进入普通工作稿；
- 新的 Scene AI 结果先预览，确认后写普通 Scene；
- imports 只调用目标模块公开 interface。

### 8.3 第三阶段清理历史状态

项目处于 demo 阶段，可以在所有读写路径和测试完成迁移后重建开发数据库：

- 清理 CoreEntity 中不再需要的 `draft / candidate` 持久化语义；
- 收敛 WritingDraft 的常规状态集合；
- 移除前端旧文案和旧筛选；
- 保留 MapObservation/MapFact、任务状态和审计状态；
- 同步 ORM、Pydantic schema、Alembic、模块 README、CONTEXT 和测试。

## 9. 实施顺序

### Phase 1：文案和展示收敛

- 将作者界面的“候选”“待确认”统一为“待处理”；
- 将结构化资产的“正史”统一为“已采用”；
- 正文只显示工作稿、已保存和已发布；
- 将冲突、低置信、需复核改成原因标签；
- 默认隐藏历史状态；
- 集中状态展示映射，删除页面间不一致翻译。

此阶段不改变 API、schema 或数据库。

### Phase 2：统一待处理体验

- 建立聚合待处理入口或在现有入口提供一致的待处理视图；
- 统一采用、编辑后采用、合并、设为别名和忽略动作；
- 展示来源、证据、影响范围和注意原因；
- 提供批量操作，但合并目标和高风险变化仍需逐项确认。

### Phase 3：写入路径收敛

- world 创设建议统一进入 suggestion queue；
- writing、outline 的 AI 结果采用“建议预览 → 工作内容”；
- deep import 切换为批量授权和异常待处理；
- 各领域模块拥有自己的采用命令和回滚行为。

### Phase 4：内部状态清理

- 删除已无调用方的重复状态和分支；
- 重建 demo 数据库；
- 更新权威文档和回归测试；
- 对旧 wire contract 完成弃用和移除。

## 10. 验收标准

### 10.1 作者体验

- 作者界面不再把“候选”和“待确认”作为两种状态；
- 任何需要作者决定的资产都能在“待处理”语义下找到；
- 每个待处理项都能回答“改什么、来自哪里、为什么需要处理、采用后影响什么”；
- 普通对象列表不再同时展示正史、已确认、已复核等重复徽章；
- AI 正文不再称为“候选草稿”；采用后就是普通工作稿；
- 人工创建的世界对象不需要再次提升为正史；
- 历史项不会干扰主工作区，但可以追溯。

### 10.2 数据与安全

- 默认 AI 输出仍不会未经确认直接污染已采用资产；
- 用户明确授权的自动流水线保留来源、可编辑和可回滚信息；
- 所有写入继续经过 Pydantic/schema 校验；
- 所有查询和命令保持 novel_id 隔离；
- 结构化资产采用和危险合并继续保留必要确认；
- MapObservation 与 MapFact 的证据/事实分层未被破坏。

### 10.3 工程质量

- 外部 contract 在兼容阶段保持稳定；
- 跨模块调用只通过现有 contracts、facade 或 DI port；
- 不新增浅层全局状态模块；
- 状态展示映射不再散落于多个前端页面；
- 受影响的 world、writing、outline、imports、context、RAG 和 map 测试通过；
- 前端状态、待处理入口和批量操作测试通过；
- 文档、ORM、schema、migration 与实现一致。

## 11. 非目标

- 不把所有模块改造成共享数据库状态机；
- 不删除 AI 输出确认、安全检查或来源审计；
- 不把任务队列的 `pending/running/failed` 改成创作资产状态；
- 不删除地图 Observation/Fact 分层；
- 不在本设计阶段引入新基础设施、前端框架或依赖；
- 不在尚未实施前修改 CONTEXT 或模块 README，把本方案误写成当前事实；
- 不为本方案单独创建 ADR。若实施中需要改变稳定 interface、跨模块所有权或不可逆数据模型，
  再根据具体决策判断是否需要 ADR。
