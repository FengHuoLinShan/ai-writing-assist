## 二、安全审计

### 🔴 Critical（3 项）

#### S-01：AI 生成内容经 `innerHTML` 渲染存在 XSS 风险

| 字段 | 内容 |
|------|------|
| **文件** | `frontend-console/views/generateView.js:741, 1342` |
| **类型** | XSS / 注入 |
| **描述** | AI 输出（`this._lastEntity`、`err.message`）通过 `innerHTML` 直接注入 DOM。`_renderEntityResult()` 虽在文本位置使用了 `esc()`，但模板字面量模式脆弱 — 小型重构即可引入未转义路径。AI 内容本质上是攻击者可控制的（通过 prompt 注入）。 |
| **建议** | 对所有 AI 来源的内容改用 `createElement` + `textContent` DOM API 渲染。全局审计所有 `innerHTML =` 赋值点。 |

#### S-02：CSRF 保护缺失于全部数据变更端点

| 字段 | 内容 |
|------|------|
| **文件** | `backend/app/core/csrf.py:1-11`；`settings/api.py:32,54,96`（已覆盖）；其余全部 API 模块（未覆盖） |
| **类型** | CSRF |
| **描述** | `require_xhr_request` 中间件只注册在 settings PUT、project LLM update 等少数端点。`POST /api/projects`、`DELETE /api/projects/{id}`、`POST /api/imports/upload`、`POST /api/imports/deep` 及全部 writing/outline/world 变更操作均无 CSRF 保护。基于 `X-Requested-With` 的校验本身已偏弱。 |
| **建议** | 对全部 state-changing 端点统一应用 CSRF 中间件；或实现 double-submit cookie / SameSite cookie 模式。 |

#### S-03：API 密钥以明文存储于数据库

| 字段 | 内容 |
|------|------|
| **文件** | `modules/project/services.py:173` |
| **类型** | 密钥管理 |
| **描述** | 用户配置的 LLM API Key 写入 `project.settings` JSONB 字段，未做应用层加密。数据库只读权限即可获取所有用户密钥。 |
| **建议** | 使用 `pgcrypto` 或 Python 级加密（Fernet），密钥衍生自服务端机密。 |

### 🟡 Medium（5 项）

#### S-04：CORS 配置中 `allow_credentials=True` 与通配符 `*` 共存

| 字段 | 内容 |
|------|------|
| **文件** | `backend/app/core/config.py:199-203`；`backend/app/main.py:222-240` |

| **建议** | `allow_credentials=True` 时过滤掉 `*`，或拒绝混合配置。 |

#### S-05：novel_id 隔离在数据层未系统验证

| 字段 | 内容 |
|------|------|
| **文件** | 所有 `repositories.py`；`core/api_params.py` |
| **类型** | 数据隔离 |
| **描述** | API 层通过路由参数验证 UUID 格式，但 9 个模块的 100+ 个 repository 方法中，未系统验证每个方法是否都包含 `novel_id` 过滤。`chaos/map_chaos.py` 测试表明这曾是已知风险。 |
| **建议** | 增加自动化测试套件，逐端点验证跨 novel_id 访问隔离；或引入数据库级行级安全策略。 |

#### S-06：缺失用户认证机制

|------|------|
