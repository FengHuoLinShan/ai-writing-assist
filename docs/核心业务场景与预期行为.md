# 核心业务场景与预期行为描述

> 本文档基于代码库实际状态与架构讨论产出，面向 E2E 测试编写和 AI 辅助 Debug。
> 采用 Given-When-Then (BDD) 格式，区分正常流与异常/边界流。
>
> 用户画像与产品体验基线见
> [`product/user-personas.md`](product/user-personas.md)。新增或修改场景时必须标记目标画像，
> 并同时验证用户是否愿意使用、前端是否自然舒服；“接口成功”不等于用户场景完成。

---

## 场景编写与验收准则

每个新增用户场景除数据与状态契约外，还应覆盖适用的：

- 目标画像（长期创作的专业/业余作家、深度读者，或两者）与真实任务；
- 首次价值：用户不理解技术或写作术语时，能否知道从哪里开始并获得有意义结果；
- 高频路径：当前状态、主操作和下一步是否清晰，是否避免 raw ID、JSON 和内部枚举；
- 舒适度：加载、空态、失败/冲突、保存反馈、离开恢复、误操作保护与窄屏；
- 控制感：AI 来源、影响范围、采用/撤销和原作事实/用户分支边界是否可理解；
- 验证信号：任务完成、首次价值时间、重复使用、采用/撤销、放弃点或定性反馈。

## 场景 1：项目创建与管理

### 【业务场景名称】

用户创建、选择、编辑、删除小说项目。项目是系统的根聚合，所有其他模块通过 `novel_id` 关联。

### 【用户视角链路】

#### 正常流：创建项目

**Given** 用户在首页
**When** 用户点击"新建项目"，填写标题（必填），可选填写题材、风格基调、目标规模
**Then**
- 项目创建成功，`language` 默认 `"zh"`，`default_reveal_policy` 默认 `"author_safe"`
- 前端跳转到该项目的工作台（写作视图），URL 变为 `/workbench/:projectId/writing`
- `projects` 表新增一行，`id` 为 UUID，`created_at` 记录创建时间

#### 正常流：列表选择

**Given** 用户已在首页
**When** 页面加载
**Then**
- 展示所有已创建项目列表，每个项目显示标题、题材标签、创建时间
- 用户点击任一项目 → 进入工作台
- 分页参数 `skip` / `limit` 控制列表数量，默认每页 20 条

#### 正常流：编辑项目

**Given** 用户在工作台
**When** 用户点击项目名称进入编辑模式，修改标题或题材后保存
**Then**
- `projects` 表对应行 `title` / `genre` / `tone` / `target_length` 更新
- `updated_at` 自动更新
- 前端项目名称面包屑同步刷新

#### 异常流：删除项目（回收站二次确认）

**Given** 用户选择删除项目
**When** 用户点击"删除项目"
**Then**
- 前端弹出确认对话框："确定要删除项目《XXX》吗？删除后可在回收站中恢复。"
- 用户确认 → 项目标记为软删除（移至回收站），数据不动
- 回收站中再次确认删除 → 级联删除项目下所有关联数据（world / outline / writing / memory / rag 等所有 `novel_id` 关联行），不可恢复
- 404：项目不存在或已删除，返回错误

#### 边界流：空标题

**Given** 用户创建项目
**When** 标题为空或纯空格
**Then**
- 后端返回 422 Validation Error
- 前端显示"请输入项目标题"

### 【数据与状态契约】

| 层级 | 变更 |
|------|------|
| 前端 UI | 项目列表刷新；面包屑更新；确认对话框 |
| `projects` 表 | INSERT / UPDATE / 软删除标记 |
| 关联表 | 回收站二次确认后级联 DELETE（world / outline / writing / memory / rag 等所有模块数据） |

## 场景 2：文件上传与章节导入

### 【业务场景名称】

用户上传本地小说文件（txt/epub/html/mobi/azw3），系统自动解析分章，存入正文章节库。

### 【用户视角链路】

#### 正常流：上传并解析

**Given** 用户在写作工作台
**When** 用户点击"导入小说"，选择本地文件（如 `novel.txt`，150 章，总大小 8MB）
**Then**
- 前端显示上传进度条
- 后端校验文件格式（白名单：`.txt .epub .html .htm .mobi .azw3`）和大小（≤50MB）
- 文件名做 `os.path.basename` 处理，防止路径穿越
- 选择合适的解析器（txt→chardet 编码检测 + 章节正则分割；epub→ebooklib；html→beautifulsoup4）
- 解析结果逐章写入 `writing_drafts` 表，每章 `version_number = 1`
- `import_records` 表新增一条记录，记录 `file_name / file_type / file_size / total_chapters / imported_chapters / status`
- 前端显示导入结果：共解析 N 章，成功 M 章
- 导入完成后提示用户："已导入 M 章，是否启动深度导入？"

#### 异常流：格式不支持

**Given** 用户选择文件
**When** 文件扩展名不在白名单（如 `.pdf`）
**Then**
- 后端返回 400："不支持的文件格式，仅支持 txt/epub/html/htm/mobi/azw3"
- 前端显示错误提示，文件不进入解析流程

#### 异常流：文件过大

**Given** 用户选择文件
**When** 文件超过 50MB
**Then**
- 后端返回 413："文件大小超过限制（最大 50MB）"
- 前端显示错误提示

#### 异常流：编码检测失败

**Given** 用户上传 txt 文件
**When** chardet 无法确定编码，或解析出空内容
**Then**
- `import_records.status` 标记为 `failed`，`error_message` 记录具体错误
- 前端显示"导入失败：无法识别文件编码，请尝试另存为 UTF-8"

#### 边界流：空文件

**Given** 用户上传文件
**When** 文件内容为空或解析后无有效章节
**Then**
- `import_records.status` 标记为 `failed`，错误信息"文件中未检测到有效章节"
- 不创建任何 `writing_drafts` 行

#### 边界流：并发限制

**Given** 导入 150 章
**When** 每章写入 `writing_drafts` 并触发发布任务
**Then**
- 发布任务统一执行 RAG 索引和 memory 快照，避免重复索引任务

### 【数据与状态契约】

| 层级 | 变更 |
|------|------|
| 前端 UI | 上传进度条；导入结果提示（成功 M 章）；错误信息 |
| `import_records` 表 | INSERT 一行，status=`done`/`failed` |
| `writing_drafts` 表 | 每章 INSERT 一行，version_number=1，status=`draft` |
| `async_tasks` 表 | 每章自动入队 `publish_chapter` 任务；该任务内部执行 RAG 索引 |

## 场景 3：深度导入流水线（三遍 Workflow）

### 【业务场景名称】

用户在启动时一次性授权深度导入，系统自动执行三遍流水线：Scene 切分 → Entity 增量提取 → 剧情结构分析。运行中不逐项打断；规则明确且可回滚的结果自动采用，异常结果进入待处理，完成后用户可修改或整批回滚本 workflow 的资产。

### 【用户视角链路】

#### 正常流：启动深度导入

**Given** 用户已完成文件导入（场景 2），章节正文已入库
**When** 用户点击"启动深度导入"，选择章节范围（默认 1 ~ 最后一章），阅读自动采用/待处理规则并明确授权
**Then**
- 前端提交 `POST /api/imports/deep`，包含 `adoption_policy="user_authorized_pipeline"` 和 `authorization_confirmed=true`，返回 `workflow_id`
- `async_tasks.meta/result` 持久化授权策略、章节范围、stage、授权时间和初始资产汇总；缺少或拒绝授权时接口返回 422，不创建任务
- 前端显示三阶段进度条（Phase 1: 40% / Phase 2: 40% / Phase 3: 20%）
- `async_tasks` 表创建一条记录，type = `deep_import`，`status = "running"`，`phase = "scene_segmentation"`
- Workflow 自动推进，用户可关闭浏览器，后台继续执行

#### 正常流：Phase 1 — Scene 候选、补强与融合

**Given** workflow 进入 Phase 1
**When** 系统执行 Phase 0 / 1a / 1b，并在高质量模式执行 Phase 1c
**Then**
- Phase 0 不调用 LLM；按正文字符预算规划 owned range、右侧 overlap、并发窗口和 token 上限
- 每个窗口冻结前一章最多 2000 字尾部、当前范围的 active working Scene/篇章纲/剧情线，
  以及相关 `author_safe` canonical 人物 Top-6、非人物世界对象 Top-16；选择和内容指纹进入阶段 artifact
- Phase 1a 主切分按叙事与因果连续性识别 Scene，不按章节或数量切分，并逐字返回起止 anchors、
  window edges、边界依据和置信度；无真实冲突时允许明确标记 `not_applicable` 并保留空 conflict
- 所有窗口完成后统一协调相邻边界；无法定位的 Scene 进入纯 anchor 修复，允许单侧修复或 unresolved
- 连续覆盖缺口一次性恢复为 `extend_left / new_scene / extend_right` segments；缺口可全部并入邻居而零新增 Scene，
  也可恢复任意数量的真实 Scene。整组必须通过精确来源与完整覆盖校验，否则保留逐章精确 fallback
- Phase 1b 按全部 `scene_chunks` 重验 draft/hash/offset 并消费完整精确 Scene 正文，不发送整章、不裁剪输入；同时复用冻结的相关剧情线/篇章纲/Scene、人物 Top-6 和非人物对象 Top-16
- Phase 1b 提炼 emotional beat、must/must-not、叙事标签与自由叙事功能，但允许真实不适用字段为空；不确定性和来源状态由本地映射为复核，不生成占位语义，也不修改 Phase 1a 锁定字段
- 高质量模式的 Phase 1c 审核相邻候选；高置信、精确来源结果自动融合，其余生成待处理建议
- scene commit 阶段才写入 `scenes` 表，并保留 provenance、workflow、needs_review / degraded 元数据
- 恢复产物、被扩展邻居、低置信或无法消歧结果进入复核；完整精确覆盖后可继续流水线
- Phase 1 进度 = 40% × (已完成子任务数 / 总子任务数)

#### 正常流：Phase 2 — Entity 增量提取（并发分析、顺序持久化）

**Given** Phase 1 全部完成，`scenes` 表已有数据
**When** Workflow 推进到 Phase 2
**Then**
- 单个 `entity_extraction` 任务入队执行
- 以 Scene 为单位并发分析，完成后按 `scene_index` 顺序持久化：
  1. `ImportContextActivation v2` 装配当前 Scene 完整精确正文、锁定 Scene 卡、相关大纲、身份候选和前序证据；不加载后续 Scene
  2. Phase 2a 调用 `scene_entity_extraction.md`，所有数据以 fenced 不可信 JSON 输入；provider 调用前关闭数据库事务
  3. Phase 2a 输出 `entities[]` + `delta_events[]` + 可选的四类
     `map_observation_proposals[]` + `uncertain_items[]`；关系与新别名不属于此契约
  4. 服务端验证 `entity-xxx` 身份引用、对象类型与当前 Scene 逐字证据，再执行名称 / embedding 去重；模型不决定持久化动作或审核状态
  5. 新实体写入 `core_entities`，`status = "candidate"`，`content_json._meta.auto_ingested = true`
  6. Delta 变更写入 `delta_log`（Scene 内坍缩后）
  7. Phase 2b 调用 `alias_relation_extraction.md`，基于 canonical / draft / candidate 工作对象索引提取 `aliases[]` + `relations[]`
  8. 别名以内联待复核元数据写入目标 `core_entities.content_json.aliases`；关系写入 `entity_relations(status="candidate")`
  9. 地图 proposal 以稳定 source item、Scene 输入指纹、逐字证据和授权来源写入地图收件箱；
     重试复用，来源 payload 冲突时停止写入，且不自动形成 Fact
  10. 更新 Memory 累积上下文
  11. 触发 Memory 增量快照 `capture_snapshot(scene_index)`
- Phase 2 进度 = 40% × (已处理 Scene 数 / 总 Scene 数)
- 单 Scene LLM 调用失败 → 重试 3 次 → 仍失败则跳过该 Scene，记录 warning

#### 正常流：Phase 3 — 结构分析（单次）

**Given** Phase 2 全部完成
**When** Workflow 推进到 Phase 3
**Then**
- 单个 `structure_analysis` 任务入队执行
- 输入：全量 Scene 摘要 + 坍缩后 Delta 变更流（仅非 Valley/Transition Scene）+ 实体索引
- LLM 输出：`plot_threads[]` / `outline_arcs[]` / `foreshadowing_plans[]` / `reveal_plans[]`
- 四类产物分别写入对应表
- Phase 3 完成 → workflow 标记 `status = "done"`
- 完成结果展示“已采用 / 待处理 / 未采用”总数和按 Scene、实体、关系、别名、结构分类的汇总
- 完成页根据当前项目只展示一个地图行动：已有 active 地图时“查看地图收件箱”；无地图但有
  已采用地点时“一键创建地图”；仅有候选地点时“先审核 N 个地点”。

#### 异常流：Phase 1 部分批次失败或 API 限流

**Given** Phase 1a 某窗口调用失败、返回空结果或无法精确覆盖
**When** 可控重试、anchor repair 与连续缺口恢复仍不能得到可原子物化的结果
**Then**
- Workflow 记录原始错误、attempt、耗时和是否 retry
- 对仍缺失的章节生成绑定当前 draft/hash 和完整 offset 的逐章 fallback，并标记 `needs_review`
- fallback 能补足全部章节覆盖时继续 Phase 1b/commit；覆盖仍不完整或结果为空时阻断任务，不进入 Phase 2

#### 异常流：用户关闭浏览器后重新打开

**Given** 深度导入正在后台执行
**When** 用户重新打开页面，进入该项目工作台
**Then**
- 前端自动查询当前 workflow 状态（`GET /api/tasks/{task_id}`）
- 显示当前 Phase 和进度条
- Phase 1：显示 "正在分析剧情结构... (Scene 切分: 15/30 批已完成)"
- Phase 2：显示 "正在提取世界对象... (第 12/38 个剧情段)"
- Phase 3：显示 "正在生成剧情线..."

#### 边界流：重复导入

**Given** 章节范围已有 Scene / Entity 数据
**When** 用户再次对相同章节范围启动深度导入
**Then**
- 系统只统计目标范围内带 `source=deep_import` 且有 workflow/auto_ingested 所有权标记的 Scene，以及带自动导入元数据的世界对象
- 检测到已有流水线资产 → 弹出覆盖警告；确认后只将替换意图写入任务，不在入队前改数据
- Scene commit 原子软废弃未编辑的 workflow-owned 工作稿；canonical、人工、user-edited 或无 ownership Scene 保持 active
- 新候选与受保护 Scene 重叠时进入持久替换审查；未采用前 Phase 2/3 继续使用旧 active Scene

#### 边界流：小规模导入

**Given** 用户只导入了 3 章
**When** 启动深度导入
**Then**
- 章数不足 5 章 1 批 → 直接作为 1 个批次处理（不做 Overlap）
- Phase 2 串行处理 1-2 个 Scene
- 流程不变

### 【数据与状态契约】

| 层级 | Phase 1 | Phase 2 | Phase 3 |
|------|---------|---------|---------|
| 前端 UI | 三阶段进度条 | 进度条更新 | workflow 完成提示 |
| `async_tasks` 表 | INSERT, type=`deep_import`, phase=`scene_segmentation` | phase=`entity_extraction` | phase=`structure_analysis`, status=`done` |
| `async_tasks` 表 | N 个子任务 INSERT | 1 个任务 INSERT | 1 个任务 INSERT |
| `async_tasks.meta/result` | 保存 authorization snapshot | 更新分项统计 | 输出 `asset_summary`（adopted/review/not_adopted） |
| `scenes` 表 | INSERT N 行 | — | — |
| `core_entities` 表 | — | INSERT 新实体, status=`candidate`, content_json._meta.auto_ingested=true | — |
| `characters` 表 | — | INSERT 新人物 | — |
| `entity_relations` 表 | — | INSERT 新关系 | — |
| `delta_log` 表 | — | INSERT 变更记录（Scene 内坍缩） | — |
| `memory_snapshots` 表 | — | 每个 Scene 完成时 INSERT | — |
| `plot_threads` 表 | — | — | INSERT 剧情线 |
| `outline_arcs` 表 | — | — | INSERT 篇章纲 |
| `foreshadowing_plans` 表 | — | — | INSERT 伏笔计划 |
| `reveal_plans` 表 | — | — | INSERT 揭示计划 |

## 场景 4：手工写作工作台

### 【业务场景名称】

用户在写作工作台中创作正文。左侧 Scene 树导航（未归类章节单独分组），中间编辑器，右侧 Scene 卡面板；编辑器内容按光标位置联动右侧 Scene 卡，保存后入库为正文版本。

### 【用户视角链路】

#### 正常流：进入工作台

**Given** 用户选择项目
**When** 进入工作台
**Then**
- URL 变为 `/workbench/:projectId/writing`
- 左侧导航栏显示核心创作环：📁写作 / 📋大纲 / 🌍世界（写作默认高亮）
- 左侧面板：Scene 树（一级节点）+ Chapter 折叠（二级节点），未关联 Scene 的章节进入"未归类"分组
  ```
  ├── Scene 1「初入江湖」(3章)
  │     ├── 第1章 穿越
  │     ├── 第2章 测试
  │     └── 第3章 启程
  ├── 未归类 (1章)
  │     └── 第5章 游离章
  ```
- 中间编辑器：加载上次编辑位置，或默认第一个有草稿的 Chapter
- 日目标、编辑器字体和首次进入时的专注模式使用当前项目的生效作者偏好（项目覆盖 → 全局默认 → 系统默认）
- 右侧面板：当前 Scene 卡（goal / core_conflict / emotional_beat / must_happen / must_not_happen / narrative_tag）
- Scene 卡数据来源于 outline 模块，写作工作台只读展示
- 用户可在右侧面板搜索角色/实体名 → 浮窗显示轻量详情（不跳转视图）

#### 正常流：撰写并保存正文

**Given** 用户在编辑器里写正文
**When** 触发自动暂存（或用户点击"暂存"）
**Then**
- 正文移除 Unicode 空白后有实质变化才调用后端；published/manual 首次修改创建 auto 版本，后续原地更新
- 标题或纯空白修改只进入 `localStorage` 备份，显示“仅本地修改”
- 自动保存请求期间继续输入时，旧响应只更新版本元数据；新输入保持在编辑器和本地备份中并随后继续暂存
- 前端 Toast 提示："已暂存"

**When** 用户点击“保存为新版本”
**Then**
- auto 工作版本转为 manual checkpoint，不额外增加版本号
- 没有实质变化时二次确认，确认后允许强制留版

**Given** 用户写完一版正文
**When** 用户点击"发布"
**Then**
- 当前 draft 原位提升为 published，不再额外生成下一版
- 自动入队 `publish_chapter` 后台任务：RAG 分块索引（含向量化），重试 3 次
- 前端 Toast 提示："已发布"，并展示 RAG 索引进度条
- 重复发布无实质变化的已发布版本时复用原版本，不重复入队
- auto 工作版本撤回到手动 checkpoint 内容后直接发布时，废弃 auto 版本并原位发布该手动版本

#### 正常流：放弃未发布更改

**When** 正文通过撤销回到基线，或用户确认“放弃未发布更改”
**Then**
- auto 工作版本可自动回退；manual checkpoint 必须由用户显式确认
- 当前未发布版本软废弃，编辑器返回 `base_draft_id`
- 废弃版本号不复用，版本历史不显示 deprecated 记录
- 如果当前 Chapter 未关联 Scene → 自动推断归属 Scene（根据 `scene_chunks` 反查），或追加到最近的 Scene

#### 正常流：创建新 Scene

**Given** 用户需要新建一个 Scene
**When** 用户切换到 outline 视图，点击"新建 Scene"
**Then**
- `scenes` 表新增一行，`scene_index` 按当前最大序号 +1，`source = "manual"`
- `narrative_tag` 默认为 `"draft"`（用户可后续修改）
- 返回写作视图后左侧 Scene 树出现新节点

> **剩余缺口**：在编辑器内通过"选中文字 → 创建新 Scene"一步到位的右键菜单尚未实现；当前需在大纲视图创建 Scene 后再关联章节。

#### 正常流：光标位置联动右侧 Scene 卡

**Given** 当前 Chapter 跨两个 Scene（如 `scene_chunks` 在 chapter 1 内分别占有 `[0,1500)` 与 `[1500,3000)`）
**When** 用户在编辑器内点击前半段 / 后半段
**Then**
- 光标 offset 通过 `selectionStart` 实时计算
- 右侧面板根据 offset 命中对应的 `scene_chunk`，显示 Scene A 或 Scene B 的 Scene 卡

#### 正常流：切换 Scene 导航

**Given** 用户在写作中
**When** 点击左侧 Scene 树中的另一个 Scene
**Then**
- 编辑器内容自动保存到 `viewStates`（前端暂存，不触发后端保存）
- 编辑器加载目标 Scene 的第一个 Chapter
- 右侧 Scene 卡面板刷新为目标 Scene 信息
- URL 不变（Scene 切换不更新路由）

#### 正常流：查看版本历史

**Given** 用户在某章写了好几版
**When** 用户点击"版本历史"
**Then**
- 弹窗列出该 Chapter 的所有版本：版本号 / 创建时间 / 字数
- 用户点击某个历史版本 → 弹窗内预览该版本内容
- 用户点击"恢复此版本" → 该版本内容写入编辑器，并记录此时章节最新版本号和更新时间；用户发布时才入库
- 恢复期间若章节最新版本或更新时间已变化，后端返回 409，不创建恢复版本或发布任务

#### 正常流：场景自动提取

**Given** 用户写完了正文
**When** 用户点击“场景自动提取”（编辑器顶部 AI 工具菜单或 Scene 工作台）
**Then**
- 弹窗选择起始/结束章节
- 明确授权采用范围后调用 `POST /api/imports/stages/scenes`
- 复用深度导入 Phase 0/1a/1b；高质量模式额外执行 Phase 1c
- 生成完成后刷新 Scene 列表，右侧 Scene 卡面板同步更新
- 低置信、fallback 或边界不确定结果进入 Scene 工作台待复核
- 用户可直接在右侧面板编辑 Scene 卡字段（编辑操作触发 outline 模块 API）

#### 异常流：网络中断

**Given** 用户正在写作
**When** 网络断开
**Then**
- 编辑器内容保留在 `viewStates` 与 `localStorage` 备份中
- 当前未实现"离线"按钮状态与 IndexedDB 同步队列（见附录 C4）
- 网络恢复后需用户手动点击"暂存"重新同步

#### 边界流：多 Tab 冲突

**Given** 用户在同一项目的两个浏览器 Tab 中编辑同一章
**When** Tab A 保存后，Tab B 再保存
**Then**
- Tab B 保存时后端校验 `expected_version`
- 版本冲突时返回 409 Conflict："该章节已被其他会话更新，请刷新后重新编辑"
- 前端提示用户，保留编辑器内容；完整手动合并 UI 尚未覆盖 E2E

#### 边界流：空内容保存

**Given** 用户编辑器内容为空
**When** 用户点击"发布"
**Then**
- 前端拦截，提示"草稿内容不能为空"
- 暂存允许空内容（占位章标记未实现）

### 【数据与状态契约】

| 层级 | 变更 |
|------|------|
| 前端 UI | Scene 树刷新；编辑器内容切换；右侧 Scene 卡面板按光标 offset 更新；Toast 提示；RAG 进度条 |
| `writing_drafts` 表 | 实质修改 copy-on-write 或 UPDATE auto 工作版本；checkpoint 留版；发布原位提升；discard/DELETE 软废弃 |
| `scenes` 表 | INSERT 手动创建的 Scene；UPDATE Scene 卡字段 |
| `async_tasks` 表 | 发布时入队 `publish_chapter` (RAG 索引) |
| `rag_chunks` 表 | RAG 索引任务更新（替换旧 chunk） |

## 场景 5：世界对象管理

### 【业务场景名称】

用户管理小说世界中的核心对象（人物/地点/势力/物品/概念/事件等）、实体关系、别名、版本回滚与人物知识边界。AI 深度导入自动入库的对象均可手动编辑。

### 【用户视角链路】

#### 正常流：浏览世界对象

**Given** 用户在 worldView（通过左侧导航栏 🌍世界 进入）
**When** 页面加载
**Then**
- 页面首次进入默认热点模式，也可显式切换普通模式；URL `mode` 优先，项目页面偏好作为回退
- 热点模式由服务端按“长期重要性 + 近期去重 Scene 出场”对全量结果排序，显示重要/近期热点/其他聚合与索引覆盖状态；同一对象可同时拥有重要和热点标签
- 普通模式完整保留既有来源分组、搜索、排序、筛选和分页
- 对象库子标签按列表展示实体，显示：状态 / 类型 / 名称 / 重要度 / 热点标签（热点模式）/ 摘要 / 操作
- 支持按实体类型与状态过滤（URL/查询参数）
- 分页列表，默认每页 20 条
- 支持搜索（名称 / 别名）
- 自动入库的批次对象会折叠在"自动入库"分组中，并带"新"标记
- 已采用对象可在当前页多选后执行“融合”或“标记为别名”，不提供“批量标记已检查”与“批量采用”。两种操作都必须明确选择保留对象并二次确认；融合会合并内容与关系，别名化只迁移关系并把来源名称登记为别名，来源对象均转入历史态而非硬删除

#### 正常流：手动创建实体

**Given** 用户在 worldView
**When** 用户点击"新建对象"，填写名称（必填）、类型（必选）、摘要
**Then**
- `core_entities` 表新增一行，`status = "canonical"`，`created_by = "manual"`，并保留人工审批来源
- 当前 UI 表单仅暴露名称、类型、摘要；去重确认弹窗、完整字段编辑在后续迭代中增强

#### 正常流：编辑实体

**Given** 用户在 worldView 列表中点击"编辑"
**When** 用户修改实体字段（名称 / 类型 / 摘要）
**Then**
- 文本字段直接更新 `core_entities` 表
- 结构化字段（importance / status 等）与 Delta Log / Text Archive 联动由后端支持，但当前编辑表单尚未暴露这些字段

#### 正常流：管理别名

**Given** 用户在 worldView 切换到"别名"子标签
**When** 用户点击"新建别名"，按名称选择对象，并输入别名文本和类型（name / title / nickname / alias / translation）
**Then**
- 调用 `POST /api/world/aliases`
- 别名写入 `core_entities.content_json.aliases` JSONB 字段
- 去重检查：别名不与已有别名重复
- 别名不创建新实体行
- 列表刷新，支持删除

#### 正常流：管理实体关系

**Given** 用户在 worldView 切换到"关系"子标签
**When** 用户按名称选择源对象和目标对象，再填写关系类型与描述
**Then**
- 调用 `POST /api/world/relations`
- `entity_relations` 表新增一行
- 校验：source_id ≠ target_id（不自环）
- 校验：source_id 和 target_id 均存在且属于同一 novel_id
- 去重：同 source_id + target_id + relation_type 不重复创建
- 列表刷新，支持删除

> **剩余缺口**：关系图谱可视化（C5）与独立实体详情面板（C6）尚未实现，当前以表格文本形式管理关系与别名。

#### 正常流：合并实体

**Given** 用户发现两个实体其实是同一个（如 AI 重复抽取的"张三"和"张老三"）
**When** 用户在待处理对象行点击"合并"，按名称搜索并选择目标对象后确认
**Then**
- 调用 `POST /api/world/entities/{candidate_id}/merge`
- 执行深度合并（9 步事务）：
  1. 排他锁（SELECT FOR UPDATE）锁定双方
  2. 别名继承（候选别名 → 目标 aliases）
  3. 关系迁移（候选的关系边重定向到目标，duplicate 边标记 deprecated）
  4. 自环清理（迁移产生的 source_id=target_id 边标记 deprecated）
  5. Character 同步（合并 character 扩展行数据）
  6. 文本字段合并（summary / public_info / hidden_truth 拼接）
  7. 冲突归档（content_json.meta.conflict_notes 记录不一致字段）
  8. 候选标记 `status = "merged"`
  9. 确保目标 `status = "canonical"`
- 全程在一个数据库事务内完成
- 前端提示"实体已合并"并刷新列表

> **当前限制**：合并入口已支持名称搜索和目标选择；带字段对比、冲突预览的完整合并向导 deferred。

#### 正常流：实体版本回滚

**Given** 用户误修改了实体
**When** 用户在实体行点击"回滚"，输入目标 Scene 索引并确认
**Then**
- 调用 `POST /api/world/entities/{entity_id}/rollback`
- 文本字段优先从 `text_archive` 按 `scene_index <= 目标` 取最新归档值覆盖
- 无归档时回退到最近 `entity_revisions` 快照
- 回滚操作本身在 `text_archive` 中记录一条 rollback 归档
- 前端提示"回滚完成"（有警告时提示"回滚完成，存在警告"）

> **当前限制**：结构化字段的 Delta Log 逆向重放尚未完全替代 revision 快照；回滚 UI 为简单场景索引输入框。

#### 正常流：管理人物档案

**Given** 用户在 worldView 的"对象库"中看到 `entity_type = "character" / "character_ref"` 的实体
**When** 用户点击"知识"按钮
**Then**
- `entity_type="character"` 的对象被创建或提升为 canonical 时已确定性补齐最小 `characters` 档案，因此深度导入人物不需要再次手工建档即可进入人物、POV 和生成中心选择器
- 旧的“先建 CoreEntity、再 POST Character”调用会原位升级自动档案，不创建重复人物；作者尚未扩展的自动档案不阻断纠正对象类型
- 弹窗添加知识边界：按名称选择目标对象，再填写了解程度、已知内容和误解内容（`false_belief` 必填）
- 调用 `POST /api/world/characters/{character_id}/knowledge`
- `character_knowledge` 表新增一行
- knowledge_level：`unknown` / `rumor` / `partial` / `full` / `restricted` / `false_belief` / `misunderstood`
- `restricted` 表示角色知道事实存在但只能使用受限内容；`misunderstood` 表示角色掌握部分信息但理解偏差，二者都必须避免暴露 hidden truth。

#### 边界流：去重高性能场景

**Given** 导入结束后大量实体入库
**When** 去重检测触发
**Then**
- 词法初筛：pg_trgm `search_text` 虚拟列（覆盖 name + aliases），`top_k = 30`
- 语义初筛：pgvector cosine similarity，`top_k = 30`
- 合并候选集（词法 ∪ 语义的并集）
- 多路信号级联评分：rapidfuzz 形似 + pinyin 音似 + 子串包含 + 语义余弦 + 长度差异 + 行政区划前缀冲突 + trigram Jaccard
- 可选 LR 模型评分（`DEDUP_MODEL_ACTIVE` 环境变量控制），失败回退级联
- 三个阈值：`DEDUP_AUTO_MERGE_THRESHOLD`（自动合并）、`DEDUP_REVIEW_THRESHOLD`（需人工）、`DEDUP_DISCARD_THRESHOLD`（忽略）

### 【数据与状态契约】

| 层级 | 变更 |
|------|------|
| 前端 UI | 实体列表/关系表/别名表刷新；合并/回滚/知识弹窗 |
| `core_entities` 表 | INSERT / UPDATE / status=`merged`（合并场景）；别名内联在 JSONB |
| `characters` 表 | canonical 人物自动 INSERT 最小档案；作者显式保存时原位 UPDATE 人物特有字段 |
| `character_knowledge` 表 | INSERT / UPDATE / DELETE |
| `entity_relations` 表 | INSERT / UPDATE / status=`deprecated`（迁移去重） |
| `delta_log` 表 | INSERT（结构化字段变更 + 知识变更） |
| `text_archive` 表 | INSERT（长文本字段变更归档 + rollback 记录） |
| `entity_revisions` 表 | 仅作为回滚 fallback，新的写入应由 Text Archive 替代 |

## 场景 6：大纲与结构管理

### 【业务场景名称】

用户在 outline 视图中管理小说总纲、剧情线、篇章纲与 Scene，并在当前层就地创作或修订。
伏笔与揭示作为剧情线的信息推进子计划统一浏览；正文 Scene 提取与 Planned Scene 创作分开。

### 【用户视角链路】

#### 正常流：浏览剧情结构

**Given** 用户在 outlineView（通过左侧导航栏 📋大纲 进入）
**When** 页面加载
**Then**
- 四个子标签：小说总纲 / 篇章纲 / 剧情线 / 场景工作台（默认"小说总纲"）
- Scene 标签：时间线式排列，每个 Scene 卡片显示：scene_index / title / narrative_tag 标签 / goal 摘要 / 状态 / 来源
- 剧情线标签：表格展示，线程类型（main / sub / background）
- 篇章纲标签：表格展示，按 arc_index / start_chapter 排序

#### 正常流：在 Scene 工作台定位当前剧情

**Given** 用户进入 `outline/scenes`
**When** 页面没有显式 Scene、页码、阶段或管理筛选
**Then**
- 首次默认热点模式，服务端按最新有效正文章把分页窗口定位到当前 Scene；没有覆盖 Scene 时定位章节距离最近者
- Scene 仍严格按 `scene_index` 展示，不使用重要性分数重排
- 顶部进度聚合显示当前 / 后续 / 已写过 / 未定位；点击阶段会清除当前 Scene 和分页并加载对应服务端结果
- 原健康聚合继续显示未复核、未关联章节、缺设定和待整理，两种聚合互不替代
- 切换普通模式后回到原管理筛选和显式分页行为；模式按项目和页面记忆，URL `mode` 优先

#### 正常流：手动创建/编辑 Scene 卡

**Given** 用户在 outlineView 的 Scene 标签
**When** 用户点击"新建 Scene"或编辑已有 Scene 卡
**Then**
- 可编辑字段：scene_index / title / goal / core_conflict / emotional_beat / must_happen / must_not_happen / narrative_tag
- narrative_tag 选项：`inciting_incident` / `rising_action` / `climax` / `valley` / `transition` / `hook` / `payoff`
- 手动创建的 Scene 默认 `narrative_tag = "draft"`，`source = "manual"`
- 保存后 `scenes` 表更新
- 写作工作台右侧 Scene 卡面板自动刷新（keepAlive 保持挂载）

#### 正常流：调整 Scene 顺序

**Given** 用户在 outlineView 的 Scene 标签
**When** 用户点击 Scene 卡片的"上移"或"下移"
**Then**
- 调用 `POST /api/outline/scenes/reorder`
- `scenes.scene_index` 批量重排
- 相关联的 `scene_chunks` 和 `chapter_ids` 不调整（只改逻辑顺序，不改物理映射）

> **剩余缺口**：自由拖拽排序与 writingView 编辑锁尚未实现；当前通过"上移/下移"按钮完成顺序调整。

#### 正常流：审查 Scene 融合与拆分建议

**Given** 用户在 Scene 工作台选择多个 Scene 融合，或从 Scene 详情发起拆分
**When** AI 返回结构化预览
**Then**
- 使用大尺寸字段对比表展示标题、目标、核心冲突、情感节奏、必须发生、禁止发生、叙事功能、叙事标签、POV 和章节映射
- 融合表并列 AI 建议、主 Scene 原值和其他来源；拆分表并列原 Scene、建议 A 和建议 B
- 默认展示全部字段；“仅看差异”只改变可见行，不移除编辑器或改变保存载荷
- AI 建议保持完整可编辑，长来源证据可按需展开；拆分章节映射保持只读
- AI 融合完整使用所有精确 Scene 正文和相关长篇结构上下文，不做应用层输入裁剪；主 Scene 只作为证据冲突时的偏好
- 不适用和不确定字段显示不同状态；保存后未解决的不确定字段仍保留复核标记
- 叙事标签的“未标注”统一保存为 `draft`；拆分建议中用户显式清空的语义字段按空值覆盖
- 保留原 Scene、继续编辑后保存和放弃结果沿用既有保存 mode；放弃持久建议与单纯关闭预览含义不同
- “废弃原 Scene 并保存”第一次点击只显示来源清单，用户再次确认后才执行废弃

#### 正常流：单行 Scene 合并

**Given** 用户在 Scene 工作台打开一个活跃 Scene
**When** 用户点击“合并”，按标题、目标或冲突搜索并选择另一个 Scene
**Then**
- 当前 Scene 和历史 Scene 不得出现在可选结果中
- 选择结果显示标题、章节、状态和目标摘要，不以 UUID 作为主标签
- 前端继续调用现有 merge preview，展示影响后要求二次确认
- 最终 request payload 仍使用 `target_scene_id` 和 `source_scene_ids`
- 任一融合保存请求进行中时禁用其他融合操作，避免重复或竞争提交；保存失败时恢复控件，预览保持打开并保留用户已编辑字段

#### 正常流：在当前层使用 AI 创作或修订

**Given** 项目已有当前小说总纲，用户位于剧情线、篇章纲或场景工作台
**When** 用户点击当前页的“AI 创作剧情线 / 篇章纲 / 细纲”
**Then**
- 用户选择“新增设计”或“修订所选”；修订必须显式选择当前层资产
- 前端确认实际参考资料并调用 `POST /api/outline/generate`，请求声明
  `target / mode / instruction` 与当前层选择；P20 不在生成中心提供入口
- 模型只输出当前层 strict preview：剧情线优先复用已有线程，篇章纲只引用已有线程，
  Planned Scene 不创建正文锚点
- preview 完整可编辑，并展示现有同层重叠、总纲冲突、作者决策项与不确定字段；生成完成不写库
- 用户明确采用后调用 `POST /api/outline/generate/apply`。服务重新校验总纲、所选资产与确认
  context fingerprint，在单一 savepoint 内全有或全无应用；漂移返回 409
- 新增资产记录 AI 来源；修订保留 ID、引用和原 source，并追加修订前值、总纲 revision、task、
  context hash 与采用时间

**And** 当前 StoryOutline 缺失时
- 三个入口阻止提交并引导到“小说总纲”页

#### 正常流：设计剧情线的信息推进

**Given** 用户在剧情线详情查看一条 PlotThread
**When** 浏览 AI 或人工维护的信息推进
**Then**
- 同一信息 movement 按时间展示隐藏、暗示、强化、局部揭示、完整揭示和兑现节点
- 底层 seed/reinforce/payoff 仍写 `foreshadowing_plans`，partial/full reveal 仍写
  `reveal_plans`，两类记录共享 `information_movement_id` 并通过 `related_thread_ids` 关联线程
- 没有关联 active PlotThread 的旧计划显示在“未归入剧情线”，作者可分配到一条线程
- 线程移入历史不删除计划；失去最后一个 active 关联后计划回到未归类区
- 旧伏笔/揭示路由重定向到该区域，不再显示独立顶层子标签或创建入口
- 底层 API 继续支持 list/create/update/delete 供 Context、Writing、深度导入和兼容调用消费，
  所有引用严格限定当前 `novel_id`

#### 正常流：保存 Planned Scene

**Given** 用户采用“AI 创作细纲”的新 Scene
**When** 服务写入 Scene
**Then**
- `scene_chunks` 与 `chapter_ids` 为空，不伪造正文位置
- `structure_meta.planning_state=planned`，保存计划章节范围与父篇章纲 ID
- 场景工作台显示“计划中”，不把它归入正文定位损坏
- 后续建立真实正文映射时转为 `materialized`
- 修订已有正文 Scene 时保留 chunks、章节映射和精确 span
- “从正文提取 Scene”继续进入 imports 深度导入 Scene stage，与细纲创作分开

#### 异常流：删 Scene 后的级联处理

**Given** 用户删除一个 Scene
**When** 确认删除
**Then**
- `scenes` 行标记 `status = "deprecated"`（软删除）
- 关联的 chapter_ids 中的 Chapter 不删除（正文保留），但脱钩
- 左侧 Scene 树刷新
- OutlineArc 的 `related_thread_ids` 如果引用了该 Scene 相关的线程 → 不级联修改

#### 边界流：Scene 与 Chapter 的 M:N 缝合

**Given** 第 5 章前 1500 字属于 Scene 1，后 1500 字属于 Scene 2
**When** 用户在编辑器里查看第 5 章
**Then**
- 通过 `scene_chunks` 精确定位：`[{"chapter_index": 5, "start_pos": 0, "end_pos": 1500}]` 属于 Scene 1
- 右侧 Scene 卡面板根据光标位置动态切换（光标在前 1500 字 → 显示 Scene 1；后 1500 字 → 显示 Scene 2）

### 【数据与状态契约】

| 层级 | 变更 |
|------|------|
| 前端 UI | outlineView 四层导航；三个页面内 P20 入口；剧情线信息推进时间线；Scene 卡片与写作面板联动 |
| `scenes` 表 | INSERT / UPDATE / 批量重排 scene_index / status=`deprecated` |
| `plot_threads` 表 | INSERT / UPDATE / DELETE |
| `outline_arcs` 表 | INSERT / UPDATE / DELETE |
| `foreshadowing_plans` 表 | 保留底层 CRUD；通过 `related_thread_ids` 与 movement provenance 投影到剧情线 |
| `reveal_plans` 表 | 保留底层 CRUD 与 reader reveal 能力；新增多剧情线关联，空数组为未归类 |

## 场景 7：项目级智能去重裁决

#### 正常流：完成重复组裁决并统一执行

**Given** 项目中存在多个可能是同一人物的世界对象，以及可能重复的结构资产
**When** 用户启动“智能去重”并打开扫描结果
**Then**
- 世界对象按重复组展示，outline 资产按 pair 展示
- 字段对比默认只显示差异；切换勾选或合格主对象时保持当前滚动位置
- 用户只能从后端给出的合格主对象中选择，不能手填 ID
- 每个非主成员都要明确选择融合、仅别名化、废弃重复项或保持独立；“稍后处理”不进入 payload
- Scene 默认选择“转入 AI 融合工作台”：只创建待处理建议，不立即修改或废弃来源
- Scene 也可显式选择“机械融合”；该路径必须先生成并确认 merge 影响预览，并把语义冲突标记复核
- 点击统一执行后，后端每组原子处理；成功组锁定，失败组保留裁决和错误原因
- 别名化命中目标对象上已有的同名待复核别名时，原位确认该别名并同步移出待处理，而不是
  以重复别名冲突跳过

#### 边界流：保持独立与资产变化

**Given** 用户对一个资产 pair 选择“保持独立”
**When** 用户在资产未变化时重新扫描
**Then** 相同 pair 与 semantic fingerprints 不再出现

**When** 任一资产的裁决相关语义字段变化，或新建了另一个重复对象
**Then** 旧指纹裁决不抑制新候选，该 pair 或新 pair 可重新进入工作台

#### 异常流：过期或伪造的组

- group apply 必须携带同项目且已完成的 `smart_dedup_scan` 任务 ID
- 成员、主对象、动作白名单或 execution fingerprint 与扫描快照不符时，该组返回稳定错误码且不写入
- 同一资产不得参与同一次提交的多个组

## 场景 8：地图候选收件箱与事实采用

深度导入产生的四类 proposal 只通过 world 稳定 facade 进入 observation。相同 workflow/Scene/
source item/type 重试复用同一候选；原始 payload hash 不同时返回冲突，不覆盖作者已经编辑的目标、
空间或 canonical value。

#### 正常流：分配、补齐并采用地图候选

**Given** 项目中存在未分配的人物位置、事件发生地、线路/阻隔或势力范围候选
**When** 用户打开地图总览中的“地图收件箱”，选择候选并点击“分配并继续”
**Then**
- 收件箱只展示当前项目、尚未分配且仍为待处理的 observation
- 用户只编辑目标对象、地图空间选择和类型化作者值；来源、证据、workflow、原始置信度和
  Scene/章节来源保持只读
- 分配不会自动生成 Fact；只有服务端 `eligibility.can_confirm=true` 时才能采用
- 采用在 observation 行锁内重验版本与资格，并创建或复用唯一逻辑 Fact
- 忽略只改变审查状态，不硬删除 observation

#### 异常流：并发修改与无效引用

- 编辑、分配、忽略、采用和批量审查都携带读取时的 `updated_at`；陈旧操作返回 409 和最新
  只读摘要，界面保留尚未提交的作者输入
- 跨项目对象、Scene、地图、地点或线路统一不可见；归档地图/线路、越界 hex、未采用目标对象、
  proposal 或 legacy untyped value 均不能形成 Fact
- 批量采用先按 UUID 稳定锁定并验证全部 observation，任一项失败时不部分写入

## 附录 A：后台自动功能（非用户直接操作）

### A1. RAG 混合检索

**触发时机**：保存正文章节时自动入队 `publish_chapter`，由发布任务内部执行 RAG 索引

**物理切块参数**：
- 子块：600-800 字（700-900 tokens）
- Overlap：18%（约 100-150 字）
- 每块强制标注 `scene_id` 标签
- embedding 失败不阻塞（chunk 仍创建，`embedding_status = "failed"`）

**父子检索流水线**：
1. 用户 Query → 向量检索子块（精确命中细节）
2. 命中子块携带 `scene_id` → 自动捞出父块（Scene 元数据 + Delta 摘要）
3. 上下文拼装：子块原文 + Scene 结构摘要

**检索模式**：search / context / extraction，支持 entity_id / character_id / thread_id / chapter_index 精确过滤

### A2. 上下文编译（Scene-Centric Compiler v2）

**输入**：Scene + POV Character + Delta Stream + Foreshadowing

**输出**：`CompiledContext` IR（非 Markdown），经 `MarkdownRenderer` 转为 LLM Prompt

**9 段 Tier 输出**：

| Tier | 段 | 截断策略 |
|------|-----|----------|
| P0 | Writing Objective（任务） | 永不截断 |
| P0 | Scene Blueprint（Scene 卡） | 永不截断 |
| P1 | POV Knowledge（知识边界，伪装模式） | 最后截断 |
| P1 | Delta Timeline（自上一 Scene 后的世界线变化） | 最后截断 |
| P2 | Open Narrative Obligations（伏笔/揭示义务） | 按条截断 |
| P2 | Retrieval Evidence Packs（RAG 父子证据包） | 按包截断 |
| P3 | Style Assets（风格素材） | 优先截断 |
| P0 | Hard Constraints（约束引擎输出） | 永不截断 |
| P4 | Compiler Warnings（风险提示） | 最先截断 |

**双模式**：Writing 模式输出 Delta 摘要；Debug 模式输出全量 Snapshot

**ConstraintEngine**：动态生成硬约束，来源：
- StaticConstraints（代码写死）
- KnowledgeConstraints（CharacterKnowledge：unknown→禁止 / rumor、partial→有限已知 / restricted→限制表达 / full→完整已知 / false_belief、misunderstood→按误判表现）
- ForeshadowingConstraints（status=seeded 且 payoff_scene > 当前 Scene → 禁止提前揭示）
- SceneConstraints（`must_not_happen` 直接列出）

**Tier 驱逐顺序**：P4 → P3 → P2（按条）→ P1（Delta 20→15→10）→ P0 不截断

## 附录 B：状态维度与内部枚举

### 作者可见资产状态

```
结构化资产：待处理(review) → 已采用(active) → 历史(archived)
正文成熟度：工作稿(working) → 已发布(published)
```

`source`、`attention_reasons` 和 `suggested_action` 与生命周期分离；冲突、低置信和
`needs_review` 是注意原因。`candidate` / `draft` / `canonical` 等原始状态在兼容接口和
内部流程中继续存在，但不再作为并列的作者状态。

### 运行与审计状态

```
pending → running → done / failed / cancelled
```

任务状态、deep import `SceneCandidate`、context confirmation/snapshot 和地图
Observation/Fact 分层保持独立。原则：业务运行时优先进入历史；项目永久删除和 demo 开发库
重建可硬 DELETE。

### Delta Log category 枚举

```
CHARACTER_PROPERTY    — 角色属性变更 (HP/灵力/状态)
RELATIONSHIP          — 关系差分 (亲密度/阵营)
GLOBAL_PLOT_LINE      — 全局线索变更 (伏笔激活/揭示)
CHARACTER_KNOWLEDGE   — 角色知识边界变更
ENTITY_CREATED        — 新实体创建
ENTITY_UPDATED        — 实体字段更新
ENTITY_MERGED         — 实体合并
MANUAL_ROLLBACK       — 用户手动回滚
```

### narrative_tag 枚举

```
inciting_incident  — 激励事件（新改变的引发点）
rising_action      — 冲突升级
climax             — 阶段高潮
valley             — 低谷/过渡（不进第三遍输入）
transition         — 纯过渡/日常（不进第三遍输入）
hook               — 黄金三章钩子
payoff             — 爽点释放/打脸完成
draft              — 手动创建默认值
```

### 前端视图路由

```
/projects                        → projectView（独立布局，无侧边栏）
/workbench/:pid/writing          → writingView（默认落地页）
/workbench/:pid/outline          → outlineView
/workbench/:pid/world            → worldView
/workbench/:pid/context          → contextView（AI 工具层，可折叠）
/workbench/:pid/rag              → ragView（AI 工具层，可折叠）
/workbench/:pid/generate         → generateView（AI 工具层，可折叠）
```

核心创作环（writing/outline/world）KeepAlive 保持挂载。AI 工具层 Lazy Load。
跨视图跳转遵循"抽屉优先，跳转兜底"原则。
