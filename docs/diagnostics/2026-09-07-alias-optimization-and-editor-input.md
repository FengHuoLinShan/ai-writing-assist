# 2026-09-07 别名读取优化与编辑器输入定位

## 结果与范围

本轮主动优化已结束。已确认的别名读取开销已处理；其余现象保留为待验证项，目前不支持追加
业务改动。只有真实用户复现、重复测量确认回归或新的阶段证据出现时，才重新开启对应诊断。

已完成 World 别名只读查询优化。3,000 对象 / 9,000 别名场景的实际 HTTP 请求中位数从
216.7ms 降至 130.7ms，三批结果方向一致。系统粘贴没有复现自动化 `fill` 的约 0.5 秒停顿；
全选后粘贴仍有应用与原生控件差异，尚未定位到可修改的业务函数。编辑器业务代码没有改动。

目标用户为长期创作的作者；期望减少查找设定时的等待并保护保存和返回上下文。
重复使用意愿与满意度仍是产品假设，本轮没有真实作者使用验证。

代码基于 `4a161a414ed974ed6df94139351c17a932bbfd5c`，分支 `codex/performance-diagnostics`。
测量时工作区未提交；每个测量记录实际 SHA、diff hash 和相关源码 hash。API/schema/任务协议、
跨模块接口和正式配置均未改变，无 migration、新依赖、缓存或 ADR。

## 最小改动与比较条件

- World repository 新增一次轻量投影：id、name、status、内联 aliases 和 `_meta`；按 novel_id
  过滤，保持 importance DESC / name / id 排序。三个别名只读入口共用它。
- 原服务继续承担状态投影、筛选、指纹、精确 total 和审核分组；工作流回滚仍使用原完整扫描及加锁。
  精确计数仍遍历别名，此改动没有把复杂度变成 O(1)。
- 原 S/L 的 300/3,000 对象没有别名；新增 AS/AL 独立项目，各含 900/9,000 条别名，包含旧字符串、
  active 和 candidate 三种载荷。原项目及第一轮证据保留；新增夹具前后 hash 核验一致。
- 沿用 M1 Pro / 16GiB、Chrome 152.0.7977.77、120Hz、Python 3.14.7、Node 24.19.0、专用
  PostgreSQL 17.10 / pgvector 0.8.6 和生产 bundle。API 关闭 reload，浏览器 1440×900，另查 390×844。
  前端资源清单重建前后 SHA-256 都是 `f7e323d0589de4d2e9b46f10ab978196024390e285da28f91863d086eadd934e`。
- 主对象测量开始时队列为空，SQL 采样与浏览器计时分开。每组 30 个实际请求，分 3 批；
  新上下文进入各 5 次。数据库/OS 缓存未清空，未声称全冷启动或可靠 p95/p99。

## 对象库结果

实际 HTTP 请求，单位 ms；请求保留 public auth 和项目门禁，绕过前端响应缓存。

| 夹具 / 待复核别名计数 | 优化前中位数 | 优化后中位数 | 前三批中位数 → 后三批中位数 |
|---|---:|---:|---|
| S：300 对象，无别名 | 21.0 | 18.6 | 20.2 / 21.5 / 22.0 → 16.8 / 20.8 / 17.7 |
| L：3,000 对象，无别名 | 126.3 | 43.8 | 127.6 / 126.0 / 125.3 → 44.7 / 43.4 / 44.2 |
| AS：300 对象，900 别名 | 29.8 | 30.9 | 28.2 / 31.2 / 30.1 → 31.7 / 32.6 / 28.1 |
| AL：3,000 对象，9,000 别名 | 216.7 | 130.7 | 215.7 / 216.5 / 219.9 → 129.5 / 133.2 / 138.1 |

大档改善明显超过其批次波动；小档没有稳定收益，不能宣称所有操作都变快。
普通 / 热点请求作为旁路对照，没有一致改善；本轮不把它们的变化算成别名优化收益。

独立 ASGI 分段采样（每组 30 次）中，L 总请求 / SQL driver 中位数为 131.0 / 104.3ms →
42.4 / 28.4ms；AL 为 222.7 / 117.3ms → 131.3 / 44.8ms。大档每请求 SQL 数量 8 → 5，
其中别名数据读取从 4 次完整对象分页变为 1 次轻量查询。小档原本只需一批，仍是每请求 5 次 SQL。
全部 12 个夹具/模式组合的响应 hash 集合前后一致；捕获查询的只读 EXPLAIN 保存在原始结果中。

热点分段将原 L 请求的主要时间指向活动统计 port：优化后活动读取中位约 64.9ms，候选读取
11.9ms，活动返回至当前页读取之间约 9.8ms，当前页读取约 2.0ms。阶段为经过时间，包含等待，
不是 CPU 时间；父阶段与子阶段不能相加。下一项最小实验应拆活动统计内部的读取和装配。

对象页新上下文就绪观察值：L 中位 869 → 363ms，AL 865 → 395ms；优化后单次最大值仍约
929 / 897ms。S 约 265 → 264ms，AS 约 269 → 343ms。此指标含 Playwright 自动等待，
不能用差值推算纯渲染时间，也不能从 5 次样本证明首屏尾延迟改善。AS 首屏波动未归因；
追加观察在启动时与只读夹具核验重叠，不作为严格对照，不据此继续扩大改动。
每组 30 次 UI 筛选只有 2 个实体网络请求，其余复用既有缓存，不混入真实 API 请求分布。

## 编辑器结果与保留的未知项

下面均为无重型 profiler 的实际剪贴板路径，每项 5 次，中位数 / 最大值，单位 ms。
时间含自动化调用、按键和两帧返回，不是 INP 或人工操作 SLA。

| 操作 | 应用 3,000 字 | 原生 3,000 字 | 应用 30,000 字 | 原生 30,000 字 |
|---|---:|---:|---:|---:|
| 空控件粘贴 | 23.0 / 35.2 | 21.4 / 25.6 | 33.8 / 41.0 | 24.0 / 28.8 |
| 全选后粘贴 | 26.9 / 31.1 | 25.7 / 29.4 | 102.2 / 119.1 | 29.7 / 47.2 |
| 替换中间一半选区 | 19.8 / 25.0 | 21.8 / 23.2 | 26.7 / 28.4 | 28.3 / 30.7 |
| 撤销局部替换 | 20.0 / 20.9 | 20.5 / 20.9 | 25.1 / 25.6 | 24.3 / 26.6 |
| 继续输入一个字符 | 15.3 / 16.6 | 17.0 / 20.8 | 19.3 / 21.0 | 14.7 / 23.4 |

记录到了 trusted paste 和 insertFromPaste；所有替换、撤销结果逐字检查，应用保存后独立 HTTP
回读一致。随后重跑原 `fill` 对照，30k 仍为应用约 538.5ms、原生约 279.5ms。这证明不同
输入路径有明显差异，不能把 `fill` 的停顿直接当作系统粘贴瓶颈，也不能忽略全选粘贴约 102ms 的差异。

早期剪贴板配对中，30k 输入 capture 到同步处理返回约 0.7ms，后续微任务约 0.7–0.8ms；
不是全部 Vue 更新时间。包含全选操作的独立 trace 中，最长 keydown EventDispatch 约 37.9ms，
最长 Layout 约 6.4ms；CPU 采样大量归于 native/program，尚不能归给某个业务函数。
最终无 profiler 的全选粘贴窗口没有记录到超过 50ms 的 longtask；Event Timing 仍有 56–64ms
的事件呈现时长。下一项最小实验是拆全选与粘贴的按键默认处理/选区路径，并补齐原生对照的
完整文本样式和容器条件，不能提前归因 Vue 或移除备份。

静置窗口各测一次：3k / 30k 的输入至自动保存响应约 3063 / 3143ms，包含原有 3 秒等待。
本地备份约在输入后 403 / 406ms 运行；当前 keyup 后 150ms 的光标更新会重新安排 250ms
持久化定时器，因此不能把它误判为固定 250ms 后的请求延迟。采样写入约 0–0.2ms，受时钟
分辨率限制；存储字段长度是 UTF-16 单元数，早期原始文件的字段名 bytes 不代表实际字节数。
自动保存和切章返回逐字核对通过，断网恢复及双标签 200/409 冲突保护另行通过。

**原生拼音输入未验证。** 系统已配置简体拼音，但 CUA 只暴露日常 Chrome 实例，没有隔离
Playwright 实例的原生目标。仅启动观察器，未向日常浏览器发送测试按键，也没有把模拟
composition 事件当成三轮真实输入。手工流程保留在运行手册，仍需人工完成 3 × 60 秒。
