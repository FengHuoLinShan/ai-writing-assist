# 文档维护 — 完整参考

## Step 1：收集本轮变化

分析本轮开发的以下维度：

| 维度 | 收集方式 |
|------|----------|
| 新增功能 | `git diff` 中新增的 API 路由、模块、facade 方法 |
| 删除功能 | `git diff` 中删除的路由、废弃的接口 |
| 行为变更 | 修改的 service 逻辑、状态机流转 |
| 架构调整 | 模块拆分/合并、新的模块依赖关系 |
| 数据模型变化 | 新增/修改的 ORM 模型、JSONB 字段结构 |
| 测试发现的问题 | E2E 测试新增的边界用例 |
| 最终采用的方案 | PR 描述和 ADR 中记录的决策 |

## Step 2：判断是否值得写入

### 必须写入（满足任一即可）

- 用户可感知的业务行为变化
- Spec 的新增、删除或修改
- API 契约变化（路由、请求/响应结构）
- 数据模型变化（表、字段、关系）
- 状态机变化（状态流转规则）
- Agent 协作方式变化（AGENTS.md 相关）
- Claude 工作流程变化（CLAUDE.md 相关）
- 架构边界变化（模块拆分/合并）
- 高代价经验教训（已造成生产问题的陷阱）
- 新增不可违反的约束

### 禁止写入

- 已完成任务记录
- Debug 过程
- 临时修复方案（workaround）
- 一次性 Prompt
- 会议纪要
- 日志输出
- 纯实现细节（算法优化、重构手段）
- "当时是怎么想到的"推理过程
- TODO 和短期计划

### 边界情况判断

| 情况 | 判断 |
|------|------|
| 修复了一个 Bug | 如果 Bug 是架构误解导致的 → 写入 ADR。否则 → 不写入 |
| 优化了性能 | 如果改变了 API 契约或数据模型 → 写入。否则 → 不写入 |
| 重构了代码 | 如果改变了模块边界 → 写入。内部重构 → 不写入 |
| 新增了测试 | 不写入（测试即文档） |
| 更新了依赖 | 不写入（除非引入新的架构约束） |

## Step 3：定位正确文档

### Spec 层（系统应该如何工作）

| 文档 | 更新条件 |
|------|----------|
| `docs/00_整体设计.md` | 架构分层变化、模块职责调整 |
| `docs/01_数据库设计.md` | 表结构、关系、索引变化 |
| `docs/modules/<name>.md` | 单模块的 API、表、facade 变化 |
| `docs/核心业务场景与预期行为.md` | 用户可感知的行为变化 |

### Guide 层（AI 应如何工作）

| 文档 | 更新条件 |
|------|----------|
| `AGENTS.md` | Agent 协作规则、禁止事项、终止条件变化 |
| `CLAUDE.md` | 开发流程、架构约束、命名约定变化 |
| `development-guide.md` | 命令、模块结构、架构原则变化 |
| `testing-guide.md` | 测试规范、Review 分级变化 |

### Archive 层（历史决策记录）

| 文档 | 新增条件 |
|------|----------|
| `docs/adr/<序号>-<标题>.md` | 重大设计决策（影响多个模块、有替代方案被否决） |
| `docs/archive/` | 废弃的文档（不移除，标记为 archived） |

### 禁止跨层写入

- 不在 Spec 中写 "Agent 应该怎样实现"
- 不在 Guide 中写 "系统应该怎样运行"
- Archive 只记录决策，不修改 Spec 或 Guide

## Step 4：最小修改原则

### 修改优先级

1. 修改已有段落/句子 → 最高优先级
2. 在已有章节内追加条目 → 仅在逻辑归属相同时使用
3. 新增章节 → 仅当现有章节完全无法容纳时
4. 新增文档 → 仅当现有文档完全无法承载时

### 禁止的操作

- ❌ 在文档末尾追加新章节而不审视是否可合并到已有章节
- ❌ 保留新旧两个版本的描述
- ❌ 重复描述同一个规则（在 Spec 写了又在 Guide 写）
- ❌ 通过注释标注 "旧版本是..."（直接删除旧内容）

### 消除冗余的操作

- 相同原则只保留一个权威版本。如果 AGENTS.md 和 CLAUDE.md 都描述了同一个禁止项 → 选一个作为权威来源，另一个用引用替代
- 多个示例 → 总结为一个模式
- "例外情况" → 提升为显式规则
- 零散经验 → 提炼为 Checklist

## Step 5：输出更新建议模板

对于每个拟修改文档，按以下模板输出：

```
【是否更新】YES / NO

【修改原因】
<一句话说明为什么未来的 AI 需要知道这个>

【修改内容摘要】
<改了什么，为什么这样改>

【建议修改位置】
<文件路径 + 章节名 / 行号范围>

【修改后的正文片段】
<完整的替换文本>

【可能影响的其他文档】
<需要同步更新的文档列表，无则写"无">
```

如果所有文档都是 NO，输出：

```
【本轮判断】无需更新文档
【理由】<一句话>
```

## Step 6：一致性检查清单

更新完成后，逐项确认：

- [ ] 不与现有 `docs/` 中的 Spec 冲突
- [ ] 不与 `AGENTS.md` 中的 Agent 规则冲突
- [ ] 不与 `CLAUDE.md` 中的开发约束冲突
- [ ] 新增内容不与已有内容重复
- [ ] 未保留过时信息（旧版本、废弃方案）
- [ ] 跨文档引用路径正确

发现问题时：**优先修正文档，而不是保留多个版本。**

## 最终验收标准

更新后的文档必须：

1. 能准确描述当前系统（与代码一致）
2. 新 AI 无需阅读历史记录即可理解核心思想
3. 文档之间职责清晰（Spec ≠ Guide ≠ Archive）
4. 不存在明显重复（同一规则只出现一次）
5. 不依赖隐含上下文（自包含、可独立理解）
6. 可以作为下一轮开发的稳定基线

## 最终判断

> 如果本轮变化不会影响未来开发决策，则不更新文档。

**默认不写入。** 只有未来的 AI 仍然需要知道的信息，才值得被保留下来。

当你无法确定时，选择**不写入**。文档的代价不是写入那一刻，而是之后每一次被读取、被误解、被维护的累加成本。
