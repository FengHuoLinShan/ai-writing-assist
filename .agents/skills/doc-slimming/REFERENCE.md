# 文档精简 — 完整参考

## 1. 保留原则（必须保留）

以下内容**绝对不能删除**：

- 会影响未来设计决策的原则
- Agent 的职责边界与协作关系
- 必须遵守的开发流程
- 架构约束与不可违反的规则
- 容易遗忘但代价高昂的经验教训
- 对新人 AI 理解系统至关重要的信息

## 2. 删除原则（优先删除）

以下内容**优先删除**：

- 已完成任务记录
- 历史讨论过程
- 临时方案（workaround）
- 被后续结论覆盖的内容
- 重复描述（同一规则在多处出现）
- 具体实现细节已迁移至其他文档的内容
- "为什么当时这样做"的长篇推理过程
- TODO、会议纪要、实验日志

## 3. 合并原则

- 相同原则只允许存在一个权威版本 → 选择一个位置作为权威来源，其余用引用替代
- 相似规则抽象为统一规范 → 如 "禁止 X" 和 "禁止 Y" 可抽象为 "禁止未确认的破坏性操作"
- 多个示例总结为一个模式 → 如 3 个命名示例 → 1 条命名规则
- 将"例外情况"提升为显式规则 → "通常禁止 X，但 Y 情况下允许" → 写入规则
- 将零散经验提炼为 Checklist → 分散的注意事项 → 合并前 Checklist

## 4. AGENTS.md 精简目标

AGENTS.md 应回答以下问题（除此之外的内容迁移或删除）：

| 问题 | 对应章节 |
|------|----------|
| Agent 体系是什么？ | 列出 Agent 类型、实例、职责 |
| 每个 Agent 的职责是什么？ | 明确能做/不能做的边界 |
| Agent 如何协作？ | 并行隔离、Issue 流转、文档同步 |
| 冲突如何解决？ | 优先级链条、冲突处理流程 |
| Loop 如何终止？ | 完成/阻塞/安全/超范围四种终止条件 |
| 什么事情绝对不能做？ | 架构/代码/数据/操作四级禁止 |

目标：**300-500 行**

## 5. CLAUDE.md 精简目标

CLAUDE.md 应回答以下问题：

| 问题 | 对应章节 |
|------|----------|
| Claude 的角色定位是什么？ | 一句话定义 + 互补文档列表 |
| 开发必须遵循什么流程？ | 修改前→修改后→合并前 Checklist |
| 修改代码前必须做什么？ | 读取顺序、边界检查 |
| 修改代码后必须做什么？ | 测试、lint、文档同步 |
| 什么是高优先级原则？ | P0 阻塞 / P1 发布前 分级 |
| 如何处理 Spec 冲突？ | 5 种冲突类型的决策树 |

避免出现：具体业务需求、历史演进过程、大段 Prompt 示例、已废弃方案。

目标：**200-400 行**

## 6. 输出模板

对每个处理的文档，按以下模板输出：

```
### [文档名] 精简分析

**保留内容摘要**：
- <列出保留的关键内容和原因>

**删除内容摘要**：
- <列出删除的内容和删除原因>

**合并内容摘要**：
- <列出合并前后的变化>

**新推荐目录结构**：
<精简后的目录树>

**精简后正文**：
<完整的新文档>
```

## 7. 质量标准

精简后的文档必须满足：

1. 新加入的 AI 能在 5 分钟内理解其核心思想
2. 文档不存在明显重复
3. 文档之间职责边界清晰
4. 不依赖历史上下文即可独立理解
5. 可作为后续自动更新的稳定基线

## 8. 边界情况处理

| 情况 | 处理方式 |
|------|----------|
| 两条规则看起来矛盾 | 判断哪条是更新版本，删除旧版。如无法判断 → 标记为 needs-triage |
| 内容在多个文档中重复 | 选择一个最权威的位置保留，其余用 "详见 X" 引用 |
| 不确定某段是否应删除 | 偏向删除。被误删的重要内容会在未来被重新发现和写入 |
| 精简后行数低于目标 | 不强制填充。低于目标说明文档更精炼，是好事 |
| 精简后行数超过目标 | 继续删，优先删示例和说明性文字，保留规则本身 |

## 9. 最终判断标准

精简完成时，问自己：

> "如果未来只能保留这一版文档，新的 AI 是否仍然能够正确接手项目？"

- 否定 → 继续重构
- 肯定 → 停止，不要再删了
