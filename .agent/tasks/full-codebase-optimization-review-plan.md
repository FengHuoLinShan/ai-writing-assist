## 1. 目标、范围与完成标准

目标是在保持现有功能和外部行为的前提下，找出并排序可降低维护成本、运行成本、故障概率及交付成本的优化机会。允许调整内部架构、模块内部组织和跨层编排，不预设必须拆模块、合模块、建立公共框架或更换技术栈。

本轮交付是审查计划。后续工作分为两个独立验收结果：先完成全量审查报告与可执行批次，再按用户后续实施指令落实优化；计划写完不等于全库已审完，审查结束不等于优化已实现。

全量审查完成须同时满足：

1. 固定基线的所有 Git 跟踪文件均进入覆盖账本，逐一标记已审、按生成来源验证、不适用或受阻；不得用目录抽样宣称逐文件完成。
2. 全部生产源码逐文件语义阅读；每个公开入口、任务注册、持久化模型和跨模块依赖均归入调用链。自动扫描只辅助定位，不能替代读码。
3. 每个审查单元完成结构、契约、数据、性能、故障恢复、测试及交付影响检查；无发现也记录覆盖与结论依据。
4. 所有候选有可定位证据、收益、兼容风险、验证方式和裁定；不存在未经审查直接进入实施的“零引用删除项”。
5. 关键用户链和横切不变量完成交叉复核；未执行的基准、PG、浏览器或真实模型验收如实列出。必需证据受阻时只能交付部分审查，不宣布全量验收完成。

不以删除比例、文件长度阈值、统一命名数量或引入新模式数量作为成功标准。优先减少真实重复和变更传播；性能优化必须有前后可比证据。

## 5. 审查顺序与阶段出口

### P0：固定基线、账本与验收环境

核对当前分支/HEAD/远端基线/WIP，读取各单元局部规则、README、适用 ADR 和测试指南。生成文件覆盖账本、入口/任务/模型清单及测试能力清单，记录 PG、对象存储、浏览器、真实模型环境可用性。先运行文档门禁，再按现有入口建立 fast、前端和适用集成基线；记录已有失败，避免混入后续变更。

出口：所有文件有主归属；基线明确；未运行门禁有原因；未批准的真实数据、费用和发布操作不会被自动触发。

### P1：逐文件审查与真实依赖图

依次审入口/共享 → account/project → 各领域 → LLM/任务 → 前端 → 数据/测试/交付。为每个公开入口追到领域编排、持久化和返回；同时反向查所有消费者、动态注册、字符串任务名、OpenAPI、CLI、配置开关与发布脚本。内部零引用只构成候选，对外接口无仓内消费者不构成删除证据。

用现有搜索/AST/测试设施识别重复、循环依赖、大查询、宽泛异常和资源泄漏；逐项读码证实。未核实的模式只记线索，不计算为确定发现。对历史约 70 项逐一给出仍成立、已解决、误报、功能变更或待查结论，不直接继承旧排序和收益估计。

出口：覆盖账本逐项完成；实际依赖与数据所有权可追踪；每个发现都有代码位置及具体影响。

### P2：端到端交叉审查

至少贯穿下列链路，并查明取消/失败/恢复和跨项目拒绝路径：

1. 账户连接 → 创建项目 → 项目配置 → LLM snapshot → worker 恢复。
2. 文稿导入 → 结构整理/抽取 → 作者确认 → 世界/Story/正文资产与索引。
3. 世界工作稿 → 校验/复核 → 显式采用/发布 → revision/影响失效 → 历史读取。
4. 总纲/篇章/Scene → Context 确认 → Story/正文候选 → 独立审查/返修 → 采用/发布。
5. 地图编辑/图片 → 版本 CAS → 查询展示 → 失败重试及并发冲突。
6. 作者 source revision → RP 分支/续写/概要 → 刷新恢复；反证 RP 无作者资产写回。
7. 助手查证 → 提案 → 领域确认 → 任务执行 → 部分失败/回执恢复。
8. 编辑器输入 → 本地备份/服务端保存 → 离开/切章/刷新 → 冲突保留与恢复。
9. 构建 → 资源 inventory → 镜像/启动 → migration → 固定 SHA 发布/回滚合同（本阶段先审查，不实际发布）。

性能先使用 `docs/diagnostics/performance.md` 的隔离流程，选代表性大小的数据集；记录输入规模、环境、重复次数、耗时分布、SQL 次数、峰值内存和 bundle 体积。不得把不同数据集、并发测试中的噪声或少量样本包装为可靠 p95/p99。只对有证据的瓶颈设计优化。

出口：单模块“简化”未破坏跨模块契约；性能候选有可复测基线；风险与环境缺口明列。

### P3：架构方案裁定

每个架构候选最多比较三个具体方案：保持现状、局部收敛、职责调整。说明当前痛点和消费者，画出必要的调用/数据归属变化，列修改面、迁移、验证、回滚和维护收益。现状成本不成立时直接保留，不为完整报告虚构重构。

优先考虑有相同语义的重复实现归于现有 owner、巨型 service 按独立职责拆内部文件、API 中业务编排下沉、重复前端生命周期归于现有机制。禁止把不同授权、状态机或事务策略压成一个多开关通用框架。

架构调整通过条件：外部兼容可证明；事实源/写入权明确；依赖方向更清楚或实际维护成本下降；无新增无价值转发；不存在无法回滚的数据步骤。重大长期取舍记录 ADR，跨模块变化同步正式架构文档。

出口：每项裁定为实施候选、保留现状、补证据或超出范围；补证据项不得进入可执行队列。

### P4：形成可执行优化批次

按依赖关系而非文件大小排序：可证明的局部清理 → 同语义复用 → 模块内部拆分 → 跨模块职责/前端生命周期收敛 → 有必要且兼容的数据结构调整。实际顺序由 P1–P3 证据修正。

每批一个可验收结果，限定文件/接口、前置批次、保留契约、测试命令、文档更新和回滚方法。机械移动与行为逻辑分开；共享 hash/schema/状态/快照接口先证明兼容，再迁移调用者，最后处理旧实现。不得以文件内联减少层数却引入越界 import。

出口：审查总报告、已裁定问题账本和带依赖的批次表可直接交给实施者；实现、合并、发布尚未执行。

## 6. 重点防误判规则

- **hash 与序列化**：逐一比对 Unicode、排序、分隔符、None、数字、默认转换及历史指纹；保留固定输入/输出样本。不得统一后让旧 confirmation 或 revision 无理由失效。
- **状态**：区分队列运行态、领域工作流态、用户展示态。`done`、`completed`、`waiting_approval` 等名称不构成等价关系；先画合法转换/终态和权威源，保持公开值与旧记录解释。
- **LLM helper**：核对 transaction/checkpoint 次序、snapshot/provider 固定、当前 Key 轮换、profile_source、注入/借用客户端和 finally 关闭语义。
- **schema/validator**：比较缺失/null/空串/非法值、宽松输入、输出和 OpenAPI；Annotated 复用不能偷偷改变接受范围。
- **repository/服务合并**：核对过滤、软删除、更新钩子、排序、批量语义及事务；差异有业务意义时保留独立实现。
- **前端共用逻辑**：查路由变化、项目/Scene 切换、keep-alive、卸载、迟到响应、重入、receipt/localStorage/IndexedDB 恢复；避免共用 store 导致页面互相污染。
- **删除与迁移**：工具、文档、测试、兼容 API、未跟踪数据不按“无 import”删除；已发布 migration 不默认 squash，历史记录与用户数据不成为优化耗材。

## 7. 证据账本、优先级与收益

后续审查启动后，在主记录附近按需要保存一份覆盖账本和一份发现账本，不预建平台或重复任务系统。

覆盖账本字段：`path | 主单元 | 基线/内容指纹 | 文件类型 | 审查状态 | 入口/消费者 | 证据 | 发现ID或无发现理由`。审查结束重新生成 Git 清单比对；新增或修改文件重新开审。

发现账本字段：`ID | 位置/符号 | 问题与触发 | 调用链证据 | 现有契约 | 最小方案 | 预期收益 | 风险 | 依赖 | 验证命令/断言 | 回滚 | 裁定`。

排序分开记录“影响”和“实施风险”，避免高风险大重构因预计删行多而靠前：

- P0：安全、数据丢失、隔离及恢复破坏风险，立即隔离/报告；功能性修复另列。
- P1：已证实的高频故障根源、严重瓶颈或高传播成本，且有可验证的兼容方案。
- P2：确有维护收益的重复收敛、边界调整、构建/测试提效。
- P3：低收益风格、命名或推测性清理，默认保留或等待顺手修改。

收益记录实测 SQL/耗时/内存/构建变化、减少的维护点/依赖边和修改传播范围；代码行数仅作附带事实。没有可靠基线则注明“收益待测”，不承诺百分比。每批若无法说明具体收益或验证成本明显高于收益，建议不做。
