### 取消 / 失败 / 恢复 / 跨项目拒绝证据

- 失败三类及用户可见后果：
  1. **优雅失败**（health/Phase0/1a/1b/commit/Phase2/3 置 `phase="failed"`，recovery_required=False）→ 任务 failed，`available_actions=["dismiss"]`（lifecycle.py:1125-1135；双 flag 为 False，worker.py:210-214），无 resume/abandon 按钮；直接调 resume API 也被 `_get_recoverable_deep_import_run` 的 `not run.recovery_required` 400 拒绝（orchestrator.py:1762-1765）。用户唯一出路是关闭后全新重提（新 run，不继承 checkpoint，Phase 1a/1b 全额重付）。
  2. **D5b-1 真实触发面（对本链后果的精确化，cross-ref D5b-1 不重编号）**：`resume→失败死循环`需要「`phase="failed"` 已持久化 + recovery_required=True」同时成立。逐源枚举：targeted_completion partial 必留 TC checkpoint（resume 时 `_progress_from_task` 特例归一，orchestrator.py:1392-1395）；standalone review_resolution 不经 `run_step`；嵌入整理失败被捕获降级（review_resolution.py:882-889）——三者都不进 `run_step` 死循环。唯一现实入口是**窗口竞争**：优雅失败经 `_record_progress` 持久化（phase=failed、rr=False）后、worker 终态化完成前进程死亡，stale 扫描把 running 转 failed+rr（lifecycle.py:1030-1096）。此后一次 resume：resume_manual/resume_interrupted 清掉双 flag（lifecycle.py:175-193；orchestrator.py:1554-1582）→ worker `_progress_from_task` 不重置 phase（无 TC checkpoint 时）→ `run_step` 抛「无法处理当前进度状态： failed」（workflow.py:272-273）→ 任务再次 failed，且第二次失败 rr=False → **available_actions 收敛为 dismiss，resume 与 abandon（资产清理）双路径永久丢失**（orchestrator.py:1762-1765 同时拒绝两者）。即链级后果是"一次性恢复机会被必然浪费 + 该 workflow 的批量软废弃清理入口不可达（已提交 Scene/候选只能逐个手动处理或 force 重导替换）"，内部错误文案进 task.error_message 对用户可见。修复方向不变（resume 路径单点归一 phase），维持 D5b-1 的 P1/单列功能性修复裁定。
  3. **中断恢复**（crash 时 phase=running）→ resume 正常：phase 归一 pending，Phase 2a/2b checkpoint 指纹跳过已完成 Scene，实体产物一致；但完整导入无 TC checkpoint 时会整体重跑 Phase 1a/1b(/1c)（→X2-2）。fenced scene stage 靠 v2 prepare 指纹拒绝漂移，产物一致性最强（orchestrator.py:1102-1226）。

## 性能取证

按 `docs/diagnostics/performance.md` 评估导入链动态基准可行性：

- 现有探针对本链的覆盖仅两段：`imports` 模式（performance.md:73）= 两种格式经真实 UI 上传到合成项目，测导航与章节数——即段 1 的上传/解析/发布路径；`contention` 模式（:77）= 300 章上传后的真实索引积压期间编辑另一项目（embedding 指向不可用 loopback，:14-15）。**深度导入 Phase 0–3、targeted_completion、review_resolution 依赖真实 LLM，探针明确"不联系付费模型、不能报告真实 LLM 性能"（:13-15）——导入链核心段无动态基准，且按约束不允许付费调用，不可行。**
- 本机执行条件不满足（计划 §10.1 在案）：performance_probe 要求无 `backend/.env` 的隔离 checkout + 专用 55439 docker PG（performance.md:11、:20-44），本机必败；本次为只读审查亦不运行服务。**动态基线未执行，如实声明。**
- 下列静态标注均为**收益待测**，不构成优化承诺：
  1. `scene_commit.py:446` 逐章 `writing_facade.get_draft`（含全文加载）串行 await 于最终 commit 事务内，N=覆盖章数（≤1000）——与 batch create、RAG 入队同事务，直接拉长写锁持有时间；替代=一次范围批量取 draft hash/长度。
  2. `scene_commit.py:390` replace 路径 `_assert_complete_active_source_coverage` 经 `get_scenes_by_novel` 全量加载项目所有 Scene 进 Python 过滤——force 重导在大项目上的事务内成本随全库 Scene 数线性增长。
  3. `orchestrator.py:1779-1800` `_check_duplicate_import` 每次提交全量加载 Scene + auto-ingested 实体后 Python 过滤（与 D6a-2/D6b-4 同族模式）；每次提交仅一次，规模上限为项目资产数。
  4. `completion_control.py:282-295` `active_asset_impact` 对每个活跃 run 以 100/页循环翻页 context_snapshots 并递归遍历 included_asset_ids——诊断端点，成本随快照量增长。
  5. 上传路径逐章 `enqueue_task`（services.py:112-117）→ N 个 publish_chapter 各自 RAG 索引，属有意设计且 contention 模式已文档化积压行为；不改。
  6. X2-2 的恢复重付：完整导入无 TC checkpoint 的 resume 每次 Phase 1a/1b 全额 LLM 重跑（high_quality 加 1c）——成本项非性能项，随 X2-2 处置。
  7. 冻结并发（Phase 1b≈200/Scene、Phase 2a=25、Phase 1c=20）与降载阈值（单波 429 或 ≥2 传输失败减半）为已验收配置（README、D5a §1），无证据不动。
