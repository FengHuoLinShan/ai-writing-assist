### 断点/缝隙检查结论

- **采用后历史不可变语义在读取侧成立**。写入侧：PageRevision/CanonRevision 由 DB trigger（0827，F4 共享事实 2）禁 UPDATE/DELETE，ORM 无更新路径；读取侧四个入口（页 revision 列表、canon head、canon revision、publication 定位）全部按 `novel_id` 过滤且只读。canon 读取在 replay 中逐一验证 manifest/resource digest（fail-closed）；页 revision 列表返回快照行但不重验 digest——不对称无害，篡改需绕过 DB trigger，且 canon replay 会兜底失败。
- **失效两档严格度触发完整性成立**。本槽位枚举了全部已采用页写路径：draft 发布（`_seal_draft_for_admission`）、legacy PATCH adopted 变更（`update_page`:271-284，fail-closed context + projection + synopsis）、workflow 归档（:247-258，同样三件套，按 README 不写 revision）、legacy 建页为 adopted（:189-195，无 context_reason——新页此前不存在消费者，无需失效，synopsis 仍标脏）。`projection_source_hash` 仅含本页内容+版本，故只标本页 projection 即完整，下游显式引用变化通过 impact 预演回执告知作者而非静默失效，与"不能把局部覆盖说成完整影响"契约一致。canon revert（`_admit_revert`:599-625）不改页行、仅换 manifest 选择，且全仓无任何消费者经 manifest active_resources 读页内容（rg 证实仅在 authority 内部使用），因此 revert 不触发失效是正确的，非缺口。
- **取消**：链 3 全部异步段（校验 run、简介刷新、生成建议 task、共创回合、别名关系补抽）无用户可发起取消入口——`modules/world/api.py` 无任何 stop/cancel 端点（rg 证实零命中）；`infrastructure/tasks/facade.py:193/208` 的 `cancel_recoverable_task/cancel_exact_task` 在 world 无调用方（仅 assistant/interaction/imports 消费）。取消态只作为简介 head 的失败恢复语义出现（`world_bible_synopsis_service.py:142-150`：failed/cancelled → 警告"已保留最后成功版本"）。项目永久删除经 `cancel_unfinished_tasks_for_novel` 兜底。→ 记 X3-3。
- **失败/恢复**：发布幂等恢复闭环完整（api.js sessionStorage attempt + 服务端 decision 双查）；409 族（canon_admission_stale / impact_scope_changed / edit_baseline_stale / required_validation / target_changed）全部保留工作稿；前端 409 统一文案指向"世界健康重新校验"（useWorldBible.js:1180-1183），与 D8b 共享事实 4 一致。
- **跨项目拒绝**：publish 走 `require_active_project_exclusive`（owner 过滤，不接受调用方 owner）；draft/page/revision 读取全部 `novel_id` 复合过滤；authority `_require_same_novel`（:1309）拒绝 manifest 内跨项目引用；legacy PATCH 建稿使用门禁内 `page_id`。

### 断点/缝隙检查结论

- **CAS 冲突前后端用户可见反馈完整**。三层 CAS（结构 base_revision_id / page·prompt·annotation expected_updated_at / 生图 generation_status claim）前后端逐点对齐（与 D8b 共享事实 1 核对一致）。结构冲突有专属 diff 面板与"采用服务器版/以我的编辑建新版"双出路；prompt 冲突有专属 promptConflict 态；页审查与标注冲突走通用错误反馈 + 权威状态重载（标注拖拽冲突会丢弃拖拽位置并重载，可接受）。
- **重试确认流闭环**：服务端在"未确认"时不是直接拒绝，而是先把页落为 `retry_requires_confirmation`+固定文案再 409（resume_run:269-278），保证刷新后状态仍可见；前端 resume/retry 两条路径都有独立 confirm 与确认后重放。确认语义只授权"可能重复扣费"，不放大为任意重试。
- **S3 补偿路径存在窄失败窗口** → 记 X3-2。
- **结构保存内的跨服务私有访问** → 记 X3-1（cross-ref D2c-6）。
- 一致性小注（不立项）：`resume_run` 对状态 `generating + stop_requested` 的 run 放行恢复；若 worker 仍在逐页收尾，旧 worker 的完成回写会被 `provider_in_flight` 复验 + 任务身份约束挡下，且双确认已披露重复扣费窗口，语义自洽。
