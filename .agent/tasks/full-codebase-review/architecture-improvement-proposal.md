# 系统架构、技术栈与数据库改进提案

日期：2026-09-12。状态：**提案，未实施、未采纳为 ADR**。

本提案基于[全库审查总报告](review-report.md)、[发现账本](findings-ledger.md)、[实施计划](implementation-plan.md)和相关槽位报告，重新核对当前代码后形成。它回答“哪些结构值得改、为什么、如何验收”，不替代原实施计划的逐项修复清单。

## 1. 总体判断

**建议保留模块化单体、FastAPI、PostgreSQL/pgvector、Vue 3 和当前有界任务执行模式；优先修复业务事实与执行状态、模型与迁移、生产入口与测试范围之间的不一致。** 当前证据不足以支持微服务化、更换数据库、引入新队列平台或重写前端。

系统已有明确的领域归属、owner/novel_id 门禁、不可变版本、CAS、任务租约和固定 SHA 发布链。这些机制有实际用途，不能因实现复杂就删掉。真正需要改善的是这些边界在少数关键路径上落实不完整，以及测试和文档有时只证明接口存在，未证明用户路径具备所宣称的能力。

优先方向是：让导入可靠续接、让记忆投影表达真实覆盖、让数据库约束可核验、让所有实际生产路径进入对应门禁。减少重复代码是这些改进的附带收益，不是主要验收指标。

## 3. 技术栈是否选错

| 选择 | 判断 | 本次建议 | 重新评估条件 |
|---|---|---|---|
| FastAPI + SQLAlchemy，模块化单体 | 与目前共享事务、领域确认和小团队维护方式相容；未发现换语言/框架可解决的根因 | 保留；把复杂编排收回领域 service，公共 seam 保持薄适配 | 可测的独立扩容需求、团队所有权或部署隔离需求出现 |

| SQLAlchemy ORM + Alembic | 工具足够；声明漂移和校验盲区是工程问题 | 修复已证实漂移，补关键约束反证；不做 ORM 全量重写 | 仅当具体查询表达或迁移能力不足且有实证时评估替代 |
| Vue 3 SFC + hash router + bridge | ADR-0009 已完成业务页迁移；“仍用 island”本身不是缺陷 | 收回残留业务 DOM 所有权；保留 Leaflet/Canvas 等必要命令式接缝 | 嵌套路由/共享状态需求确实超出现有边界，再单独评估 Vue Router/Pinia |
| JavaScript + 手写 API 契约 | 可用，但 API 扫描范围未跟上 Vue 迁移 | 先覆盖真实 `.vue`/JS 调用；不把全仓 TypeScript 转换当作修 bug 前提 | 修复覆盖后仍频繁发生可由类型系统提前发现的契约错误 |
| 私有 S3 接口 + 单机 MinIO | 图片独立于关系数据合理；单盘无异地备份是明确取舍 | 保留接口；评估完整资产恢复方案 | 用户图片成为不可重新取得的长期资产，或产品开始承诺完整恢复 |

## 4. 改进项

### A1 — 测试门禁与生产路径一致

**确定缺陷；第一批处理。** 对应 F4-1/E1-1/E1-2/E2-1。

当前 `backend/infrastructure/tasks/test_identity.py:26` 从 backend 根递归扫描 Python，未排除 `.venv`；已有 `backend/tests/support/inventory.py` 可复用。`backend/pyproject.toml:113` 的 testpaths 未包含 `tests/account_project_preferences`。前端 `frontend-console/tests/api-contract.test.js:33` 只遍历根 JS 与 shared/ui/views，没有 `vue/`，其递归函数也不读 `.vue`。

问题不只是测试慢：主要 UI 已迁移而契约守卫仍扫描旧入口；账户相关测试存在却不自动运行，容易形成“测试很多、关键路径未验”的误判。

**方案：** 先复用生产文件清单解决扫描，再补漏收集目录；确定性 eval 测试接入锁定运行器与适当 CI 目标。前端在现有守卫中明确收集 Vue 的 script 和模板调用，用已安装的解析能力处理 SFC，避免靠字符串数量声称完整覆盖。新增一个当前生产调用违规样本的反证，确认门禁真的会失败；保留已有功能/安全断言。

**验收：** 输出实际收集清单与漏收目录结果；owner/偏好关键测试可从默认门禁触达；后端扫描不进入 venv；Vue 中引入无定义 API 调用时守卫失败。原报告的 52/124 数量应在实施 HEAD 重新 collect，不能写死成永久指标。

**回退/边界：** 仅测试与运行入口变化可回退；暴露的有效失败单独修复，不通过删断言或继续排除目录恢复绿色。不需要新测试平台。

### A2 — 把导入恢复定义为领域协议

**确定缺陷与静态风险并存；最高业务优先级。** 对应 D5b-1、X2-2/3/4、X1-1；依据 [ADR-0011](../../../docs/adr/0011-keyed-task-coalescing-and-domain-owners.md)。

`import_workflow_runs` 已有阶段、授权、checkpoint、generation 和执行 owner，`async_tasks` 已有租约、attempt 与 keyed coalescing。因此无需新建通用 workflow 引擎。缺口在于用户“恢复”动作没有在所有阶段保持同一来源和同一成果身份。

原报告与当前调用链表明：显式恢复的窄进程死亡窗口可能同时保留 `phase=failed` 和 `recovery_required=true`；`_progress_from_task` 未普遍处理该恢复意图，重跑仍进入 failed 分支。普通优雅失败是 dismiss-only，不能为修复此窗口把所有 failed 都自动重试。另一些恢复路径重做 Phase 1a/1b，high_quality 融合可能改变分组，使依赖来源区间的幂等键不再命中旧成果；这属于重复计算/重复资产风险，当前未做故障注入复现。

定位：`backend/modules/imports/orchestrator.py:1368-1396,1525-1582` 与 `workflow.py:159-273` 是失败恢复链；`orchestrator.py:525-603` 的完整导入入口，与 `:1102-1164` 已重验来源的 Scene stage 不同。成果幂等见 `scene_commit.py:40-59,165-191`，融合分组见 `workflow_scene_phase.py:513-565`。实施应复用已存在的来源向量检查，不新增第二套来源身份算法。

**方案分两步：**

1. 在 imports 显式恢复入口修复 failed 阶段归一；保留自动重试、人工恢复、终止、来源过期各自语义。复用领域错误映射，使不可恢复、预算用尽和来源过期返回可识别状态，UI 只显示当前可用动作。助手同类预算/超时错误单独修复，不粗暴捕获所有 ValueError。
2. 在现有 run/checkpoint 中冻结阶段输入身份与已接受的中间结果。恢复相同输入时复用结果；来源/参数/授权改变时阻断旧恢复，转为新的用户决定。成果写入和已完成 checkpoint 在同一受 fence 保护的事务内推进；中断后以领域成果回执对账，不能仅凭 task 已重排队判定可安全继续。

不承诺模型调用“恰好一次”：模型已返回而结果尚未落盘时，除非 provider 支持可靠幂等，仍可能重复计费。目标是已持久化步骤不重复消费、业务成果不重复采用、不能继续时原因明确。

**验收：** 在独立测试库覆盖阶段提交前后强杀、旧 lease 晚到、重复点击恢复、来源变更、review 指纹漂移、项目删除、取消后残留。检查成果身份/数量、checkpoint、实际 provider 调用次数和前端提示；不能仅断言 task 最终 completed。

**回退/边界：** 先交付窄 bug 修复，再做 checkpoint 语义升级。新格式需版本化并保留旧记录读法；无法证明可恢复的旧 run 标记不可继续，不猜测补齐。旧成果按 workflow 所有权保留、展示或软回滚，禁止全项目清理。

### A3 — 记忆投影必须声明真实覆盖

**确定的语义分歧；解决方向需要产品裁定。** 对应 D3b-1/D4-1、D3b-2。原总报告把 D3b-2 放入“补性能证据”，本提案认为应先处理语义，性能是后续问题。

`backend/modules/story/continuity/services.py:764` 的章级 reducer 处理 entity_created/updated/moved 等事件，没有 manual_correction 分支；`scene_projection.py:492` 的 Scene reducer 会把部分这类变更放入 `changes`。导入增量经 `ingest_delta_events` 写入 manual_correction。于是“事件存在”“Scene 有变化记录”“章级已有完整状态”不能互相等同。历史有类型化事件的项目可能有非空状态，不能把报告的“空壳”扩展为所有真实数据库恒为空。

另有 `get_continuity_evidence_for_writing` 仅由 facade/测试消费，`writing/README.md:283` 却宣称已接入；真实模型测试要求 `continuity_location_mismatch`，生产 writing 规则没有对应产出。这是能力声明与实现不一致。

**建议：** 以已确立的 Scene 历史为权威，先明确每维度哪些事件能重放、哪些只是审计变更；不把 manual_correction 全部武断转成 entity_updated。让章级读模型从同一组已验证事件/Scene 边界派生，并返回实际覆盖和缺口。缺口不能用“空状态”冒充“已检查且无冲突”，也不能用当前 World 回填历史。

连续性检查有两个合法产品选择：补齐一条真实 writing 消费链并保留证据/截止点，或撤回未实现的能力声明并处理稳定导出兼容。建议先修覆盖语义，再决定是否接入位置连续性检查；不以删测试来认定功能完成。

**验收：** 用同一组带来源的事件验证 Scene/章级投影的可比维度；覆盖 manual_correction、位置事件、重排、缺锚点、角色截止点和旧数据。用无模型的业务测试证明 continuity 规则能产出，再做真实模型质量验收。

**回退：** 原始事件、作者修订和人工 checkpoint 保留；仅在来源足以重建时版本化重算派生快照。保留旧投影至新旧比对通过，不清空 memory 表。

### A4 — 统一数据库约束事实，避免把 schema 检查当成完整证明

**确定的 ORM/migration 漂移与局部同项目约束缺口；数据库现场影响待验证。** 对应 F4“world_library 外键漂移”与本轮增量核验。

`backend/modules/world/models/library.py:56` 等五表 `novel_id` 为裸 UUID；`20260909_world_library_topics.py:23` 等迁移声明 `projects.id ON DELETE CASCADE`。主题同项目父子复合 FK 已存在，不能误报为全部无隔离约束。问题是 ORM 建表和迁移建表表达不同：某些测试可以在更弱的 schema 上通过，autogenerate 也可能建议删除迁移已有约束。

另一类增量发现是同项目强关联只受单列 FK 保护：`worldbuilding.py:97-108,218-228,285-295,367-377` 的生成模板修订、页面投影、页面工作稿和页面模板修订分别携带项目 ID 与父对象 ID，但没有把二者组合为同项目 FK。按所读 ORM/迁移定义，数据库不能阻止“项目 A 的子行指向项目 B 的父对象”；应用过滤可以保护正常入口，但不等于数据库具有此不变量。本次没有发现公开 API 绕过，也没有查询真实库验证是否已有异常行。页面正式 revision 已有同项目约束，不能把这一缺口推广到全部版本表。

此外 `backend/infrastructure/schema_comparison.py:74` 对 migration-owned 索引仅查名称；`alembic/env.py:133` 有意不比较 server default。现有 PG 测试已检查部分 FK、索引和 trigger，不能说数据库完全没有验证，但通用 `alembic check` 绿色仍不证明所有关键定义正确。Alembic 官方也要求人工审查自动生成结果，并明确列出自动检测限制。[Alembic 自动迁移说明](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)。

**方案：**

- 首批使资料库 ORM 表达与已部署迁移一致；若目标库已经有正确 FK，不为改 ORM 再写无意义 DDL。现场缺约束时另做增量修复迁移，先检查孤儿与跨项目引用，禁止静默删除冲突数据。
- 对上述四类同项目强关联补独立迁移方案：复用或补齐父表 `(novel_id,id)` 唯一键，增加子表复合 FK；先检查存量引用并明确 NULL 语义，页面独立工作稿的 `page_id=NULL` 必须继续合法。普通 `novel_id → projects.id` FK 只证明项目存在，不能替代此项。
- 扩展现有 schema 比较/PG 测试，只对正确性关键项校验定义与行为：同项目复合 FK、活动任务/成果唯一性、不可变 trigger、部分唯一索引谓词。为已被名称豁免的关键索引加反证，证明“同名但错误定义”不能过门禁；不逐字比较所有格式化 SQL。
- 给持久化引用分类：强身份/所有权关系用 FK/唯一键；历史归档、多态 TargetRef、可重建索引等弱引用保留服务层验证与对账，不全库强加硬 FK。UUID 表示差异、表数多和手写 novel_id 本身不是风险证据。

PostgreSQL 支持多列 FK；跨行约束应选 FK/UNIQUE 等机制，不能靠跨表 CHECK 模拟。同时 FK 不自动为引用侧生成索引，因此索引应根据查询/删除路径选择，而不是给每个 FK 机械再加索引。[PostgreSQL 17 约束文档](https://www.postgresql.org/docs/17/ddl-constraints.html)。

**验收：** 空库 upgrade、代表性旧库升级到 head、`alembic check`、直接违反关键约束的 SQL 反证、项目删除引用完整性；验证显式 ADR-0018 source/consumer 例外不被误杀。实际约束缺失情况以隔离副本和受控现场检查为准。

**回退：** 优先只改 ORM 与测试。新增约束采用显式增量 migration、存量诊断和验证窗口；回滚不应撤销已经保护真实数据的约束以迎合旧代码。涉及数据修复须留修改清单与备份，不能只写 `git revert`。

### A5 — 收敛业务所有权，而非泛化全部状态和存储

**确定的维护成本；安全语义应原样保留。** 对应 F2-3/4、D3a-1/2、D4-2/3、F1-3。

story/outline 有重复入队流程，多个模块重复 snapshot 客户端生命周期与 provider 前 checkpoint 操作，hash 序列化也有多种实现。重复会让一次恢复或凭证修复必须同步多个位置；但这些代码并非全部语义等价。

**方案：** 复用 `modules.project.facade` 现有 LLM 入口和 tasks facade，只收敛已证明相同的资源生命周期/事务检查；领域准备、采用、confirmation 重验仍归各 owner。API 内已有 service 可调用的编排移回 service，不增加一层无价值转发。

先建立 hash 输入/输出兼容样例，逐项区分排序、空值、Unicode、separators、default=str 和领域版本。相同算法可共用小函数，领域 hash 名称和版本仍保留；不得把不同指纹统一成新格式后让旧 confirmation、幂等键或审计记录整体失效。

**保留：** task 传输状态、导入阶段、作者资产状态是不同状态机；task meta 与领域 run 的 snapshot 落点也有不同恢复职责。不要统一为万能 Status、万能 repository、万能工作流表或全局事件总线。JSONB 适合有版本的 checkpoint/manifest；需要独立查询、唯一性、并发 owner 的字段才提升为列。`async_tasks.novel_id` 与 `rag_index_state.generation` 已是本地可复用先例。

目前 schema 比较有意把 ORM JSON 与 PG JSONB 视为等价（`schema_comparison.py:54-67`），这是兼容策略，不是已证实的数据错误。若某列依赖 JSONB 操作符/索引或必须冻结精确序列化行为，再按列补类型与查询验证；不要为了形式统一转换所有历史 JSON。

**验收/回退：** 固定旧输入输出字节比较，覆盖任务恢复时 provider 固定、Key 轮换、关闭资源、事务 fence、排除资产和 novel_id 不匹配。按 owner 小批替换；不变更持久化格式时可代码回退，任何格式变化另作迁移提案。

### A6 — 前端业务 DOM 与本地草稿生命周期明确归属

**确定的维护缺陷及局部清理缺口。** 对应 F3-4、D8a-1；不等于需要更换 Vue。

`frontend-console/app.js:227-270` 通过全局点击、`workspace:content-rendered` 和 innerHTML 把 smartDedup 按钮注入 Vue 挂载点；Vue 页面又在挂载/更新后派发事件。这使一个业务操作由 Vue 生命周期、app.js 和 manager 共同控制。该片段只渲染内部静态内容，本次没有发现动态 XSS 证据。

**方案：** smartDedup 的状态/取消和项目切换沿用现有 manager；展示与点击归 Vue 组件/composable。先迁移这条真实业务链并移除对应全局渲染接线，保留地图 viewport、编辑器等有真实用途的命令式适配。不要只搬目录，也不要以文件行数为阈值拆组件。

**本轮纠正原报告：** D8a-1 所称六个未清理前缀中，三个 `novel_outline_*_preview:` 已被 `accountStorage.js:6` 的 `novel_` 覆盖。纯内存调用实际清理函数确认：仅 `scene_runtime_draft:v1:`、`story-outline-editor-draft:`、`story-outline-preview-draft:` 留存。应修这三个，不重复登记已经覆盖的三个。未证明另一账户可经正常 UI 读到它们；已确认的是浏览器中的内容残留。

草稿清理与业务 DOM 改造分批交付。新 key 应落入现有账号清理规则，并验证切换账号/项目、账号失效、同账号刷新与离开保护。不能为设置缓存上限而驱逐唯一未保存副本；旧账号草稿的删除策略须沿用明确的退出/失效契约。

**验收：** World/Outline 中重复挂载、移动抽屉、切项目、任务恢复均只响应一次；组件卸载后监听可释放；三个真实遗漏键被清理，同账号草稿仍可恢复；服务端与本地保存失败时不出现“已保存”。

**回退：** DOM 小批迁移可代码回退；已删除的本地草稿无法靠 revert 恢复，因此实施/浏览器验收使用合成数据，不主动清理当前真实浏览器内容。

### A7 — 生产 Prompt 与评测样本隔离

**确定的功能缺陷；应先修，不等待架构重构。** 对应 D5a-1、D5a-2。

`backend/modules/imports/entity_extraction/scene_entity_bulk.py:56-78` 按 1–7 章设置特定抽取期望，`:416-423` 将《诡秘之主》对象名和内部评测名放入生产补抽 Prompt。这会影响其他作品的候选召回；持久化证据门禁仍应保留，不能据此宣称已确认污染所有真实资产。

**方案：** 删除作品名/章节集合特判，保留基于当前来源、已有对象和长期创作价值的通用规则。评测样本只在受控 fixture/eval 使用；废弃 reducer 的机械删除另批核实。先做 Prompt 契约和异质作品样例，再评估质量，不能靠提高某一本样本得分决定生产逻辑。

**验收：** 任意来源构造出的生产 Prompt 不包含外来作品实体或评测名；少量/大量 Scene、别名、低置信和来源缺失仍满足原规则。真实模型评估单列成本与质量证据，静态检查只证明隔离。

**回退：** 版本化保留评测结果和代码；发现质量回退时调整通用规则，不恢复语料污染。已有候选只做 workflow/source 可追溯审计，真实资产修复另经领域确认。

### A8 — 完整恢复范围包含对象资产

**已接受的设计取舍；需重新决策，不能当作现行发布规则违规。** 对应 F5 运维事实与 [ADR-0014](../../../docs/adr/0014-world-object-images-and-single-node-minio.md)。

`deploy/README.md:95-97` 明确 MinIO 单盘没有外部图片备份；`deploy/scripts/backup.sh:120` 的 restic 输入是 PostgreSQL dump 与校验文件。数据库恢复后可能恢复图片引用，却无法恢复丢失的图片。这对付费生成或用户上传的不可替代图像有直接价值影响。

**建议：** 若产品要承诺完整资产恢复，先定数据库与图片各自的 RPO/RTO、保留期、容量与外发授权；再复用现有对象接口、备份工具与恢复演练体系。设计同一恢复批次的 DB 引用清单、对象版本/内容摘要和删除边界；不假设两个独立定时备份天然一致。优先证明单机可恢复，再评估是否需要托管对象存储或多节点。

**验收：** 在隔离环境恢复正文、项目关系、地图图像和对象图片；校验引用存在、图像可解码、owner/novel_id 访问仍隔离，并测量实际恢复时长。模拟对象缺失与备份失败时必须报告不完整，不能只以 pg_restore 成功判定全恢复。

**回退/边界：** 当前仅建议，不创建外部服务、不上传数据。未来备份方案回退只能停止新计划，不能擅自销毁唯一备份；保留加密、访问控制和保留策略。容量与费用没有测量，不给虚构报价。

### A9 — 性能优化以真实资源竞争为触发条件

**查询模式已确认，收益与容量上限待测。** 对应 D6a-2、D6b-4、D2a-8、D7-7、D8b-9。

例如 `backend/modules/evidence/indexing/index_state.py:786-836` 在 summary/freshness 中加载 ORM 行后统计；报告还记录候选两两比较、逐项查询和大列表加载。它们可成为瓶颈，但现有材料没有代表性数据集、p95/p99 或数据库执行计划，不能据此建议 Redis、Elasticsearch、独立向量库或分片。

**方案：** 先修复/复用现有性能探针，在合成专用库对导入、上下文检索和编辑器并发读取建立基线。记录 SQL 数量、返回行数、事务持续时间、内存、连接等待、任务排队时间及 provider 时间；将本地数据库耗时与模型网络耗时分开。

若证实超预算，依次采用数据库 count/聚合与集合操作、批量获取、稳定分页、避免无效重算；去掉冗余索引前检查谓词、唯一性、排序与真实使用。仅当这些改动后仍有明确资源瓶颈，才提新存储/调度方案及总运维成本。不把全量缓存或预计算当默认答案。

**验收/回退：** 使用固定数据集/hash、并发条件、冷暖状态和同硬件比较；报告业务结果一致性、尾延迟、内存及查询数。事前定可接受阈值，未达改善或回归则撤回查询改动。索引删除与重建有独立锁/时间窗口，不等于即时 git 回退。
