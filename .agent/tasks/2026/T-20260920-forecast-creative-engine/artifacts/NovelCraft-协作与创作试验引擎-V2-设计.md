# NovelCraft：自适应协作与创作试验引擎 V2

**设计日期：2026-09-20｜核对基线：`main@a7173869ca832537cf476e0a05e97f1f5275012a`**

**交付状态：架构与实施设计，未修改仓库、未执行迁移、未调用付费模型、未部署。**

## 0. 核心决策

不再把审稿、世界观压力测试、跨章修订、Scene 排演、RP、盲读、研究、导入会诊当作八套独立 Agent 团队。将它们组织成一个目标驱动的闭环：

> 作者目标／创作变化 → 建立问题与竞争解释 → 按需调查 → 在隔离工作区试改／推演 → 从人物与读者视角检验 → 比较方案 → 受控合并 → 追踪实际反馈。

底层共享任务调度、证据依赖、试验工作区、预算、版本和恢复；语义上保留三种协议：调查协议、反事实试验协议、角色／读者观察协议。**共用运行能力，不共用无差别全知上下文。**

主要突破：从固定角色转为按问题组队；从每份资料确认转为授权范围内动态检索；从只产生口头建议转为可撤销分支中的自主试改；从整轮失败转为依赖级重算；从各模块独立提交转为受支持资源的同库原子合并。

保留：项目与账户隔离、来源可回读、实际费用控制、作者对正式作品的决定权、RP 选中分支、角色／读者信息边界。开放自治程度不等于取消这些保障。

## 1. 最新实现给出的起点与限制

### 1.1 已核实的实现

当前 `teams/contracts.py` 注册六种助手蓝图；`teams/runner.py` 为成员建立独立 session、模型历史和工具集合，按角色固定建立工作项，再进入领域处理与汇总。`collaboration.py` 提供单宿主 DAG 调度、输出哈希与 checkpoint。`story/simulation.py` 提供行动意图与结果裁决，`interaction/ensemble.py` 将其接入 RP。[S1–S5]

ADR-0027 明确这是实验性功能，质量准入关闭。真实模型记录未完成留出集与人工盲评，部分失败受到实验夹具输出上限影响，不能据此证明团队优于单 Agent，也不能反过来证明团队无效。[S6–S7]

### 1.2 不继续沿用的限制

| 现状／此前折中 | V2 决策 | 理由 |
|---|---|---|
| 按蓝图固定三名调查员 | 蓝图退化为任务配方；Planner 可组合、替换、追加专项工作 | 不同问题需要的信息分解不同 |
| 主编最后汇总，不再查证 | 主编可提出可校验的补查、分支试验、终止或询问作者 | 调查结果应该改变后续行动 |
| 复杂状态挤进 1 MiB checkpoint | 新协议使用关系表，旧协议保留旧载体 | 动态依赖、多个工作区及恢复不适合整份 JSON 重写 |
| 资料确认同时承担阅读授权和快照 | 拆为授权 Grant、基线 Baseline、单项输入 Manifest | 允许广泛查证，不允许混用不同版本 |
| AI 只能提案、每项修改等作者 | 工作区内可自主写入修订；合并当前稿按授权策略控制 | 让系统能够验证“改完之后怎样” |
| 每个步骤机械套完整导演／审查链 | 保留每次工具的确定性权限检查，语义审查集中在高风险产物边界 | 避免重复审查同一内容与无限返修 |
| 来源变更使全轮作废 | 精确读集＋范围依赖失效，支持局部重算 | 保留仍然有效的昂贵成果 |
| 跨模块只能部分提交 | 对支持的资源提供同库原子 ChangeSet 合并 | 跨章联动不应出现规则已改、正文未改的中间态 |

这不是为了重构而更换技术栈。继续使用现有 PostgreSQL、任务 worker、Project LLM Gateway、PydanticAI、Vue。官方 PydanticAI 支持委派和图式控制流；不需要额外叠加一套 Agent SDK。[S8]

## 2. 功能整合：一个底座、三种协议

| 协议 | 输入与操作 | 产物 | 原功能如何使用 |
|---|---|---|---|
| 调查 | 问题、已知证据、授权范围；检索、比对、反证、消歧 | 有出处的判断、争议、遗漏、待验证假设 | 审稿、研究、导入会诊、影响分析 |
| 反事实试验 | 基线、干预、约束、工作区；改规则／剧情／正文，重跑受影响检查 | 分支差异、反例、修复候选、检验回执 | 世界压力测试、跨章修订、情节规划 |
| 观察／演绎 | 主体、时间点、可观察事件；形成行动、认知、预期 | 角色反应、读者认知、已裁决事件 | Scene、RP、伏笔与反转测试 |

跨章修订不是另一个独立引擎，而是“调查 → 分支试改 → 人物／读者检验 → 合并”。世界规则压力测试使用同一个反事实协议，只是检验目标换成规则不变量。RP 使用同一演绎内核，但状态提交给 Interaction，绝不进入作者正史。

### 2.1 端到端验收故事（合成示例）

作者说：“主角突然相信旧敌有点怪，但我还没想好怎么改。不要提前揭露旧敌身份，也不要改本章结局。”

系统先保留三个竞争解释：正文缺少获知事件；主角其实是在冒险合作，表达成了信任；这是有意欺骗，当前表现可以成立。推断不能自动变成作者计划。

调查成员分别寻找动机与信息来源，反证成员检查是否存在已足够的前文。系统保留原文对照，并建立两种试验：补足获知事件；不补消息、将对白和行动改成有限合作。两种方案分别排演人物反应，并让截止本章的读者代理检查是否泄密。

最终展示每个方案的实际修改、保留项、代价、证据、测试结果和未定项。作者选择后，正文与相关 Scene 计划在同一支持范围的事务中合并。后续出现相关新内容时，只让受影响判断重新待查。

**验收不是“多个 Agent 都说合理”，而是系统交付了可检查的分支、差异与验证结果。**

## 3. 核心对象与权威

### 3.1 Case：持续的问题，不是永久运行的 Agent

Case 保存目标、明确要求、推测偏好、竞争解释、未决问题与成果引用。它可以跨多次运行继续，但没有常驻模型进程。一次模型执行为 Run，预算、协议和输入范围均在该 Run 固定。

作者明确要求和系统推测必须分开。只因作者没有拒绝，不得把“猜测这是伏笔”升级为正式伏笔计划。Case 的“已处理”不等于领域问题已经解决；需引用领域处置结果。

### 3.2 Evidence graph：任务级依赖，不是第二套知识图谱

节点是实际来源、可分享判断、假设、方案、测试和领域回执；边表达支持、反证、依赖与取代。原文、World 对象、Canon 和角色档案仍在原领域。本图只保存引用、必要的受限摘录与解释。

重复来源只计一次。不同模型重复表达同一个判断不能增加独立证据。角色听到某人声称 P，只能形成“听到 P 的说法”，不等于 P 为真。

### 3.3 Workspace：基线＋覆盖层

Workspace 是整个创作任务的隔离试验分支。它可以覆盖多个领域资源，但不复制整本小说，不提供第二个正式事实入口。

```text
workspace view(resource)
  = 本工作区的覆盖版本（包括显式删除标记）
  或 父工作区的覆盖版本
  或 冻结基线中的精确版本
```

不存在的基线版本不能悄悄回退到当前主稿。删除覆盖不能从基线复活。所有生成、检索、角色投影和审查都必须显式带 workspace revision。

### 3.4 Scenario：同一基线上的可比较试验

Scenario 记录基线、干预、保留条件、主体、观察边界、停止条件、可执行检查和随机种子（仅对使用随机数的裁决）。它不是自由讨论记录。

一份规则修改、一次人物排演、一个读者盲读点均可成为 Scenario。无需先实现通用社会仿真平台：首版仅支持具体事件和少量场景的试验。

### 3.5 ChangeSet：封存的工作区版本

ChangeSet 不另建可任意变动的候选清单，而是指向已封存的 workspace revision，包含写集、读集、范围查询依赖、检查回执及拟执行领域操作。任何编辑都产生新版本并使相关旧回执失效。

作者确认绑定该版本的 digest，而不是确认“采用最新方案”。

## 4. 自主协作控制

### 4.1 Agent 是可重建执行者，产物才长期保存

不为每个小说实体创建永久 Agent。AgentSpec 由任务能力、领域专长、立场／主体、工具集合、知识投影、输出类型和模型配置组成。它可以动态组合，但权限来自服务端 Grant，不来自模型输出。

新蓝图采用版本化 Recipe，而不是修改多处 `Literal` 与分支判断。Recipe 可以定义初始问题、必需检查、可用能力与结果契约；不承担权限授权。旧版本保留供已开始的运行恢复。

### 4.2 Planner 的动作集合

Planner 可提出：调查某问题、要求反证、申请补充检索、创建／修改工作区、运行某情境、检验候选、比较方案、询问作者、停止。服务端验证任务类型、依赖、读取与输出权限、预算、上下文容量，再加入工作图。

成员可以提交补查建议，但不能递归启动无限子团队。先由控制器合并重复任务，再决定执行。工具内部自主检索不要求作者逐项批准。

Planner 默认只读取待决问题索引、新产物摘要、当前方案差异和剩余预算，按需打开证据，不累积所有成员的完整历史。控制器可以选择只运行一个 Agent；没有独立问题就不为展示“团队”额外启动成员。

### 4.3 动态图，不是自由群聊

工作项至少包含：

```text
id, case_id, run_id, logical_key, generation
capability_id, agent_spec_revision, question
input_artifact_refs, blocking_dependencies, advisory_refs
workspace_revision, scope_epoch, expected_output_type
budget_allocation_id, state, attempt, output_ref
```

每次重规划提交 GraphDelta；在短事务内验证依赖和 `expected_plan_revision`。已运行项的输入不可原地改写，须创建新 generation；旧项结果可留历史但不得完成新项的依赖。

循环通过“新工作项代次”表达，单次可执行依赖图保持无环。区分 `all_succeeded` 和 `all_terminal`：依赖产物的生成任务通常使用前者；汇总可用后者，从而明确输出部分完成。

### 4.4 调度正确性

当前调度器的失败传播只扫描一遍，再在没有 ready 项时退出。V2 必须将最终失败向阻塞后继传播到稳定状态，不能依赖列表顺序。[S3]

可重试失败保留等待重试语义，不提前永久阻塞所有后继。无 ready、无在途调用、仍有无法解释的 pending 时，报告调度不变量失败，而不是伪造完成。汇总的完成状态与领域检查通过状态分开。

成功产物先通过结构、来源、权限检查并持久化，再发布给依赖任务。取消、旧 lease、旧 generation 的晚到结果不能写当前状态。

### 4.5 如何避免无休止讨论

先独立调查，再围绕具体分歧交叉质疑。下一轮必须说明将新增什么来源、反例、试验或修订；重复措辞不算进展。没有可执行补查、方案已满足必要目标或预算触顶时，交付结果与未知项，不强求所有成员同意。

人数按任务需要决定：简单问题单 Agent；独立信息方向多成员；强耦合修改由一个整合者保持一致，审查独立进行。并发上限属于服务容量策略，不是永远写死在业务逻辑中的“三个人”。首版仍可从三路并发起步，负载数据再决定调整。

## 5. 资料授权、版本与主体知识

### 5.1 拆开三个概念

**Grant**：允许读哪些作品范围、联网渠道、可用工具、预算、截止时间、允许写入哪个工作区或工作稿。

**Baseline**：本次试验所依据的不可变资源版本。工作稿目前可原地变动时，必须在首次使用时物化不可变版本；短数据库快照不能代替长模型运行中的版本化数据。

**Manifest**：某个实际调用精确读取了什么，包含资源版本、范围 hash、workspace revision 和主体视角。

授权可以是“本项目全部正文与设定，但不联网”，系统按需检索，不再逐份确认。授权外扩张仍由作者控制。授权范围内的新检索不改变已有步骤的输入，新增来源加入新的 Manifest。

### 5.2 主体投影

至少区分 author、character(actor_id)、reader(cutoff)、environment。所有上下文通道都投影，包括任务描述、标题、同伴产物、错误提示、审查反馈、记忆、检索结果和前端 API。

全知审查员不能把包含秘密的原始理由发给角色。可发回不泄密的问题定位和“仅根据已提供资料重新判断”的要求；需要新信息时重新走角色可见来源编译，而不是让全知摘要自行去敏。

首版对未知来源依赖的产物采用保守限制继承。后续可做字段／claim 级切片，但必须重新从接收方可见来源构建，而非只改标签。

**限制声明：**来源过滤不能清除模型预训练中已有的作品知识。盲读者质量测试优先用未知合成故事或作者原创，且检查模型是否使用了没有提供的证据。

### 5.3 Claim 的最低协议

```text
kind = source_statement | interpretation | hypothesis | proposal | simulated_event
subject_view, world_time, evidence_refs, counterevidence_refs
assumptions, support_level, uncertainty
workspace_revision, input_fingerprint, output_hash
visibility_dependencies, supersedes, domain_result_ref?
```

创作提案允许没有原文证据，但需标明新设计与所依赖条件。对“前文没有交代”的判断，必须带实际搜索覆盖，不得因为一次 Top-K 未命中就宣称全书缺失。文学偏好不升级为事实错误。

## 6. 工作区与增量重算

### 6.1 最小实现

先为 Writing draft、Story Scene／信息计划、World Bible draft 提供覆盖适配器。其余资源明确返回暂不支持试改，不假装整库已经具备分支能力。

同一个 Workspace 内可以自主创建多个修订。候选 ID 用服务端预分配 UUID，引用对象不能仅靠名称定位。整个工作区不可进入正式 RAG 索引。

### 6.2 检索不混版

试验检索读取“基线索引排除被覆盖资源＋工作区新增或修改资源”。小型覆盖层先做精确全文／关键词读取，必要时新增带 workspace revision 的临时向量，不必为每个试验重建全库索引。

每次回读仍验证源 hash 和范围。尚未完成索引的覆盖文本不能被当成不存在；不得让旧索引内容以新版本身份返回。

### 6.3 依赖要覆盖不存在的记录

不只记录读到的资源，还记录范围查询依赖。例如“第 1–20 章所有给 A 传递信息的事件”会受到新增事件影响，即使原读集中的行一个都没改。

为此记录 query/predicate fingerprint、范围、结果版本集合和对应内容 epoch。合并或重新使用结论前重新验证。第一版无法精确追踪的检索可用较粗的章节／项目 epoch 使结论保守失效，不能伪装已具备精细失效。

### 6.4 来源变化后的行为

资源变化 → 标出直接依赖产物过期 → 传播到后继 → 保留其他成果。工作区基线不自动跟随主稿；需要继续时执行显式 rebase，计算 base／current／proposed 三方差异，生成新工作区修订。

用户在编辑时，旧建议可以保留，但采用必须重验当前稿和未保存输入。不能用上一轮确认覆盖本轮输入。

## 7. 受控合并：真正闭合跨域修改

### 7.1 事务边界

本设计选择在当前同一 PostgreSQL 数据库内，实现支持资源的原子合并，而不是立即引入分布式事务。PostgreSQL 的快照与串行化机制可以支持事务内的一致性，但不能替代业务版本检查，也不能让外部模型调用参与事务。[S9]

所有模型生成、来源回读与语义审查在事务外完成。各领域新增明确的 prepare/validate/apply-in-uow 接口；apply 不自行 commit，不触发网络调用。

### 7.2 合并步骤

1. 校验作者／受委托策略、精确 workspace revision、所有必要回执和操作权限。
2. 开启短事务，先查询幂等 receipt，再按全仓统一锁序取得项目／资源保护。
3. 验证写集、读集与范围依赖；检查工作稿、World、Scene 等基线是否变化。
4. 用预分配 ID 和同一 UoW 执行各领域操作，任何失败全部回滚。
5. 同事务写 merge receipt、必要的失效标记和派生更新 outbox。
6. 提交后执行索引／投影；消费者按合并 ID 与源版本幂等，过时任务不能覆盖新索引。

只给新 merge 路径加一把锁不够。受支持资源的旧写入口也必须参与相同版本／锁序契约，或在最终事务使用可靠的冲突检测并重试全部校验。跨行约束由约束与统一事务维护，不能只检查每行版本。

### 7.3 大范围修改

首版支持有明确规模上限的合并。超过上限时，只能按依赖图拆成彼此独立的原子组；存在跨组不变量则拒绝伪装全量原子提交，转为需要后续实现的 staged revisions＋统一可见提交屏障。

不要在尚未升级所有读取路径时，仅增加一个“release_id”就宣称全项目快照原子切换。

### 7.4 自主程度

默认允许 Grant 范围内读取与工作区自主写入。可选委托策略允许把符合条件的小改动合并到工作稿，例如明确范围内的格式或用词修订；有 diff、回执、撤销与来源冲突保护。

Canon 发布、正式正文发布、删除／合并实体等仍走对应权限与具体操作流程。运行时 worker 不是默认作者授权者。

回退是基于当前版本的新反向 ChangeSet，保留历史；若之后已有人工编辑，需三方合并，不能强行覆盖恢复。

## 8. 角色、读者与世界规则的共用试验内核

### 8.1 新的回合顺序

```text
本轮作者／玩家输入
→ 区分场内发言、行动意图、旁白事实、场外要求
→ 验证其权限与可执行性
→ 形成可观察事件或待裁决行动
→ 为每个角色生成独立 ObservationPacket
→ 角色提出 ActionIntent
→ 合并同一时点的行动，执行规则与环境裁决
→ 形成 ResolutionBatch：事件＋状态差量＋观察者
→ 更新角色信念／世界状态
→ 统一叙述 → 检查 → 原子提交本回合
```

当前 RP 的本轮玩家输入主要进入全局 authority，角色意图输入则是冻结资料与旧观察；V2 将本轮刺激显式前置到角色观察中。[S4–S5]

“我说 X”可以直接形成发言事件；“我一拳打倒对方”是行动意图，不能因为由玩家提出就直接变成成功结果。动作的感知起点可发生在同时性裁决前，最终结果不能提前告知其他角色。

### 8.2 Observer 不等于 Agent

角色集合是本轮需要调用模型的主体；观察者集合包括玩家、在场但不需独立模型的配角，以及符合规则的其他观察主体。私语可以发给玩家，而不必把玩家加入自动行动 Agent。

出场依据来自场景位置与状态，不仅是正文中提及姓名。名字被讨论不等于该人物在场；代词或别名不应使在场人物被遗漏。首版先使用确认的场景参与者，加受控的候选增减，而不是全自动演员搜索。

### 8.3 事件不能等同于意图原文

当前 resolver 主要从意图文本与 succeeded/failed/uncertain 生成事件。V2 增加可校验的实际发生事件与状态效果；失败的“开门”不能被当成门已经打开，失败的发言也不能自然成为所有人的既有知识。[S4]

```text
ResolutionBatch:
  base_state_revision, intents_hash, rule_revision
  events[{event_type, actor, targets, occurred_at, observation_policy}]
  state_patches[{resource_id, expected_revision, operation, value}]
  unresolved_outcomes, assumptions, seed?, evidence_refs
```

确定资源／数量／时间约束用代码验证；语言行为、社会反应由模型提出裁决候选，再通过 schema、规则和来源检查。缺少规则时保留条件式结果或创建候选分支，不能把模型裁决称为客观证明。

### 8.4 状态必须跨回合保留

统一保存位置、已发生事件、资源持有、角色观察、角色信念和未知项的版本化差量。当前 RP 初始化 `resource_holders` 为空的逻辑不能承担完整跨回合资源状态；V2 从选中祖先状态恢复。[S5]

角色状态只能继承选中路径，分支切换后不能从另一条线复活秘密、资源或人物离场状态。已有长旅程缺乏角色观察时，以只读、受范围限制的重建任务补齐；无法证明的保持未知。

### 8.5 叙述与排演的关系

叙述者统一文风，可以自由组织已裁决事件的措辞、节奏和不影响事实的表现细节；新增因果结果、人物知识或资源变化必须回到事件提案，不得在正文里绕过裁决。

排演 replay 重放已记录的事件与状态差量，不重新调用模型，因此不会把“同一个 seed”误当作保证 LLM 完全确定的依据。重新推演是新的试验，应保存独立结果。

RP 默认继续采用审查通过后释放正文。后续可研究按已批准的事件段释放稳定前缀，但不能把尚会返修的文本伪装成正式流式结果。已经释放的前缀不可被后台悄悄改写。

### 8.6 三类检查如何共用

世界规则试验：相同场景与行为，在不同规则工作区运行，记录反例与适用条件。世界规则发生变化不意味着所有人物自动知道新规则；“规则已变”和“角色已获知规则”分别作为干预，避免把全知策略误当自然演化。

人物／剧情试验：相同目标，不同信息传递或动机前提，比较角色行动是否成立。

盲读试验：按正文展示顺序更新读者认知，在揭示前冻结问题与猜测；检查是“当前资料是否支持”，不是“模型能否猜中作者答案”。

首版不强制完整心理模型、宏观社会仿真或任意可执行规则语言。这些需求可以通过相同 Scenario 接口后续增量扩展。

## 9. 预测式副驾驶：复用 Case，不另起推荐系统

正文保存、Scene 切换、规则修改只发送版本化变化事件。先用结构依赖与轻量检索定位受影响 Case，稳定后才决定是否值得调用一个 Agent，复杂且重要的问题再升级试验团队。

每条展示项必须属于：已核实问题、条件式影响预测、可选创意。没有作者计划时只保存“可能需要回应的开放问题”，不自动认定伏笔、预定揭示或改大纲。

排序优先考虑与当前决策的距离、潜在损失、证据强度、可操作性与打扰成本。先用可解释分级规则，不让模型凭空生成精确概率。默认只展示少量最重要事项，其他保留在可搜索队列，数字上限属于可调整产品设置。

后台运行由持久 Grant、项目日额度、排除项和暂停策略驱动。用户忽略提醒只改变展示，不改变事实判断；新增实质证据后才重新提示。用户放弃工作区不等于拒绝整个人物／主题方向。

缓存可复用当前工作区与检验结果，key 至少包含来源版本、主体、目标版本、排除项、规则和模型策略。不能为了缓存命中共享秘密，也不能把“上次通过”当作新稿的通过。

## 10. 风险分层审查与成本控制

### 10.1 三层检查

第一层：每次执行都做权限、项目、版本、schema、预算、lease 与工具约束。这些不交给模型裁量。

第二层：正式的用户可见判断或重要候选，运行一次与实际任务契约匹配的语义检查。对明确的事实矛盾、角色知识、作者硬约束、引文支撑进行定向检查。

第三层：合并／读者释放前检查精确候选版本和受影响不变量；高风险分歧才用独立反证者或更强的已授权模型。

新提案、角色误解、有意歧义、文学选择不因为“不在原文”就被一概阻断。反之，多名模型同意不能解除硬权限或完整性问题。

### 10.2 预算策略

Case Grant 提供跨 Run 的累计上限，Run Envelope 提供本次执行上限，成员 Allocation 只是分配视图。重规划、分支、取消恢复和新子任务不能重置累计消费。

预留最终审查和交付额度；在分支价值不明确时先做便宜检验，不马上生成整章。每个工作项完成后重新评估下一步，而不是一定把所有成员额度花完。

价格已知时按模型与价格版本记录货币估算；价格或用量未知时明确未知，并用请求／token 保守限制，不能宣称已实现精确金额硬封顶。provider 已接收但本地丢回执的请求不能算零，也不能承诺外部调用恰好一次。

V2 的 root capability 唯一，但允许服务端签发的显式能力委派链；审稿、试验、修订和最终审查保留各自 capability policy，不通过 `infrastructure.*` 命名逃避登记。委派链同时约束预算、工具与输出权限。

## 11. 工程落点与数据迁移

### 11.1 代码职责（以下为新设计路径）

```text
backend/modules/collaboration/
  api.py, facade.py, contracts.py
  cases.py                 # 作者目标、竞争解释、开放问题
  planner.py               # 有界动作选择与任务配方
  recipes.py               # 可版本化的能力组合，不授权权限
  artifacts.py             # 来源依赖与产物生命周期
  workspaces.py            # 跨域试验覆盖层
  merge.py                 # prepare/validate/apply UoW 编排
  domain_ports.py          # World/Story/Writing/Interaction 接口
  models.py, repositories.py

backend/infrastructure/llm/collaboration_v2/
  scheduler.py, state.py, persistence.py
  # 无小说业务判断；复用 Gateway、Agent runtime 和预算

backend/modules/evidence/
  # 增加 workspace-aware 读取、主体投影、Manifest 与依赖失效
backend/modules/story/
  # 实现事件/意图/观察/裁决；角色与读者语义仍归领域
backend/modules/interaction/
  # attempt、分支、场内刺激、角色状态和正文一致提交
```

Assistant 成为入口与结果展示，不继续承载所有业务分支。跨模块依赖仍通过 facade／显式 port，但不再禁止设置有实际职责的跨域协调服务。

### 11.2 七张核心表，按批次引入

| 表 | 核心字段／职责 |
|---|---|
| `collaboration_cases` | novel、目标与版本、明确约束、推测意图、Grant 引用、长期状态 |
| `collaboration_runs` | case、origin、协议与策略版本、plan revision、scope epoch、root envelope 引用、状态 |
| `collaboration_work_items` | run、logical key/generation、依赖、能力、输入指纹、状态、attempt、产物引用 |
| `collaboration_artifacts` | 类型化提案与调查产物、来源、主体、workspace revision、hash、领域回执引用 |
| `creative_workspaces` | project、父 workspace、冻结基线、当前覆盖修订与状态 |
| `creative_workspace_revisions` | 不可变 patch manifest、资源版本、读／写／范围依赖、测试引用 |
| `creative_merge_receipts` | 精确候选、确认／委托来源、幂等键、目标旧／新版本与结果 |

这些表记录协作、试验与回执，不成为正文、World 或 RP 的第二份正式权威。域内实际修订复用原表；暂未采用的覆盖资源只在 workspace-aware 读取中出现。

如仓库已有可复用 outbox，沿用；否则原子合并阶段新增专用 `domain_outbox`，与 merge receipt 同事务写入。不要在没有核对前假设已有 outbox。

所有关联包含 `novel_id`，以复合外键禁止跨项目指针；逻辑工作项 `(run_id, logical_key, generation)` 唯一，合并幂等键绑定规范化请求指纹。依赖数组在 run 锁与 plan CAS 内验证，不能只依赖模型输出合法。

### 11.3 运行权威唯一

新协议的执行状态由 CollaborationRun 与既有 task lease 管理；AssistantRun 仅保留关联和兼容投影，不再独立驱动一份同义状态机。RP attempt 仍是故事生成的领域权威，关联一次执行，根预算复用其稳定身份，不形成独立完整额度。

精确映射在迁移契约中固定：任务重排可以更换执行载体，不能更换逻辑 run 或重置额度。公开读接口从权威状态派生，禁止双写两份进度。

### 11.4 接口建议

```text
POST /api/collaboration/cases                  # 创建目标/问题
POST /api/collaboration/cases/{id}/runs        # 在 Grant 内执行
GET  /api/collaboration/runs/{id}              # 结果、阶段、覆盖与可用动作
POST /api/collaboration/runs/{id}/stop         # 取消与费用未知处理
POST /api/collaboration/workspaces/{id}/fork
GET  /api/collaboration/workspaces/{id}/diff
POST /api/collaboration/workspaces/{id}/test
POST /api/collaboration/workspaces/{id}/seal
POST /api/collaboration/workspaces/{id}/merge  # 精确 digest、幂等、权限
```

没有无约束的“执行 Agent 代码”接口。API 的 owner 来自当前 principal。条件不满足返回类型化冲突、未支持资源、需要新授权或需要重算，不统一抛 500。

### 11.5 兼容与切换

V1 蓝图、快照、恢复逻辑保持原样，新运行显式选择 V2。旧建议不能自动得到 V2 的更宽授权；旧已采用资产不回写。

V2 使用关系表后不同时维护旧 JSON 权威；旧 API 只做投影。功能关闭停止新运行，紧急撤销停止在途请求；历史工作区与回执保留。

新核心上线并有恢复证据后才清理 V1 适配，不将整库迁移作为第一个功能的前置条件。

## 12. 用户体验

作者从当前页面发起目标，不需要知道哪个 Agent 在工作。默认界面依次呈现：目标与保留项；已查清与仍未定；少量候选方案；修改对照；验证依据；采用或保留原文。

可以随时补充“不要改这个角色的底线”，系统新增目标版本，保留不受影响成果并重算关联部分。长任务退出后保留工作区与进度。停止后不再创建后继，已发生用量与已保存结果仍可查看。

常用操作是“继续查清”“试另一种改法”“看人物反应”“保留原文”，不是“启动七个专家”。默认不展示原始 Prompt、内部角色消息或供应商思考。

## 13. 分批实施与验收

| 批次 | 交付 | 必须验证 |
|---|---|---|
| P0：根因与契约 | 修调度失败传播；明确本轮玩家刺激；V2 Grant/Manifest/Artifact/领域 port | 任意依赖输入顺序；玩家发言/行动/场外指令不混淆；旧协议仍可恢复 |
| P1：自适应调查 | Case、Planner、版本化工作项、定向反证、领域报告 | 不只固定三路；真实证据驱动追加；不扩权；预算/取消/故障可恢复 |
| P2：试改闭环 | 三类资源 Workspace；两种修法与原文对照；精确检查；小规模原子 merge | 无候选污染；无混版；并发作者编辑保护；故障后全有或全无 |
| P3：共用试验内核 | Observation、ResolutionBatch、状态差量；Scene 与读者；World 场景重测 | 意图不等于事件；秘密/私语/资源跨回合正确；盲读无后见资料 |
| P4：RP 与主动副驾驶 | attempt 接入；分支状态；变化触发 Case；分级授权与提醒 | 新输入实际影响角色；兄弟分支不串；默认不骚扰、不越额度 |
| P5：扩展与质量发布 | 研究/导入配方、自定义 Recipe、可选多模型、性能治理与灰度 | 配方不授予新权限；模型/数据外发正确；保留旧回执和回退 |

**首个完整交付范围：P0–P2。** 不是“先写通用平台”，而是让前面的合成故事完整走通：查因 → 两种试改 → 检验 → 一次采用。P1 先形成独立可用能力，P2 再闭合自主改稿。

P3 的 Scene/读者能力成熟后才进入 RP；世界规则和跨章修订可以复用 P2/P3 的核心，不再各自建设存储与预算。

## 14. 评测设计

### 14.1 区分四个贡献

A：当前固定团队；B：更强的单 Agent，使用同样的工具和工作区；C：自适应团队；D：C 关闭工作区试改，仅做口头讨论。

比较 B/C 判断多 Agent 的真实增量；比较 C/D 判断收益是否主要来自试改与验证。B 必须同样能检索、修改工作区和运行检查，否则对比不公平。

固定模型和有效参数，对照资料权限、任务难度与费用口径。相同请求上限不等于同成本；报告实际 token、工具、复核、修复、缓存、未知用量和端到端耗时，必要时比较成本—质量前沿。

### 14.2 样本与指标

先构造未知合成故事和受授权原创资料，按故事族分开发与留出；不能把同一套路不同名字当独立留出。包含故意留白、不可靠叙述、角色错误信念、来源不足、规则边界、跨章后果与资源冲突。

主要业务结果：是否修好原问题、是否引入新严重问题、作者硬约束是否保留、引用是否语义支持、作者需要多少操作、可撤销性与成本。风格偏好与真实读者体验采用人工盲评，模型评分只作辅助。[S10]

仓库现有受 8192 输出上限影响的探索不能直接复用为 V2 效果证据。按实际模型能力拆分输出、设置合理思考与最终输出预算，并记录截断，不用更大上限掩盖循环失控。[S7]

### 14.3 硬测试矩阵

- DAG 输入顺序、失败传播、可重试与最终失败、汇总的 all-terminal、循环拒绝。
- 多成员争抢最后额度；checkpoint 失败前不请求；未知费用不归零；子运行不刷额度。
- 旧 lease／旧 generation 晚到不能完成新节点；取消覆盖所有后继。
- 全知任务标题、摘要、审查错误和缓存不能向角色／读者泄密。
- workspace 删除覆盖不复活；新文本索引未就绪不当不存在；版本错配必拒绝。
- 在读集之外新增一条相关事实，范围依赖能使旧结论失效。
- 原子 merge 在每个领域写入点故障注入，数据库无部分提交；重复确认只产生一份结果。
- 修改期间作者继续输入，不覆盖未保存稿；revert 也检查之后的人工改动。
- 玩家不属于 Agent 仍能被私语；提及人物不代表在场；失败行动不生成成功事件。
- RP 切分支不继承另一线资源、认知或隐藏消息；正文与状态同事务提交。

测试集未发现越界不能证明数学上的永不越界；但任何规定硬测试失败都阻止对应功能上线。

### 14.4 收益不足时的处置

没有证据表明多 Agent 比单 Agent 更划算时，对该类任务选择单 Agent＋同一工作区与验证能力。系统的长期价值是可靠的创作试验闭环，而不是保持固定 Agent 数量。

## 15. 必须避免的过度设计

暂不增加第二数据库、通用消息总线、Neo4j、每人物常驻进程、任意代码工具市场或分布式自治群。不是这些技术永远无用，而是它们不解决首个创作闭环的主要瓶颈。

暂不声称形式证明、真实读者预测、自动全书一致、精确成本保证或 provider 恰好一次。每一项都需要对应数据、接口能力和验收证据。

## 16. 结论

V2 的重点不是把当前六个蓝图改成更多角色，而是让系统能在作者给出的目标内自主完成：**调查原因、保留竞争解释、实际试改、检验后果、比较版本、可靠采用。**

最应该突破的是“固定流程＋静态资料＋只能口头提案”；最应该保留的是“来源、主体、版本、费用与作者选择”。这些边界可以成为自治能力的支撑，而不是逐步打断作者的流程负担。
