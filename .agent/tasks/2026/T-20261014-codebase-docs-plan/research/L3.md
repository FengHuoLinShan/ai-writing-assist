## 结论

Evolution 是对已写正文做来源绑定的逐 Scene 理解与候选提案流程，不是世界模拟器，也不直接把模型输出变成正史。正常路径先经 Writing / Story 来源与 Scene 结构重验，再形成带原文区间的观察和确定性身份解析；世界抽取结果需独立审查，通过后作为 World 候选与 Scene 回执在一个短事务提交。作者随后通过 World 原有采用入口显式采纳；入口会重新验证 Evolution 回执、最新 Scene 结果和当前 Writing 来源。

失败恢复同样以冻结结果和来源证明为中心：可恢复的 worker 错误保存恢复标志，恢复重用已冻结输入/输出而不重新请求模型；领域提交若报错，事务回滚但冻结结果可留存；回执已提交但响应丢失时，重放直接返回旧回执。来源、owner epoch、父回执、身份或独立审核不匹配时失败关闭。未知费用不重发，失效不会自行发起付费重算。

当前材料总体已记录上述关键边界。可以做的最小文档刷新主要是精确化和补齐：在 World 正典说明中直接列出五个 formal-disabled 家族；在 Map 图片存储说明中补全对象图片桶、总配额、单盘和无外部备份边界；Evolution P4 应把 Story 每次读取重判的 world_knowledge，与失效回执中的两个明确 unsupported consumer 分开叙述。无需新增长篇组件文档，可在 Evolution 文档增加一张受控候选到作者采用的时序图。

## 正常执行链

1. 作者侧入口位于 /api/evolution。GET 走 active-project 检查；写操作走项目独占门禁。公开接口包括 panorama / ledger、reading 状态、预览、启动、恢复、proposals、独立 World 补审和类别补扫。范围请求显式区分 bootstrap、append、continue、revise、scoped_recompute；scoped_recompute 需一个确定目标，且开始前预览并确认。
2. Workflow 读取 Story 的 Scene 合约与当前 Writing 草稿/场景范围，校验 outline 的 Scene-章映射，冻结 owner、来源与模型配置快照及预算，登记 run 与队列任务。worker 是手动恢复策略的 evolution_scene_step_v2；它分别推进准备、结构和 Scene 执行，不把 transport task 状态当作领域回执。
3. Scene 执行通过 Writing facade 取当前最新草稿的精确切片；校验 draft identity、整稿 hash、区间边界/range hash 和请求正文一致。任何 draft 被新版本替换、范围越界或来源漂移都会拒绝。Scene manifest 绑定正文、Scene 序号和来源范围；引文需要逐字命中且定位到来源区间。
4. 观察 envelope 保留来源、逐字证据、Story position 和模态（事件、陈述、信念、假设、计划、比喻、不明等）。Observation ID 按来源范围、语义和观察契约版本派生，不由模型指定；mention ID 再由 observation、表面名和序位派生。确定性身份解析仅允许唯一精确名称/别名自动复用；多个精确身份保持歧义，无精确身份则提出候选。
5. world_version=2 路径调用 Imports 纯构建器形成 World proposals；关系阶段使用相同 Scene 与本 run 前缀中的冻结关系快照，然后按身份关联组执行独立审查。独立审核未通过、范围超限或依赖未满足的组不会成为已通过候选。只有通过的候选才可供后续 identity/state gate 使用。
6. apply_frozen 是唯一窄提交边界：先检查已有回执重放，再校验执行模式、owner epoch、当前来源、父回执连续性，以及需要时的独立状态审核；然后调用领域 applier。World 抽取仅创建待采用 candidate，附带 evolution_ref；候选物化、Story 允许的派生变化、receipt 和 committed cursor 在同一事务完成。World 和 Evolution 历史只保留来源明确的候选/回执，不因这条路径直接写 Canon assertion。
7. 作者的 World 实体、关系或别名采用入口识别 evolution_ref 后取得 NOWAIT 项目独占锁，回读 run/frozen/receipt，确认候选仍是最新 Scene 结果，并重新核验源稿和当前前缀；并发写入给可重试冲突。对象提升、关系 canonical 化等入口也调用同一来源新鲜度门禁。通过后仍是 World 自己的显式确认与采用流程。

## 失败与恢复链

- 来源正文/最新 draft / Scene 映射变化：来源读取或提交重验拒绝；旧回执与作者决策保留，不把 stale candidate 静默重绑新正文。作者需预览并授权新的读取/重算范围。
- worker 暂停或异常：manual_resume handler 在回滚后检查 run、冻结阶段和未核销模型调用；只有调用结果可确认或尚未发出未知调用时保存 recovery_required。resume 复用同一冻结 attempt；付费状态未知的步骤不重新发送。预算耗尽则暂停在明确的 budget 原因。
- 领域提交失败：短事务回滚，不留下部分 World 候选、回执或游标推进；被冻结的完成结果可通过 recover_attempt 重验和重提交，无 provider 调用。若提交实际成功但响应丢失，apply_frozen 先发现既有回执并直接重放，避免重复领域写入。
- owner epoch / run parent / source / identity drift：commit conflict，worker 排除特定不可恢复的来源或身份冲突，不把它们标成可安全自动恢复。
- 身份有歧义、同名冲突、未审查或状态 review 不完整：留待处理或返回 conflict，不能自动晋升为正史。候选采用时再做一次 source-current 检查。
- Map Atlas / World Canon revision 的来源版本闭包并未登记进 Evolution 失效收据；显式显示缺口不代表地图/正典已随 Evolution 自动重验或重算。

关键恢复证据：tasks.py:94-184；commit.py:174-182, 202-259, 285-312；reading.py:358-405；world/services/common.py:147-180。测试源码中有提交回滚/重放与恢复覆盖，但本次没有执行这些测试。

## 对指定边界的核查

### World Canon 的五个 formal-disabled 家族

代码的 CanonManifestV1 以封闭集合要求五个家族恰好齐全，empty_canon_manifest 将 name、typed_scalar、binary_relation、event_time、belief 全部设为 formal-disabled。WorldAuthorityService.admit 对 AssertBatch 校验 wire 后仍明确拒绝 Phase 0 assertion admission；FamilyCutover 也拒绝，除 PagePublish / Revert 等已开放操作外，不应描述成形式事实推理或 assertion 写入已启用。ADR-0017 是权威说明。docs/modules/02_world.md 已写“所有 formal family 仍 disabled”，但正文未直接列出这五个键；建议补上名称并链到 ADR-0017。

### Map / Canon 消费关系

Evolution 的 UNSUPPORTED_CONSUMERS 只有 map_atlas 和 world_canon_revision：地图历史页未接入 Evolution 回执，Canon revision 还未作为 Story state/ledger dependency 登记。Story Scene projection 也把这两个放入 unsupported dependency 集合。相邻说明明确写 world_knowledge 会由 ReaderRevealPolicy 在每次 Story 读取时重判。因此 docs/modules/22_evolution.md 的 P4 把 world_knowledge、map_atlas、world_canon_revision 合并成同一句“缺失来源版本闭包、unsupported”时，读者可能把“读时政策重判”误解为与两个未登记 consumer 相同的缺口。最小编辑是拆成两句：world_knowledge 的 Story read-time policy recheck；Evolution/Story projection 尚未接入的两个 consumer。不得由此宣称 map/canon 已自动失效。
Map 文档已明确 Atlas 尚未切换到 CanonRevision，仍按已确认 Context/RAG/World Bible 来源与 hash 运行；World Bible PageRevision 进入 Canon 不表示地图成为其消费者。

### Map Atlas 与 World 对象图片存储

两类图片使用同一 MinIO endpoint/受限应用凭据及共用 S3 client 实现，但使用不同私有 bucket：Map Atlas 8 GiB，World 对象图 24 GiB。生产部署使用单个 minio-data named volume；两配额合计 32 GiB，是单盘对象数据总硬上限。无外部图片备份，磁盘故障会同时丢失两类图片；PostgreSQL/restic 备份不含图片恢复。ADR-0014 将无 offsite 图片备份记录为已接受的首版风险，不是当前文档发现的配置错误。
docs/modules/15_map.md 当前说明 8 GiB 和 bucket 隔离，但漏了 World 对象 24 GiB、32 GiB 同盘合计及无外部备份。建议在现有“私有对象存储与永久删除”段补一短句/链接指向 deploy/README.md 的权威部署边界。World README 已将图片接口与约束列清，且指向地图设计说明作为图片存储契约，适合以该文档为产品组件入口；不要混淆 World 对象 PNG/JPEG 上传约束与地图 atlas PNG 的存储上限。

### 关系历史及 read-set 复用证据

relation_history 只读取同一 run 的已提交前缀，限定至多 64 个相关场景；只选用相应 receipt 声明的关系，并从 frozen world_materialization 的关系 snapshot 取历史内容，不读当前可变 EntityRelation.description。缺少此前记录不能推断“首次结盟”。
test_relation_history_uses_real_prefix_and_not_mutated_world_rows 构造首 Scene 关系，随后故意把可变 World 行描述改成“后文才揭示的秘密”；第二 Scene 的 relation prompt 仍读首 Scene 的冻结描述，并用来源 receipt 绑定该前史。之后 scoped_recompute 重用 scene_sample、scene_world、scene_relations 和各 review group，累计调用仍为 8。此测试证明“实际被消费的输入不变时可重用”，不证明 relation_history 输入变化时会触发重算，因为改过的 World 行不是 relation_history 的输入。
改变真实 read-set 的测试证据来自 test_world_group_exact_read_set_reuses_only_unaffected_group：同 group_id 下一个分组的 source_read_set 改变，该组重调；另一组未变化继续复用，只派发一次、扣一次预算。这是 World audit group 的输入变更反例，不能扩大为 relation-history stage 的输入变化测试。源码测试并无本次识别到的“改动已提交关系快照内容后，断言 scene_relations 不复用”的专门反例。若 P2 需提升该特定正确性保证，可以新增这种离线回归，但 P1 不加测试。
这些测试是合成 DB fixture/provider stub 的工程覆盖；本次未运行，也不证明模型发现准确、长篇一致性或作者满意。

## 建议的单图

在 docs/modules/22_evolution.md“Scene 世界资料候选”附近加入一幅 Mermaid sequenceDiagram：

作者入口 → project/run/source 授权与冻结 → Writing/Story Scene 来源重验 → observation + 精确 identity → World extraction / relation context → 独立分组 audit → frozen attempt → apply_frozen（锁/epoch/source/parent）→ same-transaction candidate + receipt/cursor → author World adoption（NOWAIT + current source/prefix reread）。

以失败分支表现四个重要去向：来源变化→要求新预览授权；未知费用→不重发、待核对；audit/identity 不充分→pending；commit 中断→冻结 attempt 可免采样恢复、已提交 receipt 可幂等重放。图中明确候选和 Canon 是不同状态，且 Map Atlas 与 Canon revision 未接入 Evolution invalidation receipts。
