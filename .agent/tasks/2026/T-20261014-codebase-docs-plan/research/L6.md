## 正常调用链

### API、DI 与任务身份

FastAPI 的 DB session 由 core.dependencies 适配；跨模块端口由 core.container 保存为进程内单例。生产消费端使用 core.service_keys 中的类型化 ServiceKey 常量，运行时容器仍以稳定的 key.name 字符串索引。app.bootstrap.register_container_services 是装配根；app.main 启动与 run_worker.py 启动都调用它，worker 组合根还注册领域任务 handler。业务模块通过 facade、contracts 或已注册 DI 端口访问其它领域，不由组合根承载业务判断。

任务 API 将 request schema 作为提交边界。项目任务必须给出一等 AsyncTask.novel_id，提交时通过 PROJECT_REQUIRE_ACTIVE 校验当前请求的项目与 owner；通用 task API 对没有 generic_submit_schema 的业务任务拒绝提交。状态、取消和重试查询以 task_id 加 novel_id 定位。模型 before_insert 将 novel_id 与兼容 meta.novel_id 对齐，before_update 拒绝改变项目身份。

worker 没有浏览器 principal。TaskWorker.run_once/run_forever 仅在显式 system_execution_scope 中运行；run_worker.py 注入 project_task_preflight 和 project_task_commit_guard。preflight 在 handler 前从 Project facade 重新读取活跃项目、检查项目类别及 understanding owner token；成功的只读 preflight 不把 DB 事务带进 handler。每个 handler checkpoint 和终态提交都再次校验 active project、任务状态和 lease。项目软删除会取消任务并清空 lease，旧 runner 的 heartbeat/finalize 无法提交删除之后的业务写入。这里的 system scope 只区分受控 worker 身份，不代替 novel_id、当前项目状态、账号 active、owner 或来源检查。

### Task lease、attempt 与失败恢复

领取由 PostgreSQL FOR UPDATE SKIP LOCKED 完成，每次 claim 递增 attempt 并创建新的 lease_id。progress heartbeat、handler checkpoint 与 finalize 都受 task_id + running + lease_id fence 约束。慢 provider I/O 之前如果已有 DB 读写，handler 必须先提交受 fence 保护的可恢复 checkpoint；provider 返回后，领域仍需重验 source、profile 或 confirmation。

任务声明的 recovery_policy 决定 stale/失败结果：auto_requeue 仅对登记为可重放的任务使用并受 max_attempts 限制；manual_resume 将 stale 任务标为 failed + recovery_required；restart_origin 要求作者回到原业务入口；never_retry 禁止重试。worker 的明确临时 provider 重排不叠加客户端 transport retry，选择性 LLM handler 最多两个 attempt；认证、额度、过滤、schema、确认或来源冲突不因普通 worker 错误重排。manual resume 复用同一 run 和已冻结预算，只有作者明确续算才可增加请求额度。

受控 LLM 请求先由 AI run envelope reserve，再发生 provider I/O；完整 usage 回执 settle 为 recorded。请求已发出但 usage/结果证据不完整时记 requests_unknown / charge_state=possible / usage_complete=false，不能写成零。取消、崩溃、超时和 stale 恢复都会把未 settle 请求合并回 unknown/possible。run envelope 在 task 私有 meta 中 lease-fenced 持久化，不进入公开 task status；公开 operation 只投影聚合 possible_charge。普通 auto retry、resume 和 inline child 不重置累计 run 预算。详细行为已经写在 infrastructure/llm 与 infrastructure/tasks README 及 docs/modules/12_infrastructure 中。

### Project LLM 配置与可恢复快照

novel_id 业务调用通过 modules.project.facade.open_project_llm_client；Project runtime 先解析该项目的 owner，再从该 owner 的账户连接读取 provider、model 和已验证 Key。项目上下文会移除旧的 secret 字段；业务 profile 不继承 LLM_API_KEY、LLM_BASE_URL 或 LLM_MODEL 环境变量。常规 client 验证 Key、base URL、model 与有界 timeout，并在 context manager 结束时关闭。

可恢复 task 在提交/开始阶段通过 build_project_llm_execution_snapshot 固化 provider/model、非 secret 参数、endpoint 与 extra 的 hash、capability profile、cost routing 和项目工作流设置。snapshot 不含 Key、完整 endpoint 或任意 extra；恢复时校验版本、novel_id、整体 hash、原 provider 仍已连接以及 endpoint/extra 指纹。原 provider Key 轮换可使用当前 Key；provider/endpoint/extra 变化、Key 被清除、profile 不合规或历史 local_agent 文本快照均失败关闭。快照缺旧 capability 字段时只允许 unfrozen short fallback，不能声称继承了已验证预算。代表性调用方包括 Writing、Assistant、World 和 Collaboration 的任务恢复路径。project/tests/test_llm_runtime.py 有对应断言，但本轮未运行。

### Eval 与 Prompt 合约

Makefile 的评测目标把 UV_PROJECT_ENVIRONMENT 指到 backend/.venv-eval，默认使用 Python 3.13 和 locked 依赖；开发/CI backend 环境是另一目录。独立 Codex 文本评测的模型调用由 require_live_eval_calibration 失败关闭：CodexStructuredExecutor 在启动 CLI 前拒绝；Ask World teacher 在创建 holdout marker 或连数据库前拒绝；DeepSeek reviewer 分支在初始化数据库前拒绝。ProjectStructuredExecutor 类虽存在且单测验证其通过 Project facade，但固定 B 的生产 CLI 没有调用该类，不能据此称 Project reviewer 已启用。确定性 QC、报告、已有冻结元数据和 cache-only replay 仍是单独路径。testing-guide 已要求迁到已验证 owner/Project runtime 并重新校准，当前描述正确。

Prompt 合约由 backend/tools/prompt_contracts 的 JSON registry、Pydantic schema、关键持久化映射/目标列、确定性 probe 与 production modules AST capability binding 检查组成。它只覆盖已登记的 26 个合约；不运行真实模型或数据库，也不验证任意 inline prompt 的语义质量。make prompt-contracts 本轮实际执行，退出码 0，输出 Prompt contracts passed (26 contracts)。docs/prompts/Prompt体系设计.md 的范围和限制描述准确；没有改 backend/prompts 模板或契约文件。

### 发布、备份、入口代理与容量边界

release.sh 只接受 lowercase 完整 40 位 commit SHA，解析后要求 SHA 精确匹配且可从 origin/main 到达；发布以目标 commit 的 tracked tree 生成固定 build context。脚本合同包括环境与 migration preflight、服务排空、PostgreSQL 备份/隔离恢复演练、迁移和健康检查。没有运行发布脚本或读取线上状态。

backup.sh 在 production operation lock 内生成 PostgreSQL custom-format dump 与 SHA-256 sidecar，隔离校验后发布为完整 pair；随后要求 restic 仓库可用，把该 pair 加密备份到配置的 B2，并应用 7 daily / 4 weekly / 6 monthly 快照保留。MinIO 图片不在该备份范围。production Compose 使用单节点 MinIO 与单盘 named volume，README 明确写明没有外部图片备份、磁盘故障会丢地图和对象图片；数据库/restic 备份不能恢复图片。现有部署文档对此边界记录正确。

仓库文档记录的入口拓扑是 Cloudflare Tunnel → 1Panel OpenResty → loopback API/frontend，PostgreSQL、worker、MinIO 在内部 data network；这属于仓库中的部署目标说明，本轮没有验证当前主机实际网络。LLM 出站 HTTP 默认不继承系统代理，只有显式 LLM_PROXY_URL 或 LLM_TRUST_ENV 才改变代理来源；因本轮遵守“不读 env”，实际出站代理配置未知。

资源门限是进程级：core.config 默认 LLM_MAX_CONCURRENT_REQUESTS=8、RPM=0、TASK_WORKER_MAX_CONCURRENT_TASKS=2；production Compose 对应默认 LLM 并发为 4、worker task 并发为 1，RPM 要求显式值，部署 README 将 0 列为已确认设计。它们都可由部署环境覆盖；Compose 的单个 worker service 和每进程值不能证明当前运行实例数、整个账户的总并发/RPM，也不能证明 provider quota。真实 env 未检查，账户总 worker 容量与实际 proxy/egress 路由保持未知。

## 漂移与最小文档动作

- development-guide.md 的 Module Boundary Rules 说 DI port 由 app.main / worker startup 注册；实际统一装配函数是 app.bootstrap.register_container_services。建议把文案改为：API main 与 worker 启动都调用 app.bootstrap.register_container_services；生产消费用 ServiceKey 常量，key.name 仍是稳定的容器字符串。
- ADR-0031 的执行机制称 register_container_services 注册“字符串键”。运行时键确实是字符串，但生产调用 API 已迁到类型化 ServiceKey。建议补半句区分类型化常量与稳定字符串名，不改变 ADR 的依赖方向决策。
- development-guide.md 的“controlled structured steps, not an autonomous multi-agent runtime”可精确为：普通业务流程走受控 step；项目助手只用 ADR-0023 的有界单 Agent，协作只走 ADR-0027 已注册、有限成员与共享预算路径；不开放任意自治团队。
- testing-guide.md 已写明独立 Codex eval 暂停、Project 迁移与重校准要求。若需更强操作入口，可补一句当前 CLI preflight 在 provider/database/holdout 副作用前失败；ProjectStructuredExecutor 的测试不代表 CLI 已接线。无需扩大成一套新的 eval 手册。
- Prompt 目录、infrastructure/task README、docs/modules/12_infrastructure.md 与 deploy/README 对本次重点总体准确，应保留现有 source of truth 和限制。模块基础设施文档已经明确 process-local 配额、多进程放大、PG/B2 和 MinIO 单盘失效边界；无需复制一张并行表或把代码默认值写成生产实测。
