## 7. deadline / retry / possible charge 的层级总结
**deadline 优先级（自内向外）**：① provider/HTTP timeout（LLM：profile.timeout 或 timeout_override，默认 core/config.py:302 llm_timeout=180s；图片：profile.timeout，image_runtime.py:109）→ ② 领域 step timeout（run_managed_* 的 timeout= 由 asyncio.wait_for 包住整次 provider 调用+解析，agent_step_harness.py:693-699；常见 1800s：writing/semantic_review/story/world/ask 等；imports 为 600-1200s；query planner/focused evidence 另有更短值）→ ③ 领域阶段 asyncio.timeout（world chat 598、converge 715、explore 800、inspect 889、ask 590、synopsis、scene_fusion 370、outline 588、p20 228）→ ④ agent 层 asyncio.timeout(budget.remaining_seconds) ≤30 分钟（agent_runtime.py:80-85,478）→ ⑤ task 层**没有最大运行时长**，只有心跳 liveness（30s 心跳 / 120s stale 判定，shared/constants.py:54,57；lifecycle.py:1031-1096）。实际生效的是「嵌套最小」，但没有统一的可审计 deadline 字段。
**retry 层级与次数**：① transport（retry.py:119-191，max_attempts=R、delay=min(base·2^(n-1),60s)×jitter(0.75-1.25)；不可重试错误立即抛出；R 被 worker.py:591-593 按任务开关置 1 或保持 3）→ ② structured schema repair（client.py:732，≤max_fix_attempts+1 次，截断时 max_tokens 翻倍至 40000，client.py:69-72,875-895）→ ③ format repair（client.py:940-1043，format_repair_attempts 次，temperature=0 的 JSON 转换器）→ ④ 语义/知识返修（run_governed_generation ≤1 次返修+复审 workflow.py:460-516；govern_world_output ≤1 次 knowledge_governance.py:182-197；决策守卫 ≤2 world_generation_center_service.py:1480；收敛覆盖 ≤2 :3051；known-keys ≤2 structured_reference_retry.py:23；chat 可见文本 ≤2 :659）→ ⑤ 任务层整链重放（auto_requeue，×2；retry_transient_llm_errors=True 时同时关闭 ①，属「换层级不叠加」设计）→ ⑥ 领域手动续算（resume_run/retry_page、resume_manual；不校验 max_attempts，每次都是新的用户授权）。
**possible charge 三态现状**：① 请求前拒绝——只有 AgentRunBudget.reserve（agent_runtime.py:317,358）与 WorkflowBudget.before_request（workflow_budget.py:22-25）会在发请求前因额度/deadline 拒绝；其余全部能力的「请求前拒绝」只来自领域校验（context 指纹、capability policy、输入 token 预检、快照一致性），与费用无关。② 已发出但超时/中断/无 usage——文本 LLM 全链路没有 possible_charge 概念（grep 全仓仅 image_client.py 有）；不记账、不置 usage_unknown；ManagedLLMStep 超时后 token_usage 仍是调用方传入的空 dict（agent_step_harness.py:693-723），任务 requeue 时上一次尝试的花费被 worker.py:697-710 覆盖 result_data 抹掉。唯一有「可能已扣费」语义的是 Map 图片（4.5）。③ 完整响应有 usage——文本链路除 AgentRunBudget/WorkflowBudget 两个 meter 外没有任何落库；managed step 的 token_usage 恒为 {}（调用方不传）。

## 8. 给主 Agent 的三条基线结论
1. **R 不是全局常量**：worker.py:591-593 把 task 的 retry_transient_llm_errors 开关翻译成 transport retry 的 0/1 分叉，公式必须带 R 或按路径分别给出，否则 story/world/writing 系会整体高估 3 倍。
2. **请求上界的真正瓶颈不在 provider 层，而在数据规模**：imports 的 S/B、writing 的 K、world 的 S 都没有常量上限；world.entity_fusion 深导入上限 180000 是单点最大值，建议优先确认是否可接受。
3. **现有 managed_llm_steps 是 provenance 而非账本**（无 token、按 identity 去重），文本链路没有 possible charge 语义；统一运行信封若要做「请求上界 + 计费未知」的权威事实源，必须同时覆盖 6.1-6.4 四条旁路，否则流式、research、embedding、以及 transport retries 关闭时的结构化调用仍然在账本之外。
