# 写作页缺项与能力归并评估

日期：2026-09-12。状态：**评估建议，未实施、未作为新产品契约采纳**。

范围：逐项评估用户提出的21项缺口，核对当前正式写作实现、独立预览及项目Assistant边界。本轮只输出报告；不改界面、业务、规则或真实数据，不提交、推送或部署。

## 结论

**不建议把21项恢复为21个独立区域。应保留任务能力，将它们组织进文稿控制、正文编辑、本章资料、AI写作伙伴和任务进度几个明确的入口。** 其中保存安全、可编辑状态、当前稿件身份和关键决定必须可直接看见；AI适合承接复杂工作的启动、查证与建议，不适合成为所有基本操作的必经路径。

这份缺项表准确指出了当前样板距离真实写作工具仍有多远，但“缺少独立面板”不一定等于“必须补回旧面板”。相反，标题编辑、编辑器状态、保存恢复和候选审阅即使不接业务，也需要补足专属视觉状态，才能验证新版是否容得下真实写作。

目标用户是长期创作作者。收益假设是：更少寻找工具、更少离开正文、更清楚当前文字是否安全；目前没有使用频率和用户访谈证据，以下优先级属于产品判断，不冒称已验证偏好。

## 先澄清四个现状

1. **“设为正式正文”不是对外发布。** 正式实现明确说明只在本作品生效，会成为稳定的正文版本并可能启动后续整理。不应为此新增一个类似公开发布平台的大区。[正式编辑器](/Users/tywww/Desktop/项目/ai-writing-assist/frontend-console/vue/views/writing/components/WritingEditor.vue:18)
2. **当前不能无条件隐藏保存。** 正式编辑器已有自动保存，但控制器会跳过仅标题/纯排版变化；这些变化与明确留版的保存语义不同。若未来采用“所有编辑都可靠自动保存”的体验，需要单独同步保存契约和验证，不能靠移除按钮假装成立。[自动保存实现](/Users/tywww/Desktop/项目/ai-writing-assist/frontend-console/vue/views/writing/controllers/editorController.js:415)
3. **候选、历史和当前工作稿不能混成一种状态。** 正式版本筛选已有区分；新界面可统一入口，但候选应进入待决定区域，历史恢复应说明将从哪一版继续写。[版本筛选](/Users/tywww/Desktop/项目/ai-writing-assist/frontend-console/vue/views/writing/versionState.js:1)
4. **AI中心可以统一前端入口，领域能力仍各自负责。** 现有OwnerAiDrawer是页面内工具入口，Assistant是跨领域讨论/提案执行能力；它们不是天然已经合成一个完整写作中心。视觉归并可复用二者，不能据此假定所有能力已连通。[页面工具](/Users/tywww/Desktop/项目/ai-writing-assist/frontend-console/vue/components/OwnerAiDrawer.vue:54)、[Assistant职责](/Users/tywww/Desktop/项目/ai-writing-assist/backend/modules/assistant/README.md:1)

## 建议的写作页组织

这不是新增五个面板同时常驻，而是五种明确职责：

1. **文稿控制**：当前章、稿件身份、保存状态；展开做保存、留版、正式确认、历史、计划、导出。高频操作保持短路径，危险操作按需出现。
2. **正文**：标题和正文可直接编辑，历史/候选身份明确；只有发生风险时出现恢复卡片。
3. **本章资料**：当前场景、人物/地点、结构、参考来源及检查问题；相同空间按当前任务切换，作者可以固定需要持续对照的内容。
4. **写作伙伴**：统一表达创作意图、查看候选与结构化审查结果。既有直接工具入口作为快捷操作，避免再保留三套功能相同的AI菜单。
5. **任务与待决定**：展示真实运行与结果，允许离开后回来；状态归属不变，作者计划不与后台任务混算。

常态下作者先看到正文、稿件身份与少量相关资料。复杂工作通过就地展开进入；重要结果能从对应文稿/资料再次找回，不依赖记住当时在哪个聊天回合。

## AI中心的实际承接边界

核对到的注册能力包括正文生成/续写、独立审查、世界约束审查、精确修订、定向返修、候选采用、历史恢复，以及正文整理、导入候选处理、查漏和原整理任务恢复。**已有后端工具不等于新版前端已接通，也不等于已经完成真实模型体验验收。**

在本次核对的Writing工具注册中，没有把常规自动保存、设为正式正文、批量删除、导出都统一交给Agent的实现依据。这些动作即使显示在AI面板里，也应由明确按钮直接调用原领域操作，不把模型可用性变成前提。

建议统一三件事：意图入口、当前对象上下文、结果/回执展示；保留各自的正文事实源、确认采用、来源复验与任务恢复。当前未保存文字与AI引用的已保存基线不一致时，应就地提示和保存，不能静默让AI处理旧稿。

## 下一轮设计的建议顺序

**先证明它是一张可信的写作桌面。** 补齐标题编辑、编辑/只读/候选/空正文、稿件身份、保存/恢复、正式确认和基础历史恢复。仍可用虚构内容演示，不需要提前接业务。

**再补齐创作辅助的闭环。** 将写作伙伴、候选审阅、任务反馈与当前场景/来源连起来，展示从发起、运行、结果到作者决定的全部状态。AI工具能收得很简洁，但结果不能模糊。

**最后补管理效率。** 章节管理、计划、高级版本比较、地图和结构视图并入已有入口；手机另行设计。这样可以评审真实密度和信息层级，而不是在完成静态外观之后再硬塞一批按钮。

## 如何验证归并是否成立

后续应按作者任务评审，而非计算按钮数量：

- 不打开AI，能否改标题、写正文、看清保存状态、重试失败并保全当前文字？
- 作者是否能明确区分当前工作稿、正式正文、历史预览和未采用候选？
- 从一句“把这段改得克制一点”，能否看清AI使用哪份稿和哪些资料、改了什么、为何暂不能采用？
- 任务中途离开，再回来能否定位原任务和结果，而不重新生成一次？
- 打开地图/大纲/来源后，能否回到同一处文字继续写？
- 批量管理是否清楚选中了哪些章节；普通故事疑点是否被误当成写入冲突？

观察寻找入口的时间、走错页面次数、重复生成/重复提交、草稿保护和定性反馈；现在不填写虚构达标率。
