# GPT-5.6 Luna 子代理执行计划

状态：执行方案已实施，实际分工、调整和验证见TASK.md。日期：2026-09-12。

上位目标与范围以[评审修订后的PLAN.md](PLAN.md)为准：完成全部前端设计，真实业务完整性后接。本文只规定如何分工、派发、集成和验收，不改变产品范围，不授权提交、推送、部署或读取真实数据。

## 1. Luna能力依据与调度判断

本文的Luna明确指`gpt-5.6-luna`。截至2026-09-12，官方将它定位于成本敏感、高吞吐任务，支持图像输入和工具调用；这不等于已证明能独立完成NovelCraft整站设计。[OpenAI官方模型说明](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

当前宿主的`collaboration.spawn_agent`已列出`gpt-5.6-luna`，允许`low/medium/high/xhigh/max`。执行以宿主暴露的设置为准，不照搬API的其他档位，不修改项目运行时LLM配置。编制时未调用Luna；本次已按用户授权派发，实际校准见CALIBRATION.md。不把局部样板结果推算为模型通用速度或成本。

### 本项目采用的配置

以下是待首批校准的工程选择，不是官方能力上限或性能承诺。

| 工作 | 默认档位 | 交付边界 |
|---|---|---|
| 按已知路径清点入口、整理证据 | medium；纯机械核对可用low | 一组相关域；不裁决跨域产品语义 |
| 复用样板的页面、表单和列表 | high | 一个主视图及紧密相关状态；自己完成局部验证 |
| 比较、来源过期、恢复、中断和焦点 | xhigh | 先由主代理明确语义与共享接口，再实现一个状态转换组 |
| 独立视觉/交互审查 | high；复杂状态用xhigh | 一份稳定产物、一条主要任务路径及其失败/反向分支 |
| 有新证据的困难定点返修 | 必要时max | 只处理已定位问题，不靠提高档位替代缩小任务 |
| 全站设计决策、共享基础、最终集成 | 主代理维持当前模型 | 不随子代理目标一起切换；独立检查实际产物 |

调度原则是主代理先提供可操作样板、准确任务卡和真实代码入口，Luna负责有边界的实现与验证。不能凭模型名断言它只能做简单工作，也不能把全部视觉判断交给一个长会话。提高推理档位是否值得，以同类任务的返工和总耗时判断。

### 在当前宿主派发的写法

实际获得执行授权后，通过协作工具参数指定模型，不能仅在提示词写“你是Luna”。例如一个已经细化的任务卡：

```json
{
  "task_name": "p01a_writing_input",
  "model": "gpt-5.6-luna",
  "reasoning_effort": "high",
  "fork_turns": "none",
  "message": "<填入第11节任务卡，包含仓库绝对路径、规则、基线、文件范围、参考图和验收>"
}
```

本宿主指定模型时不能使用全历史fork，因此默认新上下文并显式提供任务卡；需要的历史结论从任务文档按需读取。复用代理前核对它的实际模型和未结束任务，不能把旧的其他模型代理重命名后当作Luna。首包实际确认图像可读、工具可用；模型列入目录只证明可选，不证明任务已成功运行。

## 2. 人员与并发组织

采用“主代理＋最多两个实施子代理＋一个独立评审子代理”的调度方式，在当前4个活跃代理槽位内运作。它是上限，不是必须凑满的固定编制。

- **主代理**：唯一维护主计划、总覆盖表、共享外壳、全局样式/交互接缝和集成状态的人。负责读真实差异、看结果、处理跨域判断，不能只转述子代理“已完成”。
- **实施位A/B**：均以GPT-5.6 Luna为目标执行模型。领取互不重叠的文件范围，完成设计、局部交互和必要验证。一次只领一个工作包。
- **评审位R**：同样可使用GPT-5.6 Luna，使用新的任务上下文，审查已稳定的工作包；不修改实现文件。实现者不能兼任自己工作包的独立评审者。
- **只读清点阶段**可并行三个调查子代理；**共享基础阶段**默认单写者串行；**页面阶段**通常两个实施位加一个评审位；**最终集成阶段**按写入冲突收回到单写者。

每个槽位可依次承担多个工作包，不创建几十个永久角色。叶子子代理不再自行派发孙代理。

同模型独立上下文只能降低部分遗漏，不能消除共同审美偏差；主代理仍须对照已确认参考图、正式界面范围和实际浏览器结果裁决。

## 3. 开始实施前的主代理准备

以下准备已在实施中执行，基线快照见BASELINE.json。

1. 核对分支、当前WIP、适用AGENTS、前轮成果与PLAN版本，保留用户和其他任务改动。
2. 对本任务会修改的代码、文档和未跟踪原型保存可恢复的非提交快照，记录路径和文件指纹；不把真实作品、数据库、凭据或整个用户目录复制进去。
3. 核对实际可用模型、推理参数、上下文/输出限制、图像传递、工具调用与宿主并发上限。失败时只暂停Luna派发，不改用其他模型冒充，也不影响计划交付。
4. 运行规定的前置文档检查，启动或复用隔离预览。端口以实际服务为准，8097是当前记录，不盲目启动第二份同端口服务。
5. 给出三种外壳和共享审阅的最小接口说明，以及本批具体允许写入的文件。只声明实际要用的导航、面板、主题和示例对象关系，不预建事件总线或状态引擎。

### 当前共享文件的所有权

现有原型还集中在三个页面条件组件中。没有先解除共享写入冲突，不能让多个子代理各自“负责一个域”却同时编辑同一文件。

| 文件/内容 | 默认写入者 | 处理方式 |
|---|---|---|
| `RedesignApp.vue`、`main.js`、`data.js`、`redesign.css`、`motion.css`、`motion.js` | 主代理 | 统一接入口、共享状态、样式和动效；同一批验收期间维持稳定基线 |
| `WorkspacePreview.vue`、`ExperiencePreview.vue` | 主代理或一次性串行授权的实施者 | 按实际页面逐步拆出后再并行，不安排两位实施者同时拆同一条件文件 |
| `WritingPreview.vue` | 写作包独占；接入时由主代理协调 | 章节/资料/版本等新面板先在独立文件完成，再由同一所有者接入 |
| `PreviewDialog.vue`、`PreviewNotice.vue`、`PreviewIcon.vue`及确实共享的新组件 | 主代理；必要时临时授权一个包 | 子代理提交最小共享修改请求，不能为绕开权限复制一套同用途组件 |
| 各工作包自己的页面、面板、局部样式与必要测试 | 对应实施子代理 | 派发时明确具体路径；建议新文件名只为分工，不是永久目录规则 |
| 总覆盖表、总任务记录、正式设计文档、共享测试 | 主代理 | 子代理返回本包增量，主代理统一更新，避免并发覆盖 |

复用同一工作树的前提是同一原型模块内文件严格互斥，这符合现有协作规则。若必须使用独立工作树，要把**当前未提交原型基线**按受控文件清单带过去；只从HEAD创建工作树会缺失这些成果。不得通过提交、stash、reset或覆盖其他WIP来图方便。

## 4. 任务粒度与上下文包

每包以“作者可以评阅的一件事”为单位，例如“历史版本比较与从此版继续写的状态设计”，不以“做完整世界模块”或“给100个按钮加样式”为单位。

建议初始包包含：一个主要页面/面板组、一个必要的复杂状态组、浅深色和相应交互。初始以1–3个实现文件、3–6个重点阅读文件和1–2张参考图为宜；这些是派发粒度参考，不是文件数、代码行数或模型上下文硬门禁。一个包实际包含两个可独立验收目标时再拆分，不机械拆成逐按钮任务。

主代理提供：

1. **任务卡**：目标用户、当前任务、设计归属、输入/输出边界、准确允许写入路径。
2. **当前事实**：相关正式组件及入口、已有预览、相邻调用关系、适用状态语义；让子代理能回读，不仅依赖主代理摘要。
3. **视觉参照**：已确认的当前样板和局部参考图，注明借鉴的是层级、密度、材质还是操作模式。不要让每个子代理重新定义Apple风格。
4. **共享约定**：本批外壳/面板/示例对象接口版本、已有控件和动效规则、移动适配方向。
5. **验收场景**：本包需要真正点击的入口、正常状态、重点异常、键盘/中断、返回路径和证据位置。
6. **交付格式**：文件、入口、状态、验证、截图/录屏、限制及需要主代理处理的共享修改。

只加载本包所需计划段落和关联文件，按需追踪调用链；不能为了缩短上下文漏读适用规则，也不把全部历史聊天、整个仓库和其他域的源码默认灌入每个任务。

## 5. 首批校准：用真实工作验证拆包是否合适

不另建基准测试项目。下表中的P01、D01、P03同时作为正式设计产物和三个校准包：

| 校准包 | 要观察的Luna表现 | 通过后如何调整 |
|---|---|---|
| P01 文稿编辑与状态 | 能否保留中文排版，完成本地输入/只读/空态，遵守文件边界，提供实际截图 | 可承担同等规模的表单、阅读与管理页面 |
| D01 世界资料浏览 | 能否避免重复大卡片模板，处理密集中文、筛选、详情关系与浅深色 | 可承担复杂资料与结构页面；失败则缩小到单一主视图再扩展 |
| P03 候选审阅 | 能否准确表达候选/工作稿/正式、来源过期、比较和返回，且不发明业务能力 | 可承担AI/导入结果与批次状态；语义反复错误时由主代理先补更明确样板 |

三个样板按第6.7节拆为五个叶子包，均完成关键验证后进入稳定批量派发。优先修复实际暴露的问题，不因一次失败宣布整个模型不适合，也不因一次成功扩大到“一个子代理做完整前端”。

每包记录实际模型/参数、上下文与输出用量（宿主有数据才填）、实施时间、审查修复次数、工具错误和一次验收结果。用这些数据调整后续包大小与并发，不能把公开基准的百分数换成本项目成功率、速度或费用。

## 8. 每包的执行闭环

### 派发前

主代理核对依赖已接入、基线文件指纹、允许写入路径和验收入口。为本包指定独立证据目录。尚未存在的路径标为计划新增，先确认相邻结构再创建，不误导子代理去寻找不存在的正式组件。

### 实施中

子代理读取规则与本包调用链，确认归属后实现。先完成内容和状态，再校准排版/颜色/动效；不得先堆动画来掩盖缺少真实界面。需要改共享文件时说明最小变更与影响，交主代理处理；继续不依赖该改动的本包部分。

建议先完成一个正常状态及一个关键异常让主代理看图，再扩展其余状态；这是阶段反馈，不是等待用户批准。输入/选择等本地交互必须在浏览器可操作，业务结果由明确演示状态触发。

### 实施者交付

提交本地成果而不是Git提交：文件清单、基线/产物指纹、页面入口、状态清单、实际检查和证据、未完成项、共享修改请求。不能只返回“样式完成、测试通过”。

### 独立审查

评审者先读任务卡和实际产物，再读实现者说明；依据已确认样板检查层级/密度/颜色，实际操作重点状态与返回路径。静态截图不证明中断或焦点正确，源码不证明渲染质量。报告只有具体可定位的发现，不能用“更高级、更Apple”代替问题与修改方向。

被审文件在评审期间不继续修改。其他无关域可并行；共享外壳/样式一旦改变，主代理判断哪些先前证据失效并只重验受影响包。评审者不与实施者同时写同一文件。

### 集成与复验

主代理检查差异和实际页面，接入口、主题、示例对象/返回状态及总展示。发现回到原实施者定点修复，复核发现后验收；重试不扩大到整个页面无目标重做。独立通过仍不替代主代理对全站一致性的判断。

任务记录使用“待派发、实施中、局部可消费、待联验/评审、已验收”几个实际阶段。允许依赖消费已检查的局部产物；有待联验项的包不能在最终覆盖表中标为全部通过。

## 10. Luna失速、返工和环境问题的处理

- **输出开始泛化或漏掉验收项**：收窄到当前一个视图/状态组，回读对应参考图和真实组件；不继续追加整仓库上下文或让它重新设计整站。
- **同一语义连续两次返修仍错误**：主代理检查任务卡是否含混、是否共享模式本身不清楚，再亲自裁决或将包沿自然边界拆开。先在同模型xhigh下定点修复，只有新证据支持时再考虑max，不盲目加第三级代理或擅自换模型。
- **视觉仅“像模板”**：针对排版层级、信息密度、颜色职责给出具体对照区域，由原作者修正；不能只加阴影/渐变后自称Apple风格。
- **越过文件边界**：立即停止该包的相关写入，由主代理检查实际差异；只恢复已证明属于该包的变更，绝不reset整个工作树。
- **接入端不传截图或不提供浏览器工具**：该包不能声称视觉验收完成；图像/浏览器部分交给有能力的现有执行位验证，不安装新平台绕过。不把模型原生多模态当作宿主已经支持的证据。
- **相同外部依赖连续三次失败且无新证据**：按项目规则暂停受阻部分，保存恢复快照，继续其他独立包。恢复时核对现状，不盲目重放业务或覆盖产物。

不存在“Luna连续失败就自动升级付费模型/购买额度/提交代码”的规则。若缺失条件真正需要用户决定，只暂停受影响部分；普通分工与可逆实现由主代理处理。
